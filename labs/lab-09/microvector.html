A vector is an ordered list of numbers. Each number is a coordinate. The number of coordinates is the vector’s dimension. Vector length measures the distance from the origin.

Predict

How many coordinates does (3, 4) have? Would a longer passage need more coordinates? Could its vector represent a sentence the model never received?

Check the starting idea

The vector (3, 4) has two coordinates and length 5. This model converts each accepted input into a fixed number of coordinates. A longer input does not increase that number. Text removed before the model runs cannot contribute to its vector.

Think of an embedding as a location on a learned map. Related inputs often have nearby locations. The model determines the coordinates. The index searches them. A location does not reproduce the original passage, and proximity does not prove that a passage answers a question.

A token is a piece of text recognized by the tokenizer. A token can contain a word, part of a word, or punctuation. Count tokens with the model’s tokenizer. Character counts and word counts are different measurements.

See inside an embedding model

How do token vectors become one passage vector? The first stage works like a table lookup: a token ID selects a row of numbers. Later stages combine those numbers with information from other tokens. The lookup alone does not use the surrounding text.

An encoder converts an input into a representation, such as a passage vector. Weights are stored numbers that control the model’s calculations. Activations are the values calculated for the current input. During inference, the model uses its weights without changing them. During training, an algorithm adjusts weights to reduce a numerical measure called a loss.

From tokens to one searchable vector

This toy computes every displayed value from invented weights. One attention head mixes token information. Each token has three internal coordinates, and the output has two coordinates. The toy does not run EmbeddingGemma 2.

Inference: look up token vectors → mix token information → transform each token → average → project → normalize.

Attention mixes information across retained tokens, including later tokens. A feed-forward network transforms each token vector. Mean pooling averages those vectors. A projection matrix maps the average to two coordinates. Normalization divides the projected vector by its length.

Training: encode a query and candidate passages with shared weights. Compare their vectors. Update the weights to favor the matching passage.

Enable JavaScript to trace the numbers and train the toy projection.

Follow the shapes: N tokens → N × 3 token vectors → N × 3 contextual vectors → one 3-coordinate mean → one 2-coordinate unit vector.

N is the number of retained tokens. Each contextual vector includes information from other tokens. The final unit vector has length 1.

The same encoder processes queries and passages. Contrastive training rewards the matching passage relative to the other candidates.

This toy trains only its shared projection. EmbeddingGemma 2 uses a larger model and a multi-stage training process.

Is this an encoder and decoder?

An autoencoder learns to reconstruct its input. Its encoder creates a representation, and its decoder tries to recover the input. Keeping only the encoder afterward is one way to obtain representations.

Autoencoder training

input → encoder → representation → decoder → reconstructed input

Compare the reconstruction with the original input.

Retrieval training

query and passages → shared encoder → vectors → similarity scores

Reward the matching passage relative to unrelated passages.

Contrastive training rewards a matching passage relative to other candidates. The toy measures this preference with a loss: a number that training tries to reduce. Both branches use the same encoder weights. The query and passage vectors can both change when those shared weights change.

EmbeddingGemma 2 uses contrastive training as one stage of its training process. It starts from the pretrained Gemma 4 transformer, the network that processes token vectors. This starting model is a decoder-only transformer: it generates text without a separate encoder. The name describes the starting model, not an autoencoder’s reconstruction stage.

The embedding model changes causal attention to bidirectional attention. Causal attention restricts each token to the current and earlier positions. Bidirectional attention also permits later positions within the attention mask. The mask specifies which positions a token can use.

Like the toy, EmbeddingGemma 2 uses pooling, projection, and normalization to produce a retrieval vector. It does not reconstruct the passage from that vector. Its output represents the input for comparison with other inputs.

Earlier EmbeddingGemma 2 training stages learn from a larger model’s vectors. Its final training combines contrastive learning with other objectives. The toy shows one contrastive objective and updates only six projection weights. It does not reproduce the full training process.

The real model uses 24 transformer layers, position information, and both local and full attention. The toy uses one full-attention block and omits position information, local attention, and task prefixes. Reordering the same words therefore leaves this toy’s final vector unchanged. Real EmbeddingGemma 2 produces 768 output coordinates from 512-coordinate hidden states.

Explain the distinction

Does encoding another sentence change the weights? Why do training diagrams show two encoders if both inputs use the same model?

Check your explanation

Inference changes activations while the weights stay fixed. Training adjusts weights to reduce a loss. The two encoder branches apply the same weights to different inputs. Each branch maps an input to a vector. An autoencoder instead passes its representation to a decoder that reconstructs the input.

import torch

Inspect the input window

The context window limits the input processed in one call. EmbeddingGemma 2 supports 8,192 input tokens. Its full output has 768 coordinates. These numbers measure different things. Increasing output width does not make more input fit.

The script sets model.max_seq_length = 8192 explicitly. A library setting controls preprocessing. Raising that setting above the model’s supported window does not create reliable longer-context support.

Keep the missing text with chunks

A chunk is a bounded part of a source document. Embed each chunk separately. Keep its source ID and position with the vector. Search the chunk vectors. Then open the matching source passage.

document → [chunk 0] [chunk 1] ... [last chunk: AMBER-OTTER-731]
              ↓         ↓                    ↓
            vector    vector               vector
query → query vector → compare against every chunk vector

The script splits the long text into overlapping token chunks. It checks each decoded chunk again with the document prefix. This check prevents formatting from pushing a chunk beyond the limit. Overlap repeats boundary text so a useful phrase is less likely to be split apart.

The query asks for the backup cabinet access code. The script prints the highest-scoring chunks and the chunk containing the final sentence. Read those passages. Confirm that the sentence survived chunking. Then inspect its rank. Keeping the fact makes retrieval possible, but does not guarantee first place.

The media mode loads all encoders from the same checkpoint. These calls show the input format:

import torch
from sentence_transformers import SentenceTransformer
from transformers.video_utils import load_video

model = SentenceTransformer(
    "google/embeddinggemma-2", device="cpu",
    model_kwargs={"torch_dtype": torch.float32},
)
model.max_seq_length = 8192
picture = model.encode(
    {"image": "demo-media/red-circle.png"}, normalize_embeddings=True,
)
audio = model.encode(
    {"audio": "demo-media/tone.wav"}, normalize_embeddings=True,
)
frames, metadata = load_video("demo-media/moving-circle.mp4", backend="pyav")
video = model.encode(
    {"video": frames}, normalize_embeddings=True,
    processing_kwargs={"video": {"video_metadata": [metadata]}},
)
query = model.encode(
    "a red circle moving across a white background",
    prompt_name="SearchQuery", normalize_embeddings=True,
)
print(float(query @ picture), float(query @ audio), float(query @ video))

PyAV decodes the short video before embedding. The metadata preserves frame timing for sampling. This example loads all frames into memory. Cut longer recordings into short clips before using this path.

Run the command again with --query "three short electronic tones separated by silence". Record the changed scores. A similarity score is a ranking signal, not a probability. Small synthetic fixtures test the pipeline. Use representative media to evaluate retrieval quality.

Partition the space so a query skips most of it

Use the shelf model from Lecture 11: a centroid is like a shelf label, a list is the shelf, and the vectors are its books. A query chooses promising labels before checking the contents. Distances to centroids determine list membership and which lists are searched. A nearby vector can belong to a list whose centroid is farther from the query, so the search can skip that vector.

Like the B+ tree from week 6, IVF organizes stored data so a query can skip some of it. The difference is how it chooses what to skip. IVF searches the lists with the closest centroids, but a true neighbor can belong to a list with a less similar centroid. Recall@k measures the resulting misses.

FAQ

My recall differs in the third decimal from the reference.

The supplied dataset, seeded clustering, and unchanged settings should give reproducible results. Check tie handling, vector order, and changes to the k-means inputs. The graded tests check exact results, list assignments, recall thresholds, and comparison counts. They do not apply a blanket ±0.02 tolerance to the full measurement table.

Why is Python fine here when it was "too slow" for real engines?

The 64-dimensional dataset needs about 256,000 multiply-adds per brute-force query. Moving to 384 dimensions multiplies that arithmetic by six. Actual latency also depends on the implementation and hardware. Production libraries use compiled loops, batching, and SIMD to reduce those costs.

Should my project use microvector or pgvector/FAISS?

The specification permits any real index. microvector gives you a small implementation you can inspect. Pgvector integrates vector search with PostgreSQL. FAISS provides optimized search implementations. Choose one that fits your project and defend its settings with measured retrieval quality and cost.

Is k-means the only way to partition the space?

No. Other methods include locality-sensitive hashing, tree-based indexes such as Annoy, and graph indexes such as HNSW. IVF is used here because clustering, list assignment, and exact scoring make its search behavior straightforward to inspect. The FAISS guide compares additional choices.
