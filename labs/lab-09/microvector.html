Skip most of the space

The move is week 6's, wearing geometry: build a structure that lets each query ignore most of the data. A B+ tree partitions an ordered line; k-means centroids partition a vector space,and then a query only searches the few partitions its neighborhood could plausibly live in. The cost of the analogy's imperfection (space has no clean fences; near things straddle borders) is exactly what recall@k measures.

  • Share · 2 minOne sentence: why probe buys recall back: whose borders get covered?
Show the answer

The misses live just across the borders of clusters you did not probe. A true neighbour can be geometrically very close to the query and still be assigned to a different centroid, and if that list is not probed the vector is never scored at all. It is not out-ranked, it is unseen.

So queries near a boundary are hurt far more than queries sitting near a centroid: a query in the middle of its cluster has most of its true neighbours in that same list, while a boundary query has them split across two or three. More cluster overlap makes everything worse, and real embedding topics do overlap, which is why the lab's generator was built to produce it rather than clean, well-separated blobs.

Why probe buys recall back: raising probe covers more of the borders. Probe 2 adds the second-nearest centroid, which is exactly where a boundary query's missing neighbours were hiding. That is also why recall can only rise as probe rises, never fall, and why a "probe more, recall dropped" result is always a bug rather than a discovery.

The contract

BruteForceIndex.search(q, k) # the truth, at O(n) per query
IVFIndex._build() # bucket every id under its centroid
IVFIndex.search(q, k, probe) # probe lists, then brute-force inside

About 820: 20 centroid dot products to pick the probes, plus 4 lists × roughly 200 ids each = 800 candidate comparisons.

The subtle bug that yields right answers with a too-high count: scoring every vector in the dataset and then only keeping results whose ids belong to the probed lists. Every returned neighbour is correct, every test on results passes, and you have implemented brute force with extra bookkeeping. The counter is the only thing that notices, reading 4,000 instead of 820. Instrumentation as honesty: the number you claim is graded as strictly as the answer you return, because the whole point of the structure is the number.

Where the course graded a counter before: Lab 3 counted your file's blocks after 12 inserts, catching a scan that worked but grew the file 4× too fast, and Lab 6 counted tree nodes touched per lookup. Same pattern each time: a correct answer obtained the expensive way is a bug, and only a counter can see it.

Part 1 · Build ~30 min in class

  1. Read the provided half (8 min): dot, normalize, the deliberately small kmeans, and recall_at_k. The module docstring holds the cost model.
  2. BruteForceIndex.search: score, count, top-k. EXACT group greens against a slow-but-obviously-right reference.
  3. IVFIndex._build: one assignment loop. The every-id-exactly-once test passes.
  4. IVFIndex.search: centroids, probe, brute-force inside, count everything. IVF and QUALITY groups green: recall ≥ 0.75 at probe 4, comparisons under half of brute force.
Gotchas that cost real debugging time

Sort by (-similarity, id); plain similarity sort breaks ties nondeterministically and the reference comparison notices. Count centroid dots AND candidate dots. And don't re-normalize the stored vectors inside search; they arrive unit-length from the generator; double normalization is a no-op that hides real bugs elsewhere.

Exercise · read the failure

A classmate passes everything except probing more lists never hurts recall: at probe 8 their recall dropped below probe 1. Recall mathematically cannot drop as probed lists grow (a superset of candidates). What must their search be doing with the probe parameter?

Show answer

Their probe selects the worst P centroids (sorted ascending by similarity, a missing minus sign), so probe 1 gets one bad list but probe 8's "best 8" crowd out… no: with more bad lists they'd still gain candidates. The real culprit: they take centroid_scores[:probe] unsorted, so which lists get probed is arbitrary per call; recall becomes noise, sometimes lower at 8. Monotonicity violations in a should-be-monotone knob always mean the knob isn't selecting what you think. Sort first, then slice.

FAQ

My recall differs in the third decimal from the reference.

Everything is seeded, so it shouldn't; the usual cause is tie handling (sort by (-sim, id) exactly) or k-means drift from calling random anywhere yourself. The autograder allows ±0.02; determinism is still the assignment.

Why is Python fine here when it was "too slow" for real engines?

4,000 × 32 dims is ~1M float ops per brute query; Python shrugs. The real thing does 1536 dims × millions with SIMD (FAISS) precisely because the constant factor matters at scale. The structure and the dial (what this lab teaches) are identical at both scales.

Should my project use microvector or pgvector/FAISS?

Spec says any real index. microvector earns style points and total understanding; pgvector earns SQL-side filtering; FAISS earns speed at size. All three require the same deliverable: a measured recall/speed table defending your setting, this lab, re-run on your corpus.

Is k-means the only way to partition the space?

No: LSH hashes by random projections, trees cut recursively (Annoy), graphs skip partitioning entirely (HNSW). IVF is taught first because you already own its parts (clustering + brute force) and its dial is the cleanest. The FAISS guide in the citations is the practical taxonomy.
