microvector

Implement exact and IVF search over 4,000 vectors, then measure how the number of searched clusters affects recall and work.
Follows Lecture 11 (Vector Databases) · in class: 75 min · aim to finish Build + Verify · due Thu Nov 12 at class start

This lab compares exact vector search with an approximate index. You will search embeddings of 4,000 arXiv abstracts, first by scoring every vector and then with IVF. The provided k-means implementation finds centroids; you assign vectors to lists and choose which lists a query searches. Measure recall@10 and comparisons per query to see what is gained and lost when fewer vectors are searched. The index interface is reused in next week’s micro-rag lab and can support your project.

Partition the space so a query skips most of it

Like the B+ tree from week 6, IVF organizes stored data so a query can skip some of it. The difference is how it chooses what to skip. IVF searches the lists with the closest centroids, but a true neighbor can belong to a list with a less similar centroid. Recall@k measures the resulting misses.

B+ tree (week 6)IVF (this lab)
Partitionsan ordered linea vector space
Partition boundariesnon-overlapping key rangesnearest-centroid assignments; a query’s nearest neighbors may cross boundaries
A query searchesone root-to-leaf paththe few nearest partitions
Can it miss?noyes; recall@k measures the fraction of exact neighbors returned

The vectors are real. data/arxiv_4000.f16 holds sentence embeddings of 4,000 arXiv abstracts, 800 each from databases, information retrieval, machine learning, statistics, and distributed computing, produced by the all-MiniLM-L6-v2 model. The 40 queries are real questions, embedded the same way, so a search returns actual papers and you can judge the result by reading the titles. The model's vectors have 384 dimensions; the shipped copies are reduced to 64 by principal component analysis and re-normalized so that pure-Python k-means and brute force stay fast enough to run in a loop. The full 384-dimensional vectors ship too (python3 measure_recall.py 384), and Part 3 asks what the reduction cost.

Part 1 · Build ~30 min in class

After each function, use the function-level checks to test it before completing the rest of the lab.

  1. Read the provided half (8 min): dot, normalize, the deliberately small kmeans, and recall_at_k. The module docstring holds the cost model.
  2. BruteForceIndex.search: score every vector, count the comparisons, and return the top k. The EXACT tests compare the result with a simple reference search.
  3. IVFIndex._build: assign each vector id to its closest centroid’s list. The harness checks that every id appears exactly once.
  4. IVFIndex.search: rank centroids, search the selected lists, and count all comparisons. The IVF and QUALITY groups check recall of at least 0.75 at probe 4 and fewer than half as many comparisons as brute force.
Implementation details to check

Sort by (-similarity, id) so tied scores have a deterministic order. Count centroid dot products as well as candidate-vector dot products. Reset the comparison counter for each search. Stored vectors already arrive normalized; do not repeatedly normalize them during queries.

Exercise · read the failure

A classmate’s recall at probe 8 is lower than at probe 1 for the same query. With fixed scores and tie handling, adding candidate lists cannot remove a true top-k neighbor already found. Which parts of the search implementation would you inspect?

Show answer

Check that larger probe values retain all previously searched lists, that every candidate is scored consistently, and that the final top-k is chosen across all candidates. Replacing the result heap for each list, changing list order between calls, or retaining query state can violate these conditions. A fixed unsorted centroid order is incorrect, but slicing longer prefixes of it still adds candidates and cannot by itself explain decreasing recall.

FAQ

My recall differs in the third decimal from the reference.

With the supplied dataset, seeded clustering, and the same settings, results should be reproducible. Check tie handling, vector order, and any changes to the k-means inputs. The graded tests check exact results, list assignments, recall thresholds, and comparison counts; they do not use a blanket ±0.02 tolerance against the full measurement table.

Why is Python fine here when it was "too slow" for real engines?

The 64-dimensional dataset needs about 256,000 multiply-adds per brute-force query. Moving to 384 dimensions multiplies that arithmetic by six. Actual latency also depends on the implementation and hardware. Production libraries use compiled loops, batching, and SIMD to reduce those costs.

Should my project use microvector or pgvector/FAISS?

The specification permits any real index. microvector gives you a small implementation you can inspect; pgvector integrates vector search with PostgreSQL; FAISS provides optimized search implementations. Choose one that fits your project and defend its settings with measured retrieval quality and cost.

Is k-means the only way to partition the space?

No. Other methods include locality-sensitive hashing, tree-based indexes such as Annoy, and graph indexes such as HNSW. IVF is used here because clustering, list assignment, and exact scoring make its search behavior straightforward to inspect. The FAISS guide compares additional choices.
