Implement grammar rules as parser methods

The starter includes two worked parser methods: parse_insert and parse_create. Read them alongside the grammar. In recursive descent, each method consumes the tokens for one grammar rule, using peek, next, match, and expect. Use the same approach for parse_query, including its * alternative and optional WHERE clause.

Parser and planner methods

Implement the following four methods:

parse_query # imitates parse_insert + a * case + an optional clause
_parse_predicate # parse terms separated by AND
_parse_term # field, operator, then literal or field reference
Database.plan_query # scans → products → select? → project?
Hover a line: between them they touch every layer you've built since August.

Part 1 · Build ~30 min in class

Download the nine files into microdb-lab5/. Five provide the lower database layers, and the REPL is complete. All required changes belong in sql_frontend.py. Implement the methods in this order:

  1. Read parse_insert and parse_create alongside the grammar in the module docstring (about 8 min). Identify how each method handles required tokens, repeated items, and errors.
  2. parse_query: field list (star or { , }), FROM, table list, optional WHERE. Run the first three PARSE tests.
  3. _parse_predicate and _parse_term: parse AND-separated terms, and distinguish literal values from field references represented by F. Run the remaining PARSE tests, including the error cases.
  4. plan_query: construct table scans, combine them with products, add selection when needed, and add projection unless the query requests *. Run the PLAN and SQL tests, then start the REPL with python3 microdb.py.
Common implementation mistakes

* is a PUNCT token and must be the entire field list: ["*"]. In _parse_term, accept only =, <, or > as the operator; raise ParseError for anything else. In plan_query, retrieve each table’s existing layout from self.catalog rather than constructing a new schema.

Exercise · read the failure

A classmate’s test_sql_join returns zero rows, although all PARSE tests pass. Their planner reverses the two tables from the FROM clause. The test’s join fields have distinct names. Does reversing the inputs explain the missing rows? Which parts of the plan should you inspect next?

Show answer

Reversing the inputs changes row order, not the matching pairs in this example. Dropping the predicate would return too many rows, not zero. Check that both scans can produce rows, that the product initializes its left input, and that the predicate reads the intended fields. Inspect the intermediate rows to locate the failure.

Parsing and planning in other tools

SQL submitted through tools such as pd.read_sql, duckdb.sql, or psycopg is parsed and planned by the database. Production engines support much richer syntax and planning rules, but your implementation illustrates the same separation between query text and execution operators.

Where you meet itWhat the parser is doing there
Postgres answers a typo with syntax error at or near "35" That is its parser doing what yours does in expect: the token it names is the one that failed to match the grammar, which is where the parser first noticed and may be one token past the real mistake.
df.filter(pl.col("gpa") > 35).select("name") in Polars, and the same chain in PySpark These APIs construct expression and query-plan objects through method calls. They can represent filtering and projection without parsing an equivalent SQL string.
SQL written by a language model Parsing can catch malformed SQL, but a valid statement can still refer to missing fields or express the wrong query. Additional checks are needed before execution.
EXPLAIN in a production engine The plan tree is what EXPLAIN prints, so reading your own render_plan output is practice for reading a production plan.

FAQ

The REPL says no such table in catalog after I restart it.

First check that you restarted in the same working directory: ./mydb is a relative path. Close the database normally so buffers are flushed. If a crash interrupted writes, preserve a copy of the directory before investigating; Lab 7 introduces recovery.

Why lowercase everything? SELECT and select both work but my strings changed case!

The lexer lowercases words (keywords and IDs) but not STR tokens; check that your table/field names are compared post-lowercase and that you're not lowercasing string literals somewhere. 'Ada' must stay 'Ada'.

Can two tables in a FROM share a field name?

MicroSQL does not support aliases or qualified field names. If both inputs contain a field with the same name, the left input supplies its value under Lab 4’s lookup rule. The tests avoid this ambiguity; use distinct field names in your own schemas. Supporting aliases would require changes to parsing and name resolution.

My parser works but the REPL prints columns in a weird order for SELECT *.

The catalog rebuilds each schema in stored-offset order. Check the catalog’s field offsets if SELECT * returns columns in an unexpected order.

Is this how SQL injection happens?

SQL injection can occur when an application inserts untrusted text directly into a SQL statement. The parser may interpret part of that text as SQL syntax. Parameterized queries keep parameter values separate from the statement’s syntax. A syntactically valid query alone does not establish that user input was handled safely.
