Imitation with understanding

The starter hands you two complete parsers (parse_insert and parse_create) as worked examples, because recursive descent is a pattern you absorb by reading. Each grammar rule is one method; each method consumes exactly the tokens its rule owns, using four verbs on the token stream (peek · next · match · expect). Your parse_query is the same song with two new verses: the * alternative and the optional WHERE.

The contract

Your five methods, with the moves each one borrows:

parse_query # imitates parse_insert + a * case + an optional clause
_parse_predicate # the {, } idiom wearing AND instead of a comma
_parse_term # field, op, then the F fork for join terms
Database.plan_query # scans → products → select? → project?
Hover a line: between them they touch every layer you've built since August.

Part 1 · Build ~30 min in class

Nine files into microdb-lab5/: five are the reference tower, the REPL is ready, and your work is one file. In harness order:

  1. Read the two worked examples (8 min, honestly): parse_insert and parse_create, next to the grammar in the module docstring. Every move you need appears in one of them.
  2. parse_query: field list (star or { , }), FROM, table list, optional WHERE. Three PARSE tests go green.
  3. _parse_predicate and _parse_term: the AND idiom and the F fork. The rest of PARSE passes, including the error tests you get for free from expect().
  4. plan_query: the four-step recipe. PLAN and SQL groups light up, and with them the REPL: python3 microdb.py, type SQL, grin.
Gotchas that cost real debugging time

The star: * is a PUNCT token, and it must short-circuit the field-list loop entirely (["*"], not ["*", ...]). In _parse_term, don't expect("PUNCT", "="); the operator may be any of three, so peek, check membership, and raise your own ParseError otherwise. And in plan_query, fetch each table's layout from self.catalog, not by constructing a new Schema; the catalog is the source of truth, that being the point of Lab 3.

Exercise · read the failure

A classmate's test_sql_join fails with zero rows returned, but every PARSE test passes, including the F test. Their plan_query builds: Select(pred) ← Product(Table(majors), Table(students)), tables reversed from the FROM order. Why does reversing the product's sides break nothing about the join logically… and what actually went wrong? (Hint: check their _run_query's field list for *, or their ProductScan's tie-breaking.)

Show answer

Trick question with a real lesson: reversing product sides is logically harmless; the same pairs appear in different order, and this join has no ambiguous fields. If they see zero rows, the product isn't the culprit; the usual suspect is that their planner dropped the predicate (built the SelectScan from a fresh empty Predicate, or tested if data.predicate against a Predicate with no __bool__ …). Debugging rule the exercise teaches: when a symptom survives your prime suspect's alibi, re-interrogate the description: print the QueryData before blaming the plan.

Where you'll meet this layer at work

Every SQL string you send from a notebook, through pd.read_sql, duckdb.sql, or psycopg, goes through a lexer, a parser, and a planner shaped like the three you just wrote before a single row is read. When Postgres answers a typo with syntax error at or near "35", that is its parser doing what yours does in expect: the token it names is the one that failed to match the grammar, which is where the parser first noticed and may be one token past the real mistake. The dataframe APIs you use daily are a parser you cannot see: df.filter(pl.col("gpa") > 35).select("name") in Polars, and the same chain in PySpark, build the same tree of project over select over scan that render_plan printed, with method calls as the grammar. SQL written by a language model is no exception: it is text until a parser accepts it, and the parse error is the first and cheapest check you can run on it before it touches data. The plan tree is also what EXPLAIN prints, so reading your own render_plan output is practice for reading a production plan.

Going further optional

Fast finishers: add DELETE FROM t WHERE … (a parse method plus a TableScan walk calling delete(); Sciore ch. 9 shape); add OR with parentheses to the predicate grammar (this is where recursive descent earns the "recursive"); or make expect() report the token position ("expected 'from' at token 3") and watch every error message improve at once: one helper, global upgrade, the whole argument for funneling errors through one door.

FAQ

The REPL says no such table in catalog after I restart it.

It shouldn't: ./mydb persists, and the catalog reads from disk. If tables vanish across restarts, an earlier crash likely left mydb half-written; delete the folder and re-create. (Yes: crash recovery. Lab 7 is coming for exactly this.)

Why lowercase everything? SELECT and select both work but my strings changed case!

The lexer lowercases words (keywords and IDs) but not STR tokens; check that your table/field names are compared post-lowercase and that you're not lowercasing string literals somewhere. 'Ada' must stay 'Ada'.

Can two tables in a FROM share a field name?

microSQL has no aliases, so a shared name is answered by the left table (Lab 4's tie rule), legal but a footgun. The harness avoids it; your own schemas should too. Aliases (students s) are a tidy Going-Further if the itch strikes.

My parser works but the REPL prints columns in a weird order for SELECT *.

Field order for * comes from the catalog's schema rebuild, which orders by stored offset (Lab 3). If your order looks wrong, your Lab 3 offsets were wrong first; the tower tattles on its lower floors.

Is this how SQL injection happens?

Now you can see it: injection is gluing untrusted text into SQL before your lexer runs; the attacker's words arrive as perfectly legal tokens. Your parser is blameless and helpless. The fix (parameterized queries) routes values around the front end entirely; try writing db.execute_with_params() if the itch strikes.
