    The grammar tells each method what to consume
    

    query     := SELECT fieldlist FROM tablelist [ WHERE predicate ]
fieldlist := * | field { , field }
tablelist := table { , table }
predicate := term { AND term }
term      := field ( = | < | > ) value
value     := number | 'string' | field
    

    BNF means Backus–Naur form; Extended Backus–Naur form (EBNF) adds the optional [ ] and repeated { } groups used here. | separates alternatives in the grammar. The * is a literal SQL token asking for all columns. A comma loop is “read one item, then repeat comma + item.”

    1 · SELECT becomes a QueryData object
    

    Trace SELECT name FROM students WHERE gpa > 35. Required keywords use expect; alternatives and repetitions first use match. The field and table lists are ordinary Python lists. An absent WHERE leaves predicate = None.
    

    def parse_query(self) -> QueryData:
    self.lex.expect("KEYWORD", "select")
    if self.lex.match("PUNCT", "*"):
        self.lex.next()
        fields = ["*"]
    else:
        fields = [self.lex.expect("ID")]
        while self.lex.match("PUNCT", ","):
            self.lex.next()
            fields.append(self.lex.expect("ID"))
    self.lex.expect("KEYWORD", "from")
    tables = [self.lex.expect("ID")]
    while self.lex.match("PUNCT", ","):
        self.lex.next()
        tables.append(self.lex.expect("ID"))
    predicate = None
    if self.lex.match("KEYWORD", "where"):
        self.lex.next()
        predicate = self._parse_predicate()
    return QueryData(fields, tables, predicate)
    

    The comma tests leave the comma unread; the following next() consumes it before the next name is read. The WHERE test works the same way. QueryData stores the request; it neither opens a table nor produces rows.

    2 · AND repeats terms; each term distinguishes values from fields
    

    _parse_predicate reads at least one term, then collects any additional terms after AND. Predicate(*terms) packages a conjunction; it does not evaluate it during parsing.
    

    def _parse_predicate(self) -> Predicate:
    terms = [self._parse_term()]
    while self.lex.match("KEYWORD", "and"):
        self.lex.next()
        terms.append(self._parse_term())
    return Predicate(*terms)
    

    _parse_term checks the operator and inspects the right-hand token. A number or quoted string is a constant. An identifier must be wrapped in F so execution reads that field from the current row.
    

    def _parse_term(self) -> tuple:
    field = self.lex.expect("ID")
    op = self.lex.expect("PUNCT")
    if op not in ("=", "<", ">"):
        raise ParseError(f"expected =, < or >, found {op!r}")
    if self.lex.match("ID"):
        rhs = F(self.lex.next()[1])
    else:
        rhs = self._parse_literal()
    return field, op, rhs
    

    ("gpa", ">", 35)           # numeric literal
("dept", "=", "ds")        # string literal from 'ds'
("mid", "=", F("mid2"))    # value of the other field in this pair
    

    _parse_literal is the number/string helper you just traced in INSERT. A term such as mid = mid2 needs a combined row from both tables; gpa > 35 needs only the student row. That difference will determine where a filter may safely run.
    


    3 · The planner builds operators from the description
    

    The supplied simple planner retrieves each existing table layout from the catalog. It opens table scans, combines them from left to right, adds selection if needed, and finally projects the requested fields. It checks that fields mentioned by SELECT and WHERE exist before applying the wrappers. The exception handler closes any scans already opened if construction fails.
    

    def plan_query(self, data: QueryData):
    layouts = [self.catalog.get_layout(table) for table in data.tables]
    scans = []
    try:
        for table, layout in zip(data.tables, layouts):
            scans.append(TableScan(self.bm, self.fm, table, layout))
        plan = scans[0]
        for right in scans[1:]:
            plan = ProductScan(plan, right)
        needed = set(data.fields) if data.fields != ["*"] else set()
        for field, _, rhs in data.predicate.terms if data.predicate else ():
            needed.add(field)
            if isinstance(rhs, F):
                needed.add(rhs.name)
        unknown = sorted(field for field in needed if not plan.has_field(field))
        if unknown:
            raise ParseError("unknown field(s): " + ", ".join(unknown))
        if data.predicate is not None:
            plan = SelectScan(plan, data.predicate)
        if data.fields != ["*"]:
            plan = ProjectScan(plan, data.fields)
        return plan
    except Exception:
        for scan in scans:
            scan.close()
        raise
    

    SELECT name FROM students WHERE gpa > 35

ProjectScan[name]
└── SelectScan[gpa > 35]
    └── TableScan(students)
    

    Selection must see gpa before projection hides it. SELECT * FROM students needs just the table scan. Two FROM tables create a product; its left input advances once for each complete traversal of its right input. The planner preserves the FROM order and puts the whole WHERE above the product. It does not automatically push filters down.
    


    4 · Execution pulls rows and always closes the plan
    

    def _run_query(self, data: QueryData) -> list[dict]:
    fields = data.fields
    if fields == ["*"]:
        fields = [field for table in data.tables
                  for field in self.catalog.get_layout(table).schema.fields()]
    plan = self.plan_query(data)
    try:
        plan.before_first()
        rows = []
        while plan.next():
            rows.append({field: plan.get_val(field) for field in fields})
        return rows
    finally:
        plan.close()
    

    before_first() initializes the scans; repeated next() calls on the root pull qualifying rows through the tree. get_val() reads each requested output field. The list stores the result in memory. finally releases the plan's buffer pins even if a query fails. Creating the plan alone does not enumerate the result.

    A model to reason from

    A sequential scan visits every row. A filter can reject rows after they are read. A product of L left rows and R right rows produces L × R candidate pairs. Projection changes the number of output fields. It does not provide an index or make the heap scan skip records.
    

    Separate those kinds of work. Fewer returned rows, fewer candidate pairs, fewer predicate comparisons, and fewer disk reads are different claims.

    What each measurement counts
    

    MeasurementMeaning
    

    Table row visitsSuccessful advances of each base TableScan, including rereads after rewinds. These are logical visits, not physical disk reads.
    

    Candidate pairsRows produced by ProductScan before any filter above it. For a larger product tree, counts are summed across products.
    

    Predicate comparisonsIndividual =, <, or > tests actually evaluated. AND stops at the first false term.
    

    Rows / output cellsResult rows, and rows × requested fields. Fewer cells means fewer output values decoded and stored.
    

    Execution medianMedian elapsed milliseconds for uninstrumented executions after an untimed warm-up. Includes rewind, iteration, field decoding, result materialization, and close. Excludes fixture creation, parsing, planning, and printing.
    

    

    Each process uses 4096-byte blocks and eight buffer frames. Both plans use the same generated data and repeated-run protocol. Caches are not cleared between runs, so these are not cold-storage timings. Small differences can be noise; the JSON output preserves all samples. A logical-work ratio is not a promised runtime ratio.
    


    Why the supplied early-filter alternative is valid
    

    Read early_filter_plan in the measurement script. It finds which table owns each field used by a term. A term referring to one table goes just above that table's scan. A term referring to both tables stays above the product. It preserves FROM order, then adds projection. This is a supplied comparison plan, not a cost-based optimizer.
    

    For this inner join with AND predicates, a student that fails gpa > 35 cannot appear in any final answer, whichever major it is paired with. A major that fails dept = 'ds' cannot appear either. Removing those rows before pairing them therefore preserves the answer. The equality mid = mid2 needs both rows and stays above the product. Field ownership establishes that the rewrite is valid; row counts help predict how much work it saves.
    

    Simple                            Early filter
Project[name, dept]                Project[name, dept]
└─ Select[all three terms]         └─ Select[mid = mid2]
   └─ Product                        └─ Product
      ├─ students                       ├─ Select[gpa > 35] → students
      └─ majors                         └─ Select[dept = 'ds'] → majors
    


    Worked check for J1: reveal after making your prediction

    SELECT name, dept FROM students, majors
WHERE mid = mid2 AND gpa > 35 AND dept = 'ds';
    

    With 300 students, 60 pass gpa > 35, one major passes dept = 'ds', and 20 students satisfy the full join. The simple plan produces 300 × 3 = 900 candidate pairs; the early-filter plan produces 60 × 1 = 60. Both return 20 rows and 40 output cells.
    

    The early plan still visits all 300 student rows. Its right-hand filter is restarted for each of 60 qualifying students, so it visits 60 × 3 = 180 major rows. It does not materialize and reuse the one matching major. With predicates written in J1's illustrated order, the simple plan evaluates 900 + 300 + 60 = 1260 comparisons; the early plan evaluates 300 + 180 + 60 = 540. Reordering AND terms can change comparison counts without changing the pairs or result.

    FAQ
    

    Why do both plans have the same shape for a single-table query?
    

    The filter is already directly above that table. There is no product below it to eliminate. Different execution samples can still give slightly different timings; use that variation as a reminder to avoid conclusions from one small measurement.
    

    Does the smaller output prove the query is faster?
    

    No. The engine may visit the same source rows and evaluate extra predicates to return fewer rows. Account for scanning, comparisons, pairing, and output work separately, then inspect repeated timings.
    

    Why does reversing FROM sometimes help?
    

    ProductScan restarts its right input for every left row. Reversing the inputs changes the repeated work, even when the Cartesian product size is unchanged. There is no ORDER BY here, so compare result multisets rather than row order. The measurement runner checks multiplicities too.
    

    Can I use my own tables in the measurement runner?
    

    The runner creates only the documented students and majors fixture in a temporary directory. Use microdb.py for your own persistent tables. For the required comparisons, keep the fixture fixed and change only the specified query or student count.
    

    Why did my SQL file stop with a ParseError?
    

    Check the expected and found tokens, then compare the statement with the supported grammar. Use single quotes for strings, commas between fields/tables, and one statement per semicolon. Unsupported trailing syntax is rejected. Field names must be distinct across tables for the early-filter comparison; aliases and qualified names are not supported.
