Imitation with understanding

The starter hands you two complete parsers (parse_insert and parse_create) as worked examples, because recursive descent is a pattern you absorb by reading. Each grammar rule is one method; each method consumes exactly the tokens its rule owns, using four verbs on the token stream (peek · next · match · expect). Your parse_query is the same song with two new verses: the * alternative and the optional WHERE.

Think · Pair · Share · read like a parser
  • Think · 2 minWithout running anything, trace parse_insert on INSERT INTO majors VALUES (4, 'math'): write the sequence of expect/match calls and what each consumes. Now do it on INSERT INTO majors VALUES (4 'math'), missing comma. Which call dies, and with what message?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare traces. The comma failure is subtle: the while match(",") loop simply ends, and it's the expect(")") after it that dies. Did you both catch that?
  • Share · 2 minOne sentence: why "the loop ends and the next expect dies" still produces a correct, helpful error.
Show the answer

The good trace: expect(KEYWORD,'insert'), expect(KEYWORD,'into'), expect(ID) which returns "majors", expect(KEYWORD,'values'), expect(PUNCT,'('), then a literal, then while match(',') consuming the comma and another literal, then expect(PUNCT,')').

With the comma missing, nothing dies where you would expect. match(',') simply sees 'math' instead of a comma and returns False, so the loop ends normally; the parser believes the value list is finished. It is the expect(PUNCT,')') on the next line that dies, reporting expected ')', found 'math'.

That error is still correct and still helpful, because it reports the parser's honest state: given the grammar, a value list really can end there, so the first thing that is definitely wrong is the missing close paren. The message names what was expected and what was found, which is enough to walk the user to the fault even though the diagnosis lands one token later than the typo.

The contract

Your five methods, with the moves each one borrows:

parse_query # imitates parse_insert + a * case + an optional clause
_parse_predicate # the {, } idiom wearing AND instead of a comma
_parse_term # field, op, then the F fork for join terms
Database.plan_query # scans → products → select? → project?
Hover a line: between them they touch every layer you've built since August.
Think · Pair · Share · one token, two meanings
  • Think · 2 minIn WHERE name = 'ada' the right-hand side means the string ada. In WHERE mid = mid2 it means the field mid2. Both arrive at your _parse_term as single tokens. What distinguishes them, and what must your code produce differently for each? What would silently go wrong if you returned the string "mid2" for the second?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minWork the failure: the predicate would compare each row's mid (an int) to the literal string "mid2": never equal, join returns zero rows, no error anywhere. The harness's join-term test exists for exactly this.
  • Share · 2 minOne sentence: token kind is information; STR vs ID is the lexer telling you which meaning survived the quotes.
Show the answer

The token kind distinguishes them. 'ada' arrives as a STR token because the lexer saw quotes; mid2 arrives as an ID because it did not. So _parse_term must produce a plain Python value for a STR or NUM, and an F("mid2") field marker for an ID.

Return the bare string "mid2" for the second and the failure is silent and total: the predicate compares each row's mid, an int, against the literal string "mid2". They are never equal, so the join returns zero rows, and nothing anywhere raises. A query that should join two tables quietly returns nothing, which is the hardest class of bug to notice because empty looks like a legitimate answer. That is exactly what the harness's join-term test exists to catch.

In one sentence: the token kind is information, and STR versus ID is the lexer telling you which meaning survived the quotes. Throw that distinction away in the parser and no later layer can reconstruct it.

Part 1 · Build ~30 min in class

Nine files into microdb-lab5/: five are the reference tower, the REPL is ready, and your work is one file. In harness order:

  1. Read the two worked examples (8 min, honestly): parse_insert and parse_create, next to the grammar in the module docstring. Every move you need appears in one of them.
  2. parse_query: field list (star or { , }), FROM, table list, optional WHERE. Three PARSE tests go green.
  3. _parse_predicate and _parse_term: the AND idiom and the F fork. The rest of PARSE passes, including the error tests you get for free from expect().
  4. plan_query: the four-step recipe. PLAN and SQL groups light up, and with them the REPL: python3 microdb.py, type SQL, grin.
Gotchas that cost real debugging time

The star: * is a PUNCT token, and it must short-circuit the field-list loop entirely (["*"], not ["*", ...]). In _parse_term, don't expect("PUNCT", "="); the operator may be any of three, so peek, check membership, and raise your own ParseError otherwise. And in plan_query, fetch each table's layout from self.catalog, not by constructing a new Schema; the catalog is the source of truth, that being the point of Lab 3.

Exercise · read the failure

A classmate's test_sql_join fails with zero rows returned, but every PARSE test passes, including the F test. Their plan_query builds: Select(pred) ← Product(Table(majors), Table(students)), tables reversed from the FROM order. Why does reversing the product's sides break nothing about the join logically… and what actually went wrong? (Hint: check their _run_query's field list for *, or their ProductScan's tie-breaking.)

Show answer

Trick question with a real lesson: reversing product sides is logically harmless; the same pairs appear in different order, and this join has no ambiguous fields. If they see zero rows, the product isn't the culprit; the usual suspect is that their planner dropped the predicate (built the SelectScan from a fresh empty Predicate, or tested if data.predicate against a Predicate with no __bool__ …). Debugging rule the exercise teaches: when a symptom survives your prime suspect's alibi, re-interrogate the description: print the QueryData before blaming the plan.

Part 3 · Measure ~20 min · finish as homework

Think · Pair · Share · your planner, predicted
  • Think · 2 minBefore running the measurement: your plan_query follows the four-step recipe. For the three-filter join query over 300 students × 3 majors, how many pairs will YOUR plan examine, 60 or 900? Now defend the recipe anyway: why is the shape that examines 900 the only safe default for a planner that knows nothing about the data?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minConstruct the trap together: invent a predicate where pushing a filter below the product would be flat-out WRONG. (Hint: what if a term references fields from both tables?)
  • Share · 2 minOne sentence: what a planner must know about each term before it may push it down.
Show the answer

900. The four-step recipe builds the full product first and applies the whole WHERE above it, so your planner examines every pair, exactly the shape Lab 4 called Plan A.

Defend it anyway: a planner that knows nothing about the data cannot tell whether pushing a filter helps. Filters-above-product is always correct, whatever the tables contain, and correctness that does not depend on the data is the right default when you have no statistics. Naive and honest beats clever and occasionally wrong.

The trap: a term referencing fields from both tables, such as mid = mid2, cannot be pushed to either side, because neither input can evaluate it alone. Push it below the product and the scan is asked for a field it does not have. So the rule a planner must establish before pushing any term is which input owns every field the term mentions: push it only onto an input that can answer all of them. That test is pure syntax and free; deciding whether pushing is worth it needs statistics, and that is week 9.

FAQ

The REPL says no such table in catalog after I restart it.

It shouldn't: ./mydb persists, and the catalog reads from disk. If tables vanish across restarts, an earlier crash likely left mydb half-written; delete the folder and re-create. (Yes: crash recovery. Lab 7 is coming for exactly this.)

Why lowercase everything? SELECT and select both work but my strings changed case!

The lexer lowercases words (keywords and IDs) but not STR tokens; check that your table/field names are compared post-lowercase and that you're not lowercasing string literals somewhere. 'Ada' must stay 'Ada'.

Can two tables in a FROM share a field name?

microSQL has no aliases, so a shared name is answered by the left table (Lab 4's tie rule), legal but a footgun. The harness avoids it; your own schemas should too. Aliases (students s) are a tidy Going-Further if the itch strikes.

My parser works but the REPL prints columns in a weird order for SELECT *.

Field order for * comes from the catalog's schema rebuild, which orders by stored offset (Lab 3). If your order looks wrong, your Lab 3 offsets were wrong first; the tower tattles on its lower floors.

Is this how SQL injection happens?

Now you can see it: injection is gluing untrusted text into SQL before your lexer runs; the attacker's words arrive as perfectly legal tokens. Your parser is blameless and helpless. The fix (parameterized queries) routes values around the front end entirely; try writing db.execute_with_params() if the itch strikes.
