Records, Slots & the Table Scan

The record layer identifies where each row and field begins and whether a slot is in use.
Follows Lecture 3 (Record Layout & the Catalog) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 17 at class start

The Lab 2 buffer pool loads blocks into memory but does not know where records or fields begin. You will define those positions from a schema, store records in fixed-size slots, and implement TableScan to move through a table’s heap file. The provided catalog will use your code to store and retrieve schema information.

Companion reading: Sciore, Database Design and Implementation, ch. 6–7 · Lecture 3's slides & slot inspector · a production example: PostgreSQL's page layout.

Record layout and slot addresses

Each record occupies a fixed-size slot: a four-byte status flag followed by the fields in schema order, [flag][fields]. Slot k starts at byte k * slot_size. Deleting a row sets its status flag to EMPTY so a later insert can reuse the slot. The other rows stay in place.

Classes and methods to implement

Layout calculates field offsets and the slot size. RecordPage reads and writes records within one pinned block. TableScan moves between blocks to scan or insert rows. You will implement the methods below; helpers for pinning, unpinning, and moving between blocks are provided.

Layout(schema) # id→4, name→8, gpa→20 · slot_size 24
_field_pos(slot, fld) # slot·24 + offset(fld)
get/set_int · get/set_string # read/write fields; mark writes dirty
insert_after / next_after / delete # find empty/used slots; mark deletions
TableScan.next() # cross blocks, skip tombstones
TableScan.insert() # find an empty slot, or add a block

The file and buffer managers are reference implementations from Labs 1–2, and catalog.py is complete. Implement the marked methods in record_manager.py in this order:

  1. Read the slot layout at the top of record_manager.py (3 min). It defines the required format and includes a worked example.
  2. Layout.__init__: calculate each field’s offset and the slot size. Run python3 test_records.py --unit Layout.__init__. For the students schema, the expected offsets are 4, 8, and 20 bytes; the slot size is 24 bytes.

    Pseudocode (byte offsets measured from the start of a slot):

    offsets ← empty map
next_offset ← 4                         // reserve the status flag

for each field in schema order:
    offsets[field] ← next_offset         // save where this field begins
    if the field is an integer:
        next_offset ← next_offset + 4
    otherwise, for varchar(n):
        next_offset ← next_offset + 4 + n  // length prefix + byte capacity

slot_size ← next_offset                 // flag + all reserved field bytes

    Use self._offsets for the map and self.slot_size for the final size. Here, n = schema.length_of(field) is the reserved UTF-8 byte capacity. A varchar(8) field always reserves 4 + 8 = 12 bytes, even for a shorter value.

  3. _field_pos, then the four get/set methods: calculate each field’s byte position and use the page’s read or write method. Reject strings whose UTF-8 byte length exceeds the field’s capacity. Call set_modified() after each write. Test each method with its own target, such as --unit RecordPage._field_pos or --unit RecordPage.set_string.
  4. insert_after, next_after, and delete: search for an EMPTY or USED slot as required, and update the status flag when inserting or deleting. Run --unit RecordPage.insert_after, --unit RecordPage.next_after, and --unit RecordPage.delete as you finish them.
  5. TableScan.next(), then insert(): implement the loops using the provided block-navigation helpers. Test them separately with --unit TableScan.next and --unit TableScan.insert. Then run python3 test_records.py to check all twelve integration tests, including the provided catalog.
Common implementation mistakes

Call set_modified() after every write so changes are saved before the block leaves the buffer pool. After moving to another block, search from slot -1 so the search includes slot 0. Use _move_to_block to unpin the old block before pinning the next. Leaving old blocks pinned can exhaust the pool and cause BufferAbortError.

Exercise · read the failure

After twelve inserts, a classmate’s table occupies twelve blocks instead of three. All twelve rows still read back correctly and in order. Which insertion mistake could cause this? Why is checking the row contents alone insufficient?

Show answer

insert() may be appending a block for each new row instead of searching the current block for another empty slot. Each block then contains only one row, leaving four slots unused in this example. A scan can still return every row correctly, so the tests must check both the contents and the number of blocks.

Where record storage and schema metadata appear

  • \d students in psql and DESCRIBE in DuckDB inspect schema metadata. Your catalog stores similar information: field names, types, capacities, and offsets. df.info() inspects the dataframe’s own metadata rather than querying a database catalog.
  • Columnar formats also distinguish fixed-width and variable-width data. Fixed-width values have predictable offsets; variable-width values need metadata to locate their boundaries. Your Layout avoids that lookup by reserving a fixed number of bytes for each string field.
  • In microdb, VARCHAR(8) always reserves eight bytes for the UTF-8 value and four bytes for its length, even for a shorter name. PostgreSQL allows string values to occupy different amounts of space.
  • TableScan.rid() returns a RID: the row’s block number and slot number. Lab 6’s index stores RIDs beside its keys so it can locate matching rows. Vector indexes also return identifiers for matching records, although those identifiers need not be physical block-and-slot addresses.
  • PostgreSQL retains old row versions for active snapshots. VACUUM reclaims them when they are no longer visible. This resembles our need to reuse space, but does not use microdb’s EMPTY flag.

FAQ

Why does a reused slot return an old string?

Deleting a row marks its slot EMPTY without erasing its bytes. Write each field before reading a reused slot. If get_string still returns an old or incorrect value, check that set_string writes the length prefix at _field_pos and the new bytes immediately after it.

Why does insert() mark USED before the fields are written?

Marking the slot USED reserves it, so later searches for empty slots will skip it. In this single-threaded lab, the caller writes the fields before another operation reads the row. Concurrent databases also use synchronization, such as latches, and recovery rules to protect records during updates.

Can two tables share one file?

Microdb uses one heap file per table to keep the mapping from table names to blocks simple. Other engines may store several tables in one file or split a table across multiple files.

The catalog file grew to 2 blocks for one table. Why?

field_catalog stores one row per field. Each row occupies 64 bytes, so a 128-byte test block holds two rows. The students table has three fields, requiring three catalog rows across two blocks. User tables and the catalog follow the same layout rules.
