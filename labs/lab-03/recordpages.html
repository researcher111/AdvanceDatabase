Records, Slots & the Table Scan

The ada row gets an address, the file becomes a table, and the catalog writes itself.
Follows Lecture 3 (Record Layout & the Catalog) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 17 at class start

Three layers tall now: your Lab 1 pages hold the bytes, your Lab 2 pool decides what's in memory, and today's record layer decides what the bytes mean. You'll compute layouts from schemas, pack rows into fixed slots inside the heap file, and write the two loops of TableScan, after which the provided catalog starts describing your database in its own tables, using nothing but the code you wrote.

Companion reading: Sciore, Database Design and Implementation, ch. 6–7 · Lecture 3's slides & slot inspector · the grown-up version: PostgreSQL's page layout.

Slots buy O(1)

Lecture 3 made the argument; here is the working summary you'll code against. A record slot is [4-byte flag][fields in schema order], every slot identical, so every address is arithmetic, and a deleted row is a tombstone, not a hole.

The contract

Three classes, three altitudes: Layout computes the byte map, RecordPage operates within one pinned block, TableScan walks the whole file. You write the arithmetic and the two traversal loops; all pin plumbing and block-hopping helpers are provided.

Layout(schema) # id→4, name→8, gpa→20 · slot_size 24
_field_pos(slot, fld) # slot·24 + offset(fld)
get/set_int · get/set_string # one page call each (+ set_modified)
insert_after / next_after / delete # find-EMPTY · find-USED · bit flip
TableScan.next() # cross blocks, skip tombstones
TableScan.insert() # recycle a tombstone, or grow the file
Hover a line for its spec; the harness tests them in exactly this order.

Part 1 · Build ~35 min in class

Six starter files into microdb-lab3/: two are your reference lower layers, catalog.py is complete, and all your work lives in record_manager.py. The build order matches the harness groups:

  1. Read the slot-layout spec in the module docstring (3 min); it is the whole contract, worked example included.
  2. Layout.__init__: the offset walk. Run the harness: the LAYOUT group names the exact numbers it expects (4 / 8 / 20 / 24).
  3. _field_pos, then the four get/set methods: one formula, four one-liners. Setters end with set_modified(). RECORD test 1 goes green.
  4. insert_after, next_after, delete: three flag scans. All of RECORD passes.
  5. TableScan.next(), then insert(): the two loops from the annotated code above, using the provided _move_to_block / _append_new_block helpers. SCAN, then CATALOG, go green: the catalog needs no work from you; it's your scan's first customer.
Gotchas that cost real debugging time

Forgetting set_modified() in a setter passes every in-memory test and fails the durable one. In next(), re-ask from slot -1 after moving blocks, not from current_slot, which belonged to the previous block. And never call bm.pin yourself in TableScan: _move_to_block owns the unpin-then-pin handoff; the 2-frame-pool test aborts loudly if pins leak.

Exercise · read the failure

A classmate passes everything except file grows to exactly 3 blocks: their file has 12 blocks after 12 inserts. Every row also reads back correctly, in order. Which loop has the bug, what exactly is it doing, and why do all the other SCAN tests still pass?

Show answer

insert() never retries the current block: on any miss (or unconditionally) it jumps straight to _append_new_block(), so every insert after the first lands in slot 0 of a brand-new block: 12 rows, 12 blocks, 4 empty slots each. Scans still work because next() dutifully walks all 12 blocks and finds every row in order. The block-count test exists precisely because correctness-of-contents can hide a 5× storage bug.

Where you'll meet this layer at work

df.info(), \d students in psql, and DESCRIBE in DuckDB all read a catalog: rows in a table that record each column's name, type, and width, which is what your Catalog.create_table wrote and get_layout read back. When Arrow or Parquet calls a column fixed-width (int64, float64, a timestamp) or variable-width (string, binary), it is the distinction behind your Layout: a fixed-width column can be located by arithmetic and copied straight into a NumPy array, a variable-width one needs an offsets array first, which is why string columns are the slow ones in pandas. The VARCHAR(8) you sized reserves 8 characters whether a name uses them or not; Postgres stores strings at their actual length instead, and pays for it by walking every earlier column's length to find a later column's bytes, which is why a wide table with many text columns is slow to read the last column of. The RID your TableScan.rid() returns, a block number and a slot, is what every index in Lab 6 stores next to a key, and what a vector store hands back from a nearest-neighbor query is the same thing: an id that points at a row, not the row. When a Postgres table bloats after many updates and deletes, the cause is slots marked EMPTY that no scan reclaims until VACUUM runs; you wrote the flag it checks.

FAQ

My strings come back with old garbage after slot reuse.

Working as designed: a recycled tombstone's bytes hold the ghost until you overwrite them, and the length prefix keeps reads inside whatever was last written. If you're seeing garbage, the length prefix itself is stale: check that set_string writes at _field_pos, not at the slot start.

Why does insert() mark USED before the fields are written?

So the slot is claimed: any other code path scanning for free slots must not hand out the same slot twice. The cost is a momentarily incoherent row; real engines handle that window with latches and WAL ordering; microdb handles it by being single-threaded. Week 7 makes this question serious.

Can two tables share one file?

Not in microdb: one heap file per table keeps the mapping trivial (that's what the catalog records). Real engines do both: SQLite puts a whole database in one file; Postgres gives each table its own file chain. The block abstraction doesn't care.

The catalog file grew to 2 blocks for one table. Why?

field_catalog's own slot is 64 bytes (two varchar(16)s, a varchar(8), two ints); a 128-byte harness block fits 2 rows. Three students fields → 2 blocks. Your layout arithmetic, applied to the catalog itself: pleasingly circular, easily verified.
