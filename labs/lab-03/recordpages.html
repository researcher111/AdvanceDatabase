Records, Slots & the Table Scan

The ada row gets an address, the file becomes a table, and the catalog writes itself.
Follows Lecture 3 (Record Layout & the Catalog) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 17 at class start

Three layers tall now: your Lab 1 pages hold the bytes, your Lab 2 pool decides what's in memory, and today's record layer decides what the bytes mean. You'll compute layouts from schemas, pack rows into fixed slots inside the heap file, and write the two loops of TableScan, after which the provided catalog starts describing your database in its own tables, using nothing but the code you wrote.

Slots buy O(1)

Lecture 3 made the argument; here is the working summary you'll code against. A record slot is [4-byte flag][fields in schema order], every slot identical, so every address is arithmetic, and a deleted row is a tombstone, not a hole.

Think · Pair · Share · where does row 9 live?
  • Think · 2 minstudents rows are inserted 0,1,2,… into an empty table: 24-byte slots, 128-byte blocks in the harness. Compute where row 9 lands: block number, slot number, and the byte offset of its gpa within its block. That (block, slot) pair is its RID.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare answers (5 slots per block: 9 = block 1, slot 4; gpa at 4×24+20 = byte 116). Now delete row 2 and insert a new row: what's the new row's RID, and why?
  • Share · 2 minOne sentence: why do stable RIDs matter to a structure that stores "gpa 39 lives at (0,0)", like the index you'll build in week 6?
Show the answer

128-byte blocks over 24-byte slots gives 5 slots per block, so row 9 is block 1, slot 4, and its gpa sits at 4 × 24 + 20 = byte 116 of that block. Its RID is (1, 4).

Delete row 2 and insert a new row: the new row takes RID (0, 2), the tombstone left behind, because insert_after hunts forward for the first EMPTY slot and finds the recycled one before the file ever grows.

Why stability matters: an index stores "gpa 39 lives at (0, 0)". If a delete or an update elsewhere could shift rows, every index entry, every cursor, and every saved position would silently point at the wrong row. Fixed slots mean a RID handed out today is still correct in week 6, which is what makes an index a pointer rather than a hint.

The contract

Three classes, three altitudes: Layout computes the byte map, RecordPage operates within one pinned block, TableScan walks the whole file. You write the arithmetic and the two traversal loops; all pin plumbing and block-hopping helpers are provided.

Layout(schema) # id→4, name→8, gpa→20 · slot_size 24
_field_pos(slot, fld) # slot·24 + offset(fld)
get/set_int · get/set_string # one page call each (+ set_modified)
insert_after / next_after / delete # find-EMPTY · find-USED · bit flip
TableScan.next() # cross blocks, skip tombstones
TableScan.insert() # recycle a tombstone, or grow the file
Hover a line for its spec; the harness tests them in exactly this order.

Write the exact sequence your code must perform: file operation, pin traffic, and where the new row's flag gets set. What did Lab 1's append() promise about a fresh block's bytes that makes this safe?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare sequences: append (zeroed block = all flags EMPTY) → move there (unpin old, pin new) → insert_after(-1) lands in slot 0. What breaks if append handed back garbage bytes instead of zeros?
  • Share · 2 minThe harness counts your file's blocks after 12 inserts and expects exactly 3. State the bug it's hunting in five words or fewer.
Show the answer

The sequence: append() a new block, unpin the old block, pin the new one, then insert_after(-1), which lands in slot 0, and the flag is set to USED by insert_after itself before the caller writes any fields.

What makes it safe is Lab 1's promise that append() hands back a zeroed block. Zero is the EMPTY flag value, so a fresh block is five valid empty slots by construction, with no initialisation pass required. If append returned garbage instead, random bytes would read as USED flags, and the scan would return rows that were never inserted while insert refused to use slots that were actually free.

The bug the harness hunts, in five words: appending instead of reusing tombstones. Skip the search and jump straight to a new block and you get 12 blocks for 12 rows instead of 3, with four wasted slots in each. Every read still works, which is exactly why only a block count catches it.

Part 1 · Build ~35 min in class

Six starter files into microdb-lab3/: two are your reference lower layers, catalog.py is complete, and all your work lives in record_manager.py. The build order matches the harness groups:

  1. Read the slot-layout spec in the module docstring (3 min); it is the whole contract, worked example included.
  2. Layout.__init__: the offset walk. Run the harness: the LAYOUT group names the exact numbers it expects (4 / 8 / 20 / 24).
  3. _field_pos, then the four get/set methods: one formula, four one-liners. Setters end with set_modified(). RECORD test 1 goes green.
  4. insert_after, next_after, delete: three flag scans. All of RECORD passes.
  5. TableScan.next(), then insert(): the two loops from the annotated code above, using the provided _move_to_block / _append_new_block helpers. SCAN, then CATALOG, go green: the catalog needs no work from you; it's your scan's first customer.
Gotchas that cost real debugging time

Forgetting set_modified() in a setter passes every in-memory test and fails the durable one. In next(), re-ask from slot -1 after moving blocks, not from current_slot, which belonged to the previous block. And never call bm.pin yourself in TableScan: _move_to_block owns the unpin-then-pin handoff; the 2-frame-pool test aborts loudly if pins leak.

Exercise · read the failure

A classmate passes everything except file grows to exactly 3 blocks: their file has 12 blocks after 12 inserts. Every row also reads back correctly, in order. Which loop has the bug, what exactly is it doing, and why do all the other SCAN tests still pass?

Show answer

insert() never retries the current block: on any miss (or unconditionally) it jumps straight to _append_new_block(), so every insert after the first lands in slot 0 of a brand-new block: 12 rows, 12 blocks, 4 empty slots each. Scans still work because next() dutifully walks all 12 blocks and finds every row in order. The block-count test exists precisely because correctness-of-contents can hide a 5× storage bug.

Part 3 · Measure ~20 min · finish as homework

Think · Pair · Share · the price of a wide column
  • Think · 2 minSame 4096-byte blocks. Schema A is students (24-byte slots). Schema B swaps the name for bio varchar(200). Predict: rows per block for each, and how many blocks a 10,000-row table needs. Is B's file 5× bigger, 10× bigger, or something else?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minDo the division together (4096 // slot). Now the sharper question: if most bios are 40 chars, what fraction of B's file is air?
  • Share · 2 minRun python3 measure_layout.py and check the table. One sentence: what does schema design have to do with I/O cost?
Show the answer

4096 // 24 = 170 rows per block for students, 16 bytes wasted. 4096 // 212 = 19 rows per block for the wide schema, 68 bytes wasted. So 10,000 rows need 59 blocks versus 527: not 5× or 10× but about 8.9×, because what scales is rows-per-block, not the declared width.

If most bios are 40 characters, the bio field stores 44 useful bytes in 204 reserved, so roughly 78% of that field is air, and the file is close to eight times larger than the data in it. Nobody wrote that waste; it followed from one varchar(200).

So what does schema design have to do with I/O cost? Everything, because column width sets rows per block, and rows per block sets how many blocks a scan must read. Declaring a generous varchar is not free insurance; it is a standing order to read nine times more disk on every full scan for the life of the table.

The reference output is deterministic, so yours must match:

$ python3 measure_layout.py
schema                                 |  slot | rows/blk | waste/blk | blocks for 10k
----------------------------------------------------------------------------------------
students(id int, name vc(8), gpa int)  |    24 |      170 |      16 B |             59
wide   (id int, bio vc(200))           |   212 |       19 |      68 B |            527
skinny (id int, x int)                 |    12 |      341 |       4 B |             30

actual file after inserting 10,000 students rows: 59 blocks (236 KB)
full scan read back 10,000 rows through an 8-frame pool: hit rate 1.7% (remember the cliff?)

Three lessons in one table: schema width sets I/O cost (59 vs 527 blocks for the same 10,000 rows); the arithmetic predicts the real file exactly (that's what a contract is); and the scan's ~0% hit rate is last week's cliff making a cameo: a full pass through an 8-frame pool re-uses nothing.

FAQ

My strings come back with old garbage after slot reuse.

Working as designed: a recycled tombstone's bytes hold the ghost until you overwrite them, and the length prefix keeps reads inside whatever was last written. If you're seeing garbage, the length prefix itself is stale: check that set_string writes at _field_pos, not at the slot start.

Why does insert() mark USED before the fields are written?

So the slot is claimed: any other code path scanning for free slots must not hand out the same slot twice. The cost is a momentarily incoherent row; real engines handle that window with latches and WAL ordering; microdb handles it by being single-threaded. Week 7 makes this question serious.

Can two tables share one file?

Not in microdb: one heap file per table keeps the mapping trivial (that's what the catalog records). Real engines do both: SQLite puts a whole database in one file; Postgres gives each table its own file chain. The block abstraction doesn't care.

The catalog file grew to 2 blocks for one table. Why?

field_catalog's own slot is 64 bytes (two varchar(16)s, a varchar(8), two ints); a 128-byte harness block fits 2 rows. Three students fields → 2 blocks. Your layout arithmetic, applied to the catalog itself: pleasingly circular, easily verified.
