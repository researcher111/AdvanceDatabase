Records, Slots & the Table Scan

The record layer identifies where each row and field begins and whether a slot is in use.
Follows Lecture 3 (Record Layout & the Catalog) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 17 at class start

The Lab 2 buffer pool loads blocks into memory but does not know where records or fields begin. You will define those positions from a schema, store records in fixed-size slots, and implement TableScan to move through a table’s heap file. The provided catalog will use your code to store and retrieve schema information.

Companion reading: Sciore, Database Design and Implementation, ch. 6–7 · Lecture 3's slides & slot inspector · a production example: PostgreSQL's page layout.

Record layout and slot addresses

Each record occupies a fixed-size slot: a four-byte status flag followed by the fields in schema order, [flag][fields]. Slot k starts at byte k * slot_size. Deleting a row sets its status flag to EMPTY so a later insert can reuse the slot. The other rows stay in place.

Classes and methods to implement

Layout calculates field offsets and the slot size. RecordPage reads and writes records within one pinned block. TableScan moves between blocks to scan or insert rows. You will implement the methods below; helpers for pinning, unpinning, and moving between blocks are provided.

Layout(schema) # id→4, name→8, gpa→20 · slot_size 24
_field_pos(slot, fld) # slot·24 + offset(fld)
get/set_int · get/set_string # read/write fields; mark writes dirty
insert_after / next_after / delete # find empty/used slots; mark deletions
TableScan.next() # cross blocks, skip tombstones
TableScan.insert() # find an empty slot, or add a block

    Pseudocode for Layout.__init__. Translate these steps into Python using the explanations below. The starter already handles lines 1–2; implement the remaining steps in the marked section.

     1  keep the supplied schema
 2  prepare an empty field-offset map
 3  position ← size of the slot's status flag
 4  for each field in schema order:
 5      record position as this field's offset
 6      if the field is an integer:
 7          advance position by the integer size
 8      otherwise:
 9          advance position by the length-prefix size + field capacity
10  store the final position as the slot size
    LineExplanation
    1Keep the schema so the layout can look up field names, types, and capacities later.
    2The map will associate each field name with its starting byte offset within a slot.
    3Start at byte 4. Bytes 0–3 hold the in-use flag. The position tracks the next free byte within the slot.
    4Visit fields in the order the schema defines them so their byte positions stay consistent.
    5Save the current position before advancing it; this is where the field begins.
    6Use the field’s declared type to choose how much space to reserve.
    7An integer occupies 4 bytes, so move the position forward by 4.
    8The other supported type is a variable-length string.
    9Reserve 4 bytes for the string’s length prefix plus its full UTF-8 byte capacity. A varchar(8) always needs 12 bytes, even for a shorter value.
    10After the loop, the position is the total slot size: the status flag plus all reserved field bytes. Replace the starter’s zero placeholder with this value.

    TableScan.next()Method entry · ready to step

      A search helper runs as one step; outlined slots show what it checked. Moving blocks unpins the old page before pinning the new one. The final page stays pinned until close().

      next(): find the next existing row.

      def next(self) -> bool:
    self.current_slot = self.rp.next_after(self.current_slot)
    while self.current_slot < 0:
        if self._at_last_block():
            return False
        self._move_to_block(self.rp.block.blknum + 1)
        self.current_slot = self.rp.next_after(-1)
    return True
      LineExplanation
      1Define a method that returns whether it found another row.
      2Ask the current record page for the next USED slot after the current position. Save the returned slot number, or -1 if none remains on this page.
      3While no row has been found, keep looking in later blocks. The loop can skip several empty blocks.
      4Check whether the current block is the last block in the table file.
      5No row remains on this page and there are no later blocks, so return False to end the scan.
      6Move to the next block. The helper closes the old record page to unpin it, opens the new page, and resets the current slot to -1.
      7Search the new page from before slot 0. Passing -1 lets next_after include slot 0 in its search.
      8The loop ends when the current slot identifies a USED row. Return True; the caller can now read that row’s fields.
      Question · reading the search result

      Why does next_after() return -1 while we are in block 0?

      next_after() searches for the next USED slot within the current block, starting after self.current_slot.

      In the walkthrough’s “Cross an empty block” example, block 0 contains:

      Slot01234
      StatusUSEDUSEDEMPTYEMPTYEMPTY

      The current slot is 1, so the search checks slots 2, 3, and 4. None is USED, so it returns -1, meaning “no later row in this block.”

      TableScan.next() then moves to block 1 and calls next_after(-1) to search that block starting at slot 0. As an argument, -1 starts the search before slot 0; as a return value, it means no matching slot was found.

      Test this method with python3 test_records.py --unit TableScan.next.

      insert(): reserve a slot for a new row.

      def insert(self) -> None:
    slot = self.rp.insert_after(self.current_slot)
    while slot < 0:
        if self._at_last_block():
            self._append_new_block()
        else:
            self._move_to_block(self.rp.block.blknum + 1)
        slot = self.rp.insert_after(-1)
    self.current_slot = slot
      LineExplanation
      1Define a method that positions the scan on a new row and returns no value.
      2Ask the current page to find an EMPTY slot after the current position and mark it USED. Save its slot number, or -1 if none remains.
      3If no slot was reserved, continue searching forward through the file.
      4Check whether there is another existing block to search.
      5At the last block, append a zeroed block. This helper also moves the scan to it; all its slots start EMPTY.
      6Otherwise, the file already has another block.
      7Move to that existing block, unpinning the old page before opening the next one.
      8Try to reserve a slot on the new page, starting before slot 0. If none is available, the loop repeats.
      9Store the reserved slot as the current position. The caller can now use set_int() and set_string() to fill the new row.

      insert() searches forward from the current position. Call before_first() first if you want it to consider empty slots earlier in the file.

      Test this method with python3 test_records.py --unit TableScan.insert. Once all required methods are complete, run python3 test_records.py to check all twelve integration tests, including the provided catalog.

    Common implementation mistakes

    Call set_modified() after every write so changes are saved before the block leaves the buffer pool. After moving to another block, search from slot -1 so the search includes slot 0. Use _move_to_block to unpin the old block before pinning the next. Leaving old blocks pinned can exhaust the pool and cause BufferAbortError.

    Where record storage and schema metadata appear

    • \d students in psql and DESCRIBE in DuckDB inspect schema metadata. Your catalog stores similar information: field names, types, capacities, and offsets. df.info() inspects the dataframe’s own metadata rather than querying a database catalog.
    • Columnar formats also distinguish fixed-width and variable-width data. Fixed-width values have predictable offsets; variable-width values need metadata to locate their boundaries. Your Layout avoids that lookup by reserving a fixed number of bytes for each string field.
    • In microdb, VARCHAR(8) always reserves eight bytes for the UTF-8 value and four bytes for its length, even for a shorter name. PostgreSQL allows string values to occupy different amounts of space.
    • TableScan.rid() returns a RID: the row’s block number and slot number. Lab 6’s index stores RIDs beside its keys so it can locate matching rows. Vector indexes also return identifiers for matching records, although those identifiers need not be physical block-and-slot addresses.
    • PostgreSQL retains old row versions for active snapshots. VACUUM reclaims them when they are no longer visible. This resembles our need to reuse space, but does not use microdb’s EMPTY flag.

    FAQ

    Why does a reused slot return an old string?

    Deleting a row marks its slot EMPTY without erasing its bytes. Write each field before reading a reused slot. If get_string still returns an old or incorrect value, check that set_string writes the length prefix at _field_pos and the new bytes immediately after it.

    Why does insert() mark USED before the fields are written?

    Marking the slot USED reserves it, so later searches for empty slots will skip it. In this single-threaded lab, the caller writes the fields before another operation reads the row. Concurrent databases also use synchronization, such as latches, and recovery rules to protect records during updates.

    Can two tables share one file?

    Microdb uses one heap file per table to keep the mapping from table names to blocks simple. Other engines may store several tables in one file or split a table across multiple files.

    The catalog file grew to 2 blocks for one table. Why?

    field_catalog stores one row per field. Each row occupies 64 bytes, so a 128-byte test block holds two rows. The students table has three fields, requiring three catalog rows across two blocks. User tables and the catalog follow the same layout rules.
