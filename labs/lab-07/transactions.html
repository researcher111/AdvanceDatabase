Transactions & Recovery

A crash can interrupt a transfer after the debit reaches disk but before the credit does. Use the log to restore the incomplete transaction.
Follows Lectures 7–8 · in class: 75 min · aim to finish Build + Verify · due Tuesday Oct 20 at class start (before the midterm)

In this lab, you will complete microdb’s transaction layer. Implement set_int and set_string so old values reach the log before data pages change. Then implement commit, rollback, and recover() with the required flush ordering. Finally, crash_demo.py will terminate the engine during a transfer. Your recovery code must preserve the completed transfer and undo the incomplete one.

Companion reading: Sciore, Database Design and Implementation, ch. 5 · Lectures 7 (WAL) and 8 (locks & MVCC) · a production recovery design: the ARIES paper.

Sync the old value before changing the page

The write-ahead rule is precise: recovery information must reach durable storage before the data it protects. This lab syncs each log append by default, then uses FORCE at commit: flush dirty data pages before syncing COMMIT. JSON lines make the log readable; production formats add checksums and recovery metadata.

Commit completes after the required data writes and the COMMIT log record are durable. This lab performs multiple syncs per transaction.

Implement five transaction operations in the required order

The provided LogManager appends records and reads them backward. The LockTable controls access to blocks and holds locks until transaction completion. Read both before implementing the five operations below.

set_int: xlock · sync OLD value to log · write new · set_modified
commit: flush pages · fsync COMMIT · release · unpin
rollback: scan backward · restore old values · flush · sync ROLLBACK · release
recover: identify completed transactions · undo the others · flush · sync ROLLBACK
Hover or tap a line to see the required read, write, and flush order.

  1. Read LogManager and LockTable (about 8 min). Check that log appends sync by default, and identify where the transaction code must flush data pages.
  2. set_int, then set_string: follow the lock, log, modify, and mark-dirty sequence. Run the WAL test group.
  3. commit: flush the pages, sync COMMIT, release locks, and unpin. Run the first COMMIT test.
  4. rollback: scan your transaction’s changes backward, restore old values, flush, then record completion. Check the test that updates the same slot twice.
  5. recover: implement the module-level recovery function. Identify finished transactions during the backward scan, undo the others, then flush repairs before recording completion. Run the subprocess crash tests.
Common implementation mistakes

Read the old value from the buffer's page, not from disk; the current value may never have been flushed. In rollback, stop at your own START record, not the first START you meet (other transactions' records interleave). And in recover, the ROLLBACK records must be written after the undo flush; otherwise a later recovery could skip a repair that never became durable.

A classmate passes everything except recovery twice is harmless: the second recover() returns [2] again instead of [], though the balances stay correct. What did their first recovery forget, and why do the balances hide the bug?

Show answer

The first recovery did not record completion with ROLLBACK records visible to the next log read. The second pass therefore treats tx2 as unfinished and restores its old values again. Assigning the same old values leaves the balances unchanged, but the return value reveals that recovery repeated completed work. Flush the repairs before appending and syncing the completion records.

Production databases use different recovery designs

Your lab uses physical undo. PostgreSQL instead replays WAL and uses transaction visibility to keep aborted row versions out of query results. Both protect a transaction’s all-or-nothing outcome, but their recovery algorithms differ. A retryable pipeline also needs idempotency: an earlier attempt may have committed before the client lost its connection. PostgreSQL’s WAL introduction explains its redo design.

Where you'll meet itRequired behavior
A pipeline dies halfway through writing its outputin-place file writes may leave partial output. A database transaction makes the output atomic: either the commit succeeds or unfinished changes are excluded after recovery
An Airflow task is retried after a crashrequires idempotency or deduplication if the earlier attempt may already have committed
A loop commits one row at a timemany small transactions incur repeated commit overhead. Bulk loading with COPY or grouping inserts into a transaction can amortize that cost; logging and data writes are still required
Two notebooks write the same tableuncoordinated file writes can overwrite each other. In microdb, conflicting exclusive-lock requests raise LockAbortError; production engines may wait or abort

Going further optional

Optional: add a quiescent checkpoint. Stop admitting transactions, finish or roll back all active transactions, flush data, then sync a CHECKPOINT record. Only then may undo recovery stop at that record. Supporting checkpoints while transactions remain active needs additional recovery metadata. Another extension is to add redo records and study the extra machinery ARIES requires.

FAQ

Why does the RECOVER test fail before recovery begins?

The test first asserts A=$0 is on disk pre-recovery, proving the steal happened. If that assert fails, your set_int isn't calling set_modified(), so the "dirty" page was never really dirty and flush_all wrote nothing. The bug is in the write path, not the recovery.

Why JSON for log records? Real WALs are binary.

JSON keeps log records easy to inspect. Use cat microdb.log to check transaction IDs, record locations, old values, and completion records while debugging. This format favors readability for the lab; production formats use additional metadata and integrity checks. ARIES records also support redo and restartable undo.

Could two transactions deadlock in microdb?

No lock-wait deadlock can form because the lab raises an error immediately on a conflicting request. The caller must roll back that transaction. This simplifies a single-threaded implementation but can abort work that a waiting system could eventually complete. Lecture 8 explains deadlock handling in engines that wait.
