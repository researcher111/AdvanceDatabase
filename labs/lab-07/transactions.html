One rule, one fsync

Everything in this lab is consequences of one sentence: the old value reaches the log before the page changes, and the COMMIT record's fsync is the moment of truth. The log is an append-only file of JSON lines, which is not a toy stand-in; an append-only file with disciplined fsyncs is what a WAL is.

Think · Pair · Share · order the commit
  • Think · 2 mincommit() must do three things: flush the dirty data pages, fsync a COMMIT record, release locks & pins. Six orderings exist. For each of the two wrong-looking ones (record-before-flush, and release-before-record), construct the crash that burns you.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minRecord-before-flush: crash after the record → recovery sees COMMIT, skips undo, but the data never hit disk (that's why NO-FORCE engines need redo). Release-before-record: another tx reads your data, then the crash uncommits you: a dirty read with extra steps.
  • Share · 2 minRecite the safe order: flush · fsync · release. The tests check it by consequence.
Show the answer

Record-before-flush: the COMMIT record is fsync'd, then the crash arrives before the data pages are written. Recovery reads the log, sees a COMMIT, concludes the transaction finished, and skips undo. But the changes never reached disk, so committed work is silently missing. That is precisely why NO-FORCE engines must log new values and redo them; microdb avoids the whole problem by flushing first.

Release-before-record: locks are released, another transaction reads your data and acts on it, and then the crash arrives before your COMMIT record was durable. Recovery finds you unfinished and undoes you, so the other transaction read a value that officially never existed. That is a dirty read with extra steps, and it can propagate arbitrarily far before anyone notices.

The safe order is therefore flush, fsync the COMMIT record, then release: make the data durable, make the decision durable, and only then let anyone else see it. The tests check it by consequence rather than by inspection, which is why getting it merely nearly right still fails them.

The contract

The LogManager (append + backward read) and the strict-2PL LockTable ship complete and are worth reading; together they're 60 lines. You write five things:

set_int: xlock · log OLD value · write new · set_modified
commit: flush pages · fsync COMMIT · release · unpin
rollback: walk back · restore olds · receipt · release
recover: fates first, then undo the unfinished · receipts
Hover a line: five jobs, and every one is an ordering discipline more than an algorithm.
Think · Pair · Share · same slot, twice
  • Think · 2 minOne transaction sets A := 1 (logging old=100), then A := 2 (logging old=1), then rolls back. Walk the undo BOTH directions: oldest-first and newest-first. Which one leaves A = 100, and why does the other leave the wrong answer with perfect confidence?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minNewest-first: 2→1, then 1→100 ✓. Oldest-first: 1→100, then… the old=1 record restores 1. Wrong, silently. The harness's "same slot twice" test is exactly this trap.
  • Share · 2 minOne sentence: why undo must retrace steps in reverse, like leaving a maze.
Show the answer

Newest-first is correct. The records are old=100 then old=1. Walking backwards: restore 1 (A becomes 1), then restore 100 (A becomes 100). Correct.

Oldest-first: restore 100 (A becomes 100), then restore 1 (A becomes 1). Wrong, and this is the dangerous part: nothing errors, no invariant is violated, and the final value 1 is a perfectly plausible account balance. The undo ran to completion with perfect confidence and left corrupted data. The harness's "same slot twice" test exists for exactly this trap, because a rollback that touches each slot only once cannot tell the two orders apart.

In one sentence: undo must retrace the steps in reverse because each log record restores the state that existed immediately before its own change, so the records are only valid when applied in the reverse of the order they were written. It is leaving a maze: you have to walk the turns backwards, and taking them in the original order just gets you lost somewhere new.

  2. set_int, then set_string: the four-step dance. WAL group greens.
  3. commit: four calls in the sacred order. First COMMIT test passes.
  4. rollback: backward walk, restore, receipt. Mind the same-slot-twice test.
  5. recover: the module-level function; fates before writes, receipts after. The subprocess-murder tests go green, and with them, the semester's promise.
Gotchas that cost real debugging time

Read the old value from the buffer's page, not from disk; the current value may never have been flushed. In rollback, stop at your own START record, not the first START you meet (other transactions' records interleave). And in recover, the receipts must be written after the undo flush; a receipt for an un-flushed undo is a lie the next crash exposes.

Part 2 · Verify ~20 min in class

Nine tests, four groups. WAL checks the rule literally (the log record must hold the old value, with its address). COMMIT checks durability-in-order and both rollback traps. RECOVER is the showpiece: a subprocess commits one transfer, half-finishes another, and dies by os._exit: your recovery must keep the committed money and erase the rest, and doing it twice must change nothing (idempotence). Exercise · read the failure

A classmate passes everything except recovery twice is harmless: the second recover() returns [2] again instead of [], though the balances stay correct. What did their first recovery forget, and why do the balances hide the bug?

Show answer

No ROLLBACK receipts were written (or written without reaching the log before the second read). The second pass finds tx2 still fate-less and re-undoes it, harmlessly, because restoring an old value twice restores it once. Idempotence of the data masked non-idempotence of the bookkeeping; the return value is the tell. In ARIES the same receipt exists (the end record) for the same reason.

Part 3 · The kill ~25 min · finish as homework

No predictions to commit this time, just an execution. crash_demo.py stages the full drama: a committed transfer, a half-done one, a stolen dirty page, and an os._exit(1). Reference output:

FAQ

My recovery works but the RECOVER test says the wreckage isn't wrecked.

The test first asserts A=$0 is on disk pre-recovery, proving the steal happened. If that assert fails, your set_int isn't calling set_modified(), so the "dirty" page was never really dirty and flush_all wrote nothing. The bug is in the write path, not the recovery.

Why JSON for log records? Real WALs are binary.

Readable logs debug themselves: cat microdb.log is a complete forensic timeline, which is worth more to a student (and frankly to many engineers) than the bytes JSON wastes. The structure per record is identical to ARIES's: who, where, old-what.

Could two transactions deadlock in microdb?

No: conflicts abort immediately instead of waiting, and no wait means no wait-cycle. The price is spurious aborts a waiting system would have survived. Single-threaded honesty again: we keep the protocol, we lose the drama. Lecture 8's FAQ has the production version.

Is my microdb now… an actual database?

Files, cache, records, catalog, operators, SQL, indexes, transactions, crash recovery: yes. Slower than SQLite and missing forty years of polish, but structurally the real thing, and you hold every line of it in your head. That's the midterm, and it's also the point.
