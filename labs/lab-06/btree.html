The one distinction the drill hammers: a leaf's middle key is copied up (leaves keep all data); an internal node's is moved up (guides only). Most Thursday bugs are that one word.

Values → RIDs

The tree stores no rows. Its leaves map field values to the stable addresses Lab 3 gave every row, and the reference TableScan gained a three-line move_to_rid() so a scan can jump wherever the tree points. An index is a second, sorted road into the same heap.

The contract

The Node class, the descend helper, the index builder, and IndexSelectScan ship complete. You write the four methods that make the structure a structure:

search(key) # descend, find in leaf, return the RID list
insert(key, rid) # insort into the leaf, then repair upward
_split(node, parent) # the lecture table, transcribed
range(lo, hi) # descend once, then walk the chain
Hover a line. Read the provided Node class first; its docstring shows both node shapes with real values.

Part 1 · Build ~35 min in class

  1. Read Node and _descend (5 min); the docstring draws both node shapes with live values; child_index_for is the only subtle helper and it's provided.
  2. search: warm up on the easy descent. First SEARCH test greens once insert can feed it, so write it now, test it after step 3.
  3. insert without splits: bisect into the leaf, duplicates share a slot. The first TREE test passes.
  4. _split: transcribe the lecture table: leaf case, internal case, new-root case. Then wire the bottom-up repair loop in insert. TREE and SEARCH groups green.
  5. range: descend to lo, walk the chain. All nine tests green; run the drill widget once more and feel smug.
Gotchas that cost real debugging time

Split from the bottom of the path upward: a parent may only split after its child's hoist landed. When the root splits there is no parent: build the new root yourself and bump self.height (a test reads it). And return a copy of the rid list from search; handing out your internal list lets callers mutate the tree by accident.

Exercise · read the failure

A classmate passes everything except 500 keys, height stays logarithmic: their height reaches 9 at 500 sequential keys (expected ≤ 6). All invariants hold; search still works. Their _split uses mid = 1 instead of len(keys) // 2. Why does everything stay correct, and what exactly degrades?

Show answer

Splitting at 1 leaves a one-key left node and a fat right node, legal by every invariant, so correctness holds. But sequential inserts keep splitting the fat right edge, minting nearly-empty nodes: occupancy craters, so far more nodes exist, so the tree needs more levels to hold the same keys. Height is a quality metric, not just a correctness one; mid-splits keep nodes half-full minimum, which is where the logarithm's promised base comes from.

FAQ

My height is 12, the reference says 11. Failed?

Only the invariants and the ≤ bounds are graded; exact height depends on split ties your bisect direction decides. If check_invariants passes and 500 keys stay ≤ 6, you're correct; note your height honestly for the discussion.

Why does the index rebuild each run instead of persisting?

A 75-minute budget: persistence is Lab 1 plumbing (nodes into blocks, pointers into block numbers) with no new ideas, and Sciore ch. 12 walks it. The half-second rebuild on 100k rows also honestly shows what CREATE INDEX costs.

What happens if two students share the same gpa, or a thousand do?

Duplicates share one key entry whose rid list grows, fine at course scale. A thousand-rid list makes that key's leaf huge; real engines either treat (key, RID) as the sort key (making every entry unique) or spill big families to overflow pages. The harness's duplicate test keeps you honest at three.

Is bisect cheating?

It's the standard library doing binary search within a node, exactly what a real engine does inside a page. The tree's job is choosing which node; bisect's job is the last twenty comparisons inside it. Use it with pride.
