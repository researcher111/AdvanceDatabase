The one distinction the drill hammers: a leaf's middle key is copied up (leaves keep all data); an internal node's is moved up (guides only). Most Thursday bugs are that one word.

Values → RIDs

The tree stores no rows. Its leaves map field values to the stable addresses Lab 3 gave every row, and the reference TableScan gained a three-line move_to_rid() so a scan can jump wherever the tree points. An index is a second, sorted road into the same heap.

Think · Pair · Share · why not sort the table itself?
  • Think · 2 minInstead of a side structure, why not keep the heap file itself sorted by uid: binary search, no extra space? List what breaks, using what Lab 3 taught about inserts and stable RIDs. Then: what if you want fast lookup by uid AND by name?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare damage lists: inserts shift rows (RIPs for every RID), and one physical order can serve one key at most. A side tree dodges both; that's the entire design argument for indexes.
  • Share · 2 minOne sentence: what does "the heap stays dumb, the smartness lives beside it" buy an engine?
Show the answer

Two things break, and Lab 3 taught both. Inserts: keeping the heap sorted means every insert shifts the rows after it to make room, which is the packed-page nightmare that fixed slots abolished, and every shift invalidates every RID pointing past it. Only one order: a file has exactly one physical arrangement, so sorting by uid makes lookup by name no better than a full scan. You cannot sort one file two ways.

A side structure dodges both. The heap keeps its fast unordered inserts and its stable RIDs, and the sorted thing lives beside it holding (key, RID) pairs. Want a second access path by name? Build a second tree. What that buys an engine is independence: access paths can be added, dropped and rebuilt without touching the data or invalidating anything, and each one is paid for only by the writes that maintain it. The heap stays dumb precisely so that the smartness can be plural.

The contract

The Node class, the descend helper, the index builder, and IndexSelectScan ship complete. You write the four methods that make the structure a structure:

search(key) # descend, find in leaf, return the RID list
insert(key, rid) # insort into the leaf, then repair upward
_split(node, parent) # the lecture table, transcribed
range(lo, hi) # descend once, then walk the chain

  • Pair · 3 minMatch: (a) → "a LEAF split must keep every key in the leaves"; (b) → the invariants check (children ≠ keys+1); (c) → "range walks the leaf chain" silently missing keys. Agreeing on symptoms now is debugging later, prepaid.
  • Share · 2 minOne sentence: why copy-vs-move differs between leaf and internal at all.
Show the answer

(a) Moving the leaf's middle key up instead of copying it is caught by "a LEAF split must keep every key in the leaves": the key vanishes from the data level, so searching for it returns nothing and a range scan skips it, while the tree looks perfectly well formed. (b) Giving the internal sibling keys[mid:] is caught by the invariants check, because an internal node must have exactly one more child than keys; keep the middle key and the counts no longer line up. (c) Forgetting the leaf chain passes every point lookup and is caught only by "range walks the leaf chain", which silently returns too few keys.

Why copy versus move differs at all: leaves hold the data, internal nodes hold only directions. A key in a leaf is a real entry with a RID attached, so it must stay there; the parent gets a copy to use as a signpost. A key in an internal node is already just a signpost, so promoting it moves it, with nothing left behind to lose. The rule follows from what each kind of node is for.

Gotchas that cost real debugging time

Split from the bottom of the path upward: a parent may only split after its child's hoist landed. When the root splits there is no parent: build the new root yourself and bump self.height (a test reads it). And return a copy of the rid list from search; handing out your internal list lets callers mutate the tree by accident.

Exercise · read the failure

A classmate passes everything except 500 keys, height stays logarithmic: their height reaches 9 at 500 sequential keys (expected ≤ 6). All invariants hold; search still works. Their _split uses mid = 1 instead of len(keys) // 2. Why does everything stay correct, and what exactly degrades?

Show answer

Splitting at 1 leaves a one-key left node and a fat right node, legal by every invariant, so correctness holds. But sequential inserts keep splitting the fat right edge, minting nearly-empty nodes: occupancy craters, so far more nodes exist, so the tree needs more levels to hold the same keys. Height is a quality metric, not just a correctness one; mid-splits keep nodes half-full minimum, which is where the logarithm's promised base comes from.

Show the answer

Height about 11, one search touching 11 nodes plus 1 heap block, against a scan of 100,000 rows across 294 blocks. Measured: 128 ms versus 0.03 ms, a 4,091× speedup, and the speedup is the number that humbles everyone, always in the good direction. (Dividing the two printed times gives about 4,300; the script reports 4,091 because it divides the unrounded timings.)

Height is computable rather than guessable: an ORDER-4 tree at roughly half occupancy holds about 2 keys per node, so height ≈ log₂(100,000) ≈ 17 at worst and about 11 in practice, since real occupancy runs better than the worst case.

Re-answered at real-page fan-out 200: the same 100,000 rows need height 3, and 100 million rows need height 4. That is the whole point of sizing nodes to blocks. Your ORDER-4 tree pays 11 node visits for what a real engine does in 4, and the difference is not a better algorithm, it is a bigger base on the same logarithm.

FAQ

My height is 12, the reference says 11. Failed?

Only the invariants and the ≤ bounds are graded; exact height depends on split ties your bisect direction decides. If check_invariants passes and 500 keys stay ≤ 6, you're correct; note your height honestly in measurements.txt.

Why does the index rebuild each run instead of persisting?

A 75-minute budget: persistence is Lab 1 plumbing (nodes into blocks, pointers into block numbers) with no new ideas, and Sciore ch. 12 walks it. The half-second rebuild on 100k rows also honestly shows what CREATE INDEX costs.

What happens if two students share the same gpa, or a thousand do?

Duplicates share one key entry whose rid list grows, fine at course scale. A thousand-rid list makes that key's leaf huge; real engines either treat (key, RID) as the sort key (making every entry unique) or spill big families to overflow pages. The harness's duplicate test keeps you honest at three.

Is bisect cheating?

It's the standard library doing binary search within a node, exactly what a real engine does inside a page. The tree's job is choosing which node; bisect's job is the last twenty comparisons inside it. Use it with pride.
