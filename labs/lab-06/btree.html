The B+ Tree Index

Build an index that locates rows by key, then compare its lookup work and timing with a full table scan.
Follows Lecture 6 (B+ Trees from First Principles) · in class: 75 min · aim to finish Build + Verify · due Thu Oct 8 at class start

Microdb currently finds a row such as uid = 77777 by scanning the table. In this lab, you will build a B+ tree that maps field values to record IDs in the heap file. Implement search, insertion, node splitting, and range lookup. The provided IndexSelectScan uses the resulting IDs to retrieve matching rows. The measurement compares a scan of 100,000 rows with an index lookup that visits 11 tree nodes in the reference run.

Companion reading: Sciore, Database Design and Implementation, ch. 12 · Lecture 6's slides & live tree · Comer's The Ubiquitous B-Tree.

In a leaf split, copy the first key of the new right leaf into the parent; keep that key in the leaf with its data. In an internal-node split, move the middle separator into the parent and remove it from both resulting children.

The tree stores no rows, only RIDs into your heap

This index stores keys and record IDs rather than complete rows. Each record ID identifies a block and slot in the heap file. The reference TableScan.move_to_rid() positions the scan at that address. Index entries must be updated when rows are inserted, deleted, or moved so they continue to identify the intended rows.

The index provides a sorted lookup structure for the same rows stored in the heap file.

Methods to implement

The starter provides Node, the descent helper, the index builder, and IndexSelectScan. You will implement these four methods:

search(key) # descend, find in leaf, return the RID list
insert(key, rid) # insort into the leaf, then repair upward
_split(node, parent) # split the node and update its parent
range(lo, hi) # descend once, then walk the chain
Hover a line. Read the provided Node class first; its docstring shows both node shapes with real values.

Part 1 · Build ~35 min in class

  1. Read Node and _descend (5 min). The docstring illustrates leaf and internal-node layouts. Check how the provided child_index_for chooses a child when the search key equals a separator.
  2. search: descend to the leaf and look up the key. Implement it now, then test it once insertion and splitting can construct a tree.
  3. insert without splits: bisect into the leaf, duplicates share a slot. The first TREE test passes.
  4. _split: implement leaf splits, internal-node splits, and creation of a new root. Then add the bottom-up split loop in insert. Run the TREE and SEARCH tests.
  5. range: descend to lo, then follow the leaf chain through the requested range. Run all nine tests and revisit the widget if a split rule is still unclear.
Common implementation mistakes

Process splits from the leaf toward the root because splitting a child can make its parent overflow. If the root splits, create a new root and increment self.height. Return a copy of the RID list from search so a caller cannot accidentally modify the index’s internal list.

Exercise · read the failure

A classmate passes everything except 500 keys, height stays logarithmic: their height reaches 9 at 500 sequential keys (expected ≤ 6). Ordering and equal-depth checks hold; search still works. Their _split uses mid = 1 instead of len(keys) // 2. Why does everything stay correct, and what exactly degrades?

Show answer

Splitting at index 1 can preserve key ordering and equal leaf depth, so searches may still return the right results. However, it leaves too little data in the left node. Sequential inserts then repeatedly split the larger rightmost node, creating many sparsely occupied nodes and increasing tree height. Splitting near the middle maintains better occupancy and reduces the number of levels needed.

The tree uses a deliberately small node capacity; a disk index with a larger fan-out could store these keys in fewer levels. Buffering reduces the cost of repeated block reads, while indexing can reduce how many blocks a query needs to request.

When a B-tree index can help a query

For example, CREATE INDEX ON features (user_id) gives PostgreSQL another way to find rows for a particular user. A selective lookup may become much faster because the engine can locate matching entries without scanning every row. The improvement depends on selectivity, table size, caching, and the chosen plan.

An ordered index can locate equality matches and key ranges efficiently. Whether an engine uses it depends on the predicate, index definition, and estimated cost. Indexes can also help with ordering or supply needed columns directly. Use EXPLAIN to inspect the chosen access path.

Indexes also add storage and write work. An insert usually needs a new index entry, and updates or deletes may change existing entries. For some bulk loads, building an index after loading the data is cheaper than maintaining it row by row. Lab 9 explores vector indexes, which address a related problem: finding nearby vectors without comparing the query with every stored vector.

FAQ

My tree has height 12 instead of 11. Is that a failure?

Only the invariants and the ≤ bounds are graded; exact height depends on insertion order and occupancy; use the specified split rule for the reference experiment. If check_invariants passes and 500 keys stay ≤ 6, you're correct; note your height honestly for the discussion.

Why does the index rebuild each run instead of persisting?

The lab focuses on search, insertion, and splitting within the available time. Persisting the tree also requires a node format, allocation rules, and updates to stored child references. Sciore chapter 12 develops that design. The rebuild time in this lab measures the cost of constructing the in-memory index.

What happens if two students share the same gpa, or a thousand do?

Duplicate values share a key entry whose RID list grows. This is convenient at the lab’s scale, but a large list would exceed a fixed-size disk page. Production designs can order entries by (key, RID) or use additional pages for large duplicate lists. The duplicate test checks that all three matching RIDs are returned.

Is bisect cheating?

bisect performs binary search within a sorted node. Your tree code chooses which node to visit; bisect helps locate a key or insertion position inside it. Using the standard-library helper is allowed.
