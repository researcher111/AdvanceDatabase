Scan Operators

Your TableScan reads one table, but the Lecture 1 demo query filters, projects, and joins two: what goes in between, and why does its shape cost 15×?

Every operator wraps the scan below it and copies nothing

Each operator holds a reference to the scan beneath it and answers the same five methods, mostly by delegation. Nothing is copied; a plan over a terabyte is a few dozen bytes of Python objects plus one pinned block per table. The craft is knowing which method each operator actually changes:

OperatorChangesDelegates untouched
SelectScannext: skip until the predicate passeseverything about row shape
ProjectScanget_val / has_field: answer only for kept columnseverything about row flow
ProductScanall four: it has two childrennothing (it's the interesting one)

Five lines are the whole engine; read them aloud

Everything you write today, in one annotated card. These are the actual lines of the reference solution, shown because reading them is most of the work:

SelectScan.next: while scan.next(): if pred.is_satisfied(scan): return True
ProjectScan.get_val: raise ValueError unless fld in self.fields
ProductScan.before_first: left rewind + next · right rewind
ProductScan.next: right.next() or (right rewind · left.next() and right.next())
ProductScan.get_val: ask the side whose has_field says yes
Hover a line: if you can explain each one aloud, the lab is dictation.

Join conditions need no new machinery: a predicate term's right side may be F("mid2") (a field instead of a literal), and Predicate.is_satisfied (provided) already handles it. The cartesian product plus that predicate is the join.

  2. SelectScan.next: the skip-loop. SELECT group goes green.
  3. ProjectScan.get_val / has_field: answer only for kept columns, raise for the rest. PROJECT green.
  4. ProductScan: before_first first (left gets a next(), right doesn't), then the odometer, then routing. PRODUCT green, including the course's first join.
Gotchas that cost real debugging time

In ProductScan.before_first, the left side needs next() called once; a product positioned "before" both sides yields nothing (the cardinality test reads 0 or 15 instead of 18). In the odometer, rewind the right before advancing the left. And close() must reach both children; the pin test runs a whole join and then audits the pool.

Exercise · read the failure

A classmate's product passes the cardinality test (18 pairs) but fails before_first rewinds the whole tree: the second run of the same product yields 0 rows. Their before_first is self.left.before_first(); self.right.before_first(). What's missing, and why did the first run work anyway?

Show answer

The left side is never advanced onto its first row. The first run worked because next()'s rollover branch (left.next() and right.next()) rescued it: right was exhausted-at-birth, so the very first next() rolled over and advanced left. On the second run the right side isn't freshly exhausted in the same way and the accident doesn't repeat. Moral: code that works by accident fails by schedule; position the left explicitly.

Two lessons for the price of one: filter placement bought 15× with an identical answer, and the right input of a nested loop is re-executed once per left row, which is why "small table on the right" is ancient DBA wisdom and why week 9 invents the hash join.

pandas holds the whole product; your ProductScan holds one pair

ToolWhat the join does with the 900 pairsPlan shape
pandasdf.merge builds the whole joined frame, then each filter builds another complete frame from it; the product sits in RAM and can raise MemoryErrorPlan A, held in memory
Your ProductScanbuilds the same pairs one at a time through next() and holds onePlan A, streamed
Python generatorsyield is next(); a chain of generators is a plan tree pulling from the bottomwhatever you chain
Polars lazy · Spark DataFramefilter(...).select(...) builds a plan, nothing runs until .collect(), and the optimizer moves the filter below the joinPlan B, chosen for you

pandas runs Plan A every time: df.merge builds the whole joined frame in memory, df[df.gpa > 35] builds a second frame from it, df[['name']] a third, and each intermediate is complete before the next line starts. That is why a join of two frames that each fit in RAM can still raise MemoryError: the joined frame in the middle is your 900-pair product, and nothing streams it. Your ProductScan built the same 900 pairs one at a time through next() and held one at a time, which is why a database finishes a join on a laptop where pandas does not.

A Python generator is the iterator model in different spelling: yield is next(), and a chain of generators is a plan tree that pulls one row at a time from the bottom.

Polars' lazy API and Spark's DataFrame make the tree visible: df.filter(...).select(...) builds a plan, nothing runs until .collect(), and the optimizer moves the filter below the join for you, which is the Plan B you assembled by hand. A Spark stage is one of these pipelines with a shuffle at each end: rows still flow from one operator to the next, but between stages they cross the network, so every pair you avoided building by filtering early is a pair that never left the machine.

FAQ

My join returns 18 rows, not 3.

Your SelectScan's predicate isn't being consulted, or the plan stacked Product over Select instead of Select over Product. Print the plan as you build it; the tree reads bottom-up.

My join returns 0 rows but cardinality passes.

Almost always field routing: get_val("mid2") is being answered by the left side (which lacks it) or has_field lies. Check ProductScan asks has_field before choosing a side.

Does the order of terms inside a Predicate matter?

For correctness, no: it's a conjunction. For speed, mildly: is_satisfied stops at the first failing term, so putting the cheapest, most-often-failing test first saves comparisons. Real optimizers reorder terms for exactly this reason.

Why "left wins ties" instead of an error on ambiguous fields?

Honesty about scope: real SQL makes you qualify (students.id) and errors on ambiguity, which needs a name-resolution layer we haven't built. microdb documents its simple rule and the tests avoid collisions; a teaching engine should be predictable before it's featureful.
