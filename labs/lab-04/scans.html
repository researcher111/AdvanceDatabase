How each operator uses its input scans

Each operator refers to its input scan or scans and implements the same five methods. These operators expose one current row at a time without storing a copy of the full result. Their memory use depends on the plan and its active scans, rather than the number of result rows. The table shows which behaviors each operator changes.

OperatorChangesDelegates untouched
SelectScannext: skip until the predicate passeseverything about row shape
ProjectScanget_val / has_field: answer only for kept columnseverything about row flow
ProductScanall five: it has two childrennone; it coordinates two inputs

Control flow for the scan operators

The annotated sketches below describe the control flow; they are not executable Python. Handle empty inputs. Once ProductScan.next() returns False, it must keep returning False until the product is rewound.

SelectScan.next: while scan.next(): if pred.is_satisfied(scan): return True
ProjectScan.get_val: raise ValueError unless fld in self.fields
ProductScan.before_first: left rewind + next · right rewind
ProductScan.next: right.next() or (right rewind · left.next() and right.next())
ProductScan.get_val: ask the side whose has_field says yes
Hover a line: if you can explain each one aloud, you are ready to implement the operators.

Join conditions need no new machinery: a predicate term's right side may be F("mid2") (a field instead of a literal), and Predicate.is_satisfied (provided) already handles it. The cartesian product plus that predicate is the join.

Common implementation mistakes

In ProductScan.before_first, rewind both children and store the result of left.next() in self._left_ready. The unit tests use this shared state to test before_first and next independently. During iteration, advance the right child; when it is exhausted, rewind it and advance the left child, updating self._left_ready. Keep it false once either input is exhausted and no pair remains. Finally, close() must close both children so their buffer pins are released.

Exercise · read the failure

A classmate’s product has before_first() rewind both children, but does not advance the left child. Its first next() advances the right child. Why is the resulting pair invalid?

Show answer

The left scan is still before its first row, so there is no valid left value to pair with the right row. Rewind both children, advance the left once, and remember whether that advance succeeded. If either input is empty, the product must return no rows.

15× less pair-building work from moving one filter below the join, with the same 20 rows out

Filtering before the product reduces the number of pairs examined by a factor of 15 in this example, while returning the same rows. The right input is scanned once per left row, so input order also affects the work. Caching the inner input can reduce repeated reads; Lecture 9 introduces hash joins as another way to avoid enumerating every pair.

Now change something. Both plans in measure_pipeline.py filter on ("gpa", ">", 35). Change the 35 to 25 in both places and run, then to 20 and run again. pandas materializes join results; ProductScan streams pairs

ToolHow rows are processedPlan shape
pandasdf.merge materializes matching rows; a large many-to-many result can exhaust memory without constructing the full Cartesian productResult materialized in memory

Python generatorsnext() resumes a generator, and yield returns its next value. Chained generators can process rows incrementally.whatever you chain
Polars lazy · Spark DataFrameBuilds a plan that executes when an action requests results; the optimizer can move eligible filters earlier.Filter placement chosen by the optimizer

A pandas merge materializes its result, so joins with many matches can require much more memory than either input. An equality merge does not normally build the full Cartesian product. Our ProductScan does enumerate every pair, but streams them one at a time. Filter placement matters in both approaches.

Python generators use a similar pull-based model. Calling next(generator) resumes execution until the next yield, which returns a value to the caller. A chain of generators can therefore pass one row at a time through several processing steps.

Polars’ lazy API and Spark DataFrames describe computations as plans. An action such as collect() executes the plan. Their optimizers can move a filter closer to its input when doing so preserves the result. In distributed processing, filtering before a shuffle can also reduce the rows sent across the network.

FAQ

My join returns 18 rows, not 3.

Check that the plan places the join’s SelectScan above ProductScan and that SelectScan.next() evaluates the predicate before returning a row. The product generates 18 pairs; the selection must keep only the three that match.

My join returns 0 rows but cardinality passes.

Check field routing first. ProductScan.get_val("mid2") must ask the child that contains mid2. Use each child’s has_field method to choose which child supplies the value.

Does the order of terms inside a Predicate matter?

For correctness, no: it's a conjunction. For speed, mildly: is_satisfied stops at the first failing term, so putting the cheapest, most-often-failing test first saves comparisons. Real optimizers reorder terms for exactly this reason.

Why "left wins ties" instead of an error on ambiguous fields?

Microdb checks the left input first when both inputs have the same field name. The tests avoid that ambiguity. SQL normally requires a qualified name such as students.id when an unqualified reference is ambiguous; supporting that would require a name-resolution layer beyond this lab.
