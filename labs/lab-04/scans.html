Wrap, don't copy

Each operator holds a reference to the scan beneath it and answers the same five methods, mostly by delegation. Nothing is copied; a plan over a terabyte is a few dozen bytes of Python objects plus one pinned block per table. The craft is knowing which method each operator actually changes:

OperatorChangesDelegates untouched
SelectScannext: skip until the predicate passeseverything about row shape
ProjectScanget_val / has_field: the fenceeverything about row flow
ProductScanall four: it has two childrennothing (it's the interesting one)

I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare rules. microdb says "ask has_field, left wins ties"; what does real SQL make you do about ambiguous columns instead? (You've seen the error message.)
  • Share · 2 minOne sentence: why the tests name majors' key mid2, not mid.
Show the answer

The routing rule: ask the left side has_field; if it says yes, delegate there, otherwise delegate right. Neither side needs to know anything about the other, which is what lets any scan sit on any other scan.

If both sides have a field called id, microdb's rule silently answers from the left. Real SQL refuses: Postgres raises column reference "id" is ambiguous and makes you qualify it, students.id, because guessing is worse than complaining. microdb documents its simple rule and then arranges never to rely on it, which is why the tests name the majors key mid2 rather than mid: with distinct names the tie rule never fires, so a passing test proves your routing works rather than proving your tie-break happened to match the reference. A teaching engine should be predictable before it is featureful.

The contract

Think · Pair · Share · loud or silent?
  • Think · 2 minA ProjectScan kept only name, and some code above it asks for gpa anyway. Three possible behaviors: return the value (it IS still down there), return None, or raise. Pick one and defend it:what does each choice do to the poor soul debugging a wrong query result at 2am?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare choices. Which one turns a caller bug into a wrong-but-plausible answer? That's the one that costs a retraction.
  • Share · 2 minOne sentence: what "loud beats silent" means as an API design rule.
Show the answer

Raise. A ProjectScan is a fence, not a filter, and asking it for a field it does not publish is a bug in the caller, not a question with an answer.

Compare the costs at 2am. Raise gives you a stack trace pointing at the exact line that asked for the wrong field: minutes to fix. Return None gives you a None that flows onward and surfaces as a crash or a wrong comparison somewhere far away, with nothing connecting it to the projection. Return the value is the genuinely dangerous one: it produces a wrong-but-plausible answer with no error at all, so the query looks like it worked and the projection silently meant nothing. That is the choice that costs a retraction rather than an afternoon.

"Loud beats silent" as an API rule: when a caller violates the contract, fail immediately and say so, rather than inventing a plausible result. The cost of an exception is bounded and lands on the person who caused it; the cost of a plausible wrong answer is unbounded and lands on whoever trusted it.

Everything you write today, in one annotated card. These are the actual lines of the reference solution, shown because reading them is most of the work:

SelectScan.next: while scan.next(): if pred.is_satisfied(scan): return True
ProjectScan.get_val: raise ValueError unless fld in self.fields
ProductScan.before_first: left rewind + next · right rewind
ProductScan.next: right.next() or (right rewind · left.next() and right.next())
ProductScan.get_val: ask the side whose has_field says yes
Hover a line: if you can explain each one aloud, the lab is dictation.

Join conditions need no new machinery: a predicate term's right side may be F("mid2") (a field instead of a literal), and Predicate.is_satisfied (provided) already handles it. The cartesian product plus that predicate is the join.

Gotchas that cost real debugging time

In ProductScan.before_first, the left side needs next() called once;a product positioned "before" both sides yields nothing (the cardinality test reads 0 or 15 instead of 18). In the odometer, rewind the right before advancing the left. And close() must reach both children; the pin test runs a whole join and then audits the pool.

Exercise · read the failure

A classmate's product passes the cardinality test (18 pairs) but fails before_first rewinds the whole tree: the second run of the same product yields 0 rows. Their before_first is self.left.before_first(); self.right.before_first(). What's missing, and why did the first run work anyway?

Show answer

The left side is never advanced onto its first row. The first run worked because next()'s rollover branch (left.next() and right.next()) rescued it: right was exhausted-at-birth, so the very first next() rolled over and advanced left. On the second run the right side isn't freshly exhausted in the same way and the accident doesn't repeat. Moral: code that works by accident fails by schedule; position the left explicitly.

Part 3 · Measure ~20 min · finish as homework

Think · Pair · Share · predict the traffic
  • Think · 2 min300 students (a third in cs, gpas evenly 20–39), 3 majors. The query: names of cs students with gpa > 35. Plan A filters after the product; Plan B filters both inputs first. Predict each plan's pairs-built number.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare: A = 300 × 3 = 900. B = 60 survivors × 1 major = 60. Now the trap: the counter on B's majors filter reads 60, not 1. Why might that be?
  • Share · 2 minRun it, read the note under the table aloud, and agree on what the nested loop does to its right input.
Show the answer

A builds 900 pairs (300 × 3), B builds 60 (60 gpa survivors × 1 cs major), and both return the same 20 rows: a 15× difference in work from filter placement alone.

The trap is the counter on B's majors filter, which reads 60, not 1. The filter really does keep only one row, but the nested loop re-runs its right input once per left row: 60 surviving students, so the majors scan is rewound and walked 60 times, and the filter is asked 60 times over. It kept 1 row, sixty separate times.

That is the second lesson, and it is the one people forget: in a nested-loop join the right side's cost is multiplied by the left side's cardinality. It is why "put the small table on the right" is folklore, and why week 9's hash join exists at all, since building a hash table once beats re-scanning sixty times.

Reference output is deterministic, yours must match:

Two lessons for the price of one: filter placement bought 15× with an identical answer, and the right input of a nested loop is re-executed once per left row, which is why "small table on the right" is ancient DBA wisdom and why week 9 invents the hash join.

FAQ

My join returns 18 rows, not 3.

Your SelectScan's predicate isn't being consulted,or the plan stacked Product over Select instead of Select over Product. Print the plan as you build it; the tree reads bottom-up.

My join returns 0 rows but cardinality passes.

Almost always field routing: get_val("mid2") is being answered by the left side (which lacks it) or has_field lies. Check ProductScan asks has_field before choosing a side.

Does the order of terms inside a Predicate matter?

For correctness, no: it's a conjunction. For speed, mildly: is_satisfied stops at the first failing term, so putting the cheapest, most-often-failing test first saves comparisons. Real optimizers reorder terms for exactly this reason.

Why "left wins ties" instead of an error on ambiguous fields?

Honesty about scope: real SQL makes you qualify (students.id) and errors on ambiguity, which needs a name-resolution layer we haven't built. microdb documents its simple rule and the tests avoid collisions; a teaching engine should be predictable before it's featureful.
