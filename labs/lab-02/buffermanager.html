Buffer Manager

A fixed pool of frames, two verbs, and the hit rate that decides everything.
Follows Lecture 2 (Memory & the Buffer Pool) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 10 at class start

Today microdb stops touching the disk directly. Every page access from this lab forward goes through the buffer manager you build: a fixed set of memory frames, a pin/unpin protocol, LRU eviction, and write-back of dirty pages. Four methods, ten tests, and at the end, a measurement with a cliff in it that most professional engineers have never seen drawn.

The protocol playground · 3 frames, LRU, write-back

Each disk block stores one number. Pin brings a block into a frame and locks it there; modify writes value+1 through the buffer (memory only; the frame turns dirty); unpin releases; eviction writes back dirty pages before reuse. Disk chips show what's actually on disk.

Why pin/unpin exists

Before the code, earn the protocol. It exists because of one hazard, and once you've named it, every rule in this lab follows.

Think · Pair · Share · the vanishing page
  • Think · 2 minSuppose the pool had only get_page(block) (no pin, no unpin) and evicted by LRU whenever it needed room. Your code gets a page reference and starts reading row 2 from it. Construct the exact sequence of events where your read returns another table's data without any error being raised.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare sequences. Whose disaster is quieter: a wrong read, or a write landing in a frame that now holds a different block?
  • Share · 2 minState the fix as a rule about who may evict what, when, then check it against the contract below.
Show the answer

The sequence: you call get_page(block 3) and get a reference to frame 1. Before you read row 2, another part of the query misses on block 9, the pool is full, and LRU picks frame 1 as its victim. It loads block 9 into that memory. Your reference is still perfectly valid and still points at frame 1, which now holds block 9. You read row 2 and get bytes from a different block, possibly a different table. No exception, no warning, no way to detect it.

The quieter disaster is the write. A wrong read produces a wrong answer that someone might notice; a write landing in a frame that now holds a different block corrupts that other block, gets flushed to disk as though it were legitimate, and outlives the query that caused it. The rule that fixes both: a frame that someone is using may never be chosen as a victim. Callers declare use with pin and end it with unpin, and eviction skips any frame with a non-zero pin count.

The hazard: between your get_page and your read, someone else's miss evicts your frame and loads a different block into the same memory. Your reference still points at the frame; the frame no longer holds your data. No exception, no warning, just wrong answers. The fix is a lease: pin marks the frame in-use (eviction must skip it), unpin ends the lease. That single invariant (never evict a pinned frame) is what the tests enforce most fiercely, because it's the one whose violation corrupts data silently.

The contract

You implement four methods; the frame class (Buffer) and its flush/load machinery ship complete. Hover each line, then keep the LRU spec table beside you while coding; the tests check it literally.

def _find_existing(block) -> Buffer | None # already resident?
def _choose_victim() -> Buffer | None # LRU among unpinned
def pin(block) -> Buffer # hit, or evict + load
def unpin(buf) # release the lease

I've done the Think step. Reveal Pair & Share
  • Pair · 3 minSwap rules and attack each other's: does it evict a pinned frame? Does a hit refresh recency, or only a load?
  • Share · 2 minCompare the table's spec against your rule. The difference is exactly what the tests will catch in your code.
Show the answer

The rule, precise enough to code: evict the frame with the smallest last_used among frames whose pins is 0; if no frame qualifies, raise BufferAbortError.

Two details decide whether your version passes. First, last_used is stamped on every successful pin, hits included, not only on loads. Stamp only on misses and you have built insertion order wearing an LRU costume, and the LRU-order test is built to catch exactly that. Second, pinned is untouchable regardless of age: the oldest frame in the pool is not a candidate if someone holds it, which is what makes the rule survive the previous section's hazard. And "no frame qualifies" must be a loud error rather than a silent stall, because in a single-threaded engine waiting would wait forever.

Part 1 · Build ~30 min in class

Download the four starter files into microdb-lab2/. Note that file_manager.py is the reference Lab 1 implementation; use it even if yours passed, so your layer 1 matches everyone's. Then build in this order:

  1. Read buffer_manager.py top to bottom (5 min). The Buffer class is complete; notice that assign_to_block already flushes-if-dirty before loading. Your four methods orchestrate; they never touch bytes.
  2. _find_existing: a loop and an ==. Run the harness: the first PIN test should flip once pin exists, so keep going.
  3. _choose_victim: filter unpinned, min by last_used, or None.
  4. pin: follow the docstring's spec exactly: tick, lookup, hit-count or victim/abort/load/miss-count, then pins += 1 and the stamp. PIN and LRU groups should now pass.
  5. unpin: two lines plus the ValueError guard. All ten tests green.
Gotchas that cost real debugging time

Stamp last_used on hits, not just misses; the LRU-order test is built to catch exactly that omission. Increment self._tick before using it, or two pins can share a tick. And don't reset pins in pin(): the same block pinned twice must reach pins == 2 on the same frame, not load twice.

Part 2 · Verify ~20 min in class

Ten tests in three groups, and each failure message names its usual cause. The PIN group checks the protocol: data actually loads, re-pins are hits on the same frame, pin counts nest, double-unpin raises. The LRU group checks the policy: victim choice, recency updates, pinned immunity, and the all-pinned abort. The DIRTY group checks write-back: a modified page must survive its own eviction, and flush_all must push everything down before shutdown.

Exercise · read the failure

A classmate passes every test except dirty page written back on eviction. Their pin() handles the miss path like this: victim.block = block; self.fm.read(block, victim.page); ..., assigning the fields themselves instead of calling assign_to_block. All the LRU tests still pass. What exactly is being lost, and why do only the DIRTY tests notice?

Show answer

By setting victim.block and reading directly, they skipped assign_to_block's first step: self.flush(), the write-back of the victim's modified page. The old page's changes are silently overwritten in memory and never reach disk. LRU tests don't notice because they only read; the modification is only missed when the DIRTY test evicts a modified block and then checks the disk. Moral: the provided helpers encode invariants; bypassing them compiles fine and corrupts quietly.

Part 3 · Measure ~25 min · finish as homework

Your buffer manager now has a hit-rate counter. Time to see the number every database engineer carries around, but commit to a prediction first.

Think · Pair · Share · one frame short
  • Think · 2 minA 50-block file, scanned start to finish, twice. Your pool has 49 frames, room for all but one block. Predict the hit rate on the second pass: roughly 98%? 50%? Something else? Reason it through with LRU's rule before you peek.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minWalk the pointer: when the scan re-reads block 0, which block did LRU just evict to make room for block 49? And then?
  • Share · 2 minRun python3 measure_hits.py and read the table out loud. One sentence on why 49 frames buys nothing.
Show the answer

0%. Not 98%, not 50%: exactly zero hits on the second pass, and measure_hits.py prints it.

Walk the pointer. Reading block 49 needs a frame, and the least recently used block is block 0, so block 0 is evicted. The scan then wraps to block 0, which is now missing, and loading it evicts block 1, which is the very next block the scan wants. Every single access misses, forever, because LRU evicts each block exactly one step before the scan returns to it. Add one more frame, 50 for 50 blocks, and the hit rate jumps to 50%.

So why does 49 frames buy nothing? Because a cache does not reward the amount of data you touched, it rewards re-use that fits. A working set one block too large for the pool is, for LRU, exactly as good as no cache at all. That cliff is the reason real engines detect sequential scans and give them a small private ring rather than letting them flood the pool.

Meanwhile the hot set, whose working set is 5 blocks, cruises at 90%+ with a pool a tenth the size. Which column your workload resembles matters more than any tuning parameter you will ever set.

Going further optional

Fast finishers, in rough order of payoff: give pin() a scan-resistant mode: a boolean sequential=True that makes the pinned block eligible for immediate eviction (a one-frame "ring buffer", exactly Postgres's trick) and re-run measure_hits.py to show the hot set is now protected from the scan; or implement clock eviction (a rotating hand and one reference bit per frame, LRU's cheap approximation) and verify all ten tests still pass; or replace _find_existing's linear scan with a dict page table ({BlockId: Buffer}; BlockId is hashable for exactly this reason) and keep it consistent through evictions.

FAQ

My scan hit rates don't match the table exactly.

They should: both workloads are seeded, and the file layer is the shipped reference. A mismatch almost always means last_used isn't stamped per the spec (tick on every pin) or eviction is choosing a different victim than smallest-last_used.

Why does pin() abort instead of waiting for a frame?

In a single-threaded microdb, waiting would wait forever: nobody else is running to do the unpinning. Real engines block the requesting thread and get woken by an unpin; the abort is the honest single-threaded translation, and it still catches the same bug (leaked pins).

Is my pool's memory really fixed? Python doesn't work that way…

The pages are: each frame allocates its bytearray once, and blocks are copied into it. Python objects around them churn, but the design mirrors the real thing: a real engine allocates shared_buffers once at boot and never grows it.

Does the OS page cache mess up my measurement?

It sits underneath, making misses cheaper than real disk, but hit rates are computed by your counters, not by timing, so the OS cache can't touch them. That's why this lab measures rates, not milliseconds.
