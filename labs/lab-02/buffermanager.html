Buffer Manager

Build a buffer pool and measure why some access patterns benefit from caching while repeated full scans may not.
Follows Lecture 2 (Memory & the Buffer Pool) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 10 at class start

In this lab, you will build a buffer manager that keeps a fixed number of database blocks in memory. It tracks which frames are in use, chooses a frame to evict with an LRU policy, and writes modified pages back before reusing their frames. You will implement four methods, run ten tests, and measure how access patterns affect the cache hit rate.

Explore a three-frame buffer pool

The widget models a buffer pool with three frames and six disk blocks. Select a block, pin it, modify it, and unpin it. Then load other blocks to see when the modified page is written back. Try pinning when all frames are in use, modifying an unpinned block, and unpinning a block that is not pinned.

The protocol playground · 3 frames, LRU, write-back

Each disk block stores one number. Pinning loads or finds that block in memory and prevents its frame from being evicted. Modify adds one to its value in memory and marks the frame dirty. Unpinning reduces the pin count; the frame becomes eligible for eviction when the count reaches zero. Evicting a dirty frame first writes its changes to disk. Why pinned frames cannot be evicted

A buffer frame can hold different blocks over time. Pinning keeps the current block in its frame while a caller uses it.

Suppose you obtain a reference to a page, but its frame is evicted before you read from it. The reference still points to the same memory, which now contains a different block. Pinning prevents this: a frame with a positive pin count cannot be evicted. Each caller must unpin the frame when finished. The frame can be reused only after every caller has released its pin.

Common implementation mistakes

Stamp last_used on hits, not just misses; the LRU-order test is built to catch exactly that omission. Increment self._tick before using it, or two pins can share a tick. And don't reset pins in pin(): the same block pinned twice must reach pins == 2 on the same frame, not load twice.

Exercise · read the failure

A classmate passes every test except dirty page written back on eviction. Their pin() handles the miss path like this: victim.block = block; self.fm.read(block, victim.page); ..., assigning the fields themselves instead of calling assign_to_block. All the LRU tests still pass. What exactly is being lost, and why do only the DIRTY tests notice?

Show answer

The code skips the initial self.flush() call in assign_to_block. Loading the new block then overwrites the old page’s changes before they reach disk. The LRU tests use unmodified pages, so they do not detect the loss. The DIRTY test modifies a page, evicts it, and checks its stored value. Calling assign_to_block preserves the required flush-before-load order.

Why repeated scans can have a zero hit rate

With 49 frames, the repeated scan has a 0% hit rate: LRU evicts each block before the next scan reaches it. With 50 frames, the first scan loads the file and the second scan hits every block, producing a 50% overall hit rate. The hot-set workload reuses a small group of blocks often enough to get a high hit rate with a smaller pool. Cache effectiveness depends on the sequence of requests as well as pool size.

Caching in data workflows

Where you meet itIn buffer-pool terms
pd.read_parquet on a file larger than RAMA pandas read materializes its result in memory and can fail if that result is too large. A query engine can often process a larger input incrementally, depending on the query.
Spark .cache() / .persist()requests caching; evicted partitions may be recomputed or read from disk, depending on storage level
Second run of a notebook cell that reads a large fileThe operating system may still hold file data from the first read in its page cache, making a repeated read faster.
Feature store serving online predictionsFrequently accessed users or features can form a hot set that benefits from caching. The benefit depends on how requests are distributed.
Nightly backfill scanning the whole table through the same poolA large scan can evict frequently accessed pages. PostgreSQL can use a limited buffer ring for large sequential scans to reduce their effect on the rest of its buffer pool.

A dataframe must fit its materialized result in memory; a query engine can often stream a larger input through a bounded pool. Spark’s cache() and persist() request reuse, but do not pin partitions against eviction. Lost partitions can be recomputed, and some storage levels spill them to disk. In every case, reuse and memory pressure determine the benefit.

FAQ

My scan hit rates don't match the table exactly.

They should: both workloads are seeded, and the file layer is the shipped reference. A mismatch almost always means last_used isn't stamped per the spec (tick on every pin) or eviction is choosing a different victim than smallest-last_used.

Why does pin() abort instead of waiting for a frame?

Microdb runs one thread. If every frame is pinned, waiting inside pin() would prevent the same thread from reaching the code that unpins a frame. Raising BufferAbortError reports the problem immediately. A concurrent engine can instead wait for another thread to release a frame, often with a timeout.

Is my pool's memory really fixed? Python doesn't work that way…

The page storage is fixed: each frame allocates its bytearray once and reuses it for different blocks. Other Python objects may still be allocated while the program runs. Production engines also manage a bounded pool of page memory, although whether that pool can resize depends on the engine.

Does the OS page cache mess up my measurement?

The operating system’s page cache can make a buffer-pool miss faster by serving it from RAM. It does not change whether the requested block was in your buffer pool. This lab measures your manager’s hit and miss counters rather than elapsed time, so those rates do not depend on the OS cache.
