SQL and machine learning in one Python program

DuckDB is an in-process database. When you use it from Python, the database engine runs inside your Python program. You do not need a separate database server. SQL can prepare the data, and Python libraries can work with the results in the same program.

In-database machine learning means training or applying a model through the database. In the SQL example, DuckDB fits a straight line to predict fare from distance. In the neural-network example, DuckDB selects the rides, PyTorch trains the network, and a SQL query calls the trained network to make predictions. PyTorch does the neural-network training; it runs alongside DuckDB in the same Python process.

The question: can distance help predict a taxi fare, and does a curve work better than a straight line? Test both models on rides they did not train on. This investigation is the core of Lab 8 and needs no cloud account.

2. Follow a batch from SQL into the network

What is Arrow?

Apache Arrow is a format for storing columns of values in memory. In this lab, it carries the distance and fare columns from DuckDB to Python. A batch is a group of rows passed together.

The script uses 50,000 January–October rides for training. This query selects only the two columns training needs. Arrow carries the query result in batches of up to 1,024 rows.

reader = con.execute("""
    SELECT distance, fare FROM features
    WHERE month <= 10 ORDER BY hash(ride_id)
""").to_arrow_reader(batch_size=1024)

model = nn.Sequential(
    nn.Linear(1, 16), nn.ReLU(), nn.Linear(16, 1)
)

Why ORDER BY hash(ride_id)?

It mixes the rides before we form training batches. The saved sample groups rides by month. The network updates its weights after each batch, so mixing lets those updates learn from rides across the training months instead of working through January, then February, and so on.

  1. WHERE month <= 10 keeps only the training rides.
  2. hash(ride_id) calculates a scrambled numeric value from each ride's ID.
  3. ORDER BY sorts the rides by those values. Arrow then divides that mixed result into batches.

The whole row moves together, so each distance stays paired with its fare. Hashing is a convenient way to mix the rows; training can run without it. This script reuses the same mixed order on every pass through the training rides. The month filter still keeps the test rides out. See DuckDB's hash documentation.

The network takes one distance, passes it through 16 hidden units, and returns one fare prediction. ReLU keeps positive intermediate values and replaces negative ones with zero, allowing the fitted curve to bend. PyTorch compares predictions with training fares and updates the weights.

One epoch is one pass through all training rides. In pytorch_fares.py, find this line in main():

parser.add_argument("--epochs", type=int, default=30)

default=30 sets the number of passes when you run the script without an --epochs option. main() passes that value to fit(), where for epoch in range(epochs): repeats the loop over all training batches 30 times.

Find loss.backward() and optimizer.step() in the script: these are the PyTorch operations that calculate gradients and update weights. DuckDB does the selection and ordering. The script also learns the scaling of distances and fares from training rows only.

What do the prediction and loss lines mean?

Before making predictions, the script converts each Arrow batch into two tensors, the numeric arrays PyTorch uses. x holds the distances and y holds the matching fares, each arranged as one column. This conversion allocates memory.

prediction = model((x - x_mean) / x_std)
loss = loss_fn(prediction, (y - y_mean) / y_std)

Before training starts, the script looks at all January–October training rides. It calculates the average distance (x_mean) and average fare (y_mean). It also calculates x_std and y_std: the standard deviations, which describe how much distances and fares vary around their averages.

These four numbers stay fixed. The script uses them to put every training batch and every later prediction on the same scale. The November–December test rides are not used to calculate them.

  1. Scale each distance, then predict. (x - x_mean) / x_std subtracts the average distance and divides by its spread. A value of 0 means an average distance; 1 means one standard deviation above average. Keeping typical values near 0 can help training. model(...) uses the current network weights to predict a scaled fare. It receives distances, not recorded fares.
  2. Put the recorded fares on the same scale. (y - y_mean) / y_std scales the training targets. We can now compare each prediction with its target using matching units. The model's output is not yet a dollar amount. A negative scaled value simply means below the training average.
  3. Measure the batch error. The script defines loss_fn = nn.MSELoss(). It subtracts each target from its prediction, squares each error, then averages across the batch. This mean squared error is one number used during training. It differs from the mean absolute error in dollars reported later.

A made-up example: assume the full training set gave a distance mean of 3 miles and std of 2 miles, plus a fare mean of $20 and std of $10. These statistics come from the larger training set, not just the two rides below. Suppose the current model returns 0.2 and 0.8.

RideDistance and scaled inputFare and scaled targetScaled predictionSquared error
A3 miles: (3 − 3) ÷ 2 = 0$20: (20 − 20) ÷ 10 = 00.2(0.2 − 0)² = 0.04
B5 miles: (5 − 3) ÷ 2 = 1$30: (30 − 20) ÷ 10 = 10.8(0.8 − 1)² = 0.04

The batch loss is (0.04 + 0.04) ÷ 2 = 0.04, measured in squared scaled-fare units. It is not a $0.04 error. These two lines calculate predictions and loss without changing the weights. Next, optimizer.zero_grad() clears previous gradients, loss.backward() calculates gradients, and optimizer.step() updates the weights and biases.

Convert back to dollars for SQL. The prediction callback reverses the fare scaling:

fares = model((x - x_mean) / x_std) * y_std + y_mean

Here, 0.2 × $10 + $20 = $22, and 0.8 × $10 + $20 = $28. Each toy prediction is $2 away from its recorded fare, so their mean absolute error is $2. Converting a new prediction needs only the saved training statistics, not that ride's actual fare.

Working through two rides helps us see what each step does. The results below show the same process applied to the taxi data. For more detail on how the training loss is calculated, see PyTorch's MSELoss explanation.

3. Call the trained network from SQL

What is an Arrow function?

An Arrow Python UDF is a function we provide to DuckDB that accepts and returns batches in Arrow format. UDF means user-defined function.

We register the lab's prediction function like this:

con.create_function(
    "predict_fare_nn", predict_fare,
    ["DOUBLE"], "DOUBLE",
    type="arrow")
ArgumentWhat it tells DuckDB
"predict_fare_nn"The function name to use in SQL.
predict_fareThe Python function to call. Passing its name without parentheses gives DuckDB the function itself.
["DOUBLE"], "DOUBLE"One numeric SQL argument and one numeric result per row. DOUBLE is a floating-point number. These declarations describe row values, not batch sizes.
type="arrow"Send column batches to Python and expect an Arrow batch back.

Predict a fare for each ride in the batch. DuckDB groups distances into a batch before calling Python. The distances parameter receives a PyArrow ChunkedArray, a column that can hold multiple chunks. The lab's callback converts it to a tensor and applies the saved model:

def predict_fare(distances):
    x = torch.tensor(
        distances.to_numpy(), dtype=torch.float32
    ).reshape(-1, 1)
    with torch.inference_mode():
        fares = model((x - x_mean) / x_std) * y_std + y_mean
    return pa.array(fares.flatten().numpy().astype(np.float64))

Read the function line by line

  1. Receive a batch of distances. def predict_fare(distances): defines the Python function DuckDB calls. For example, distances might contain [3.0, 5.0]: a 3-mile ride followed by a 5-mile ride.

  2. Turn those values into a PyTorch tensor. distances.to_numpy() converts the Arrow column to a NumPy array. torch.tensor(...) copies those numbers into a tensor. dtype=torch.float32 stores each number as a 32-bit floating-point value, matching the model's weights.

  3. Put one ride on each row. .reshape(-1, 1) changes [3.0, 5.0] into [[3.0], [5.0]]. The 1 means one column: distance. The -1 tells PyTorch to work out the number of rows from the batch size. The complete expression is assigned to x.

  4. Make predictions without tracking gradients. with torch.inference_mode(): turns off the bookkeeping needed to calculate gradients for the indented code. We are using the trained weights here; this function has no training step that updates them.

  5. Predict a fare for each distance. In fares = model((x - x_mean) / x_std) * y_std + y_mean, first (x - x_mean) / x_std puts distances on the training scale. Then model(...) predicts scaled fares. Finally, * y_std + y_mean converts those predictions back to dollars. Using the earlier example, scaled predictions [[0.2], [0.8]] become [[22.0], [28.0]].

  6. Return a column DuckDB can use. The last line reverses the data conversions. fares.flatten() changes [[22.0], [28.0]] into [22.0, 28.0]. .numpy() converts the CPU tensor to a NumPy array. .astype(np.float64) converts its numbers to 64-bit floats, matching the SQL return type DOUBLE. Finally, pa.array(...) wraps them in an Arrow array, and return sends it back to DuckDB. Here, np means NumPy and pa means PyArrow.

Keep each fare with its ride. The function returns the same number of values in the same order: [3.0, 5.0] becomes [22.0, 28.0] in our example. The first fare belongs to the first distance. Sorting the predictions would attach them to the wrong rides.

Why use batches? One Python call can process many distances, reducing call overhead. The model can also work on the whole tensor at once. This script uses torch.tensor, which copies data, so the conversion still has a cost. See DuckDB's Arrow function documentation.

Two uses of Arrow in this lab: to_arrow_reader(batch_size=1024) sends query results to our Python training loop. type="arrow" lets a SQL query call our Python prediction function with batches. DuckDB controls the prediction batch sizes; the earlier 1,024 setting does not set them.

4. Discover where the models struggle

Start with mean absolute error (MAE): how many dollars does a prediction miss by, on average? Then group the errors by trip distance. Does the overall score hide a group with much larger errors?

SELECT CASE WHEN distance < 2 THEN '1. Under 2 miles'
            WHEN distance < 5 THEN '2. 2 to under 5'
            WHEN distance < 10 THEN '3. 5 to under 10'
            ELSE '4. 10 miles or more' END AS distance_group,
       count(*) AS test_rides,
       avg(abs(fare - linear_fare)) AS linear_mae,
       avg(abs(fare - neural_fare)) AS neural_mae
FROM predictions
GROUP BY distance_group ORDER BY distance_group;

A window lets one row look at other rows

Suppose we want to follow changes in taxi fares. For each trip, calculate the average fare of that trip and the two trips just before it. A SQL window function can add that average beside each trip. It keeps the individual trips in the result.

Use rides 1, 2, and 3. Ride 4 comes later, so it is outside this frame.

The frame moves; the rows stay. Moving from ride 3 to ride 4 drops ride 1 from the calculation and brings ride 4 in. Both trips still appear in the result.

Read the SQL as instructions for choosing rows

SELECT ride_id, fare,
       AVG(fare) OVER (
         ORDER BY ride_id
         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
       ) AS recent_avg
FROM example_rides
ORDER BY ride_id;

OVER (...) defines the window. Here, ORDER BY ride_id puts the rides in order. ROWS BETWEEN 2 PRECEDING AND CURRENT ROW chooses the current ride and up to two earlier rides. Those selected rows are the frame used by AVG. At the beginning, use the rows available: ride 1 averages one fare; ride 2 averages two.

The final ORDER BY ride_id, outside OVER, puts the displayed results in ride order. The controls above let us inspect each calculation; they do not prescribe how the database physically executes the query.

Run this four-ride example in DuckDB

Create the tiny example table below, then run the query above. Its invented fares keep the arithmetic easy; they are not measurements from the NYC sample.

CREATE OR REPLACE TEMP TABLE example_rides AS
SELECT * FROM (VALUES (1, 12), (2, 18), (3, 30), (4, 24))
AS t(ride_id, fare);
How is this different from GROUP BY?

SELECT AVG(fare) FROM example_rides returns one summary row: $21. Adding GROUP BY payment to a table with payment types would return one summary per payment type. A window function instead adds a result to each row it receives: our four trips stay four trips.

Optional: separate card and cash averages with PARTITION BY

The query above does not use PARTITION BY. It treats all four rides as one set. Add this clause when you want a separate calculation for each category. For example: what is the recent average fare for rides paid the same way as this ride?

This variation gives our four made-up rides a payment type. The WITH clause supplies that tiny table so you can run the whole example on its own.

WITH payment_rides(ride_id, payment, fare) AS (
  VALUES (1, 'card', 12), (2, 'card', 18),
         (3, 'cash', 30), (4, 'card', 24)
)
SELECT ride_id, payment, fare,
       AVG(fare) OVER (
         PARTITION BY payment
         ORDER BY ride_id
         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
       ) AS recent_avg
FROM payment_rides
ORDER BY ride_id;
Result: each ride keeps its row and gets an average within its payment group.
RidePaymentFareRecent average
1card$12$12
2card$18$15
3cash$30$30

Follow ride 4: its two preceding card rides are 1 and 2. The average is ($12 + $18 + $24) ÷ 3 = $18. Ride 3 is cash, so it does not contribute. Without PARTITION BY, ride 4 uses rides 2, 3, and 4, giving the $24 average shown above.

PARTITION BY chooses the group; ORDER BY orders rows within that group; ROWS chooses the frame within it. These are groups inside the query, not Parquet folders. See DuckDB’s window function examples.

Eight worked DuckDB SQL examples

Each question below includes a complete query you can run and explore. The same queries are supplied in assignment.sql. These examples support the machine-learning investigation; there is no eight-query worksheet to complete.

Run the table setup first so rides and zones are available. These queries use the full 60,000-trip sample. Revenue means recorded fare + tip; cash tips are not recorded. Monthly totals describe the sample, not all taxi trips in the city.

Q1 · How many rides and how much recorded revenue?

Return one row for the whole sample. Add fares and recorded tips, then round the total to cents.

SELECT COUNT(*) AS n_rides,
       ROUND(SUM(fare + tip), 2) AS revenue
FROM rides;

Q2 · How much revenue was recorded each month?

GROUP BY combines trips from the same month. ORDER BY puts the twelve monthly results in calendar order.

SELECT month,
       ROUND(SUM(fare + tip), 2) AS revenue
FROM rides
GROUP BY month
ORDER BY month;

Q3 · Do card and cash rides differ in distance?

Return a ride count and average distance in miles for each payment type.

SELECT payment,
       COUNT(*) AS n,
       ROUND(AVG(distance), 2) AS avg_distance
FROM rides
GROUP BY payment
ORDER BY payment;

Q4 · Which five rides have the highest fares?

Sort fares from highest to lowest. If fares tie, the smaller ride_id comes first.

SELECT ride_id, fare
FROM rides
ORDER BY fare DESC, ride_id ASC
LIMIT 5;

Q5 · What fraction of rides were paid by card each month?

CASE turns each card payment into 1 and each cash payment into 0. Their average is the card share: 0.8 means 80%.

SELECT month,
       ROUND(AVG(CASE WHEN payment = 'card'
                      THEN 1.0 ELSE 0.0 END), 3) AS card_share
FROM rides
GROUP BY month
ORDER BY month;

Q6 · How does revenue accumulate through the year?

The monthly step produces one total per month. The window then adds those totals from the first month through the current month, keeping one result per month. Round only the displayed results.

WITH monthly AS (
  SELECT month, SUM(fare + tip) AS revenue
  FROM rides
  GROUP BY month
)
SELECT month,
       ROUND(revenue, 2) AS revenue,
       ROUND(SUM(revenue) OVER (
         ORDER BY month
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ), 2) AS running_revenue
FROM monthly
ORDER BY month;

Q7 · What are the totals for October–December?

Read the partitioned Parquet files directly. hive_partitioning makes month available from folder names such as month=10. The month filter lets DuckDB skip files for January–September; use EXPLAIN to inspect the scan.

SELECT COUNT(*) AS n_rides,
       ROUND(SUM(fare + tip), 2) AS revenue
FROM read_parquet(
  'data/rides_by_month/*/*.parquet',
  hive_partitioning = true
)
WHERE month IN (10, 11, 12);

Q8 · Which pickup boroughs have the most recorded revenue?

Join each trip to its pickup zone to find the borough. Then group by borough and show the five highest revenue totals.

SELECT z.Borough AS borough,
       COUNT(*) AS n_rides,
       ROUND(SUM(r.fare + r.tip), 2) AS revenue
FROM rides AS r
JOIN zones AS z ON r.pickup_zone = z.LocationID
GROUP BY z.Borough
ORDER BY revenue DESC
LIMIT 5;

What to notice: Q4 uses ride_id ASC to break fare ties. Q5 averages a numeric card indicator. Q6 windows over monthly totals. Q8 joins each ride to one zone, so an accidentally duplicated dimension key would multiply revenue.

FAQ

Do my model errors or timings need to match the reference?

No. Report your own model errors and explain them. Package versions can change exact values. The core submission is your model investigation. The eight worked SQL examples and storage measurements are optional reference material. Runtime depends on hardware, caching, library versions, and the query. Report what you measured and use the plans and data layout to explain it, including cases where a speedup is smaller than expected.

Why does the harness compute reference answers live instead of hardcoding?

Computing the reference results from the same files keeps the expected answers tied to the dataset used in the test. The checks confirm that the supplied examples return those results on your local data.

Is this really the city's taxi data? Can I use it elsewhere?

Yes. The sample comes from the TLC’s published 2024 yellow-taxi trip records after cleaning. Cite the TLC and describe the sampling and cleaning when using it in another project. The sample does not measure cash tips, and equal sampling per month means monthly sample totals are not estimates of total citywide revenue without appropriate weighting.

DuckDB read my 60k-row CSV in 60ms. Why did the lecture make CSV sound so bad?

A 60 ms query may be fast enough for this dataset. At larger sizes or with repeated queries, parsing a whole CSV can become expensive. Parquet can avoid unused columns and nonmatching row groups, but neither runtime nor speedup scales by a fixed factor. Use a larger dataset and inspect the plan to test how the difference changes.

Is hive_partitioning something to do with Apache Hive?

Yes. The key=value/ folder convention comes from Apache Hive. Compatible readers infer partition values from paths and can exclude files when a filter rules them out. The convention is now supported by tools beyond Hive, including DuckDB and Spark.
