Real SQL at last

You built microSQL's SELECT-FROM-WHERE; this lab uses its three grown-up cousins, each of which your Act I knowledge decodes:

ConstructWhat it meansThrough Act I eyes
GROUP BY monthpartition rows by value; aggregate each groupa materializing operator (Lecture 4's pipeline-breaker); must see all rows before emitting
SUM(...) OVER (ORDER BY month)a running total: each row sees an aggregate over a moving framean operator with memory: sort, then stream with state
ORDER BY fare DESC LIMIT 5top-kthe optimizer keeps a 5-row heap instead of sorting 60k, cost models at work

Part 1 · Build ~30 min in class

  1. pip install duckdb, download the four starter files, run python3 gen_data.py once (60k rows, seeded; your data equals everyone's).
  2. Work the queries in order: they escalate. Test constantly: python3 test_duckdb.py after every query; or explore interactively first with python3 -c "import duckdb; duckdb.sql(open('scratch.sql').read()).show()".
  3. Q5's hint is load-bearing: AVG(CASE WHEN payment = 'card' THEN 1.0 ELSE 0.0 END), the indicator-variable trick, the same one your statistics courses use, now in SQL.
  4. Q6 stacks a window on a group: SUM(SUM(fare + tip)) OVER (ORDER BY month) reads strangely once, then forever makes sense: inner SUM per group, outer SUM across groups.
Gotchas that cost real debugging time

Round exactly where the question says: round(sum(...), 2) and sum(round(..., 2)) differ by pennies and the harness notices. Column aliases must match the question's names (n_rides, not count). And Q7 needs hive_partitioning = true or month won't exist as a column; it lives in the folder names.

Exercise · read the failure

A classmate's Q2 fails with "result differs: yours starts [(1, 118000.0)], expected starts [(1, 117987.66)]". Their query looks right. What did they round, and where?

Show answer

They rounded to whole dollars (or rounded each fare before summing). Floating-point aggregation order can also bite at higher precision, which is why the reference rounds the sum to 2 decimals, one canonical answer. Money in real systems uses DECIMAL types for exactly this reason; DuckDB has them, and Going Further invites the refactor.

FAQ

My times differ from the reference. Failed?

Times are your machine's; only counts (rows, 1/12 files) are graded exact. If your CSV/Parquet ratio is 20× instead of 89×, your SSD and CPU differ; the direction and magnitude class is the lesson.

Why does the harness compute reference answers live instead of hardcoding?

So data and answers can never drift, the same single-source principle as the course's quiz generators. Yes, you can read the reference SQL; the Gradescope set uses variants, and understanding beats copying on those.

DuckDB read my 60k-row CSV in 42ms. Why did the lecture make CSV sound so bad?

Scale: 42ms at 60k rows is 42 seconds-ish at 60M, minutes beyond, while Parquet's advantage compounds (compression improves with size, and stats let whole row groups be skipped). Laptop-scale data forgives everything; the formats exist for the data that doesn't.

Is hive_partitioning something to do with Apache Hive?

The naming convention (key=value/ folders) comes from Hive, the 2009 Hadoop-era SQL layer, long since superseded, its folder convention immortal. Week 13 tells that lineage's story properly (MapReduce → Hive → Spark).
