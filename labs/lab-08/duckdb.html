GROUP BY, windows, and LIMIT are Act I operators in disguise

You built microSQL's SELECT-FROM-WHERE; this lab uses its three grown-up cousins, each of which your Act I knowledge decodes:

ConstructWhat it meansThrough Act I eyes
GROUP BY monthpartition rows by value; aggregate each groupa materializing operator (Lecture 4's pipeline-breaker); must see all rows before emitting
SUM(...) OVER (ORDER BY month)a running total: each row sees an aggregate over a moving framean operator with memory: sort, then stream with state
ORDER BY fare DESC LIMIT 5top-kthe optimizer keeps a 5-row heap instead of sorting 60k, cost models at work

The data is real, and it was cleaned

Every earlier lab ran on the six students of the students table. This one runs on 60,000 trips taken by real New York City yellow cabs in 2024. The city's Taxi and Limousine Commission publishes every trip as a monthly Parquet file of about three million rows; the lab's gen_data.py unpacks a sample of 5,000 trips from each month, drawn once with a fixed seed so that everyone's file is identical and the harness can compare answers. The rows were cleaned before sampling, and the cleaning rules matter because they shape every number you will compute. Real data does not arrive clean; deciding what to drop is part of the job.

RuleWhat it dropsShare of a raw month
passengers between 1 and 6null and zero passenger counts, and the odd 9-passenger vanabout 6%
distance between 0.1 and 100 mileszero-length trips and GPS glitches that report 10,000 milesunder 2%
fare between $1 and $500refunds (negative fares), voided trips, and a handful of $10,000 typosabout 1%
payment is card or cashdisputes, no-charge trips, and unknown payment typesabout 7%
duration between 1 and 180 minutesmeter errors: trips that ended before they started or ran for a dayunder 1%

One quirk survives on purpose. Every cash ride has tip = 0, not because cash riders never tip but because the meter only records tips paid by card. Group tip by payment and you will see it, and it is the first lesson of the lab: a column that is always zero for one group is usually a fact about how the data was collected, not about the world.

Two tables make the smallest possible star schema

There are two tables, which makes this the smallest possible star schema: rides is the fact table, one row per trip, and zones is a dimension table, one row per taxi zone with its borough, joined on rides.pickup_zone = zones.LocationID.

  3. Q5's hint is load-bearing: AVG(CASE WHEN payment = 'card' THEN 1.0 ELSE 0.0 END), the indicator-variable trick, the same one your statistics courses use, now in SQL.
  4. Q6 stacks a window on a group: SUM(SUM(fare + tip)) OVER (ORDER BY month) reads strangely once, then forever makes sense: inner SUM per group, outer SUM across groups.
  5. Q8 is your first join since Lab 4, and DuckDB plans it the way Lecture 9 described: it hashes the small table (265 zones) and probes it with the big one. Read the plan with EXPLAIN and find the build and probe sides.
Gotchas that cost real debugging time

Round exactly where the question says: round(sum(...), 2) and sum(round(..., 2)) differ by pennies and the harness notices. Column aliases must match the question's names (n_rides, not count). And Q7 needs hive_partitioning = true or month won't exist as a column; it lives in the folder names.

Exercise · read the failure

A classmate's Q2 fails with "result differs: yours starts [(1, 111,003.0)], expected starts [(1, 111,003.22)]". Their query looks right. What did they round, and where?

Show answer

They rounded to whole dollars (or rounded each fare before summing). Floating-point aggregation order can also bite at higher precision, which is why the reference rounds the sum to 2 decimals, one canonical answer. Money in real systems uses DECIMAL types for exactly this reason; DuckDB has them, and Going Further invites the refactor.

More than 100× from the file format alone, and a WHERE clause that skipped eleven files without opening them. Every mechanism has an Act I name: fewer blocks, pushdown, layout-follows-workload, now measured on the real stack. Step 4 is the one to carry into your notebooks: once a dataframe is loaded, DuckDB can run SQL over it in place, with no copy, at about the speed of pandas itself. You do not have to choose between the two; you can write the GROUP BY in whichever is clearer and hand the frame back and forth.

Part 4 · Fix the slow query ~20 min · homework

Every query in Parts 1 to 3 was written the way the engine wants it. Most queries in real notebooks are not, and they are slow in ways that EXPLAIN makes visible. slow_queries.py computes three answers twice each: once the way a notebook usually does it, once the way the engine wants. The ratios are your machine's; the shapes are universal.

$ python3 slow_queries.py
A. PUSHDOWN   WHERE month = (SELECT max(month) ...):      1.8 ms   (no file filter in the plan: every file is opened)
              WHERE month = 12 (looked up first):        0.7 ms   File Filters:
              2.8x here, and the gap grows with the data: a value hidden inside a
              subquery is unknown when the planner decides which files to open, so it opens all of them

B. FETCH-FILTER  SELECT * then filter in Python:     40.3 ms   (60,000 rows x 12 columns cross into Python)
                 WHERE month = 12 in SQL:             0.4 ms   (about 5,000 rows x 2 columns are touched)
                 102x: move the filter to the data, not the data to the filter

C. LOOP       twelve queries, one per month:          4.4 ms   (twelve scans of the file)
              one GROUP BY month:                     1.0 ms   (one scan)
              4.3x: a for-loop over groups is a join the engine never got to plan

Read each pair against the machinery you built. In A, the planner chooses which Parquet files to open before it runs anything, so a value that only exists after a subquery runs is invisible at that moment: it opens all twelve. Look up the value first and it is a literal the planner can see. In B, SELECT * moves 60,000 rows by 12 columns across the DuckDB-to-Python boundary, one Python tuple at a time, and then Python does the filtering; the SQL version touches about 5,000 rows of two columns inside the engine and returns one number. In C, the loop is twelve scans of the same file with twelve planning passes, when one GROUP BY does the work in a single scan. Every one of these is a pattern you will recognize in your own past notebooks.

Exercise · the nested file

gen_data.py also wrote data/rides.jsonl, one JSON object per ride with nested fields: pickup.zone, pickup.hour, dropoff.minutes, payment.type, payment.fare, payment.tip. Logs, API responses, and event streams arrive in this shape, not as flat tables. Using read_json_auto('data/rides.jsonl'), reproduce Q8 (revenue by pickup borough, top 5) straight from the nested file. Check DESCRIBE first to see how DuckDB typed the nested fields.

Show answer 
SELECT z.Borough AS borough, count(*) AS n_rides,
       round(sum(r.payment.fare + r.payment.tip), 2) AS revenue
FROM read_json_auto('data/rides.jsonl') r
JOIN zones z ON r.pickup.zone = z.LocationID
GROUP BY z.Borough ORDER BY revenue DESC LIMIT 5;

DESCRIBE shows each nested object typed as a STRUCT, and dot notation reaches inside it. The result must match Q8 exactly: same rides, different container. The JSON file is four times the size of the CSV and fourteen times the size of the Parquet for the same 60,000 rides, which is the price of carrying the field names in every row.

FAQ

My times differ from the reference. Failed?

Times are your machine's; only counts (rows, 1/12 files) are graded exact. If your CSV/Parquet ratio is 20× instead of 130×, your SSD and CPU differ; the direction and magnitude class is the lesson.

Why does the harness compute reference answers live instead of hardcoding?

So data and answers can never drift, the same single-source principle as the course's quiz generators. Yes, you can read the reference SQL; the Gradescope set uses variants, and understanding beats copying on those.

Is this really the city's taxi data? Can I use it elsewhere?

Yes. The TLC publishes every yellow-cab trip as open data, and the lab's file is a seeded sample of the 2024 files after the cleaning rules listed above. Use it in your own projects freely; just cite the TLC. The one thing the sample cannot tell you is anything about cash tips, because the source never recorded them.

DuckDB read my 60k-row CSV in 60ms. Why did the lecture make CSV sound so bad?

Scale: 60ms at 60k rows is 60 seconds-ish at 60M, minutes beyond, while Parquet's advantage compounds (compression improves with size, and stats let whole row groups be skipped). Laptop-scale data forgives everything; the formats exist for the data that doesn't.

Is hive_partitioning something to do with Apache Hive?

The naming convention (key=value/ folders) comes from Hive, the 2009 Hadoop-era SQL layer, long since superseded, its folder convention immortal. Week 13 tells that lineage's story properly (MapReduce → Hive → Spark).
