Real SQL at last

You built microSQL's SELECT-FROM-WHERE; this lab uses its three grown-up cousins, each of which your Act I knowledge decodes:

ConstructWhat it meansThrough Act I eyes
GROUP BY monthpartition rows by value; aggregate each groupa materializing operator (Lecture 4's pipeline-breaker); must see all rows before emitting
SUM(...) OVER (ORDER BY month)a running total: each row sees an aggregate over a moving framean operator with memory: sort, then stream with state
ORDER BY fare DESC LIMIT 5top-kthe optimizer keeps a 5-row heap instead of sorting 60k, cost models at work
Think · Pair · Share · the tie that bites
  • Think · 2 minQ4 asks for the five most expensive rides with ORDER BY fare DESC, ride_id. Suppose you wrote only ORDER BY fare DESC LIMIT 5 and two rides tie at the 5th-highest fare. What can happen to your result between runs, and why would an autograder (or a dashboard diff, or a re-run report) care?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minTies are returned in ANY order the engine likes; parallel scans make it genuinely nondeterministic. The tiebreak column makes results reproducible. Where else in DS does nondeterministic ordering quietly poison reproducibility?
  • Share · 2 minHouse rule, one sentence: every ORDER BY that feeds a LIMIT or a diff gets a total order.
Show the answer

With a tie at the fifth-highest fare, which of the tied rides appears is undefined, and it can differ between runs of the same query on the same data. DuckDB scans partitions in parallel, so the order rows arrive in is a scheduling accident, not a property of the data.

That is why an autograder cares: your answer is not wrong, it is unstable, and a diff against a reference answer fails on some runs and passes on others. The same poison shows up all over data science: a train/test split that ties on a sort key, a "top 10 customers" dashboard that reshuffles overnight, a groupby whose first-per-group depends on arrival order.

House rule: every ORDER BY feeding a LIMIT or a diff gets a total order. Add a unique tiebreak column, here ride_id, so the sort has exactly one correct answer rather than a set of equally legal ones.

Gotchas that cost real debugging time

Round exactly where the question says: round(sum(...), 2) and sum(round(..., 2)) differ by pennies and the harness notices. Column aliases must match the question's names (n_rides, not count). And Q7 needs hive_partitioning = true or month won't exist as a column; it lives in the folder names.

Exercise · read the failure

A classmate's Q2 fails with "result differs: yours starts [(1, 118000.0)], expected starts [(1, 117987.66)]". Their query looks right. What did they round, and where?

Show answer

They rounded to whole dollars (or rounded each fare before summing). Floating-point aggregation order can also bite at higher precision, which is why the reference rounds the sum to 2 decimals, one canonical answer. Money in real systems uses DECIMAL types for exactly this reason; DuckDB has them, and Going Further invites the refactor.

Part 3 · Measure ~25 min · finish as homework

Think · Pair · Share · call all three shots
  • Think · 2 minBefore running measure_parquet.py, predict: (a) Parquet vs CSV on a full-column sum: 2×, 10×, or 50×+? (b) can reading 2 columns of 8 beat reading 1 column of 1 file? (c) for month = 12 over 12 partition files, how many files does DuckDB open?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minRun it. The EXPLAIN output literally prints Scanning Files: 1/12; find that line and read it aloud; it is predicate pushdown's furthest push.
  • Share · 2 minOne sentence connecting today's three numbers to a BigQuery bill.
Show the answer

(a) 89×. Two separate sins compound: CSV must be parsed (every byte of every column becomes text to scan), and it has no column structure, so the whole file moves even for one column. Parquet stores typed binary columns with per-chunk statistics. (b) Yes, easily. Reading 2 columns of 8 from Parquet took 0.8 ms against CSV's 42 ms for one column, because "one column of CSV" still means dragging the whole file through a parser. (c) One. EXPLAIN prints it literally: Scanning Files: 1/12, with the other eleven directories never opened.

Connecting all three to a bill: scan-priced warehouses like BigQuery charge by bytes scanned, so format, projection and pruning are not performance tuning, they are line items. The same query costs 89× more against CSV, several times more if you write SELECT *, and twelve times more if the table is not partitioned on the column you filter by. Schema and layout decisions are a budgeting skill.

FAQ

My times differ from the reference. Failed?

Times are your machine's; only counts (rows, 1/12 files) are graded exact. If your CSV/Parquet ratio is 20× instead of 89×, your SSD and CPU differ; the direction and magnitude class is the lesson.

Why does the harness compute reference answers live instead of hardcoding?

So data and answers can never drift, the same single-source principle as the course's quiz generators. Yes, you can read the reference SQL; the Gradescope set uses variants, and understanding beats copying on those.

DuckDB read my 60k-row CSV in 42ms. Why did the lecture make CSV sound so bad?

Scale: 42ms at 60k rows is 42 seconds-ish at 60M, minutes beyond, while Parquet's advantage compounds (compression improves with size, and stats let whole row groups be skipped). Laptop-scale data forgives everything; the formats exist for the data that doesn't.

Is hive_partitioning something to do with Apache Hive?

The naming convention (key=value/ folders) comes from Hive, the 2009 Hadoop-era SQL layer, long since superseded, its folder convention immortal. Week 13 tells that lineage's story properly (MapReduce → Hive → Spark).
