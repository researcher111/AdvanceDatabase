Disk & File Manager

microdb begins: blocks, pages, and the actual bytes on disk.
Follows Lecture 1 (Anatomy of a Database) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 3 at class start

Postgres's storage manager (storage/smgr) and SQLite's file format both bottom out in code like the code you write today: open a file, seek to block × block_size, move exactly one block of bytes. No SQL, no tables, no cleverness, just the disk's contract, honored precisely. It is the least glamorous layer of microdb and the one every other layer will stand on for the next seven weeks.

Companion reading: Sciore, Database Design and Implementation, ch. 3 (SimpleDB's file manager) · Python struct docs · for fun afterwards: the real SQLite file format, which is this lab with twenty years of scar tissue.

Why whole blocks

Before writing the code, settle the design question the whole layer is built on: what unit should read() move? A row? An arbitrary byte range? Every serious engine lands on the same answer: move fixed-size blocks, and make them generous: 4 KB in microdb, 8 KB in Postgres, up to 64 KB in analytics systems. Since the trip costs the same anyway, fetching the whole neighborhood is free insurance that the next request is already in memory. Fixed size (rather than "exactly what was asked for") is what makes the bookkeeping sane: block k of a file always lives at one computable place, and memory can be managed as identical-sized frames:

byte range of block k   =   [ k × block_size ,  (k+1) × block_size )

so with block_size = 4096:   block 0 → bytes 0…4095
                             block 1 → bytes 4096…8191   ← seek here, read 4096

One caution that will save you a debugging hour: when your Python "writes" a block, the OS usually just copies it into its own page cache and returns instantly. The bytes reach the physical SSD later, unless you demand otherwise with fsync. The gap between those two kinds of "written" is Part 3 of this lab, and in week 7 it becomes the entire design problem of the write-ahead log.

A file is not a page

Your laptop keeps bytes in two places, and they could hardly be more different. The disk holds students.tbl: it keeps its bytes through a power cut, but every trip to it costs about 25 µs on an SSD (the latency ladder from Tuesday). Memory (RAM) holds every Python object you have ever made: it answers in about 100 ns, 250× faster, but forgets everything the moment your process exits. Your code can only work on bytes in memory, and bytes only survive on disk, so a database spends its whole life copying between the two. This layer is that ferry.

microdb gives each side of the ferry its own word, so the code can never confuse them:

WordLivesWhat it is
blockon diskslice number k of a file: bytes k×4096 to k×4096+4095. Survives restarts.
pagein memoryone block-sized bytearray your code reads and edits. Gone when the process exits.
BlockIdnowhere, reallya name: a filename plus a block number. Holds no bytes; it just says which block you mean.

Same 4096 bytes, two homes, and one class that moves them: fm.read copies a block into a page, fm.write copies a page back over a block.

Three classes, one contract



The whole layer is three classes, and two of them fit on an index card. Hover each line,
then keep the byte-layout table close while you code, because the tests enforce it literally.




  
class BlockId:                                # ('students.tbl', 1), a name, not data

  
    filename: str; blknum: int                # provided for you

  
class Page:                                   # a block-sized bytearray + typed get/set

  
    def get_int(off) -> int                   # read 4 bytes as an int

  
    def set_int(off, val)                     # write an int as 4 bytes

  
    def get_bytes(off) -> bytes               # read [length][payload]

  
    def set_bytes(off, b)                     # write [length][payload]

  
    def get_string(off) -> str                # get_bytes, then decode UTF-8

  
    def set_string(off, s)                    # encode UTF-8, then set_bytes

  
class FileManager:                            # db_dir, block_size=4096

  
    def read(block, page)                     # disk → page

  
    def write(block, page, sync=True)         # page → disk (+fsync if sync)

  
    def append(filename) -> BlockId           # grow the file by one empty block

  
    def length(filename) -> int               # how many blocks the file holds

  
Hover any line to see what it does and which Python call implements it.





An int is easy to lay out: always exactly 4 bytes, wherever it sits. A string
is not, because its length changes from row to row, so the layout has to pin down where one
ends before the next field begins. microdb settles that with a specific rule, stated in the
contract table below.



The contract, in one table. This exact layout is what test_filemanager.py
round-trips, and every later lab assumes it:

byteslength as an int at off, payload at off+44 + lenset_int + slice

bytes_needed("ada")  =  4 + 3  =  7      → the ada row: 4 (id) + 7 (name) + 4 (gpa) = 15 bytes
bytes_needed(s)      =  4 + len(s.encode('utf-8'))

Encode first, then count. Characters are not bytes:

    'héllo'      h     é       l     l     o
    as bytes     68    C3 A9   6C    6C    6F   ← 'é' takes TWO bytes

    len('héllo')                  = 5 characters
    len('héllo'.encode('utf-8'))  = 6 bytes      ← reserve this many, or you truncate



The Tool column above names a function most people have never used:
struct.pack_into. It is worth a minute, because it does not behave the way ordinary
functions do. It returns nothing. You hand it a buffer you already have, an
offset, and a value, and it writes the bytes into that buffer in place, leaving every
other byte exactly as it was. That is precisely what a page needs, because a page is one fixed
block of memory that many fields have to share. Try it here before you implement
set_int on Thursday.

  Gotchas that cost real debugging time
  
"w+b" truncates an existing file (the mode letters are pulled
  apart in the table below). The starter's _file() helper already
  creates-without-truncating; use it, don't reopen files yourself.
  struct.pack returns bytes while pack_into writes in place;
  you want pack_into. And slicing a bytearray copies: write with
  self._data[a:b] = payload, not chunk = self._data[a:b]; chunk[:] = payload.





Reading the mode string



That gotcha is only frightening while "w+b" looks like magic. It is three
independent choices concatenated, and once you can read them apart you will never truncate a
table file by accident. Every Python mode string is one base letter, an optional
+, and an optional b.




  
PieceShort forWhat it does to the file

  
    
rreadOpen for reading only, positioned at byte 0. FileNotFoundError if it isn't there. This is the default when you omit the letter.

    
wwriteOpen for writing only, and truncate an existing file to zero bytes. Creates the file if it's missing.

    
aappendOpen for writing only, keeping the contents. Creates if missing. Every write lands at the end of the file no matter where you seek.

    
xexclusive createCreate and open for writing, but raise FileExistsError rather than touch an existing file.

    
+the other direction tooAdds the half the base letter left out, so the one handle can both read and write. It changes nothing about truncation: w+ still wipes the file.

    
bbinaryRead and write raw bytes: no text decoding, no newline translation. Without it you get str, and your page bytes get corrupted on the way through.

  Why _file() opens the file twice
  
No single mode both creates a missing file and refuses to truncate an existing
  one, so the starter spends two lines buying exactly that: open(path, "wb").close()
  only when os.path.exists says the file is missing, then open(path, "r+b")
  every time. That is the whole reason the helper exists, and why reopening files yourself is the
  fastest way to lose a table.

  
The b is not optional either. Drop it and Python decodes your page as text and
  rewrites line endings on the way through: the four bytes 0D 0A C3 A9 read back in
  text mode as the two characters '\né': 0D 0A silently collapsed to one
  newline, and two bytes fused into one é. A page of student records would come back
  a different length than it went in.





The cursor: seek and tell



Every open file object carries one number. The docs call it the stream position;
everyone else calls it the cursor. It is the byte offset where the next read or
write will happen. It starts at 0 when _file() opens the file, and every
read(n) or write(b) moves it forward by the number of bytes moved. Two
methods let you move it and ask where it is:



f.seek(offset, whence=0)    move the cursor. Returns the new absolute position.
f.tell()                    report the cursor's absolute byte position.



The second argument to seek, called whence, says what
offset is measured from. Python accepts the integer or the named constant from the
os module; they are the same value.




  
whenceNameOffset is measured fromIn this lab

  
    
0os.SEEK_SET (the default)the start of the filef.seek(blknum * block_size) jumps to a block

    
1os.SEEK_CURthe current cursor positionnot needed; every call seeks from the start

    
2os.SEEK_ENDthe end of the filef.seek(0, 2) means "go to the very end"

  





  
Where the cursor is after each call

  
  
Each row is the same file. seek only changes the number; it
  does not touch the disk. A block is moved when you read or write from
  wherever the cursor is.





Put the two together and you get length() for free. f.seek(0, 2)
walks the cursor to the end of the file, so the position f.tell() reports
is the file size in bytes; integer-divide by block_size and you have the
number of whole blocks. os.fstat(f.fileno()).st_size returns the same number without
moving the cursor, and either is fine for this lab.




  Seek before every read and write
  
The cursor is shared by everything that touches the handle. A read leaves it at
  the end of the block it just read, and a length() call leaves it at the end of the
  file. If read(block, page) assumes the cursor is already in the right place, it will
  return the wrong block exactly often enough to be confusing. Compute
  blknum * block_size and seek to it at the top of both
  read and write, every time. That habit is the whole fix for the
  "writing block 1 clobbered block 0" failure in Part 2.

Part 2 · Verify ~20 min in class



The tests come in two groups. The PAGE tests never touch disk. Each one
writes a value into a page and reads it back: ints (including negatives, which is why the spec
says signed), strings with multibyte UTF-8 characters, and the adjacent-values
test, which stores the full ada row and then checks that no field's write spilled into its
neighbor.



The FILE tests go through disk. They check that append and
length agree with each other, that a page written to a block comes back unchanged
when you read it, and that writing block 1 leaves block 0 alone (the classic seek-arithmetic
bug). Reading past the end of the file must raise ValueError. The last test checks
durability: the harness closes your
FileManager, opens a fresh one, and expects the data to still be there. That is the smallest
possible version of surviving a restart.

  get_int(11) returns 39 correctly, but get_string(4)

Show answer
  
set_bytes (or set_string calling it) is writing the payload at
  off instead of off+4, then writing the length prefix over the first
  payload bytes, or writing the length as more than 4 bytes. The string's stored length claims
  more bytes than were written, so get_string reads into the neighboring field.
  The length prefix and payload have swapped or overlapped territory; re-check who writes at
  off and who writes at off+4.

Your file manager has a switch you haven't evaluated yet: write(…, sync=True) ends
with fsync, the call that turns "the OS accepted my bytes" into "the bytes are on
the SSD".



Run it and note all three numbers; you will want them in class:



$ python3 measure_io.py
buffered writes (sync=False):      465,849 blocks/sec
durable  writes (sync=True):        30,788 blocks/sec
ratio (buffered / durable):           15.1x



Now change something. BLOCK_SIZE in measure_io.py
is 4096. Set it to 512, run, then set it to 65536 and run again. Report both rates and the ratio
at each size, and say which of the two rates moved more and why: the answer tells you whether
your SSD charges per byte or per fsync.




  
What one machine measured

  
Instructor's Apple-silicon laptop: representative shape, not a
  target. Fast SSDs with write caches show 10–20×; many laptops and most cloud disks show
  100–1000×. Yours is correct if your tests pass.

  

  
The gap is the price of honesty: sync=False is "the OS has
  it (probably)"; sync=True is "it will survive the power cord being pulled right now."
  (macOS caveat in the FAQ.)





Hold on to your ratio: it is the founding constraint of Lab 7.
A database cannot fsync every page it touches and stay usable, yet it promises durability on
every commit. The escape from that trap is called a write-ahead log, and the number you just
measured is why it exists.



Where you'll meet this layer at work



You will not write another file manager, but every write-heavy job you run pays this
layer's prices. A training job that dies partway through writing a CSV leaves whatever the OS page
cache had flushed, cut off at an arbitrary byte, so the rerun has to start from a clean file:
nothing on disk records where the good bytes end. A model checkpoint is no different: after
torch.save returns, your guarantee is the sync=False one unless something
called fsync, which is why careful checkpoint code writes a temporary file, fsyncs it,
and renames it over the old one. The ratio you just measured is what a pipeline gives up when it
insists on durability per record instead of per batch, and it is the reason every bulk loader
(Postgres COPY, or one transaction wrapped around many INSERTs) groups
thousands of writes under a single fsync. Parquet's row groups are this lab's blocks at a larger
size: a fixed chunk at a known offset that a reader can seek to directly, which is how
pyarrow skips a row group whose min and max statistics rule it out, where a CSV reader
has to read the whole file. When DuckDB or Postgres reports that a query read some number of
pages, each page is a BlockId.

FAQ



My two runs of measure_io.py differ by 30%. Is something broken?


No, you're timing a real OS with other work to do. Run it three times, report the middle
result, and remember the lab grades the presence and interpretation of your numbers, not their
absolute size.



I'm on macOS and my fsync ratio seems suspiciously small.


Sharp eyes. On macOS, fsync flushes to the drive but doesn't force the drive's
own cache to persist; real engines use F_FULLFSYNC there, which is far slower.
Your measurement is still valid for this lab; mention the caveat when
ratios get compared in class, for a nod of respect. (SQLite and Postgres both special-case
this; databases collect such scars.)



Windows: anything different?


Everything works natively (os.fsync maps to FlushFileBuffers).
Just work in a local folder, not a OneDrive-synced one; sync clients hold file locks at the
worst moments.



Why little-endian? Postgres stores big-endian on the wire!


Either works as long as everyone agrees; we picked the byte order your CPU already uses so
that a hexdump of your file matches what the widget shows. The lesson is that it's a
contract: the tests pin it so week 3's record code can trust week 1's bytes.



Can I keep my own design instead of the given API?


Not for the method signatures: Labs 2–7 starters call these exact names with these exact
semantics. Inside the methods, style is yours.
