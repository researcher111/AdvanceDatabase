Disk & File Manager

microdb begins: blocks, pages, and the actual bytes on disk.
Follows Lecture 1 (Anatomy of a Database) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 3 at class start

Postgres's storage manager (storage/smgr) and SQLite's file format both bottom out in code like the code you write today: open a file, seek to block × block_size, move exactly one block of bytes. No SQL, no tables, no cleverness, just the disk's contract, honored precisely. It is the least glamorous layer of microdb and the one every other layer will stand on for the next seven weeks.

Companion reading: Sciore, Database Design and Implementation, ch. 3 (SimpleDB's file manager) · Python struct docs · for fun afterwards: the real SQLite file format, which is this lab with twenty years of scar tissue.

Dotted-underlined terms like this one are systems jargon; hover or tap for a plain-language explainer that opens right below the sentence you're reading.

Why whole blocks

Before writing the code, settle the design question the whole layer is built on.

Think · Pair · Share · the disk's contract
  • Think · 2 minA file is just a long array of bytes, and the ada row is 15 bytes. Yesterday's latency ladder said a storage trip costs the same whether it moves 8 bytes or 8 KB. Given that one fact, design the read API. Should read() fetch a row? A byte range? Something else? Commit to an answer.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare APIs. If you fetch exactly one row per trip, what happens to the query from lecture that needed all six?
  • Share · 2 minAgree on the unit a storage layer should move, then check it against the API below.
Show the answer

read() should fetch a fixed-size block, not a row and not an arbitrary byte range. If the trip costs the same either way, fetching only 15 bytes throws away the rest of the trip you already paid for.

Fetch one row per trip and the six-row query from lecture pays six full storage trips for data that was sitting in one neighbourhood. Fetch the block and it pays one, with the other five rows arriving free. Why fixed size rather than "whatever was asked for"? Because it turns finding a block into arithmetic. Block k starts at k × block_size, so with 4096-byte blocks, block 3 begins at byte 12288 and runs to byte 16383. Nothing has to be recorded or looked up to find it. Blocks of varying size would need a table saying where each one begins, maintained forever and consulted on every single read.

Fixed size pays a second time in memory. Every frame in next week's buffer pool is the same size, so any block can be loaded into any free frame. That is what lets the pool be a plain array of frames rather than a memory allocator. Every serious engine lands here: 4 KB in microdb, 8 KB in Postgres, up to 64 KB in analytics systems.

Every serious engine lands on the same answer: move fixed-size blocks, and make them generous: 4 KB in microdb, 8 KB in Postgres, up to 64 KB in analytics systems. Since the trip costs the same anyway, fetching the whole neighborhood is free insurance that the next request is already in memory. Fixed size (rather than "exactly what was asked for") is what makes the bookkeeping sane: block k of a file always lives at one computable place, and memory can be managed as identical-sized frames:

byte range of block k   =   [ k × block_size ,  (k+1) × block_size )

so with block_size = 4096:   block 0 → bytes 0…4095
                             block 1 → bytes 4096…8191   ← seek here, read 4096

One caution that will save you a debugging hour: when your Python "writes" a block, the OS usually just copies it into its own page cache and returns instantly. The bytes reach the physical SSD later, unless you demand otherwise with fsync. The gap between those two kinds of "written" is Part 3 of this lab, and in week 7 it becomes the entire design problem of the write-ahead log.

Three classes, one contract

The whole layer is three classes, and two of them fit on an index card. Hover each line, then keep the byte-layout table close while you code, because the tests enforce it literally.

class BlockId: # ('students.tbl', 1), a name, not data
filename: str; blknum: int # provided for you
class Page: # a block-sized bytearray + typed get/set
def get_int(off) -> int # read 4 bytes as an int
def set_int(off, val) # write an int as 4 bytes
def get_bytes(off) -> bytes # read [length][payload]
def set_bytes(off, b) # write [length][payload]
def get_string(off) -> str # get_bytes, then decode UTF-8
def set_string(off, s) # encode UTF-8, then set_bytes
class FileManager: # db_dir, block_size=4096
def read(block, page) # disk → page
def write(block, page, sync=True) # page → disk (+fsync if sync)
def append(filename) -> BlockId # grow the file by one empty block
def length(filename) -> int # how many blocks the file holds
Hover any line to see what it does and which Python call implements it.

An int is easy to lay out: always exactly 4 bytes, wherever it sits. A string is not, because its length changes from row to row, so the layout has to pin down where one ends before the next field begins. microdb settles that with a specific rule, stated in the contract table below. Work out your own version first.

  • Share · 2 minCheck your design against the spec table below; if yours differs, name the tradeoff you made.
Show the answer

Write the length first: a 4-byte int holding the byte count at off, then the payload at off+4. So "ada" at offset 4 is 03 00 00 00 then 61 64 61, occupying bytes 4 through 10.

Just writing the three letters fails because the reader has no idea where to stop: the page is full of other data, and get_string(4) would happily return "ada" followed by whatever bytes came next. A terminator byte fixes that only if the terminator can never appear in the data, which is false for arbitrary bytes and false for UTF-8 in general, and it also makes reading O(length) instead of O(1). Fixed width works but wastes space and imposes a maximum. The length prefix costs 4 bytes, permits any byte in the payload, and tells you the size before you read it, which is why it is the spec the tests enforce.

The contract, in one table. This exact layout is what test_filemanager.py round-trips, and every later lab assumes it:

TypeLayout at offset offBytes usedTool
int4 bytes, little-endian, signed4struct '<i'
byteslength as an int at off, payload at off+44 + lenset_int + slice
stringUTF-8 encode, then store like bytes4 + len(utf-8)encode / decode
 
bytes_needed("ada")  =  4 + 3  =  7      → the ada row: 4 (id) + 7 (name) + 4 (gpa) = 15 bytes
bytes_needed(s)      =  4 + len(s.encode('utf-8'))

Encode first, then count. Characters are not bytes:

    'héllo'      h     é       l     l     o
    as bytes     68    C3 A9   6C    6C    6F   ← 'é' takes TWO bytes

    len('héllo')                  = 5 characters
    len('héllo'.encode('utf-8'))  = 6 bytes      ← reserve this many, or you truncate

The Tool column above names a function most people have never used: struct.pack_into. It is worth a minute, because it does not behave the way ordinary functions do. It returns nothing. You hand it a buffer you already have, an offset, and a value, and it writes the bytes into that buffer in place, leaving every other byte exactly as it was. That is precisely what a page needs, because a page is one fixed block of memory that many fields have to share. Try it here before you implement set_int on Thursday.

A 16-byte page, all zeros. Choose an offset and a value, then pack. The warm bytes are the ones the call just wrote; everything else is untouched.

The cursor: seek and tell



Every open file object carries one number. The docs call it the stream position;
everyone else calls it the cursor. It is the byte offset where the next read or
write will happen. It starts at 0 when _file() opens the file, and every
read(n) or write(b) moves it forward by the number of bytes moved. Two
methods let you move it and ask where it is:



f.seek(offset, whence=0)    move the cursor. Returns the new absolute position.
f.tell()                    report the cursor's absolute byte position.



The second argument to seek, called whence, says what
offset is measured from. Python accepts the integer or the named constant from the
os module; they are the same value.




  
whenceNameOffset is measured fromIn this lab

  
    
0os.SEEK_SET (the default)the start of the filef.seek(blknum * block_size) jumps to a block

    
1os.SEEK_CURthe current cursor positionnot needed; every call seeks from the start

    
2os.SEEK_ENDthe end of the filef.seek(0, 2) means "go to the very end"

  





  
Where the cursor is after each call

  
  
Each row is the same file. seek only changes the number; it
  does not touch the disk. A block is moved when you read or write from
  wherever the cursor is.





Put the two together and you get length() for free. f.seek(0, 2)
walks the cursor to the end of the file, so the position f.tell() reports
is the file size in bytes; integer-divide by block_size and you have the
number of whole blocks. os.fstat(f.fileno()).st_size returns the same number without
moving the cursor, and either is fine for this lab.




  Seek before every read and write
  
The cursor is shared by everything that touches the handle. A read leaves it at
  the end of the block it just read, and a length() call leaves it at the end of the
  file. If read(block, page) assumes the cursor is already in the right place, it will
  return the wrong block exactly often enough to be confusing. Compute
  blknum * block_size and seek to it at the top of both
  read and write, every time. That habit is the whole fix for the
  "writing block 1 clobbered block 0" failure in Part 2.

  os.SEEK_SET / SEEK_CUR / SEEK_END ·
  os.fstat





Part 2 · Verify ~20 min in class



The tests come in two groups. The PAGE tests never touch disk. Each one
writes a value into a page and reads it back: ints (including negatives, which is why the spec
says signed), strings with multibyte UTF-8 characters, and the adjacent-values
test, which stores the full ada row and then checks that no field's write spilled into its
neighbor.



The FILE tests go through disk. They check that append and
length agree with each other, that a page written to a block comes back unchanged
when you read it, and that writing block 1 leaves block 0 alone (the classic seek-arithmetic
bug). Reading past the end of the file must raise ValueError. The last test checks
durability: the harness closes your
FileManager, opens a fresh one, and expects the data to still be there. That is the smallest
possible version of surviving a restart.

The honest answer is that nobody's intuition is reliable here, which
      is why the lab makes you measure rather than guess. The instructor's laptop showed about
      15× (465,849 buffered writes/sec against 30,788 durable). Fast SSDs with
      write caches land in the 10 to 20 range; many laptops and most cloud disks show 100 to
      1000×. Yours is right if your tests pass; the number is a property of your hardware, not of
      your code.

      
The Share answer is the one that matters, and it sets up week 7. If durability costs that
      much per write, a database that promises it on every COMMIT cannot
      afford to pay it per page. So it arranges to pay once per transaction instead of
      once per change, and to pay it on a sequential append rather than
      scattered page writes. One small record forced to disk stands in for every page the
      transaction touched. That is the write-ahead log, and your ratio is exactly the number that
      makes it worth building.

Hold on to your ratio: it is the founding constraint of Lab 7.
A database cannot fsync every page it touches and stay usable, yet it promises durability on
every commit. The escape from that trap is called a write-ahead log, and the number you just
wrote down is why it exists.

FAQ



My two runs of measure_io.py differ by 30%. Is something broken?


No, you're timing a real OS with other work to do. Run it three times, report the middle
result, and remember the lab grades the presence and interpretation of your numbers, not their
absolute size.



I'm on macOS and my fsync ratio seems suspiciously small.


Sharp eyes. On macOS, fsync flushes to the drive but doesn't force the drive's
own cache to persist; real engines use F_FULLFSYNC there, which is far slower.
Your measurement is still valid for this lab; mention the caveat in
measurements.txt for a nod of respect. (SQLite and Postgres both special-case
this; databases collect such scars.)



Windows: anything different?


Everything works natively (os.fsync maps to FlushFileBuffers).
Just work in a local folder, not a OneDrive-synced one; sync clients hold file locks at the
worst moments.



Why little-endian? Postgres stores big-endian on the wire!


Either works as long as everyone agrees; we picked the byte order your CPU already uses so
that a hexdump of your file matches what the widget shows. The lesson is that it's a
contract: the tests pin it so week 3's record code can trust week 1's bytes.



Can I keep my own design instead of the given API?


Not for the method signatures: Labs 2–7 starters call these exact names with these exact
semantics. Inside the methods, style is yours.
