Disk & File Manager

microdb begins: blocks, pages, and the actual bytes on disk.
Follows Lecture 1 (Anatomy of a Database) · in class: 75 min · aim to finish Build + Verify · due Thu Sep 3 at class start

Postgres's storage manager (storage/smgr) and SQLite's file format both bottom out in code like the code you write today: open a file, seek to block × block_size, move exactly one block of bytes. No SQL, no tables, no cleverness, just the disk's contract, honored precisely. It is the least glamorous layer of microdb and the one every other layer will stand on for the next seven weeks.

Companion reading: Sciore, Database Design and Implementation, ch. 3 (SimpleDB's file manager) · Python struct docs · for fun afterwards: the real SQLite file format, which is this lab with twenty years of scar tissue.

Why whole blocks

Before writing the code, settle the design question the whole layer is built on.

Think · Pair · Share · the disk's contract
  • Think · 2 minA file is just a long array of bytes, and the ada row is 15 bytes. Yesterday's latency ladder said a storage trip costs the same whether it moves 8 bytes or 8 KB. Given that one fact, design the read API. Should read() fetch a row? A byte range? Something else? Commit to an answer.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare APIs. If you fetch exactly one row per trip, what happens to the query from lecture that needed all six?
  • Share · 2 minAgree on the unit a storage layer should move, then check it against the API below.
Show the answer

read() should fetch a fixed-size block, not a row and not an arbitrary byte range. If the trip costs the same either way, fetching only 15 bytes throws away the rest of the trip you already paid for.

Fetch one row per trip and the six-row query from lecture pays six full storage trips for data that was sitting in one neighbourhood. Fetch the block and it pays one, with the other five rows arriving free. Why fixed size rather than "whatever was asked for": block k always lives at one computable place, [k × block_size, (k+1) × block_size), so addressing is arithmetic instead of bookkeeping, and memory can be managed as interchangeable frames of one size. Every serious engine lands here: 4 KB in microdb, 8 KB in Postgres, up to 64 KB in analytics systems.

Every serious engine lands on the same answer: move fixed-size blocks, and make them generous: 4 KB in microdb, 8 KB in Postgres, up to 64 KB in analytics systems. Since the trip costs the same anyway, fetching the whole neighborhood is free insurance that the next request is already in memory. Fixed size (rather than "exactly what was asked for") is what makes the bookkeeping sane: block k of a file always lives at one computable place, and memory can be managed as identical-sized frames:

byte range of block k   =   [ k × block_size ,  (k+1) × block_size )

so with block_size = 4096:   block 0 → bytes 0…4095
                             block 1 → bytes 4096…8191   ← seek here, read 4096

One caution that will save you a debugging hour: when your Python "writes" a block, the OS usually just copies it into its own page cache and returns instantly. The bytes reach the physical SSD later, unless you demand otherwise with fsync. The gap between those two kinds of "written" is Part 3 of this lab, and in week 7 it becomes the entire design problem of the write-ahead log.

Three classes, one contract

The whole layer is three classes, and two of them fit on an index card. Hover each line, then keep the byte-layout table close while you code, because the tests enforce it literally.

class BlockId: # ('students.tbl', 1), a name, not data
filename: str; blknum: int # provided for you
class Page: # a block-sized bytearray + typed get/set
def get_int(off) -> int / set_int(off, val) # struct '<i'
def get_bytes(off) -> bytes / set_bytes(off, b) # [len][payload]
def get_string(off) -> str / set_string(off, s) # UTF-8, stored like bytes
class FileManager: # db_dir, block_size=4096
def read(block, page) # disk → page
def write(block, page, sync=True) # page → disk (+fsync if sync)
def append(filename) -> BlockId / length(filename) -> int

Where did the string rule come from? Design it yourself before you accept ours.

Think · Pair · Share · store a string
  • Think · 2 minYou must store "ada" at offset 4 of a byte array, so that code which knows only the offset can read it back exactly. The page around it is full of other data. Sketch the bytes you'd write. What goes wrong if you just write the three letters?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare designs: length prefix, terminator byte, or fixed width? What breaks a terminator if the string can contain any byte?
  • Share · 2 minCheck your design against the spec table below; if yours differs, name the tradeoff you made.
Show the answer

Write the length first: a 4-byte int holding the byte count at off, then the payload at off+4. So "ada" at offset 4 is 03 00 00 00 then 61 64 61, occupying bytes 4 through 10.

Just writing the three letters fails because the reader has no idea where to stop: the page is full of other data, and get_string(4) would happily return "ada" followed by whatever bytes came next. A terminator byte fixes that only if the terminator can never appear in the data, which is false for arbitrary bytes and false for UTF-8 in general, and it also makes reading O(length) instead of O(1). Fixed width works but wastes space and imposes a maximum. The length prefix costs 4 bytes, permits any byte in the payload, and tells you the size before you read it, which is why it is the spec the tests enforce.

The contract, in one table. This exact layout is what test_filemanager.py round-trips, and every later lab assumes it:

TypeLayout at offset offBytes usedTool
int4 bytes, little-endian, signed4struct '<i'
byteslength as an int at off, payload at off+44 + lenset_int + slice
stringUTF-8 encode, then store like bytes4 + len(utf-8)encode / decode
 
bytes_needed("ada")  =  4 + 3  =  7      → the ada row: 4 (id) + 7 (name) + 4 (gpa) = 15 bytes
bytes_needed(s)      =  4 + len(s.encode('utf-8'))     # 'héllo' is 6 bytes, not 5: count encoded bytes

Part 1 · Build ~35 min in class

Download the three starter files (buttons under the page widget) into a folder called microdb-lab1/, and work in this order; the tests are arranged so each step turns a new group green.

  1. Read file_manager.py top to bottom first (5 min). The header docstring is the spec; BlockId and the file-handle plumbing are already written. Your work is the twelve TODO-marked methods.
  2. Page.set_int / get_int: two lines each with struct.pack_into("<i", …) / unpack_from. Run python3 test_filemanager.py: the first PAGE test goes green.
  3. set_bytes / get_bytes: write the length with the set_int you just finished, then slice the payload in. Mind the off+4.
  4. set_string / get_string: one line each: UTF-8 encode/decode around the bytes methods. All four PAGE tests should now pass.
  5. FileManager: length, then append, then write, then read, in that order, because each uses the previous. Seek arithmetic is the equation from above; read must raise ValueError past the end of the file.
Gotchas that cost real debugging time

"w+b" truncates an existing file. The starter's _file() helper already creates-without-truncating; use it, don't reopen files yourself. struct.pack returns bytes while pack_into writes in place; you want pack_into. And slicing a bytearray copies: write with self._data[a:b] = payload, not chunk = self._data[a:b]; chunk[:] = payload.

Part 2 · Verify ~20 min in class

Green tests are the deliverable, so know what each one is accusing you of when it fails. The PAGE group runs entirely in memory: round-trips for ints (including negatives: sign bit handling is why the spec says signed), multibyte UTF-8 strings, and the adjacent-values test, which stores the full ada row and catches writes that spill past their field. The FILE group touches disk: append/length bookkeeping, write-then-read round-trips, block independence (writing block 1 must not disturb block 0, the classic seek-arithmetic bug), the past-the-end ValueError, and finally durability: the harness closes your FileManager, opens a fresh one, and expects the data still there, the smallest possible version of surviving a restart.

Exercise · read the failure

A classmate's harness shows adjacent values don't clobber failing: get_int(11) returns 39 correctly, but get_string(4) comes back as "ada\x00\x00\x00\x27"-ish garbage, too long. Which single method has the bug, and what exactly is it doing wrong?

Show answer

set_bytes (or set_string calling it) is writing the payload at off instead of off+4, then writing the length prefix over the first payload bytes, or writing the length as more than 4 bytes. The string's stored length claims more bytes than were written, so get_string reads into the neighboring field. The length prefix and payload have swapped or overlapped territory; re-check who writes at off and who writes at off+4.

Part 3 · Measure ~20 min · finish as homework

Your file manager has a switch you haven't priced yet: write(…, sync=True) ends with fsync, the call that turns "the OS accepted my bytes" into "the bytes are on the SSD". Before you run the benchmark, commit to a prediction.

Think · Pair · Share · the price of a promise
  • Think · 2 minYour SSD and OS can absorb a buffered 4 KB write in a few microseconds. How much slower is a write that must be physically durable before returning: 2×? 10×? 1000×? Write your ratio down.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare predictions, then both run python3 measure_io.py and compare measurements; laptops will differ, sometimes wildly. Whose ratio is bigger, and what hardware difference explains it?
  • Share · 2 minOne sentence for the room: if durability costs this much per write, how must a database that promises durability on every COMMIT arrange its writes?
Show the answer

The honest answer is that nobody's intuition is reliable here, which is why the lab makes you measure rather than guess. The instructor's laptop showed about 15× (465,849 buffered writes/sec against 30,788 durable). Fast SSDs with write caches land in the 10 to 20 range; many laptops and most cloud disks show 100 to 1000×. Yours is right if your tests pass; the number is a property of your hardware, not of your code.

The Share answer is the one that matters, and it sets up week 7. If durability costs that much per write, a database that promises it on every COMMIT cannot afford to pay it per page. So it arranges to pay once per transaction instead of once per change, and to pay it on a sequential append rather than scattered page writes. One small record forced to disk stands in for every page the transaction touched. That is the write-ahead log, and your ratio is exactly the number that makes it worth building.

Run it and record all three numbers in measurements.txt:

$ python3 measure_io.py
buffered writes (sync=False):      465,849 blocks/sec
durable  writes (sync=True):        30,788 blocks/sec
ratio (buffered / durable):           15.1x
What one machine measured

Instructor's Apple-silicon laptop: representative shape, not a target. Fast SSDs with write caches show 10–20×; many laptops and most cloud disks show 100–1000×. Yours is correct if your tests pass.

The gap is the price of honesty: sync=False is "the OS has it (probably)"; sync=True is "it will survive the power cord being pulled right now." (macOS caveat in the FAQ.)

Hold on to your ratio: it is the founding constraint of Lab 7. A database cannot fsync every page it touches and stay usable, yet it promises durability on every commit. The escape from that trap is called a write-ahead log, and the number you just wrote down is why it exists.

FAQ

My two runs of measure_io.py differ by 30%. Is something broken?

No, you're timing a real OS with other work to do. Run it three times, report the middle result, and remember the lab grades the presence and interpretation of your numbers, not their absolute size.

I'm on macOS and my fsync ratio seems suspiciously small.

Sharp eyes. On macOS, fsync flushes to the drive but doesn't force the drive's own cache to persist; real engines use F_FULLFSYNC there, which is far slower. Your measurement is still valid for this lab; mention the caveat in measurements.txt for a nod of respect. (SQLite and Postgres both special-case this; databases collect such scars.)

Windows: anything different?

Everything works natively (os.fsync maps to FlushFileBuffers). Just work in a local folder, not a OneDrive-synced one; sync clients hold file locks at the worst moments.

Why little-endian? Postgres stores big-endian on the wire!

Either works as long as everyone agrees; we picked the byte order your CPU already uses so that a hexdump of your file matches what the widget shows. The lesson is that it's a contract: the tests pin it so week 3's record code can trust week 1's bytes.

Can I keep my own design instead of the given API?

Not for the method signatures: Labs 2–7 starters call these exact names with these exact semantics. Inside the methods, style is yours.
