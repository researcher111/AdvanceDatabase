Google's Playbook: Bigtable, LSM Trees & NoSQL

How to accept a million writes a second on machines that keep dying, and why every piece of the answer is a course topic you already own.
Daniel G. Graham · UVA School of Data Science

In 2006 Google described the store behind web search, Maps, and Gmail: Bigtable1. Read today, the paper is mostly a collection of ideas this course has already covered: a WAL, write-ahead log (week 7), a sorted in-memory buffer flushed to immutable sorted files (your B+ tree's ideas, rearranged), range partitioning (last week), and caching (week 2), all riding on commodity machines that fail constantly. The one genuinely new structure is the LSM tree, the log-structured merge tree (the write-optimized mirror image of your read-optimized B+ tree), and it now sits inside Cassandra, HBase, RocksDB, LevelDB, and the storage engine of half the databases shipped since. No lab Thursday (Thanksgiving); today is the last new-systems lecture, and it closes the storage story.

Companion reading: Chang et al., Bigtable: A Distributed Storage System for Structured Data (OSDI 2006) · O'Neil et al., The Log-Structured Merge-Tree (1996, the idea predates the need2) · RocksDB's architecture overview (the modern production LSM).

Today's claim: the B+ tree and the LSM tree are the two poles of one trade (organize on write (pay before reads) or organize later (pay during reads)), and every storage engine you'll ever meet sits somewhere on that line.

Google's 2004 problem

The insight: writes love sequential, reads love sorted

the tension:   fast writes  want  append-only, sequential I/O     (never seek, never overwrite)
               fast reads   want  sorted, indexed structures      (binary search, range scans)

B+ tree:   sorts on the way IN   → reads cheap, every write is a random page touch
LSM tree:  appends on the way IN → writes cheap, sorting deferred to background merges

Bigtable's bet: for crawl/serving workloads, take the LSM side, and make reads
tolerable with memory, sorted files, and filters.

The Bigtable data model

The paper's own sentence, unpacked: "a sparse, distributed, persistent, multidimensional sorted map." Not a relational table, a map1:

(row_key, column_family:qualifier, timestamp)  →  bytes

row_key    "com.cnn.www"      · URLs reversed so domains sort together (row keys are SORTED)
column     "anchor:cnnsi.com" · families fixed & few (schema); qualifiers open-ended (data!)
timestamp  3 versions kept    · MVCC's trick, week 8: writes make versions, reads pick one

Read the map signature one coordinate at a time. The row key is an arbitrary string, and Bigtable keeps every row of a table sorted by it, so keys that share a prefix (all the pages of one domain, once the URL is reversed) sit next to each other on disk. A column is named in two parts: the column family, such as anchor, is declared up front and there are only a handful per table; the qualifier after the colon, such as cnnsi.com, is free-form and can be created by any write, so a row can have as many columns as it has data. The timestamp is the third coordinate: a write never replaces a cell, it adds a new version, and a read chooses which version it wants (usually the newest). The value is an uninterpreted byte string; Bigtable never looks inside it.

Tablets

Because rows are sorted, the table splits into contiguous key ranges: tablets, ~100–200 MB each. A tablet is last week's range partition plus the machinery that manages it automatically: a master assigns tablets to tablet servers, hot or overgrown tablets split, cold ones merge, and a dead server's tablets are reassigned in seconds1; recovery is routine precisely because the data (in GFS, the Google File System, replicated 3×) never lived on the server's own disk. The tablet server holds only a cache of its tablets and the writes in progress; the durable copy of every byte lives in the file system, so a dead server loses nothing that another server cannot pick up3.

Note the row-key design consequence: keys prefixed by timestamp make the newest tablet the hotspot every write hammers: last week's skew, in range-partition form. Bigtable schema design is mostly key design; reversing the URL so that all pages of one domain sit together in the sorted key space is a performance decision, not a cosmetic one.

Key design is capacity planning: prove it

one sorted key space, four tablets · pick a key design, send writes

Each box is a tablet (a contiguous key range) on its own server. Send a burst of writes under each key design and watch where they land. When one tablet grows hot, split it; then send more writes and see whether splitting actually helped.

Four tablets, four servers, empty. Choose a key design.

The trap, demonstrated: splitting the hot tablet under timestamp keys just crowns a new final tablet; the next burst chases the end of the key space forever, because the keys are monotonic. Splits fix size; only key design fixes direction. This is why Bigtable schemas hash or reverse their key prefixes.

The LSM tree

Inside one tablet server, the write path, the part the whole NoSQL generation inherited:

write(k, v):   1. append to WAL            sequential disk: durability, week 7 verbatim
               2. insert into MEMTABLE     sorted structure in RAM: fast, bounded size

memtable full: flush to an SSTABLE        Sorted String Table: immutable file of sorted (k,v)
                                           + a sparse index: written once, NEVER edited

background:    COMPACTION                  merge-sort several SSTables into one,
                                           dropping shadowed versions and tombstones (week 3!)

Every disk write is sequential: the WAL, the flushes, the merges. Random writes have been abolished, at the price of the same key now living in several places at once: the memtable, maybe three SSTables. That price lands on reads, which is the next section, but first, run the write path yourself in the widget below.

Run the write path

A tablet server's storage engine with a 6-entry memtable. Write keys, watch flushes make SSTables, compact, and then look keys up to see where reads must search.

LSM engine · memtable (cap 6) → L0 SSTables → compaction

Each write goes to the memtable (sorted, in RAM). At 6 entries it flushes to an immutable SSTable. Compact merge-sorts all SSTables into one, dropping old versions of re-written keys. Then look up a key: every structure that must be checked lights up, newest first.

Write ~20 keys without compacting, then look one up: a read may check the memtable plus every SSTable. Compact and repeat: one file, one check. That cycle, tuned by heuristics, is the whole operational life of Cassandra and RocksDB.

The read path

A key can live anywhere from RAM to the oldest SSTable, so get(k) checks newest-to-oldest and returns the first hit. Three tools keep that from being a disaster:

Three read rescues

Bloom filterseach SSTable carries a Bloom filter, a tiny bitmap that answers "definitely absent" or "maybe here." Most SSTables are skipped without touching disk; the filter is wrong (a false "maybe") ~1% of the time, and it is never wrong in the dangerous direction: it never says "absent" for a key that is actually in the file, so no read can miss data by trusting it4.
Sparse indexes + cachesan SSTable keeps every Nth key, with the file offset of the block it starts, in memory as a sparse index. A lookup binary-searches that small index to find the one block that could hold the key, then reads only that block from disk1. Week 2's buffer-pool logic caches the hot blocks so repeat reads never touch disk; week 6's "index = skip most of the data" logic finds the rest.
Compaction itselfcompaction merges many small SSTables into fewer, bigger files whose key ranges do not overlap, so there are fewer places a key can hide. It runs in the background and consumes disk bandwidth that incoming writes could have used; that is the price paid to keep read amplification bounded. How hard to compact, and when, is the engine's central tuning dial.

Build a Bloom filter

The first rescue, small enough to build in a page: 32 bits, 3 hash functions per key. Insert keys, then query keys you never inserted, and keep querying until the filter answers "maybe here" for a key that is not there (a false positive):

Bloom filter · 32 bits, 3 hashes · insert, then try to catch it lying

Insert sets each key's 3 bits (hover a bit for which keys set it). A query checks the same 3 bits: any zero means definitely absent; skip the SSTable, no disk read; all ones means only maybe here.

The filter starts empty: every query answers "definitely absent" for free.

The lie is one-sided by construction: a "maybe" for an absent key (a false positive) costs one wasted disk read; a false "absent" for a present key would lose data, and can never happen, because inserting a key sets exactly the bits its queries check. Real filters size the bitmap so the lie rate stays near 1%.

LSM vs B+ tree

B+ tree (microdb, Postgres, MySQL)LSM (Bigtable, Cassandra, RocksDB)
write pathdescend to the leaf page that owns the key and modify it in place; each write lands on a random page, so it costs a random disk I/Oappend the write to the WAL and insert it into the memtable; every disk write is sequential
read pathone root-to-leaf descent; each key has exactly one home, so one descent always finds itcheck the memtable, then up to K SSTables, newest first; Bloom filters let most SSTables be skipped without a disk read
background costpage splits as leaves fill up, plus an occasional vacuum to reclaim space from dead rowscompaction runs continuously and must be tuned; keeping it healthy is the main operational burden
range scansexcellent: leaf pages are linked, so a scan walks sibling leaves in key ordergood: a scan merges K sorted runs, one per SSTable plus the memtable, in a single pass
wins whenread-heavy, point-lookup OLTPwrite-heavy: ingest, events, time series, crawls

Same bargain, opposite poles: the B+ tree pays the sorting cost on the write so reads are one descent; the LSM defers it to compaction so writes are one append. Neither wins in general; the workload picks. You now own both poles: you built one and just drove the other.

Replication & CAP

CAP

CAP stands for Consistency, Availability, and Partition tolerance. A replicated system keeps copies of the same data on several machines. A partition is a network failure that splits those machines into groups that can no longer reach each other, while each group is still up and still receiving requests. While that lasts, a replica that cannot hear from the others has only two options when a request arrives: answer from what it has, which may be stale, or refuse until it can confirm it holds the latest write. That forced choice, and only that, is what the theorem is about.

During a network partition, a replicated system chooses ONE:

  C  consistency   every read sees the latest write        → some requests must fail/wait
  A  availability  every request gets a (possibly stale)   → replicas diverge; reconcile later
                   answer

No partition, no choice: normal operation can have both. "P" isn't chosen; networks fail.5

  CP lineage:  Bigtable, HBase, Spanner    (refuse rather than lie)
  AP lineage:  Dynamo, Cassandra, Riak6     (answer, then reconcile: eventual consistency)

The descendants

Nearly every NoSQL system of the 2006–2012 wave is an open-source reworking of one or both of two papers, Bigtable and Dynamo. The "no SQL, no joins, no transactions" slogans of that era have faded, but the LSM engine at the core of those systems has lasted:

Where you'll meet this material again

HBaseBigtable, literallythe open-source clone, on Hadoop's HDFS-as-GFS

Spanner is the arc's punchline: after a decade of "no joins, no transactions, no SQL," Google rebuilt all three on top of Bigtable's bones. The relational model wasn't the bottleneck; the 2004 storage engine was. Which is why this course taught you engines, not brand names.

War story · Discord's trillion messages, 202312

Every dial on this slide's engines shows up in Discord's engineering blog, which reads like this lecture's final exam. Their message store (a Cassandra cluster holding trillions of rows) suffered exactly the pathologies you can now name: hot partitions (busy channels are skew), compaction falling behind (the background merging could not keep pace with incoming writes, so reads had ever more SSTables to check), and JVM garbage-collection pauses turning one slow node into cluster-wide latency12. Their 2023 migration to ScyllaDB (same LSM design, no JVM) plus a Rust data layer is a case study in a truth this course keeps landing on: they didn't change the ideas (memtables, SSTables, compaction, tablets) they changed the implementation's constants. The ideas are the part you now own.

Recap & next time

  • Bigtable = course reunion: WAL + sorted-map records + range partitions + caching, run on failure-is-normal hardware; the model is a sorted map, and key design is schema design.
  • The LSM tree abolishes random writes: memtable → immutable SSTables → compaction; reads pay the spread and are rescued by Bloom filters, sparse indexes, and merging.
  • CAP is a forced choice only during partitions: refuse (CP) or serve stale and reconcile (AP); pick per application, not per slogan.

FAQ

Is Postgres/MySQL "obsolete" for big workloads then?

No: B+ tree engines serve the overwhelming majority of production workloads, because most workloads are read-heavy OLTP where one-descent reads and real transactions win. The LSM claims the write-flood niche (events, telemetry, feeds) and the embedded-engine niche (RocksDB). The honest question is never "SQL or NoSQL"; it's "where on the read/write trade does this workload sit, and do I need transactions?"

Where do deletes go if SSTables are immutable?

You write a tombstone: a "k is deleted" record that shadows older versions during reads and merges, until a compaction that can see every copy finally drops both. This is week 3's tombstone flag at a much larger scale: in Cassandra, tombstone pile-ups are a famous operational pathology (delete-heavy workloads make reads wade through graveyards), and "why is my read slow" often means "tombstones13."

Does my phone really run an LSM tree?

Very likely several. LevelDB and RocksDB are embedded in Chrome (IndexedDB), many Android components, and countless apps' local storage14; SQLite (B+ tree) runs alongside them. The two poles of today's table are probably both in your pocket, serving the workloads each is shaped for; the cleanest possible proof that neither "won."

Could microdb grow an LSM engine?

Cleanly: it's the best possible final-project appendix. Keep the WAL, replace RecordPage-in-place with a sorted dict + flush-to-sorted-file, and compaction is heapq.merge over readers. ~200 lines gets write throughput your slotted pages can't touch; then measure the read cost and you'll have reproduced this lecture's table from your own code, which is the course's whole method in one exercise.
