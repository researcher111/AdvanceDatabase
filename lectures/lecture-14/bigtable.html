Bigtable, LSM Trees & NoSQL

The old value is still in a file. How does a later update or delete win?
Daniel G. Graham · UVA School of Data Science

A fictional classroom investigation

Maya keeps a student club’s records in an ordered notebook. When a batch is complete, she copies it onto sealed pages.

She can read those pages, but she cannot edit their entries. New changes go into her current notebook.

One sealed page still says k = old. Here, k is a record’s label, or key. The team has since written a new value and then deleted that key.

Noor asks: If we can’t change this file, what stops that value coming back? Maya reaches for the eraser.

Noor stops her: First show which record a current read must see. We will follow the same key from an old value to a new value and a deletion.

Companion reading: Chang et al., Bigtable: A Distributed Storage System for Structured Data (OSDI 2006) · O'Neil et al., The Log-Structured Merge-Tree (1996, an earlier description of the storage design2) · RocksDB's architecture overview (the modern production LSM).

Starting point and class plan

Starting knowledge: keys and values, B+ tree leaf pages, and the difference between memory and durable storage. Memory holds working data but can lose it during a crash. Durable storage retains data across the failures its protocol promises to survive.

RAM means random-access memory, the working memory in these diagrams. I/O means input/output, such as reading or writing stored data.

Goal: Explain where Bigtable sends a row, how a write survives a crash, and why deleting a key does not immediately erase every older record.

Class plan

Start with Quiz 10, a 10-minute quiz on MapReduce, Spark, and Ray. Then study Bigtable and storage for workloads with many writes.

1 · Organize writes into sorted batches

Open slide 1 ↗

A web crawler collects pages from many sites. Updating all those records can change many different B+ tree leaf pages.

A dirty page is a memory copy changed since its last storage write. The buffer pool holds working copies of storage pages in memory. It can combine updates before writing dirty pages. However, scattered keys can still require writes to many separate storage locations.

A log-structured merge-tree, or LSM tree, organizes updates into batches. It records changes in a log and keeps recent entries sorted in memory. It then writes each completed batch as a sorted file.

A log is an ordered record of changes used for recovery. Sequential output writes a stream of data instead of repeatedly updating scattered locations. A sorted run is a sequence of entries ordered by key.

A flush writes a memory batch to storage. Compaction merges existing sorted files into new sorted files. Later sections explain how each operation preserves reads.

Notebook comparisonStorage mechanism
Current ordered notebookThe memtable holds recent writes in memory, sorted by key.
Sealed pagesA completed sorted file is immutable: later writes do not edit its entries.
Copying several sealed batches into oneCompaction merges records and removes obsolete versions only when safe.

The notebook explains organization. It does not make memory durable or decide which old records are safe to remove. Recovery and version rules supply those guarantees.

The essential tradeoff: batching can reduce scattered writes, but reads may need several files and merging adds storage work.

Writes: sequential output can reduce scattered storage operations.
Reads:  sorted files and indexes help locate a key or scan a range.

B+ tree: update the key’s leaf page; the buffer pool batches dirty-page writes.
LSM tree: buffer updates, flush sorted files, and merge them with compaction.

The LSM design reduces some write costs while adding read and compaction work.

2 · Locate a value with row, column, and time

Open slide 2 ↗

Bigtable distributes an ordered map of records across servers. This lecture explains the original 2006 design and its storage mechanisms. Modern products can add interfaces and guarantees beyond that paper.

A row key names a row. A column names a field within that row. The intersection of one row and column is a cell.

A column family is a declared group of related columns. A qualifier names a column within that family. In anchor:cnnsi.com, anchor is the family and cnnsi.com is the qualifier.

A timestamp identifies one version of a cell. A version is a value saved for that cell at a particular timestamp. The application can interpret these timestamps as page-fetch times, for example.

Bigtable stores each value as bytes. The application decides whether those bytes represent text, an image, or another format.

The paper describes a “sparse, distributed, persistent, multidimensional sorted map.” Its address combines the row, column, and timestamp. A retention policy specifies which versions to keep. The next section explains sparse storage and retention. [1]

(row_key, column_family:qualifier, timestamp) → bytes

row_key    "com.cnn.www"      · reversed domains group related rows in key order
column     "anchor:cnnsi.com" · declared family, dynamic qualifier
timestamp  a cell version    · reads select versions under the retention policy

Rows follow row-key order. A prefix is the beginning of a key. Reversing domain components puts related addresses under a shared prefix, such as com.cnn. A range scan reads keys between chosen bounds in that order.

Predict, then explain

Two values share a row and column but have different timestamps. Did we create another row?

Check your explanation

No. We stored two versions of one cell. A read can request a particular timestamp or the newest retained version.

3 · Store present cells and selected versions

Open slide 3 ↗

Sparse means the system stores present cells without reserving a fixed value slot for every absent cell. Different rows can have different qualifiers within the same declared family.

The diagram starts with three rows and three columns. A later step adds a fourth column. Colored cells contain values. Empty boxes show possible positions, not allocated empty records.

A new qualifier can appear in one row without adding a value to every other row. Column names and other bookkeeping still consume storage.

A retention policy states which cell versions to keep. For example, a family can retain the latest versions or versions younger than a chosen age. Each retained version consumes storage.

Original Bigtable choiceMeaning and limit
Sorted rowsNearby row keys support ordered scans and contiguous row ranges.
Sparse cellsAbsent cells need no fixed value slots. This differs from microdb’s fixed record layout.
Timestamped cell versionsVersions can be selected and retained. Cell timestamps alone do not create a consistent transaction view across rows.
Atomic operations within one rowAtomic means the operation takes effect as a whole. The original design does not supply general transactions across rows.
A nonrelational interfaceThe original interface does not provide SQL joins. Applications must arrange that work separately. [1]

NoSQL is a broad label for systems with data models or interfaces outside the traditional relational model. The label does not specify a storage engine or transaction guarantee.

4 · Assign each row range to a tablet server

Open slide 4 ↗

A tablet is a contiguous range of row keys managed as one unit. A tablet server is a process that serves reads and writes for assigned tablets. One server can serve several tablets.

The system finds the tablet whose boundaries contain the requested row key. It then sends the request to that tablet’s assigned server.

In the diagram’s simplified alphabetic ranges, kim belongs to h–m. A scan from dee through kim needs both a–g and h–m. The original design maintains location information so clients can find the correct server.

A master coordinates tablet assignments. It can assign tablets to another server after failure or when balancing work. The original paper describes tablets of roughly 100–200 MB. [1]

Partitioning divides data into portions. Replication keeps multiple copies of data. A tablet is one portion of the table, not a copy of the whole table.

The original design stores files and recovery logs in the Google File System, or GFS. GFS replicates stored data across machines. Losing a tablet server therefore need not destroy its durable files. [3]

The replacement server opens those files and replays the log: it applies saved changes to rebuild lost memory state. Section 6 explains the required write ordering. Reassignment and recovery still take time.

Predict, then explain

Why does assigning a tablet to a new server differ from making another durable copy?

Check your explanation

Assignment changes who serves the row range. Replication creates another stored copy. Both can help recovery, but they solve different problems.

5 · Explain why a split can leave a hotspot

Open slide 5 ↗

A hotspot is a range that receives much more traffic than other ranges. Row-key design determines which tablet receives each new write.

Keys that begin with increasing timestamps keep moving toward the end of the ordered key space.

The diagram uses numeric intervals. In [75, 100), the left boundary is included and the right boundary is excluded. Key 99 belongs to that interval.

A tablet split divides one range into two adjacent ranges. Splitting the last range reduces its size. However, the next increasing keys still reach the new last range.

These counts are an illustrative workload, not measured Bigtable throughput. The example with distributed user IDs spreads writes by assumption. Actual user IDs can also be uneven.

one sorted key space, four tablets · pick a key design, send writes

Each box is a tablet: a contiguous key range on a server. Each interval includes its left boundary and excludes its right boundary. Send a burst of writes with each key design. Inspect their destinations. Split a heavily used tablet. Send more writes to check whether the split improves distribution.

Four tablets, four servers, empty. Choose a key design.

With increasing timestamp keys, splitting the last tablet creates a new final tablet that receives the next writes. Splitting reduces tablet size but does not spread this write pattern. Distributing prefixes can help balance writes, though it may make range scans contact more tablets.

A hash prefix can spread writes across ranges. Here, a hash is a repeatable function that maps a key to a numeric value. This can make one logical range scan contact more tablets.

Choose keys for both writes and reads. Reversed domains group related pages, but a heavily used domain can still create a hotspot.

6 · Protect a write with a durable log

Open slide 6 ↗

A write-ahead log, or WAL, records changes before later storage actions depend on them. For the durable write shown here, the engine makes the log record durable before reporting success.

Append means add a record at the end of the log. Sync means request the persistence required by the durability protocol. An acknowledgment, abbreviated ack, tells the caller the write succeeded.

Follow k2 = v3. The engine appends its recovery record, makes that record durable, and updates the sorted memtable. It then acknowledges success.

If the server crashes before the memory batch reaches a sorted file, recovery replays the log. The new process can restore k2 = v3.

This is a redo use of a log: recovery reapplies a recorded update. It differs from microdb’s physical undo protocol, which restores earlier values. The lab’s ordering rules cannot be copied unchanged into this design.

Engines can share one persistence operation across several writes. They can also offer weaker durability settings. Our trace assumes the acknowledged write has durable recovery information.

Predict, then explain

The caller received success, but the update never reached a sorted file. What must recovery still be able to read?

Check your explanation

The durable log record. Losing the memtable is recoverable if that record and the required older stored data survive.

7 · Keep recent writes in a sorted memtable

Open slide 7 ↗

The memtable holds recent entries in memory, sorted by key. Arrival order can differ from key order.

The example receives k8, k2, k5, k1, k7. Its ordered structure keeps k1, k2, k5, k7, k8. That order lets a flush write the entries sequentially.

A later k2 write changes its newest value. This simple drawing keeps one current value per key in memory. Production engines can retain older versions for reads that require earlier views.

The notebook analogy applies to key order. A real memtable uses an ordered data structure. Ordinary dictionary insertion order does not automatically sort keys.

8 · Flush a frozen memtable to an SSTable

Open slide 8 ↗

An SSTable, short for Sorted String Table, is an immutable file of sorted key-value entries. It also has an index that helps locate data within the file.

At its size threshold, the engine freezes the current memtable: it stops changing that batch. A flush writes the frozen entries to an SSTable. New writes enter another active memtable.

The frozen batch can remain readable while the file is written. A later update goes into active memory and eventually another file. It does not edit the older SSTable.

The notebook has now become sealed pages. Those pages can coexist with a newer notebook entry for the same key. The next section explains which record a read selects.

9 · Choose the newest visible record

Open slide 9 ↗

Return to k. The toy trace assigns each change an increasing sequence number, which records its order. old@5 means the old value was written at sequence 5.

A snapshot is a retained view used by a read. In this toy model, snapshot 8 admits records numbered 8 or earlier. A record is visible when the chosen view permits the read to use it.

A tombstone is a deletion marker stored as a newer record. DELETE@9 means the key is absent from sequence 9 onward, until another update.

Keep two kinds of time separate. These update numbers explain a generic LSM version rule. Bigtable’s application cell timestamps do not automatically provide a transactionally consistent snapshot across rows.

Snapshot 8old@5, new@8new@8new
Snapshot 9old@5, new@8, DELETE@9DELETE@9Absent

The animation first adds the three records. It then previews a partial compaction: a merge that includes only some files. The final merge includes all older records and assumes no retained snapshot needs them.

A read must resolve versions across relevant structures. The original Bigtable paper describes a merged view of the memtable and SSTables. File location alone does not determine which version wins. [1]

Our simpler latest-value widget searches memory and files from newest to oldest. That shortcut depends on its version ordering. General engines use their file organization, timestamps, and visibility rules.

Predict, then explain

Snapshot 8 remains active after DELETE@9 arrives. Can the engine erase new@8 immediately?

Check your explanation

No. Snapshot 8 must still return new. The engine must preserve the information needed for that earlier view.

10 · Merge sorted files without changing answers

Open slide 10 ↗

Compaction merges sorted files and writes new sorted output. It can reduce the number of files a read checks and reclaim obsolete versions.

A merge cursor marks the next unread entry in each input. Compare those entries, output the next key, and advance the corresponding cursor.

At duplicate k2, this current-value example keeps k2:v2 instead of k2:v1. Its output keys are k1, k2, k4, k7, k8.

Actual compaction must also retain versions needed by active snapshots. It must retain tombstones while older values could reappear. Sequential merging still reads and rewrites stored bytes.

11 · Keep a deletion marker until removal is safe

Open slide 11 ↗

Deleting an in-memory entry does not remove an older value from an immutable file. A later lookup could otherwise find that older value and incorrectly return it.

The engine writes a newer tombstone. A current read that selects the tombstone returns absent. It must not continue looking for an older value to return.

Trace a delete through older sorted files

SSTable A holds old@5. B holds new@8. C holds the flushed DELETE@9. A partial compaction merges B and C while A remains outside that merge.

If the output drops the tombstone, a later read can find A’s old value. Therefore, the merged output must keep DELETE@9.

The walkthrough starts earlier, with DELETE@9 still in memory. It then flushes that record to C before the partial merge.

Worked result: At snapshot 9, DELETE@9 is the newest visible record. The read returns absent despite older values at 8 and 5. A partial compaction must retain the tombstone while an older value could reappear.

Enable JavaScript to step through the code and intermediate state.

Safe removal requires checking every older value that could reappear and every retained read view. In replicated systems, repair and retention rules can add further constraints.

Predict, then explain

A complete merge includes A, B, and C, but snapshot 8 is still active. Is removing every record for k safe?

Check your explanation

No. Including every file prevents an outside value from reappearing, but snapshot 8 still needs new@8. Both conditions matter.

12 · Use a Bloom filter to rule out files

Open slide 12 ↗

A missing key can force a read to check several files. A Bloom filter is a compact membership test that can rule out a file before reading its entries.

A bit stores either 0 or 1. Our filter has 32 bits and 3 hash functions. Each function chooses a bit position from the key.

Insertion sets the key’s chosen bits to 1. A query checks those same positions. Any zero proves absence, because insertion would have set that bit.

All ones mean possibly present. Other keys can set those same bits. A false positive occurs when an absent key passes this test.

The diagram inserts k1 through k6. Query k7 has a required zero and can skip the file. Query k17 finds all required bits set, but the key is absent.

Bloom filter · 32 bits, 3 hashes · look for a false positive

An insertion sets 3 bits for each key. Hover over a bit to see which keys set it. A query checks the same 3 bits. Any zero means definitely absent, so the engine can skip the SSTable. Three ones mean only maybe here.

The filter starts empty, so every key is definitely absent without reading an SSTable.

If an absent key’s three bits are all set by other keys, the filter returns “possibly present.” The engine may then read a file unnecessarily. An inserted key cannot produce “definitely absent,” because inserting it set the same bits that its query checks. Real systems size filters for a chosen false-positive rate.

A correctly maintained Bloom filter has no false negatives: it does not report an inserted key as absent. A false positive costs another check, not a lost result. [4]

Do not clear shared bits to delete one key from an ordinary Bloom filter. Another inserted key can depend on those bits. Filter size and hash count affect the false-positive rate.

Predict, then explain

The filter says possibly present. Can the read return a value without checking the stored entries?

Check your explanation

No. The filter stores membership evidence, not the value or its visibility. The engine must inspect the candidate data.

13 · Find a block and reuse its cached copy

Open slide 13 ↗

A block is a chunk of file data read as a unit. A sparse index records selected boundary keys and the blocks where their ranges begin.

For the diagram’s query k9, the index entries are k1 → 0, k8 → 1, and k16 → 2. Under the example’s numeric key order, k9 falls between k8 and k16. The engine searches block 1.

A block cache keeps recently read blocks in memory. If a needed block is cached, the engine can inspect that copy without another storage read.

MechanismQuestion answeredWork avoided
Bloom filterCan this file contain the key?Checking a file that is definitely absent
Sparse indexWhich block could contain it?Scanning unrelated blocks
Block cacheIs that block already in memory?Reading the same block from storage again
CompactionCan files be merged safely?Some future file and version checks

The filter can skip a file. Otherwise, the engine locates a candidate block and uses a cached copy when available. It still checks actual entries and applies the version rule.

Illustrations use numeric order for labels such as k8 and k16. Real Bigtable row keys use byte-string order. Applications can pad numeric components when they need numeric order to match key order.

14 · Compare the full storage workload

Open slide 14 ↗

Read amplification is extra work needed to answer a logical read, such as searching several files for one key. Write amplification is stored data written or rewritten relative to the application’s writes. Space amplification is extra storage beyond the live data, including retained obsolete versions.

Compaction can reduce read and space costs by doing more write work. If incoming writes outpace compaction, extra files and pending maintenance can accumulate.

OperationB+ tree organizationLSM organization
WriteChange the page for the key. The buffer pool can batch dirty-page writes.Log and buffer changes. Flush sorted files and merge them later.
Point lookupFollow the index to a leaf. Depending on the layout, fetching the row can need another access.Resolve the key across relevant memory structures and files. Filters and indexes can reduce file accesses.
Range scanRead leaf pages in key order.Merge relevant sorted runs and resolve duplicate versions.
MaintenanceSplit pages, write dirty pages, and perform the engine’s required cleanup.Read and rewrite files during compaction. Preserve required versions and deletions.

Both designs maintain sorted data and can support transactions. B+ tree engines appear in systems such as microdb, PostgreSQL, and MySQL. Bigtable, Cassandra, and RocksDB use related LSM techniques.

Choose using the full workload. Compare read response time, writes completed per second, memory, storage space, and maintenance under the required durability settings. Neither design is faster for every workload.

Predict, then explain

A test times only log appends and ends before any compaction. Does it establish sustained LSM write performance?

Check your explanation

No. Sustained performance also requires flush and compaction to keep up. Include their costs and the required read workload.

15 · Explain the choice during a network failure

Open slide 15 ↗

A replica is another copy of data. A network partition is a communication failure that prevents some machines from exchanging messages. This differs from a data partition, which divides records into portions.

Imagine Maya and Noor each keep a copy of the club’s record. Both copies show v1. Maya records v2 and confirms the write, but Noor’s copy cannot receive it.

A caller then asks Noor for the current value. Noor cannot infer v2 from silence. This copy analogy explains missing information, not a particular replication protocol.

Linearizability requires operations to behave like one current copy while respecting completed operations. In this example, a read begun after the completed v2 write cannot correctly return the earlier v1.

CAP names consistency, availability, and network partitions. CAP availability requires every request to a nonfailed node to eventually receive a non-error response. Waiting indefinitely or rejecting that read sacrifices this guarantee.

During a partition, a system cannot guarantee both linearizability and availability for all requests. Some systems continue on one side while another side rejects requests. [5]

During a network partition, both guarantees cannot hold for all requests:

  Consistency (linearizability): operations behave as if there were one current copy.
  Availability: every request to a nonfailed node eventually gets a non-error response.

Preserving the first can require delaying or rejecting some requests.
Preserving the second can allow replicas to disagree until communication recovers.

Bigtable, HBase, Spanner: examples that prioritize strong consistency.
Dynamo, Cassandra, Riak: designs that support availability-oriented choices.
Exact guarantees depend on the operation and configuration.56

The product names above summarize design directions, not every modern configuration. In original Bigtable, atomicity concerns operations within a row. Choose a guarantee for the operation before applying a system label.

Reconciliation brings copies into agreement after communication returns, using the system’s conflict rules. Eventual consistency allows temporary disagreement but promises convergence if updates stop and communication and reconciliation continue.

Predict, then explain

Noor returns v1 immediately after the completed v2 write. Which guarantee fails in this trace?

Check your explanation

Linearizability fails because the read misses an earlier completed write. Returning an answer promptly does not establish that the answer reflects the current value.

16 · Return to the deleted key

Open slide 16 ↗

Return to k. Old bytes can remain in files, but a current read must use the newest visible record. A deletion marker is a record that wins that comparison.

The log protects acknowledged updates. The memtable orders recent entries. A flush creates sorted files, and compaction merges them while preserving required reads.

Predict, then explain

SSTable A still holds old@5. A compaction merges only B’s new@8 and C’s DELETE@9. Can it simply drop both records?

Check your explanation

No. Removing the tombstone could expose A’s old value in a later current read. Retain the marker while that value can reappear. Also preserve versions that required snapshots need.

Predict, then explain

Now all files are included and no retained snapshot needs k. What two checks make removing its tombstone safe in this toy trace?

Check your explanation

No older value remains outside the merge to reappear, and no retained read view needs the removed records. Deletion alone was not enough.

  • Bigtable assigns ordered row ranges to tablet servers. Key design determines where writes go and which ranges a scan needs.
  • LSM storage reduces some write costs through batching. Reads and compaction must still resolve all relevant versions correctly.
  • Filters, indexes, and caches avoid different kinds of read work. They do not replace the version rule.
  • During network failure, another durable copy may still lack the latest completed update. Replication needs explicit read and write guarantees.

Related storage systems

This comparison extends the main lecture. An embedded engine is a library used inside an application process. A managed service runs the database infrastructure for its users.

Bigtable emphasizes ordered data and its placement across servers. The original Dynamo paper emphasizes replication and availability. Later systems combine these ideas in different ways. [6]

SystemConnection to this lecture
HBaseA Bigtable-inspired store with column families. It uses Hadoop’s distributed file system, HDFS, for stored files. Apache HBase overview.
CassandraCombines related sorted storage with Dynamo-inspired replication. Configurable consistency controls how many replicas must participate in an operation. [7]
DynamoDBA managed key-value and document service. It has a different design from the original Dynamo paper. [8]
RocksDB / LevelDBEmbedded key-value engines using related LSM techniques. [9] RocksDB supplies storage for systems such as Kafka Streams and Flink.
PebbleCockroachDB’s related LSM engine, introduced as its default in version 20.2 in fall 2020. [10]
SpannerA later Google system with replicated data and transactions across distributed data. Its TrueTime interface reports clock uncertainty. [11]

Spanner shows that distributed storage can coexist with a relational interface and transactions. A query language, storage layout, and transaction model are related choices. One choice does not uniquely determine the others.

Case study · Discord’s trillion messages, 2023

Discord’s 2023 engineering report describes hot partitions and costly maintenance in its Cassandra message store. Automatic memory cleanup, or garbage collection, also caused pauses.

The team moved to ScyllaDB in May 2022. It also introduced Rust data services to control database traffic.

Both stores use LSM techniques, but their implementations and supporting services differ. Workload distribution and resource management also affect response time. [12]

FAQ

Is Postgres/MySQL "obsolete" for big workloads then?

No. B+ tree engines support large workloads and distributed systems. LSM engines can help with sustained writes, but add compaction and read costs. Compare required queries, transaction guarantees, and measured workloads. SQL and NoSQL labels alone do not determine the appropriate engine.

Where do deletes go if SSTables are immutable?

A delete writes a tombstone: a record that marks the key as deleted and hides older values. Compaction must retain it while removing it could expose an older value elsewhere. It must also preserve required snapshot results. Accumulated tombstones can increase read costs, especially with frequent deletes.13

Does my phone really run an LSM tree?

Embedded applications use both designs. Chromium’s IndexedDB has used LevelDB, an LSM engine, while SQLite uses B-tree storage. This illustrates how an application can choose different storage engines for different local data needs.14

Could microdb grow an LSM engine?

Yes, as an optional extension. Retain the logging layer. Replace updates to existing record pages with a sorted memtable and immutable files. Add a merge operation for compaction. Implement version and deletion handling. Compare write throughput and read cost with the existing engine.

Any improvement depends on the workload and implementation.
