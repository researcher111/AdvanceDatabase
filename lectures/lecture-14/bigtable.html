Bigtable, LSM Trees & NoSQL

What problem does Bigtable solve?
Daniel G. Graham · UVA School of Data Science

A web crawler saves CNN’s home page in the morning. By afternoon the headline has changed. How can the crawler save the new copy and still find the morning one?

One server can do this for one page. A crawl of many sites can exceed one server’s storage capacity or its ability to keep up with updates. Bigtable divides the work among servers while the crawler continues to read and update one table. [1]

Companion reading: Chang et al., Bigtable: A Distributed Storage System for Structured Data (OSDI 2006) · O'Neil et al., The Log-Structured Merge-Tree (1996, an earlier description of the storage design2) · RocksDB's architecture overview (the modern production LSM).

Learning goals

By the end of this lecture, you will be able to:

  • explain how Bigtable distributes a growing table across servers and why the choice of row keys can concentrate writes.
  • judge whether Bigtable’s NoSQL data model fits an application that needs key lookups, range scans, joins, or transactions across rows.
  • explain how Bigtable batches writes in a log-structured merge-tree (LSM tree) and recovers confirmed writes from a durable log.
  • predict what current reads and older snapshots should return as an LSM tree merges files containing updates and deletions.
  • compare the read, write, and maintenance costs of LSM trees and B+ trees for a given workload.
  • explain why guaranteeing the latest value can force a distributed database to delay reads when replicas lose contact.

2 · Locate a value with row, column, and time

Open slide 2 ↗

In the Bigtable paper’s Webtable example, the designers chose one row per web page. A reader looking up CNN wants its HTML and the words other sites use to link to it. When the crawler finds a link to CNN on another site, which page’s row should receive the link text?

The link lives on cnnsi.com, but it points to CNN. The crawler uses that destination to choose CNN’s row and the source site to name the column. A reader can now look up com.cnn.www once to get both the HTML and the incoming link text. Bigtable paper, Figure 1.

To find the link text, start in row com.cnn.www and choose column anchor:cnnsi.com. That intersection is one cell. The application declares the column families contents and anchor in advance. The qualifier identifies a column within its family. It is empty in contents:.

What if the source changes its link text? The crawler can write the new words to the same cell with a later timestamp. In the paper, timestamp t9 selects the version containing the three letters CNN.

Try the same addressing rule in Python with a different link. This example uses anchor:example for the source and 1 for the timestamp. The tuple is the address. The byte string b"example link text" is the value stored there.

cells = {}
row = "com.cnn.www"
column = "anchor:example"
timestamp = 1  # One illustrative version

address = (row, column, timestamp)
cells[address] = b"example link text"
value = cells[address]

Reading the same tuple returns b"example link text". Bigtable stores values as bytes, so the crawler can use the same addressing scheme for the contents of a page or an image.

(row_key, column_family:qualifier, timestamp) → bytes

row_key    "com.cnn.www"      · reversed domains group related rows in key order
column     "anchor:cnnsi.com" · declared family, dynamic qualifier
timestamp  a cell version    · reads select versions under the retention policy

3 · Store present cells and selected versions

Open slide 3 ↗

Now a school links to one of the pages in the crawl. Only that page needs a value in anchor:school. Should every other row reserve space for the school’s link text?

Use three short page keys, r1, r2, and r3, to see what grows. The example starts with five cells across three rows and three columns. The school links to r2. Look for the fourth column in that row as you step through the example.

cells = {
    ("r1", "anchor:example", 1): b"link",
    ("r1", "contents:", 1): b"page",
    ("r2", "anchor:news", 1): b"news",
    ("r3", "anchor:example", 1): b"link",
    ("r3", "contents:", 1): b"page",
}

cells[("r2", "anchor:school", 1)] = b"old"
cells[("r2", "anchor:school", 2)] = b"prior"
cells[("r2", "anchor:school", 3)] = b"new"

Only r2 gains the new column. This is sparse storage. Bigtable stores the cells that have values and their names, without reserving a value slot for each missing cell.

The last three writes share a row and a column. Their timestamps differ, so they create three versions of that cell. Keeping all three costs space. A retention policy lets the application specify how many recent versions a family keeps or how old they may be.

Original Bigtable choiceMeaning and limit
Sorted rowsNearby row keys support ordered scans and contiguous row ranges.
Sparse cellsAbsent cells need no fixed value slots. This differs from microdb’s fixed record layout.
Timestamped cell versionsVersions can be selected and retained. Cell timestamps alone do not create a consistent transaction view across rows.
Atomic operations within one rowAtomic means the operation takes effect as a whole. The original design does not supply general transactions across rows.
A nonrelational interfaceThe original interface leaves joins to the application. NoSQL is a broad name for systems with nonrelational interfaces or data models. Each system has its own storage design and transaction guarantees. [1]

The 2006 paper calls Bigtable a “sparse, distributed, persistent, multidimensional sorted map.” Consider the word distributed. If the CNN row moves to a different server, how will the crawler find it? [1]

4 · Assign each row range to a tablet server

Open slide 4 ↗

Return to the CNN row. Reversing the hostname also gives news.cnn.com the key com.cnn.news. Both CNN keys begin with com.cnn.. This shared beginning is a prefix. A range scan can read all the rows with that prefix by walking consecutive keys in order.

Bigtable manages each consecutive range of keys as a unit called a tablet. A tablet server handles reads and writes for its assigned tablets. One server can serve several tablets. Adding servers or replacing a failed one can change the assignment while the row keys stay the same.

The crawler’s Bigtable client keeps a local cache of tablet locations. It first checks for an entry whose range contains com.cnn.www. If the entry is missing or stale, the client looks up the current assignment in Bigtable’s location metadata. The client then sends the request directly to the assigned tablet server. [1]

The next example uses shorter keys. The labels a–g and h–m describe the first two alphabetic ranges. The second range starts at h and stops before n, so kim belongs to [h, n). A scan from dee through kim crosses both ranges.

Teaching Python: bisect_right counts the sorted boundaries no greater than the requested row key. For kim, it returns tablet number 1. The servers list maps that number to its serving process:

from bisect import bisect_right

bounds = ["h", "n", "t"]
row = "kim"
tablet = bisect_right(bounds, row)
servers = ["S0", "S1", "S2", "S3"]

server = servers[tablet]

The result is server == "S1". After S1 fails, the toy directory can name S2 as the replacement:

servers[1] = "S2"
server = servers[tablet]  # "S2"

The same key now leads to S2. In the 2006 design, a coordinator called the master assigns the tablet to its replacement. The original paper describes tablets of roughly 100–200 MB. Before S2 can serve the range, it must open the stored data and recover recent changes. [1]

Dividing the rows into tablets is partitioning. Preserving the data when a server fails requires another mechanism. The original Bigtable stores its files in the Google File System (GFS), which keeps copies across machines. Keeping those copies is replication. The replacement can open the surviving files and use saved changes to rebuild what the failed server held in memory. Recovery takes time. [3]

Predict, then explain

Why does assigning a tablet to a new server differ from making another durable copy?

Check your explanation

Assignment changes who serves the row range. Replication creates another stored copy. Both can help recovery, but they solve different problems.

5 · Explain why a split can leave a hotspot

Open slide 5 ↗

Separate servers can share the work only if requests reach different ranges. Try changing the first part of the row key. Suppose each new row begins with the time of its visit. Later writes go to the end of the sorted table. That last range becomes a hotspot when it receives much more traffic than the others.

Can splitting the busiest tablet spread the next writes? Use numbers for the ordered keys so you can see the boundary move. The final range, [75, 100), contains 75 through 99. A tablet split divides it at 88. Predict which of the two new ranges receives key 99.

Teaching Python: reuse bisect_right from the preceding section with numeric boundaries. Key 99 reaches the final tablet before and after the split:

before = bisect_right([25, 50, 75], 99)      # Tablet 3
after = bisect_right([25, 50, 75, 88], 99)  # Tablet 4

These counts are an illustrative workload, not measured Bigtable throughput. The example with distributed user IDs spreads writes by assumption. Actual user IDs can also be uneven.

one sorted key space, four tablets · pick a key design, send writes

Each box is a tablet: a contiguous key range on a server. Each interval includes its left boundary and excludes its right boundary. Send a burst of writes with each key design. Inspect their destinations. Split a heavily used tablet. Send more writes to check whether the split improves distribution.

Four tablets, four servers, empty. Choose a key design.

With increasing timestamp keys, splitting the last tablet creates a new final tablet that receives the next writes. Splitting reduces tablet size but does not spread this write pattern. Distributing prefixes can help balance writes, though it may make range scans contact more tablets.

A hash prefix can spread writes across ranges. Here, a hash is a repeatable function that maps a key to a numeric value. This can make one logical range scan contact more tablets.

Choose keys for both writes and reads. Reversed domains group related pages, but a heavily used domain can still create a hotspot.

6 · Protect a write with a durable log

Open slide 6 ↗

Follow just one write that reached Server 1. The crawler sends the morning CNN update. Suppose the server changes a copy in memory, replies “saved,” and then crashes. What surviving record could the replacement use to keep that promise?

Before replying, the server appends a record of the change to a write-ahead log (WAL). Appending puts the record at the end of the log. The server waits until the record is durable, meaning it can survive the failure covered by the storage protocol. Recovery can then replay the change even if the in-memory copy disappears.

The slide uses k2 = v3 as a short example write. Follow it through the engine pseudocode below. The call to sync_log() waits for durability. Only after that wait and the memory update does the engine send its acknowledgment, the success reply.

record = ("k2", "v3")

append_log(record)
sync_log()  # Wait for required durability.

memtable.put("k2", "v3")
reply_success()

Here memtable.put updates the working copy in memory. The function names describe storage operations the engine must implement. A Python list append or a buffered file write alone cannot make the log durable.

If the server crashes after the reply, the replacement can restore k2 = v3 by applying the logged update again. This is redo. In microdb’s earlier undo exercise, recovery used a saved value to restore the state before a change.

One sync can make several writes durable together. Engines also offer weaker durability settings. The example assumes the caller requested durable writes.

The caller received success, but the update never reached a sorted file. What must recovery still be able to read?

Check your explanation

The durable log record. Losing the memtable is recoverable if that record and the required older stored data survive.

7 · Keep recent writes in a sorted memtable

Open slide 7 ↗

The log protects the morning CNN update. Server 1 still has to store that update alongside changes to other sites. Recall how a B+ tree would handle com.cnn.www. The engine finds the leaf for that key in its buffer pool, where it keeps working copies of database pages. After the update, the leaf is a dirty page until the engine writes it back.

If a second update changes that leaf before the write, one write saves both changes. Now suppose a hundred updates land on a hundred different leaves. The server may have to write a hundred pages scattered across storage. Could it collect those updates and write them together?

Bigtable uses a log-structured merge-tree (LSM tree) to batch the updates. As each logged write arrives, the server places it in a memtable. This structure keeps entries sorted by key in random-access memory (RAM).

Try a fresh batch with five short keys. They arrive as k8, k2, k5, k1, k7. In what order could the server copy them out?

Teaching Python: the integers below represent the suffixes of k8, k2, and the other short labels. The keys list records their order. The values dictionary holds each key’s current value:

from bisect import insort
keys = []
values = {}

for key in [8, 2, 5, 1, 7]:
    insort(keys, key)
    values[key] = "v1"

values[2] = "v2"
rows = [(key, values[key]) for key in keys]

insort inserts each arriving key at its sorted position. The five initial keys are distinct. Updating values[2] changes the value without inserting that key again.

The final expression pairs each ordered key with its current value. This list model explains ordering, not production memtable performance. Real Bigtable row keys use byte-string order.

The server can now copy k1, k2, k5, k7, k8 in one pass. The example keeps just the current value for each key. A production engine can also retain older versions for readers that need them. Once this batch fills, where can the next write go?

8 · Flush a frozen memtable to an SSTable

Open slide 8 ↗

The morning batch reaches its size limit just as more updates arrive. To write a stable copy, Server 1 freezes that memtable. Readers can still use its entries. New writes go into a fresh memtable.

The server flushes the frozen batch by writing its entries sequentially to a new file. The entries already form a sorted run because the memtable kept them in key order. The resulting Sorted String Table (SSTable) includes an index to locate data inside it. The file is immutable, so its entries stay as written.

In this engine pseudocode, follow the two batches. Which one can accept an afternoon update while the server is still writing the morning file?

frozen = active
active = new_memtable()

# Background flush of the frozen batch:
file = write_sstable(frozen.entries())
make_durable(file)
publish(file)
retire_when_no_readers(frozen)

write_sstable writes ordered entries. make_durable establishes the required storage guarantee. publish installs the file where readers can find it. These helpers stand for storage and coordination work, not Python library calls.

Retire the frozen batch only after readers no longer need it. New writes follow the WAL protocol and can proceed while the background flush runs. This fragment does not discard the recovery log.

That afternoon, the crawler finds a new headline on CNN’s home page. The row key is still com.cnn.www. Follow the two copies of the page through the next flush.

9 · Choose the newest visible record

Open slide 9 ↗

File A holds the morning copy of CNN’s home page. File B holds the afternoon copy. Both entries have the same row key, which we shorten to k. Which copy should a reader get?

Give the two writes sequence numbers to record their order. File A holds old@5, the morning copy. File B holds new@8, the afternoon copy. After both writes, a current read chooses sequence 8 and returns new.

Suppose a reader kept a snapshot at sequence 5. That reader can see changes through 5, so it still gets old. A record is visible to a read when its sequence falls within the read’s boundary.

At sequence 9, the crawler deletes its saved copy of the page. The server writes DELETE@9, a deletion marker called a tombstone. Predict what a current read returns now. Would a reader holding snapshot 8 get the same answer?

Read viewVisible records for kNewest visible recordResult
Snapshot 5old@5old@5old
Snapshot 8old@5, new@8new@8new
Snapshot 9old@5, new@8, DELETE@9DELETE@9Absent

At 9, the newest visible record is the tombstone, so the read reports the key absent. At 8, the tombstone is still outside the reader’s view. These sequence numbers model update order inside an LSM engine. Bigtable’s application cell timestamps label cell versions and do not themselves establish a consistent snapshot across rows.

Teaching Python: each tuple contains a sequence number and a value for one key. DELETE is a distinct marker object. The result None means absent in this model:

DELETE = object()  # A distinct marker.
records = [(5, "old"), (8, "new"), (9, DELETE)]

def read_at(records, snapshot):
    visible = [(seq, value) for seq, value
               in records if seq <= snapshot]
    if not visible:
        return None
    seq, value = max(visible, key=lambda r: r[0])
    return None if value is DELETE else value

The filtering expression keeps records allowed by the snapshot. A lambda is a short function. Here, it selects tuple position 0, the sequence number, so max chooses the newest visible record.

The is comparison checks whether the selected value is the exact deletion marker. Once that marker wins, the function returns absence. It does not search for an older value.

read_at(records, 5)  # "old"
read_at(records, 8)  # "new"
read_at(records, 9)  # None: absent

The same rule works while the deletion is still in memory. The server considers relevant entries in the memtable and sorted files together. The original Bigtable paper describes this merged read view. [1]

Check your explanation

The first reader sees new@8 and gets the afternoon copy. The current reader sees DELETE@9 and gets no page.

10 · Merge sorted files without changing answers

Open slide 10 ↗

The crawler keeps visiting sites. Every flush adds a file, so a lookup for one page may need to check several files. The server can reduce that work by merging selected files into new sorted output. This operation is compaction.

Start with two sorted files in a separate example. File A contains k1, k2, k7. File B contains k2, k4, k8. Readers here need only current values, and these files contain no deletions. Those assumptions let us work out the merge one key at a time.

A merge cursor marks the next unread entry in each file. A starts at k1 and B starts at k2, so the server copies k1 and advances A. Now both cursors point to k2. Which version belongs in the output?

Teaching Python: each input triple contains an integer key suffix, a version number, and a value. These separate inputs match the diagram:

# Each entry is (key, version, value).
a = [(1, 1, "v1"), (2, 1, "v1"),
     (7, 1, "v1")]
b = [(2, 2, "v2"), (4, 1, "v1"),
     (8, 1, "v1")]

heapq.merge reads already sorted inputs in key order. It advances the input cursor that supplies the next entry. groupby gathers consecutive entries with the same key:

from heapq import merge
from itertools import groupby

def compact_current(a, b):
    merged = merge(a, b, key=lambda r: r[0])
    groups = groupby(merged, key=lambda r: r[0])
    return [max(group, key=lambda r: r[1])
            for key, group in groups]

output = compact_current(a, b)

The first two lambda expressions select the key at position 0. For the two k2 entries, the last lambda compares the versions at position 1. The merge keeps B’s k2:v2. Both cursors move past that key.

The output contains keys 1, 2, 4, 7, 8 in order. This function assumes no deletions and no retained snapshots. It is not a general compaction algorithm.

A lookup can now find k2:v2 in one output file. To produce that file, the server read both inputs and wrote their surviving entries again. With retained snapshots, more than one version of a key may have to survive.

The label L0 means level 0, the initial group of sorted files in LevelDB-style storage. [9] This is modern LSM terminology. The original Bigtable paper uses minor, merging, and major compaction for its flush and merge operations. [1]

LSM engine · memtable (cap 6) → L0 SSTables → compaction

Each write enters the sorted memtable in RAM. At 6 distinct keys, the widget flushes the memtable to an immutable SSTable. Compact merges all displayed SSTables into one and keeps the newest value of each key. A lookup highlights the structures it checks, starting with the newest data. The widget searches memory and files in newest-first order, which works with its simplified version ordering. Its merge covers all displayed files. Real compactions often cover only some files. 11 · Keep a deletion marker until removal is safe

Open slide 11 ↗

Return to CNN’s page. File A holds old@5, and file B holds new@8. A flush moves DELETE@9 from memory into file C. A current read still finds the marker and reports the page absent.

Trace a delete through older sorted files

The server merges just B and C. Suppose it discards both the afternoon copy and the deletion marker. Which entry can a new reader still find?

File A still holds the morning copy. Without the marker, a current read would return that copy after the crawler had deleted the page. Keeping DELETE@9 in the output hides the older entry. The shared trace starts with the marker in memory and follows it through the partial merge.

12 · Use a Bloom filter to rule out files

Open slide 12 ↗

The server now knows which records must survive a merge. A lookup still has to find them among the remaining files. Some files contain only other sites. How can the server skip those files before reading their entries?

When writing a file, the server can build a small summary of its keys called a Bloom filter. Try a separate toy file with six keys, k1 through k6. Its filter has 32 bits, initially all zero. Each of 3 hash functions maps an inserted key to a bit position. Inserting the key sets those positions to 1.

To look up k7, the server checks the same three positions that inserting k7 would set. One bit is zero, so the file cannot contain k7. For k17, all three bits are 1. Could another key have set each of those bits?

Teaching Python: these fixed functions reproduce the diagram’s bit positions. ord converts an ASCII character to its numeric code. enumerate supplies the character’s position. The remainder operation % 32 keeps each result between 0 and 31:

def hashes(key):
    a = b = c = 0
    for i, ch in enumerate(key):
        n = ord(ch)
        a = (31 * a + n) % 32
        b = (17 * b + 7 * n) % 32
        c = (13 * c + (i + 3) * n) % 32
    return [a, b, c]

bits = [0] * 32

Reuse hashes below. The set stored represents the keys actually in this toy file. range(1, 7) produces 1 through 6. Insertion sets every selected bit:

stored = {f"k{i}" for i in range(1, 7)}
bits = [0] * 32
for key in stored:
    for position in hashes(key):
        bits[position] = 1

def might_contain(key):
    return all(bits[p] for p in hashes(key))

possible = might_contain("k17")
present = "k17" in stored

all returns true only when every required bit is set. For k7, positions 12, 30, 9 include a zero, so might_contain("k7") returns false.

For k17, positions 17, 21, 16 are all set by the six stored keys. The filter reports possibly present, yet a check of the actual entries finds no k17. This is a false positive. In the code, possible is true and present is false.

Use the controls below to insert k1 through k6. Compare the highlighted positions for k7 and k17.

Bloom filter · 32 bits, 3 hashes · look for a false positive

An insertion sets 3 bits for each key. Hover over a bit to see which keys set it. A query checks the same 3 bits. Any zero means definitely absent, so the engine can skip the SSTable. Three ones mean only maybe here.

The filter starts empty, so every key is definitely absent without reading an SSTable.

If an absent key’s three bits are all set by other keys, the filter returns “possibly present.” The engine may then read a file unnecessarily. An inserted key cannot produce “definitely absent,” because inserting it set the same bits that its query checks. Real systems size filters for a chosen false-positive rate.

A correctly maintained Bloom filter has no false negatives: it does not report an inserted key as absent. A false positive costs another check, not a lost result. [4]

Do not clear shared bits to delete one key from an ordinary Bloom filter. Another inserted key can depend on those bits. Filter size and hash count affect the false-positive rate.

Predict, then explain

Check your explanation

No. The filter stores membership evidence, not the value or its visibility. The engine must inspect the candidate data.

13 · Find a block and reuse its cached copy

Open slide 13 ↗

A Bloom filter can leave the server with a file to search. Take a different file that contains k9. The server reads file data in units called blocks. Which block should it open for k9?

A sparse index lists the first key in each block. Here the entries are k1 → 0, k8 → 1, and k16 → 2. The example compares numeric suffixes. Since 9 falls between 8 and 16, only block 1 can contain k9.

The first request loads block 1 and finds k9. The server keeps the block in memory in a block cache. A second request for the same block can reuse its contents.

Teaching Python: integers represent the diagram’s numeric key suffixes. bisect_right finds the position after index boundaries no greater than the query. Subtracting one selects the preceding block start:

from bisect import bisect_right
first_keys = [1, 8, 16]
key = 9
block_id = bisect_right(first_keys, key) - 1

disk = {1: {8: "v8", 9: "v9", 12: "v12"}}
cache = {}
def read_block(block_id):
    if block_id not in cache:
        cache[block_id] = disk[block_id]
    return cache[block_id]

For key 9, block_id is 1. The disk dictionary stands in for stored blocks. It holds the one block this example needs and performs no storage input/output (I/O).

Continue with the same index, cache, and read_block function:

block = read_block(block_id)
value = block.get(key)
again = read_block(block_id)

The first call loads block 1 into the toy cache. block.get(key) checks its entries and returns "v9". The second call reuses the cached block.

This query lies within the index’s covered range. A general lookup must also handle keys below the first boundary. The model omits cache eviction and version resolution inside blocks.

The filter can skip a file. Otherwise, the engine locates a candidate block and uses a cached copy when available. It still checks actual entries and applies the version rule.

Illustrations use numeric order for labels such as k8 and k16. Real Bigtable row keys use byte-string order. Applications can pad numeric components when they need numeric order to match key order.

14 · Compare the full storage workload

Open slide 14 ↗

Give two engines the same job. Both must save the crawler’s updates, serve lookups for individual pages, and scan rows for one domain. Both must meet the same durability requirement. What storage work does each engine perform for those requests?

In a B+ tree, updates to the same leaf can share a write from the buffer pool. Updates to many different leaves can leave the server with many scattered dirty pages. An LSM engine collects updates in key order and writes each batch sequentially. A later read may have to check several files to find the current page.

That extra work per lookup is read amplification. Compaction reduces the number of candidate files, but it reads and rewrites entries that the crawler already saved. Write amplification compares the bytes the engine writes with the bytes the application writes. Retaining obsolete versions also uses space beyond the live data, contributing to space amplification. If merges fall behind, the number of files can keep growing.

OperationB+ tree organizationLSM organization
WriteChange the page for the key. The buffer pool can batch dirty-page writes.Log and buffer changes. Flush sorted files and merge them later.
Point lookupFollow the index to a leaf. Depending on the layout, fetching the row can need another access.Resolve the key across relevant memory structures and files. Filters and indexes can reduce file accesses.
Range scanRead leaf pages in key order.Merge relevant sorted runs and resolve duplicate versions.
MaintenanceSplit pages, write dirty pages, and perform the engine’s required cleanup.Read and rewrite files during compaction. Preserve required versions and deletions.

Both designs maintain sorted data and can support transactions. B+ tree engines appear in systems such as microdb, PostgreSQL, and MySQL. Bigtable, Cassandra, and RocksDB use related LSM techniques.

Run the same mix of updates, lookups, and domain scans on both engines. Measure read response time, sustained writes per second, memory use, storage space, and maintenance work. Include the merges that the LSM engine needs to keep up with the crawler.

15 · Explain the choice during a network failure

Open slide 15 ↗

So far, the server answering a read could see the relevant writes. Consider a separate model where two servers hold the same row. Each copy is a replica. What can a reader learn when the two copies lose contact?

Both replicas start with v1, the morning headline. A network partition cuts communication between the servers. Replica 1 accepts the afternoon headline, v2, and confirms the write. A reader then asks replica 2 for the current headline. Replica 2 still has v1. Can it tell from its local data whether the afternoon write happened?

If replica 2 returns v1, the reader misses a write that already completed. That answer breaks linearizability, the guarantee that operations behave like one current copy and respect completed operations.

Replica 2 could wait for the missing update. If the partition lasts indefinitely, the read may never finish. The CAP theorem relates consistency, availability, and partition tolerance. Its availability guarantee requires every request to a nonfailed node to eventually receive a non-error response. Rejecting the read also gives up that guarantee.

During a partition, a system cannot guarantee both linearizability and availability for all requests. Some systems continue on one side while another side rejects requests. [5]

During a network partition, both guarantees cannot hold for all requests:

  Consistency (linearizability): operations behave as if there were one current copy.
  Availability: every request to a nonfailed node eventually gets a non-error response.

Preserving the first can require delaying or rejecting some requests.
Preserving the second can allow replicas to disagree until communication recovers.

Bigtable, HBase, Spanner: examples that prioritize strong consistency.
Dynamo, Cassandra, Riak: designs that support availability-oriented choices.
Exact guarantees depend on the operation and configuration.56

The product names above summarize design directions, not every modern configuration. In original Bigtable, atomicity concerns operations within a row. Choose a guarantee for the operation before applying a system label.

Reconciliation brings copies into agreement after communication returns, using the system’s conflict rules. Eventual consistency allows temporary disagreement but promises convergence if updates stop and communication and reconciliation continue.

Check your explanation

Linearizability fails because the read misses the completed write. A cache hit saves a local storage read. Only communication can bring replica 2 the missing update.

FAQ

Is Postgres/MySQL "obsolete" for big workloads then?

No. B+ tree engines support large workloads and distributed systems. LSM engines can help with sustained writes, but add compaction and read costs. Compare required queries, transaction guarantees, and measured workloads. SQL and NoSQL labels alone do not determine the appropriate engine.

Where do deletes go if SSTables are immutable?

A delete writes a tombstone: a record that marks the key as deleted and hides older values. Compaction must retain it while removing it could expose an older value elsewhere. It must also preserve required snapshot results. Accumulated tombstones can increase read costs, especially with frequent deletes.13

Does my phone really run an LSM tree?

Embedded applications use both designs. Chromium’s IndexedDB has used LevelDB, an LSM engine, while SQLite uses B-tree storage. This illustrates how an application can choose different storage engines for different local data needs.14

Could microdb grow an LSM engine?

Yes, as an optional extension. Retain the logging layer. Replace updates to existing record pages with a sorted memtable and immutable files. Add a merge operation for compaction. Implement version and deletion handling. Compare write throughput and read cost with the existing engine.

Any improvement depends on the workload and implementation.
