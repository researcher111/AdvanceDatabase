Bigtable, LSM Trees & NoSQL

How do distributed storage engines handle a sustained stream of writes, and what extra work does that create for reads and background maintenance?
Daniel G. Graham · UVA School of Data Science

Bigtable was built for large, write-heavy datasets spread across many machines. Its 2006 paper combines ideas you already know: logging, caching, sorted data, and range partitioning. Today we connect those ideas through the LSM design: collect writes in memory, flush sorted files, and merge them in the background. Then we examine the cost this shifts to reads. There is no lab on Thanksgiving; graph databases follow next week. Read the original Bigtable paper.

Companion reading: Chang et al., Bigtable: A Distributed Storage System for Structured Data (OSDI 2006) · O'Neil et al., The Log-Structured Merge-Tree (1996, an earlier description of the storage design2) · RocksDB's architecture overview (the modern production LSM).

Today's plan

Quiz 11 first (MapReduce, Spark & Ray, 10 min), then the write-optimized half of the storage world.

A large crawler generates a steady stream of writes across a growing key space. B+ tree buffering can combine updates, but scattered dirty pages still create pressure on storage. LSM engines organize the write path around sequential output and background merging. The question is how much read and compaction work that choice adds.

Today’s main idea: B+ trees and LSM trees organize updates differently. B+ trees update pages in place; LSM trees buffer updates and merge sorted files. Each choice changes the work required for writes, reads, and maintenance.

B+ tree writes can become a storage bottleneck

Scattered leaf updates can make B+ tree writes expensive. Buffering, batching, key order, and storage hardware determine the actual disk I/O.

Sequential output can reduce scattered writes

Writes: sequential output can reduce scattered storage operations.
Reads:  sorted files and indexes help locate a key or scan a range.

B+ tree: update the key’s leaf page; the buffer pool batches dirty-page writes.
LSM tree: buffer updates, flush sorted files, and merge them with compaction.

The LSM design reduces some write costs while adding read and compaction work.

Bigtable stores a sparse, sorted map

The Bigtable paper describes a “sparse, distributed, persistent, multidimensional sorted map.” A value is addressed by three coordinates: row key, column name, and timestamp:1

(row_key, column_family:qualifier, timestamp) → bytes

row_key    "com.cnn.www"      · reversed domains group related rows in key order
column     "anchor:cnnsi.com" · declared family, dynamic qualifier
timestamp  a cell version    · reads select versions under the retention policy

The row key is a string, and rows are sorted by that key. Related prefixes, such as reversed domain names, keep related rows together. A column name contains a declared family and a free-form qualifier, such as anchor:cnnsi.com; only populated cells need storage. The timestamp identifies a version of that cell. Reads can select versions, usually starting with the newest. Each value is a byte string whose interpretation belongs to the application.

Tablets divide the sorted key space

The unitA tablet holds a contiguous range of row keys. The original paper describes tablets of roughly 100–200 MB. Tablets let the system assign different ranges to different servers.
The machineryA master assigns tablets to tablet servers. Tablets split as they grow, and their assignments can change to balance load or recover from a server failure.1
Why recovery worksThe original design stores durable files and commit logs in GFS, the replicated Google File System. If a tablet server fails, another server can open those files and replay the log to restore committed writes that had not yet reached an SSTable.3
Key designMonotonically increasing timestamp prefixes direct new writes toward the end of the key space, potentially overloading the final tablet. Choose keys with both write distribution and required scans in mind. Reversed domain names, for example, group pages from the same domain.

See how row keys distribute writes

one sorted key space, four tablets · pick a key design, send writes

Each box is a tablet (a contiguous key range) on its own server. Send a burst of writes under each key design and watch where they land. When one tablet grows hot, split it; then send more writes and see whether splitting actually helped.

Four tablets, four servers, empty. Choose a key design.

With increasing timestamp keys, splitting the last tablet creates a new final tablet that receives the next writes. Splitting reduces tablet size but does not spread this write pattern. Distributing prefixes can help balance writes, though it may make range scans contact more tablets.

The LSM write path buffers and flushes updates

Inside a tablet server, writes pass through a log and an in-memory structure before becoming sorted files:

write(k, v):   1. append a log record       recovery information
               2. update the memtable      sorted state in memory

memtable full: flush an SSTable            immutable sorted entries and an index

background:    compact selected SSTables   merge entries; remove obsolete versions
                                          and tombstones only when safe

The WAL, SSTable flushes, and compaction outputs favor sequential I/O. This reduces scattered in-place writes, but a key can appear in several runs at once. Reads must find the newest visible version, and compaction must keep the number of runs manageable.

Run the write path

A tablet server's storage engine with a 6-entry memtable. Write keys, watch flushes make SSTables, compact, and then look keys up to see where reads must search.

LSM engine · memtable (cap 6) → L0 SSTables → compaction

Each write enters the sorted memtable in RAM. At 6 entries, the widget flushes it to an immutable SSTable. Compact merges all displayed SSTables into one and keeps the newest value of each key. A lookup highlights the structures it checks, starting with the newest data. The widget omits WAL persistence so it can focus on flushes and compaction.

Write about 20 keys without compacting, then run a lookup. It may check the memtable and several SSTables. Compact and repeat to see how merging reduces the number of files searched. Real engines schedule partial compactions and use indexes and filters to avoid unnecessary reads.

Use filters, indexes, and compaction to reduce reads

A key may have versions in memory and in several SSTables. A lookup must find the newest visible value or deletion marker. This simplified engine checks newest to oldest; filters, indexes, and compaction reduce the work:

Three ways to avoid unnecessary file reads

Bloom filtersAn SSTable’s Bloom filter answers “definitely absent” or “possibly present.” An absent result lets the engine skip the file. A possible match still needs checking because the filter can have false positives. Filter size and hash count control the false-positive rate; correctly maintained filters have no false negatives.4
Sparse indexes + cachesAn SSTable index stores selected keys and block offsets. Searching that smaller index identifies which block may contain the key. A block cache can then satisfy frequently repeated reads without accessing storage.1
Compaction itselfCompaction merges sorted files and removes obsolete entries when safe. This reduces the number of files or versions a lookup must check. The exact overlap rules depend on the compaction strategy. Merging also consumes CPU and storage bandwidth, so more aggressive compaction has a cost.

Build a Bloom filter

This small example uses 32 bits, 3 hash functions per key. Insert keys, then query keys you never inserted, and keep querying until the filter answers "maybe here" for a key that is not there (a false positive):

Bloom filter · 32 bits, 3 hashes · look for a false positive

Insert sets each key's 3 bits (hover a bit for which keys set it). A query checks the same 3 bits: any zero means definitely absent; skip the SSTable, no disk read; all ones means only maybe here.

The filter starts empty, so every key is definitely absent without reading an SSTable.

If an absent key’s three bits are all set by other keys, the filter returns “possibly present.” The engine may then read a file unnecessarily. An inserted key cannot produce “definitely absent,” because inserting it set the same bits that its query checks. Real systems size filters for a chosen false-positive rate.

Compare B+ tree and LSM costs

Different update paths, different costs: B+ trees update the page containing a key. LSM trees collect updates in memory, write sorted files, and merge them later.

B+ tree (microdb, Postgres, MySQL)LSM (Bigtable, Cassandra, RocksDB)
write pathdescend to the leaf page that owns the key and modify it in place; updates may touch scattered pages; the buffer pool batches dirty-page writesappend the write to the WAL and insert it into the memtable; WAL, flush, and compaction output favor sequential I/O
read pathan index lookup descends from root to leaf; fetching the row may require another access, depending on the storage layoutcheck the memtable, then up to K SSTables, newest first; Bloom filters let most SSTables be skipped without a disk read
background costpage splits and dirty-page flushing; engines may also need version cleanup or space reclamationbackground compaction rewrites data and must keep pace with the workload
range scansexcellent: leaf pages are linked, so a scan walks sibling leaves in key ordergood: a scan merges K sorted runs, one per SSTable plus the memtable, in a single pass
often useful forread-heavy, point-lookup OLTPwrite-heavy: ingest, events, time series, crawls

Both designs maintain sorted data. A B+ tree updates pages as writes arrive; an LSM tree combines buffered writes into sorted files and later merges those files. Neither is faster for every workload. Compare read latency, write throughput, memory use, and maintenance cost for the operations you need.

During a network partition, consistency and availability conflict

When replicas cannot communicate, they cannot always agree on the latest value. To preserve a single up-to-date view, the system may have to delay or reject some requests. Serving every request instead can allow different replicas to return different results.

CAP

CAP refers to consistency, availability, and network partitions. Here, consistency means linearizability: operations behave as if there were one current copy. Availability means every request to a nonfailed node eventually receives a non-error response. During a partition, some nodes cannot exchange messages. The theorem says that a system cannot guarantee both properties for all requests while that partition persists.

During a network partition, both guarantees cannot hold for all requests:

  Consistency (linearizability): operations behave as if there were one current copy.
  Availability: every request to a nonfailed node eventually gets a non-error response.

Preserving the first can require delaying or rejecting some requests.
Preserving the second can allow replicas to disagree until communication recovers.

Bigtable, HBase, Spanner: examples that prioritize strong consistency.
Dynamo, Cassandra, Riak: designs that support availability-oriented choices.
Exact guarantees depend on the operation and configuration.56

Related storage systems

Bigtable and Dynamo influenced several distributed storage systems, but their designs address different concerns. Bigtable emphasizes a sorted data model and storage layout; Dynamo emphasizes availability and replication. Later systems combine and extend these ideas:

Spanner shows that distributed scale can coexist with a relational interface and transactions. Its design adds replication, transaction coordination, and a clock-uncertainty API. The storage layout, query language, and transaction model are related design choices, but one does not uniquely determine the others.

Case study · Discord's trillion messages, 202312

Discord’s 2023 engineering report describes hot partitions, expensive maintenance, and garbage-collection pauses in its Cassandra message store. The team moved the store to ScyllaDB in May 2022 and introduced Rust data services to control database traffic. Both stores use LSM techniques, but their implementations and surrounding services differ. The case shows why identifying an engine’s data structures is only the start: workload distribution and resource management also determine latency.12

Recap & next time

  • Bigtable combines logging, sorted records, range partitioning, and caching across servers. Row-key design affects which records are stored together and where writes go.
  • An LSM engine buffers writes, flushes immutable SSTables, and compacts them. Filters, sparse indexes, and caching help reads avoid unnecessary file access.
  • During a network partition, a system cannot guarantee both linearizable results and a non-error response to every request at every nonfailed node. Choose behavior that fits the application’s requirements.

FAQ

Is Postgres/MySQL "obsolete" for big workloads then?

No. B+ tree engines support large workloads, and distributed systems can use them too. LSM engines are often useful for sustained writes, but also incur compaction and read costs. Compare the required queries, transaction guarantees, and measured workload rather than choosing from the SQL or NoSQL label alone.

Where do deletes go if SSTables are immutable?

A delete writes a tombstone, a record that marks the key as deleted and hides older values. Compaction may remove it only when doing so cannot expose an older value that still exists elsewhere or is needed by a snapshot. Accumulated tombstones can make reads more expensive, especially in delete-heavy workloads.13

Does my phone really run an LSM tree?

Embedded applications use both designs. Chromium’s IndexedDB has used LevelDB, an LSM engine, while SQLite uses B-tree storage. This illustrates how an application can choose different storage engines for different local data needs.14

Could microdb grow an LSM engine?

Yes, as an optional extension. Keep the logging layer and replace in-place record updates with a sorted memtable and immutable files. Use a merge operation to compact the files, then add version and deletion handling. Compare write throughput and read cost with the existing engine; an improvement depends on the workload and implementation.
