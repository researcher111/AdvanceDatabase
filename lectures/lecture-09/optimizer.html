The Query Optimizer

For the example join, your Lab 5 planner examines 900 pairs. In Lab 4, you found a plan that examines 60. How can an optimizer choose between them before execution?
Daniel G. Graham · UVA School of Data Science

Your Lab 5 planner builds the join plan that examines 900 pairs. In Lab 4, you rearranged that plan to examine just 60 pairs and return the same answer. Today we will see how an optimizer searches for such improvements automatically. It uses statistics about the data, a cost model to estimate work, and a search through equivalent plans. We will use EXPLAIN ANALYZE output to compare estimates with measurements. Lab 7 is due today, and the final third of class reviews material for Thursday’s midterm.

An optimizer chooses a plan using cost estimates. It has limited planning time and incomplete information about the data. Comparing its estimates with actual execution helps explain both good and poor plan choices.

Follow the operator tree and check row-count estimates

Read from the input scans toward the operators that consume their rows. At each step, compare estimated row counts with measured counts. A large discrepancy can explain why the optimizer chose an inefficient join order or algorithm, though it is not the only possible cause of a slow query.2

Row-count estimates drive cost estimates

Selectivity is the fraction of a table's rows that a predicate keeps: if gpa > 35 keeps 60 of 300 rows, its selectivity is 0.2. The optimizer needs this number before it runs anything, because every cost formula in the next section starts from how many rows each step will produce. It cannot know the number exactly, so it estimates it from a few facts it stores per table and per column. Those facts, and the formulas that turn them into an estimate, are what this section is about.

Basic selectivity formulas and their assumptions

Per table: N rows and B blocks. Per column: the number of distinct values V, the min and max, and a histogram3. The following introductory estimates use ideas from System R; production planners refine them with more detailed statistics4:

\[ \text{sel}(f = c) = \frac{1}{V(f)} \qquad \text{sel}(f_1 = f_2) = \frac{1}{\max\bigl(V(f_1), V(f_2)\bigr)} \qquad \text{sel}(f > c) = \frac{\max(f) - c}{\max(f) - \min(f)} \]

The last one assumes values are spread uniformly between the min and the max. Clamp the estimate to [0, 1], handle a constant-valued column separately, and treat this as a continuous approximation for integer data. Equality estimates also assume the queried value exists; join estimates assume compatible value domains. Then

\[ \text{survivors}(\sigma) \;=\; N \cdot \text{sel} \]

and for ANDed terms the selectivities are multiplied together, which assumes they are independent5.

Two simplifying assumptions: uniformity and independence

These simple formulas assume uniform value frequencies or distributions and, when combining predicates, independence. Real data often violates those assumptions. A range estimate based only on min and max misses clusters of values. Multiplying the selectivities of city = 'Charlottesville' and state = 'VA' underestimates matches when every Charlottesville row in the dataset is already a Virginia row. Histograms and statistics across multiple columns can improve these estimates.3

Estimate a plan’s block accesses before execution

Table scans and index scans provide different access paths to rows. A cost model estimates each candidate plan’s work from its operators and estimated row counts. Our teaching model counts block accesses, extending the measurements from Lab 4. Production models also account for CPU work, caching, and differences between sequential and random I/O.

Five simplified formulas for block-access cost

\[ \begin{aligned} \text{cost}(\text{TableScan}) &= B(\text{table}) \\ \text{cost}(\text{IndexSelect}_{=}) &= \text{height} + \text{matching RIDs} \\ \text{cost}(\text{NestedLoopJoin}) &= B(L) + N(L) \cdot B(R) \\ \text{cost}(\text{HashJoin}) &= B(L) + B(R) \\ \text{cost}(\text{MergeJoin}) &= \text{sort costs} + B(L) + B(R) \end{aligned} \]

These are simplified I/O estimates: hash join assumes the build side fits in memory; repeated heap visits may hit cached pages; spilling, output size, and CPU work add cost. The table scan is week 1's lesson formalized and the index select is week 6's. The nested loop's N(L) · B(R) accounts for rereading the right input for each left row4; the hash join reads each side once, plus memory for the hash table. Pick the plan with the smallest total, computed from statistics, before running anything.

These formulas estimate the block accesses that you measured with CountingScan in Lab 4. They let the optimizer compare candidate plans before executing the query.2

In this cost model, the crossover is about 1% selectivity

Table scancosts B blocks no matter how many rows match: the whole table is read either way.
Index lookupcosts about one block read per matching row, so it gets more expensive as more rows match.
The crossoverthe cheaper of these two plans changes with selectivity. Drag the slider and watch the optimizer's choice flip.
index scan vs sequential scan · 100,000 rows, 1,000 blocks, tree height 3

The slider sets the predicate's selectivity (fraction of rows kept). Costs come from the formulas above: seq scan always pays B = 1,000 blocks; the index pays height + one block touch per matching RID. The cheaper plan is the one the optimizer picks.

For this table and cost model, the two plans cost about the same near 1% selectivity. Below that point the index avoids enough heap accesses to be cheaper; above it the sequential scan wins. Real crossover points also depend on caching, row clustering, index coverage, and I/O costs, so the threshold is not universal.

Choose both the join algorithm and the join order

A join plan must choose an algorithm for matching rows and an order for combining tables. These choices interact: an early filter or a smaller intermediate result can change which algorithm is cheapest for the next join.

Ten tables can be joined 17 billion ways

Counting table permutations and binary-tree arrangements, 10 tables have about 17 billion possible join plans before algorithm choices. Dynamic programming reduces repeated work by retaining useful plans for small table subsets and using them to build larger plans. The search still grows rapidly, so planners also use restrictions and heuristics. PostgreSQL can switch to genetic search when the query has enough joins; its default threshold is 12 tables.89

17 billion distinct shapes for a 10-table join: the search that System R's dynamic programming makes feasible

Updated statistics can change the selected plan

A data load or statistics refresh can change estimated row counts and make a different plan look cheaper. When performance changes, compare the old and new EXPLAIN output and check whether table statistics are current. Join order is one possible change; scan types and join algorithms can change too.2

FAQ

Will microdb get an optimizer in a later lab?

No: Act II begins after the midterm, and microdb stays at its seven layers. The Going-Further path exists (Lab 6 wired an index into the planner; add statistics to the catalog and a cost comparison between candidate plans, and you have a small version of the System R optimizer). You could include such an extension in a final-project appendix if it supports your project’s goals.

Why do plans change when I add LIMIT 10?

The optimizer prices first rows differently from all rows: a plan that streams cheap early rows (nested loop via an index) can beat one with a big setup cost (hash join) when only 10 are wanted. Cost models track both startup and total cost for exactly this reason2.

Is the exam cumulative with the quizzes? Same style?

The midterm uses multiple-choice questions like the quizzes and covers the lecture concepts, lab discussion prompts, measurements, and FAQs from the first part of the course. Bring a pencil; scratch paper is provided and not collected.

Which examples should I prioritize for review?

The measured outputs. Every one of the eight numbers in the review table has a mechanism behind it, and mechanisms are what get asked. Second place: the force/steal grid and the WAL ordering; practice explaining why those writes must occur in that order.
