The Query Optimizer

Statistics, selectivity, and the machine that finds the fast plan you proved exists, plus the midterm map.
Daniel G. Graham · UVA School of Data Science

Your Lab 5 planner is correct, but the plan it builds is the naive one, the same 900 pairs you counted in Lab 4. In Lab 4 you also found, by hand, a plan that did 15× less work (60 pairs instead of 900); the Lab 5 planner has no way to find that plan. Today: the machine that finds it automatically. An optimizer needs three things: knowledge about the data (statistics), a way to price plans without running them (a cost model), and a search over the space of equivalent shapes. None of it is magic, all of it can guess wrong, and reading its output (EXPLAIN) is the single most useful practical skill this course confers. Today's claim: an optimizer is a guesser with a budget. It never runs a plan to learn what it costs; it predicts the cost from a few stored numbers, and it has only a moment to search among the candidate plans. Respect it for guessing well, and know how to catch it guessing badly.

Read a real plan

The skill to leave with: decoding EXPLAIN ANALYZE. EXPLAIN asks the engine to print the plan it chose, with its cost and row-count estimates, instead of the query's results; adding ANALYZE also runs the query and prints the measured row counts and times next to each estimate. Here's a real Postgres plan for our join, annotated; hover every line.

EXPLAIN ANALYZE SELECT name, dept FROM students JOIN majors ON mid = mid2 WHERE gpa > 35;
Hash Join (cost=1.07..8.72 rows=20 width=13) (actual time=0.04..0.11 rows=20 loops=1)
Hash Cond: (students.mid = majors.mid2)
-> Seq Scan on students (cost=0.00..6.75 rows=60 ...) (actual ... rows=60 ...)
Filter: (gpa > 35) Rows Removed by Filter: 2402
-> Hash (cost=1.03..1.03 rows=3 ...) -> Seq Scan on majors (rows=3)
Planning Time: 0.28 ms Execution Time: 0.15 ms2
Hover a line: estimated-vs-actual is the diagnostic; inside-out is the reading order.

The two habits: read inside-out, and compare estimated rows to actual rows; where they diverge, the optimizer was working from wrong information about the data, and the plan it built from that information is usually where your query went wrong2.

Statistics & selectivity

What the engine keeps, and the formulas it runs

Selectivity is the fraction of a table's rows that a predicate keeps: if gpa > 35 keeps 60 of 300 rows, its selectivity is 0.2. The optimizer needs this number before it runs anything, because every cost formula in the next section starts from how many rows each step will produce. It cannot know the number exactly, so it estimates it from a few facts it stores per table and per column. Those facts, and the formulas that turn them into an estimate, are what this section is about.

per table:   N rows, B blocks          per column:  distinct values V, min/max, histogram3

selectivity guesses (System R's, still everywhere):4
  field = literal      1 / V(field)
  field = field (join) 1 / max(V(left), V(right))
  field > literal      (max − literal) / (max − min)     ← uniformity assumed

survivors(σ) = N × selectivity       , chain them for ANDed terms (independence assumed!)5

Two simplifying assumptions power every formula above, and both are usually false, which is why this lecture calls them the two famous lies. Uniformity: a column's values are spread evenly between its min and max, so a range predicate keeps a share of rows equal to the share of the range it covers. Independence: two predicates do not correlate, so the fraction of rows surviving both is the product of the two fractions. When plans go bad at 3am, one of these lies is usually why: city = 'Charlottesville' AND state = 'VA' is not two independent filters, because every Charlottesville row is already a Virginia row3.

Check yourself · be the planner for one minute

students: N = 300, gpa min 20 / max 39, V(mid) = 3. Using only the formulas above, estimate the survivors of gpa > 30 AND mid = 2, and then say which of the two famous lies each step of your estimate leaned on.

Show answer

gpa > 30: (39 − 30)/(39 − 20) ≈ 0.47 → ~142 rows (leaning on uniformity; gpas might really cluster near 30). mid = 2: 1/V = 1/3. Chained: 300 × 0.47 × 0.33 ≈ 47 rows (leaning on independence; but what if the mid-2 department grades harder?). Every EXPLAIN's rows= guess is exactly this arithmetic; when it's far from actual rows, you now know which lie to suspect.

Costing a plan

The cost model prices a plan without running it: it repeats your Lab 4 counting experiment hypothetically, over plan shapes it never executes, using statistics in place of the real row counts. The unit of cost is the one this course has used since week 1, the block read:

Blocks, again, always blocks

cost(TableScan)          = B(table)                      ← week 1's lesson, formalized
cost(IndexSelect, eq)    = height + matching RIDs        ← week 6
cost(NestedLoopJoin)     = B(left) + N(left) × B(right)  ← the multiplier that hurts4
cost(HashJoin)           = B(left) + B(right)            ← read each side once (+ memory)
cost(MergeJoin)          = sort costs + B(left) + B(right)

pick the plan with the smallest TOTAL, computed from statistics, before running anything.

Same currency since Lecture 1: count block touches2. The optimizer is your Lab 4 CountingScan experiment, run hypothetically over every candidate shape.

Watch the plan flip

The first two formulas above, the table scan and the index lookup, disagree about which is cheaper, and the answer depends entirely on selectivity. The table scan costs B blocks no matter how many rows match; the index costs about one block read per matching row, so it gets more expensive as more rows match. Drag the slider and watch the optimizer's choice flip:

index scan vs sequential scan · 100,000 rows, 1,000 blocks, tree height 3

The slider sets the predicate's selectivity (fraction of rows kept). Costs come from the formulas above: seq scan always pays B = 1,000 blocks; the index pays height + one block touch per matching RID. The cheaper plan is the one the optimizer picks.

The crossover sits near 1% on this table, far lower than most people's instinct. "I added an index, why isn't it used?" is usually this chart: the optimizer did the same arithmetic and the index lost. Below the crossover, where few rows match, the index wins by orders of magnitude; above it, where many rows match, every match costs its own block read, and the plain scan, which reads each block exactly once, is cheaper.

Join order & join algorithms

Two independent choices per join (which algorithm pairs the rows, and which order the tables meet in), and the second one explodes combinatorially. Both were foreshadowed weeks ago:

The algorithms, finally named

AlgorithmIdeaShines whenYou've basically built it
Nested loopfor each row of the left table, read through the right table looking for rows that match itthe right side is tiny, or has an index on the join column, so each pass over it is cheap6Lab 4's ProductScan
Hash joinread the smaller table once and put every row into an in-memory hash table keyed by its join column; then read the bigger table once and, for each row, look up its join value in that hash table6the join condition is an equality, and the smaller side fits in memory7Lab 4's Going-Further CachingScan plus a Python dict keyed on the join column
Merge joinsort both tables on the join column, then walk the two sorted streams together, advancing whichever side is behind, so each row is read onceboth inputs are already sorted on the join column, which a B+ tree index gives for free by walking its chained leaves6Lab 6's chained leaves are a sorted stream

Order matters exponentially

The number of ways to order a join grows faster than exponentially with the number of tables: 10 tables can be joined in roughly 17 billion distinct shapes. System R's dynamic programming avoids trying them all: it finds the cheapest way to join each small group of tables once, then builds larger groups only from those cheapest pieces, which keeps the search feasible8; modern planners add heuristics and genetic search above ~12 tables9 (all descendants of System R's access-path selection). This is the reason your dashboards sometimes "flip plans" overnight: the statistics shifted, the costs were recomputed, and a different join order came out cheapest2. Now you know who to interrogate (EXPLAIN) and what to refresh (ANALYZE).

Feel the explosion: pick an order

Three tables, two join predicates, three left-deep orders (each join takes the result so far on its left and one fresh table on its right); every order returns the same 3,000 rows, but the amount of work in the middle differs:

join order · students (300 rows) ⋈ majors (3) ⋈ enrollments (3,000)

Predicates: students.mid = majors.mid2 and students.uid = enrollments.uid. Click an order; the bars show each intermediate result's row count (the cost proxy: rows a plan must produce and carry). Note what happens to the order that joins majors and enrollments first: no predicate connects them.

Order 3 builds a 9,000-row cross product it then filters down: the same answer, 3× the intermediate work of order 2 and 30× order 1's first step. At 10 tables this gap is why join ordering is THE optimization, and why the planner's dynamic programming earns its complexity.

FAQ

Will microdb get an optimizer in a later lab?

No: Act II begins after the midterm, and microdb stays at its seven layers. The Going-Further path exists (Lab 6 wired an index into the planner; add statistics to the catalog and a cost comparison between candidate plans, and you have a small version of the System R optimizer). Some students make it a final-project appendix; it's a good one.

Why do plans change when I add LIMIT 10?

The optimizer prices first rows differently from all rows: a plan that streams cheap early rows (nested loop via an index) can beat one with a big setup cost (hash join) when only 10 are wanted. Cost models track both startup and total cost for exactly this reason2.

Is the exam cumulative with the quizzes? Same style?

Same style, same sources (lab discussion prompts, measured numbers, FAQ subtleties), longer sitting. If your quiz scores have been comfortable, the midterm will feel like a long quiz. Bring a pencil; scratch paper is provided and not collected.

What's the single most exam-relevant thing to re-read?

The measured outputs. Every one of the eight numbers in the review table has a mechanism behind it, and mechanisms are what get asked. Second place: the force/steal grid and the WAL ordering; the exam enjoys orderings.
