The Query Optimizer

Two plans can answer the same query by examining 900 or 60 student–major pairs. How can an optimizer choose between them before execution?
Daniel G. Graham · UVA School of Data Science

A fictional classroom investigation

Maya wants student names and departments for one selected department. The students must have a GPA above 3.5. One plan pairs all 300 students with all three majors before filtering. The other keeps 60 qualifying students and one selected major before making pairs. Both return twenty rows, but they examine 900 and 60 pairs. Noor asks, Which rows can we rule out before making pairs?

The student fixtures store GPA in tenths, so 3.5 is stored as 35. The SQL condition is therefore gpa > 35.

An optimizer estimates the work of equivalent plans. It uses statistics, a cost model, and a search with limited planning time. First, examine the small join example. Then estimate page accesses for scan and index plans. Finally, compare estimates with measured execution. This material is optional.

EXPLAIN ANALYZE compares estimates with measurements

EXPLAINasks the engine to print the plan it chose, with its cost and row-count estimates, instead of the query's results.
Adding ANALYZEAlso executes the query. It displays measured row counts and times beside the estimates. Interpreting EXPLAIN ANALYZE output helps locate estimation errors.

Follow the operator tree and check row-count estimates

Read from the input scans toward the operators that consume their rows. At each step, compare estimated and measured row counts. A large difference can explain an inefficient join order or algorithm. Other causes can also make a query slow.2

Row-count estimates drive cost estimates

Choosing a query plan is like choosing a route from a map before a trip. Statistics summarize row counts and value distributions. The cost model estimates each operator’s work. Plan search compares combinations of operators. Compare estimated and measured row counts, especially when the data violates the model’s assumptions.

Selectivity is the fraction of rows that a predicate keeps. If gpa > 35 keeps 60 of 300 rows, its selectivity is 0.2. The optimizer needs this estimate before execution. Cost formulas depend on the estimated number of rows from each step. The optimizer derives these estimates from table and column summaries. The following examples show the calculation and its assumptions.

Basic selectivity formulas and their assumptions

Table summaries include N rows and B blocks. Column summaries include the distinct-value count V, minimum, maximum, and a histogram.3 The introductory estimates below use ideas from System R. Production planners use more detailed statistics to refine them.4

\[ \text{sel}(f = c) = \frac{1}{V(f)} \qquad \text{sel}(f_1 = f_2) = \frac{1}{\max\bigl(V(f_1), V(f_2)\bigr)} \qquad \text{sel}(f > c) = \frac{\max(f) - c}{\max(f) - \min(f)} \]

The range formula assumes a uniform distribution between the minimum and maximum. Clamp the estimate to [0, 1]. Handle a constant-valued column separately. For integer data, this is a continuous approximation. Equality estimates assume the queried value exists. Join estimates assume compatible value domains.

\[ \text{survivors}(\sigma) \;=\; N \cdot \text{sel} \]

For AND conditions, multiply the selectivities. This calculation assumes independent conditions.5

Two simplifying assumptions: uniformity and independence

These formulas assume uniform value frequencies or distributions. Combining predicates also assumes independence. Real data often violates these assumptions. A range estimate from only the minimum and maximum misses clusters of values. Multiplying selectivities for city = 'Charlottesville' and state = 'VA' underestimates matches when every Charlottesville row is already in Virginia. Histograms and statistics across columns can improve the estimates.3

Practice estimating a filtered row count

Check yourself · estimate the matching rows

The students table has N = 300, gpa min 20, gpa max 39, and V(mid) = 3. Estimate the rows that satisfy gpa > 30 AND mid = 2 with the formulas above. Identify the uniformity or independence assumption at each step.

Show answer

For gpa > 30, \(\frac{39 - 30}{39 - 20} \approx 0.47\), or about 142 rows. This assumes uniformity, although GPAs could cluster near 30. For mid = 2, \(1/V = 1/3\). Combining the conditions gives \(300 \times 0.47 \times 0.33 \approx\) 47 rows. This assumes independence, although the mid-2 department could grade harder. These calculations illustrate the planner’s rows= estimate.

If the measured count differs substantially, examine the value distribution. Check whether the predicates are correlated.

Estimate a plan’s block accesses before execution

Estimated row counts supply inputs to cost formulas. Compare plans with the same units and assumptions. A smaller block-access estimate means less work in this model.

Table scans and index scans provide different access paths to rows. A cost model estimates each candidate plan’s work from its operators and estimated row counts. Our teaching model counts block accesses, extending the measurements from Lab 4. Production models also account for CPU work, caching, and differences between sequential and random I/O.

Five simplified formulas for block-access cost

\[ \begin{aligned} \text{cost}(\text{TableScan}) &= B(\text{table}) \\ \text{cost}(\text{IndexSelect}_{=}) &= \text{height} + \text{matching RIDs} \\ \text{cost}(\text{NestedLoopJoin}) &= B(L) + N(L) \cdot B(R) \\ \text{cost}(\text{HashJoin}) &= B(L) + B(R) \\ \text{cost}(\text{MergeJoin}) &= \text{sort costs} + B(L) + B(R) \end{aligned} \]

These formulas give simplified I/O estimates. Hash join assumes its smaller input fits in memory. Repeated heap visits can use cached pages. Spilling, output size, and CPU work add costs. The table-scan and index formulas extend the ideas from weeks 1 and 6.

The nested-loop term N(L) · B(R) counts another right-input scan for each left row.4 Hash join reads each input once and uses memory for its hash table. Calculate each plan’s total from the statistics. Select the plan with the smallest estimate before execution.

These formulas estimate page-access work before execution. Lab 4’s CountingScan.rows instead counts rows yielded by a scan. Row counts help explain work, but they are not measurements of block reads.2

The slider sets selectivity: the fraction of rows that the predicate keeps. A sequential scan always costs B = 1,000 block accesses. The index costs its height plus one block access per matching RID. The optimizer selects the plan with the smaller estimate.

The plans have approximately equal costs near 1% selectivity in this model. Below that point, the index avoids enough heap accesses to cost less. Above that point, the sequential scan costs less. Actual thresholds depend on caching, row clustering, index coverage, and I/O costs.

Choose both the join algorithm and the join order

So far, we have chosen how to obtain rows from one table. With several tables, we must also decide how to match their rows and which intermediate results to build first.

Join order and algorithm choice affect each other. An early filter or smaller intermediate result can change which algorithm costs least for the next join.

Ten tables can be joined 17 billion ways

Ten tables have about 17 billion possible join plans when counting table permutations and binary-tree arrangements. Algorithm choices add more alternatives. Dynamic programming retains useful plans for small table subsets and uses them to construct larger plans. The search still grows rapidly, so planners also use restrictions and heuristics. PostgreSQL can switch to genetic search when a query has enough joins. Its default threshold is 12 tables.89

17 billion distinct shapes for a 10-table join: the search that System R's dynamic programming makes feasible

Updated statistics can change the selected plan

A data load or statistics refresh can change row-count estimates. A different plan can then appear cheaper. When performance changes, compare the old and new EXPLAIN output. Check whether the statistics are current. Join order, scan types, and join algorithms can all change.2

FAQ

Will microdb get an optimizer in a later lab?

There is no required optimizer implementation. The core microdb sequence stops at B+ trees. Transactions and optimization are optional extensions. For an optional extension, first connect the Lab 6 index to the planner. Then add catalog statistics. Compare the estimated costs of candidate plans.

These steps produce a small cost-based optimizer. You can include this extension in a final-project appendix if it supports your project’s goals.

Why do plans change when I add LIMIT 10?

The optimizer estimates costs for first rows and all rows separately. With LIMIT 10, an indexed nested loop can return early rows without a large setup cost. A hash join must first build its hash table. Cost models therefore track startup cost and total cost.2
