Anatomy of a Database

Why can the same query run faster when its data is already in memory?
Daniel G. Graham · UVA School of Data Science

The same SQL query can run faster a second time because the database has kept its data in memory. Today we follow one SELECT through the parser, planner, operators, buffer pool, and disk to see why. Over the next seven Thursday labs, you will implement these components in Python and combine them into a working database engine called microdb.

Built on: Edward Sciore, Database Design and Implementation (the SimpleDB book) · Hellerstein, Stonebraker & Hamilton, Architecture of a Database System · latency figures after “Numbers Every Programmer Should Know”.

When an application needs more than pandas and CSV files

pandas is useful for analyzing tables in memory. A database adds storage and coordination features that a script reading and writing a CSV file must otherwise implement itself.

Transactions provide ACID guarantees

A transaction groups database operations into a unit of work. The ACID properties are atomic, consistent, isolated, and durable: its changes happen together, preserve declared constraints, obey the chosen rules for concurrent execution, and survive a crash after a durable commit. A pandas operation followed by a CSV save does not provide these guarantees by itself1.

Rows, schemas, and keys

A relation is a set of rows (tuples) sharing a schema: a list of named fields and their types. We will use this six-row student table throughout the first part of the course:

The toy table · students(id int, name varchar, gpa int)

This student table is a recurring example. GPA is stored ×10 as an integer (3.9 → 39) because the core microdb labs support integers and strings.

Lecture widgets sometimes display GPAs as decimals for readability. In runnable microdb examples, use the stored integer scale: gpa > 35 means a GPA above 3.5. The two-block widget is an illustration; the Lab 3 layout fits 170 student rows in a 4096-byte block.

Rows 1–3 live in block 0 of students.tbl; rows 4–6 in block 1. The widget spreads the rows across two blocks to make caching visible; the later record layout packs more rows into each block.

A key must identify each row uniquely as the table changes

A key is a minimal set of fields that uniquely identifies a row. Here, id is the key. Uniqueness must hold as new rows are added; it is not enough for the current six rows to happen to have different names. A student ID can stay the same when a student changes their name or GPA2.

Exercise

The registrar proposes (name, gpa) as the key for students. Explain one problem with uniqueness and one problem with using changing values as references.

Show answer

Two students can share both a name and a GPA, so the proposed key would not reliably distinguish them. Names and GPAs can also change. If other tables refer to students using these values, those references must be updated whenever the values change.

Declarative SQL lets the planner choose an access strategy

SQL is declarative: it describes the desired result without specifying every step needed to produce it. The planner chooses an execution strategy, such as scanning the table or using an index:

Strategy A: read everything
Scan all blocks of students
→ test every row against gpa > 3.5
→ keep 3
cost ≈ all table blocks
Strategy B: jump straight there
Walk a gpa index to 3.5
→ follow pointers to just the matching rows
→ keep 3
cost ≈ index traversal plus the blocks holding matching rows

Two plans can return the same rows while reading very different numbers of blocks.

Both strategies return the same answer. For a selective query on a large table, an index can reduce block reads by orders of magnitude. The benefit depends on how many rows match and where their blocks are stored. Lectures 5 and 9 explain how the planner chooses between alternatives.

The file manager handles bytes at calculated offsets. The record and query layers rely on these reads and writes, so it is the first component you will build.

The write-ahead log supports crash recovery

The write-ahead log records changes in an append-only file. The required log records must reach durable storage before the corresponding changed data pages do. After a crash, recovery uses the log to restore committed changes and remove incomplete changes, according to the engine’s recovery policy6.

The kill -9 test

In Lab 7 you will use kill -9 to stop microdb during a transaction, restart it, and check that recovery preserves committed work and undoes incomplete work. Lab 1’s fsync measurement introduces the cost of making writes durable.

Storage access has a substantial fixed cost

A storage request has overhead beyond the time needed to transfer its bytes. That overhead helps explain why databases read blocks and keep recently used blocks in memory.

One spinning-disk seek costs ten million L1 hits

The latency ladder

Log scale: every gridline is 10× the one to its left, so bar length counts decades, not multiples: the disk bar is three times the L1 bar and ten million times the latency. That is why the true ratio is printed on the right7. Toggle human scale to feel it: if one L1 cache hit took one second, a spinning-disk seek would take four months.

Figures are representative, after Colin Scott's interactive latency page; your hardware varies. The ratios are what to remember.

Consequence 1: read and cache a whole block

For small reads, the fixed cost of a storage request can dominate transfer time. Reading a whole block lets the database reuse nearby data from memory instead of issuing another storage request.

The arithmetic of a wasted trip

Suppose an NVMe SSD read takes about 25 µs and a buffer-pool hit takes 100 ns. If ada and ben occupy the same block, reading the block for ada also brings ben into memory. A later access to ben can then avoid another SSD read. In this simplified model, that memory access is 250× faster.

250× one NVMe trip (25 µs) costs what 250 buffer-pool hits (100 ns) cost

Consequence 2: start by counting disk trips

Our first cost model counts block accesses. Some requests require a disk read; others find the block in memory. We estimate their total time separately:

\[ T(\text{query}) \;\approx\; n_{\text{disk}} \cdot t_{\text{disk}} \;+\; n_{\text{mem}} \cdot t_{\text{mem}} \]

with tdisk ≈ 25 µs, one NVMe trip8, and tmem ≈ 100 ns, one buffer-pool hit7. One disk trip therefore costs what 250 memory reads cost (100,000 of them, if the disk spins)7.

students lives in 2 blocks, so the demo's two runs of the same query cost:

\[ \text{cold run: } 2 \cdot 25\,\mu\text{s} + 0 \cdot 100\,\text{ns} = 50\,\mu\text{s} \qquad\quad \text{warm run: } 0 \cdot 25\,\mu\text{s} + 2 \cdot 100\,\text{ns} = 0.2\,\mu\text{s} \]

In this simplified I/O model, the warm run is 250× faster. These figures count block access only; they are not measured end-to-end Python query times.

Reducing disk reads is our first optimization target. CPU work, memory bandwidth, parsing, and network traffic also matter; later lectures extend this cost model.

Check yourself: the speedup grows with the table

Check yourself · count block reads

A table occupies 500 blocks. Query A scans all of them. Query B uses an index that reads 4 index blocks, then jumps to the 3 blocks holding matching rows. With a disk trip at ~25 µs and a memory read effectively free: how much faster is B, and what happens to that ratio when the table grows to 500,000 blocks?

Show answer

A costs \(500 \times 25\,\mu\text{s} \approx 12.5\ \text{ms}\); B costs \(7 \times 25\,\mu\text{s} \approx 0.18\ \text{ms}\), about 70× faster. If the table grows 1000× while the matching rows still occupy three blocks, A’s work grows 1000×. B’s work grows much more slowly as the index gains levels. The exact ratio depends on the index height and number of matching blocks; Lab 6 measures this difference.

These systems group data into different units. Pages are small physical storage units; analytical row groups organize much larger collections of rows and are not necessarily read in a single I/O request:

Reading and writing must use the same byte order

The decisionset_int(0, 1) has to put four bytes somewhere, and the order it puts them in is a decision, not a fact.
Both in usemicrodb uses little-endian integers. Many network protocols specify big-endian order; other formats make different choices. Always follow the format’s declared byte order.1213
Thursday's specpicks one, struct '<i' (little-endian), and the tests enforce it literally.

Every byte in this course prints as two hex digits, and reading one is a multiply and an add: the first digit counts 16s, the second counts 1s, and the digits A through F stand for 10 through 15. Keep this table handy; it decodes every byte the widget below prints.

Hex byteArithmeticDecimal
0x090×16 + 99
0x101×16 + 016
0x272×16 + 739 (ada's gpa)
0x1F1×16 + 15, because F is 1531
0xFF15×16 + 15255, the largest value one byte holds
One int, two byte orders · change the value

The highlighted byte is the least significant byte: it contains the units from 0 to 255. Watch which end of the four-byte sequence holds it.

microdb stores integers in little-endian order, with the least significant byte first. This matches x86 and common ARM configurations. If both your reader and writer use the same incorrect order, your own round-trip test can still pass. Tests must also check the stored bytes against the required file format14.

Recap & next time

Three ideas to carry into the labs:

  • The engine has cooperating layers: front end, operators, records, buffer pool, and file manager. The write-ahead log supports crash recovery across those layers.
  • Reading and caching blocks can reduce storage requests. We will begin performance analysis by counting those requests, then add CPU and other costs.
  • Declarative SQL leaves execution choices to the planner. Different valid plans can return the same rows with very different amounts of work.

FAQ

Do I need a systems or databases background?

No, that's the point of the course. You need comfortable Python and basic SQL (SELECT/JOIN/GROUP BY). Everything below the SQL line is built, not assumed.

What should I review if my SQL is rusty?

For the first lecture, review single-table SELECT … WHERE queries. Familiarity with basic joins and grouping will help later; the course explains how an engine implements these operations.

What do I need installed for Thursday?

See the setup checklist above: Python 3.11+, an editor, the three starter files, and nothing else. Windows users: everything works natively; if os.fsync misbehaves under OneDrive-synced folders, work in a local directory like C:\dev\microdb.

Can I use Copilot / Claude / ChatGPT on labs?

You may use these tools to help understand the material. For submitted code, the course rule is the same as the project rule: you must be able to explain each line when asked. Use the lab work to prepare for the midterm’s questions about how the engine works.

Is there a textbook to buy?

No purchase is required. Sciore’s Database Design and Implementation provides additional explanations of the components we build. UVA’s library has electronic access.
