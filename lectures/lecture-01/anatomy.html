Transactions provide ACID guarantees

A transaction groups database operations into a unit of work. The ACID properties are atomic, consistent, isolated, and durable.

Atomic changes happen together. Consistency preserves declared constraints. Isolation controls concurrent execution according to the selected isolation rules. Durability preserves changes after a durable commit, including after a crash. A pandas operation followed by a CSV save does not provide these guarantees by itself1.

Rows, schemas, and keys

The query returns names. The engine needs rules for every field that it reads. First, give the six rows a schema. Then identify a stable key.

A relation is a set of rows, also called tuples. The rows share a schema, which lists field names and types. We will use this six-row student table throughout the first part of the course:

The toy table · students(id int, name varchar, gpa int)

This student table is a recurring example. GPA is stored ×10 as an integer (3.9 → 39) because the core microdb labs support integers and strings.

Lecture widgets sometimes display GPAs as decimals for readability. In runnable microdb examples, use the stored integer scale: gpa > 35 means a GPA above 3.5. The two-block widget is an illustration. The Lab 3 layout fits 170 student rows in a 4096-byte block.

Rows 1–3 occupy block 0 of students.tbl. Rows 4–6 occupy block 1. The widget uses two blocks to show caching. The later record layout fits more rows into each block.

A key must identify each row uniquely as the table changes

A key is a minimal set of fields that uniquely identifies a row. Here, id is the key. The key must remain unique when the table receives new rows. Different names in the current six rows do not establish a valid key. A student ID can stay the same when a student changes their name or GPA2.

Exercise

The registrar proposes (name, gpa) as the key for students. Explain one problem with uniqueness. Then explain one problem with references that use changing values.

Show answer

Two students can share both a name and a GPA, so the proposed key would not reliably distinguish them. Names and GPAs can also change. If other tables refer to students using these values, those references must be updated whenever the values change.

Declarative SQL lets the planner choose an access strategy

SQL is declarative: it describes the desired result without specifying every step needed to produce it. The planner chooses an execution strategy, such as scanning the table or using an index:

Strategy A: read everything
Scan all blocks of students
→ test every row against gpa > 3.5
→ keep 3
cost ≈ all table blocks
Strategy B: use an index
Walk a gpa index to 3.5
→ follow pointers to just the matching rows
→ keep 3
cost ≈ index traversal plus the blocks holding matching rows

Two plans can return the same rows while reading very different numbers of blocks.

Both strategies return the same answer. For a selective query on a large table, an index can reduce block reads by orders of magnitude. The benefit depends on how many rows match and where their blocks are stored. Lectures 5 and 9 explain how the planner chooses between alternatives.

Five layers help us understand a database engine

Think of following an order through a workshop. The front desk records the request. Each station asks the next station for the items it needs. SQL is the request, and the plan gives the work instructions. Operators and storage layers act as the stations. The analogy describes responsibilities, while the interfaces below define the actual operations.

We will study a database engine as five cooperating layers. Production systems organize their code differently, but these layers give us a useful way to separate their responsibilities.

The file manager handles bytes at calculated offsets. The record and query layers rely on these reads and writes, so it is the first component you will build.

The write-ahead log supports crash recovery

The write-ahead log records changes in an append-only file. The required log records must reach durable storage before the corresponding changed data pages do. After a crash, recovery reads the log. The engine’s recovery policy determines how to restore committed changes and remove incomplete changes6.

The kill -9 test

Optional Lab 7 tests crash recovery. Use kill -9 to stop microdb during a transaction. Restart microdb. Check that recovery preserves committed work and undoes incomplete work. Lab 1’s fsync measurement introduces the cost of making writes durable.

Storage access has a substantial fixed cost

The file manager now reads the requested block. How many bytes does that read bring into memory, and which later requests can reuse them without another disk read?

A storage request has overhead beyond the time needed to transfer its bytes. That overhead helps explain why databases read blocks and keep recently used blocks in memory.

One spinning-disk seek costs ten million L1 hits

The latency ladder

The chart uses a logarithmic scale. Each gridline represents 10× the value to its left. Bar length therefore counts powers of ten. The disk bar is three times the L1 bar length, but its latency is ten million times larger. The right column gives the latency ratio7.

Select human scale to compare familiar durations. If one L1 cache hit took one second, a spinning-disk seek would take four months.

Consequence 1: read and cache a whole block

For small reads, the fixed cost of a storage request can dominate transfer time. Reading a whole block lets the database reuse nearby data from memory instead of issuing another storage request.

Compare one storage read with one memory access

Suppose an NVMe SSD read takes about 25 µs and a buffer-pool hit takes 100 ns. If ada and ben occupy the same block, reading the block for ada also brings ben into memory. A later access to ben can then avoid another SSD read. In this simplified model, that memory access is 250× faster.

250× one NVMe trip (25 µs) costs what 250 buffer-pool hits (100 ns) cost

Consequence 2: start by counting disk trips

Our first cost model counts block accesses. Some requests require a disk read. Other requests find the block in memory. We estimate their total time separately:

\[ T(\text{query}) \;\approx\; n_{\text{disk}} \cdot t_{\text{disk}} \;+\; n_{\text{mem}} \cdot t_{\text{mem}} \]

with tdisk ≈ 25 µs, one NVMe trip8, and tmem ≈ 100 ns, one buffer-pool hit7. One disk trip therefore costs what 250 memory reads cost (100,000 of them, if the disk spins)7.

students lives in 2 blocks, so the demo's two runs of the same query cost:

\[ \text{cold run: } 2 \cdot 25\,\mu\text{s} + 0 \cdot 100\,\text{ns} = 50\,\mu\text{s} \qquad\quad \text{warm run: } 0 \cdot 25\,\mu\text{s} + 2 \cdot 100\,\text{ns} = 0.2\,\mu\text{s} \]

In this simplified I/O model, the warm run is 250× faster. These estimates count only block access. They do not measure the complete Python query execution time.

Reducing disk reads is our first optimization target. CPU work, memory bandwidth, parsing, and network traffic also affect query time. Later lectures extend this cost model.

Check yourself: the speedup grows with the table

Check yourself · count block reads

A table occupies 500 blocks. Query A scans all of them. Query B uses an index that reads 4 index blocks, then jumps to the 3 blocks holding matching rows. Assume each disk read takes ~25 µs and memory-read time is negligible. How much faster is B? What happens to that ratio when the table grows to 500,000 blocks?

Show answer

A costs \(500 \times 25\,\mu\text{s} \approx 12.5\ \text{ms}\). B costs \(7 \times 25\,\mu\text{s} \approx 0.18\ \text{ms}\), about 70× faster. If the table grows 1000× while the matching rows still occupy three blocks, A’s work grows 1000×. B’s work grows much more slowly as the index gains levels. The exact ratio depends on index height and the number of matching blocks. Lab 6 measures this difference.

Reading and writing must use the same byte order

The decisionset_int(0, 1) stores four bytes. The file format specifies their order.
Both in usemicrodb uses little-endian integers. Many network protocols specify big-endian order. Other formats make different choices. Always follow the format’s declared byte order.1213
Thursday's specpicks one, struct '<i' (little-endian), and the tests enforce it literally.

The byte displays in this course use two hexadecimal digits per byte. The first digit counts groups of 16. The second digit counts units. Digits A through F represent 10 through 15. To convert a pair to decimal, calculate 16 × the first digit + the second digit. Use this table to decode the widget bytes.

The highlighted byte is the least significant byte: it contains the units from 0 to 255. Watch which end of the four-byte sequence holds it.

microdb stores integers in little-endian order, with the least significant byte first. This matches x86 and common ARM configurations. If both your reader and writer use the same incorrect order, your own round-trip test can still pass. Tests must also check the stored bytes against the required file format14.

Three ideas to carry into the labs:

  • The engine has cooperating layers: front end, operators, records, buffer pool, and file manager. The write-ahead log supports crash recovery across those layers.
  • Reading and caching blocks can reduce storage requests. We will begin performance analysis by counting those requests, then add CPU and other costs.
  • Declarative SQL leaves execution choices to the planner. Different valid plans can return the same rows with very different amounts of work.

FAQ

Do I need a systems or databases background?

No. You need Python proficiency and basic SQL (SELECT/JOIN/GROUP BY). The course teaches the components below the SQL interface.

What should I review if my SQL is rusty?

For the first lecture, review single-table SELECT … WHERE queries. Basic joins and grouping will help in later lectures. The course explains how an engine implements these operations.

What do I need installed for Thursday?

See the setup checklist above: Python 3.11+, an editor, the three starter files, and nothing else. The lab runs natively on Windows. If os.fsync fails in a OneDrive-synced folder, use a local directory such as C:\dev\microdb.

Can I use Copilot / Claude / ChatGPT on labs?

You may use these tools to help understand the material. The project rule also applies to submitted lab code. You must be able to explain each line when asked. Use the lab work to prepare for the midterm’s questions about how the engine works.

Is there a textbook to buy?

No purchase is required. Sciore’s Database Design and Implementation provides additional explanations of the components we build. UVA’s library has electronic access.
