Anatomy of a Database

Why does the same query take 50 µs, then 0.2 µs a second later, when nothing in the SQL changed?
Daniel G. Graham · UVA School of Data Science

You have run thousands of queries without ever being able to say why one took the time it did: the same SELECT costs 50 µs one moment and 0.2 µs the next, and nothing in the SQL explains the gap. Today we open the box the query disappeared into. This lecture walks one SELECT through every layer of a database engine: parser, planner, operators, buffer pool, disk. Then it lays out the plan for the rest of Act I: over the next seven Thursdays, you will build each of those layers yourself, in Python, until you have a working engine called microdb.

Built on: Edward Sciore, Database Design and Implementation (the SimpleDB book) · Hellerstein, Stonebraker & Hamilton, Architecture of a Database System · latency figures after “Numbers Every Programmer Should Know”.

Dotted-underlined terms like this one are systems jargon you're not expected to know yet: hover or tap one and a plain-language explainer opens right below the sentence you're reading.

Today's plan

The problem in one run: your query touched two blocks and took 50 µs; the same query a second later took 0.2 µs. Nothing in the SQL explains why, and until you can, every slow query you will ever meet is a guess.

One lecture, one arc: watch a query go through a real engine, understand why each piece it passed through has to exist, and leave with the build plan for making your own.

A database promises ACID; pandas never signed that contract

Those four fixes aren't features; they're a contract. When a database says a write is committed, it is promising the write is atomic, consistent, isolated, and durable: all-or-nothing, rule-preserving, safe from concurrent readers, and crash-proof1. Everything heavy inside an engine exists to keep that promise while staying fast. pandas never signed it, which is exactly why pandas is light.

The relational model says what, never how

You've written SQL, so this is a refresher with sharpened definitions; we'll need them precise later. A relation is a set of rows (tuples) sharing a schema: named fields with types. Our pinned example for the next seven weeks is this six-row table:

The toy table · students(id int, name varchar, gpa int)

Six rows, pinned. You will meet these exact values in every widget from here to the midterm: gpa is stored ×10 as an int (3.9 → 39) because microdb won't grow floats until Lab 3.

Rows 1–3 live in block 0 of students.tbl; rows 4–6 in block 1. That placement is real: Thursday you write the code that puts them there.

A key is a promise about rows that don't exist yet

A key is a minimal set of fields that uniquely identifies a row2: id here. The subtlety students miss: a key is not a fact about the rows you have, it's a promise about every row you will ever have. name works until the second ada enrolls; id exists precisely to be meaningless and immortal.

Exercise

The registrar proposes (name, gpa) as the key for students. Give two distinct reasons this is a bad key, using only the six pinned rows and common sense about future rows.

Show answer

(1) Nothing prevents two students named ada with gpa 39; uniqueness isn't guaranteed by the meaning of the data, and a key is a promise about all future rows, not the current six. (2) Both fields change (name changes, gpa changes every term); a key that mutates forces every reference to it to be rewritten.

Declarative SQL lets the planner pick a plan 1000× cheaper

SQL is declarative: the query names the rows you want, never the steps to find them. That one design decision creates the entire middle of a database engine, because someone still has to choose the steps, and that someone is the planner, not you:

Strategy A: read everything
Scan all blocks of students
→ test every row against gpa > 3.5
→ keep 3
cost ≈ every block (fine for 2, fatal for 2 million)
Strategy B: jump straight there
Walk a gpa index to 3.5
→ follow pointers to just the matching rows
→ keep 3
cost ≈ 3–4 blocks, almost regardless of table size

1000× the work between two correct plans for one query; the planner picks, not your phrasing

Same query, same answer, and on a table of a few thousand blocks Strategy A does 1000× the work. The freedom to pick B without you rewriting anything is what "declarative" buys, and why I dedicated two lectures to the planner (week 5, week 9).

The write-ahead log is why COMMIT means something

One component sits beside the stack rather than in it, touching everything: the write-ahead log. Before any layer changes a page, it writes a note ("I am about to change X from a to b") to an append-only file. After a crash, replaying and undoing those notes restores a clean database6.

The kill -9 test

In Lab 7 you will kill -9 microdb halfway through a transaction, restart it, and watch recovery put back exactly the committed work, no more, no less. That demo is the whole reason COMMIT means something, and the fsync price you measure Thursday is the reason the log exists at all.

Storage pays by the trip, not by the byte

One design decision explains more of database architecture than any other: storage is brutally slower than memory, and it pays by the trip, not by the byte.

One spinning-disk seek costs ten million L1 hits

The latency ladder

Log scale: every gridline is 10× the one to its left, so bar length counts decades, not multiples: the disk bar is three times the L1 bar and ten million times the latency. That is why the true ratio is printed on the right7. Toggle human scale to feel it: if one L1 cache hit took one second, a spinning-disk seek would take four months.

Figures are representative, after Colin Scott's interactive latency page; your hardware varies. The ratios are what to remember.

Consequence 1: fetch the whole block, never the value

Because each trip to storage costs the same whether it fetches 8 bytes or 8 KB, databases never read a value; they read a whole block and keep it around, betting that nearby bytes will be wanted next.

The arithmetic of a wasted trip

One trip to an NVMe SSD (Non-Volatile Memory express, the interface modern solid-state drives speak) costs about 25 µs whether it moves 8 bytes or 4096. Take two rows of the pinned students table: fetching ada (row 1) on its own and then coming back for ben (row 2) means paying 25 µs twice for neighbors whose bytes sit 15 apart on disk. Fetch the block once and ben arrives with it; that second read is served from memory at 100 ns, a 250× discount for one design decision.

250× one NVMe trip (25 µs) costs what 250 buffer-pool hits (100 ns) cost

Consequence 2: count the disk trips, nothing else

A query reads every block it needs from one of two places: from disk, or from memory because some earlier read left it there. The first costs hundreds to hundreds of thousands of times more than the second, so a query's time is decided almost entirely by how many blocks it has to fetch from disk. That is the course's first cost model, crude and genuinely useful:

\[ T(\text{query}) \;\approx\; n_{\text{disk}} \cdot t_{\text{disk}} \;+\; n_{\text{mem}} \cdot t_{\text{mem}} \]

with tdisk ≈ 25 µs, one NVMe trip8, and tmem ≈ 100 ns, one buffer-pool hit7. One disk trip therefore costs what 250 memory reads cost (100,000 of them, if the disk spins)7.

students lives in 2 blocks, so the demo's two runs of the same query cost:

\[ \text{cold run: } 2 \cdot 25\,\mu\text{s} + 0 \cdot 100\,\text{ns} = 50\,\mu\text{s} \qquad\quad \text{warm run: } 0 \cdot 25\,\mu\text{s} + 2 \cdot 100\,\text{ns} = 0.2\,\mu\text{s} \]

The warm run is 250× faster. The query did not change; only the first term did.

So the first term is the only one worth attacking, and every speed technique in this course (the buffer pool, B+ trees, column stores, even the vector indexes in Act II) is one strategy for shrinking it: touch fewer blocks.

Check yourself: the speedup grows with the table

Check yourself · the only arithmetic that matters

A table occupies 500 blocks. Query A scans all of them. Query B uses an index that reads 4 index blocks, then jumps to the 3 blocks holding matching rows. With a disk trip at ~25 µs and a memory read effectively free: how much faster is B, and what happens to that ratio when the table grows to 500,000 blocks?

Show answer

A costs \(500 \times 25\,\mu\text{s} \approx 12.5\ \text{ms}\); B costs \(7 \times 25\,\mu\text{s} \approx 0.18\ \text{ms}\), about 70× faster. Grow the table 1000× and A pays 1000× more while B pays almost the same (the index gets one level deeper at most); the ratio balloons toward 70,000×. That scaling behavior, not any single number, is why indexes exist; you'll measure a real 4,091× in Lab 6.

Byte order is a choice, and the wrong one still round-trips

The decisionset_int(0, 1) has to put four bytes somewhere, and the order it puts them in is a decision, not a fact.
Both in useyour laptop's CPU is little-endian, every integer that crosses a network is big-endian12, and SQLite's file header is big-endian inside files your little-endian machine wrote13.
Thursday's specpicks one, struct '<i' (little-endian), and the tests enforce it literally.

Every byte in this course prints as two hex digits, and reading one is a multiply and an add: the first digit counts 16s, the second counts 1s, and the digits A through F stand for 10 through 15. Keep this table handy; it decodes every byte the widget below prints.

Hex byteArithmeticDecimal
0x090×16 + 99
0x101×16 + 016
0x272×16 + 739 (ada's gpa)
0x1F1×16 + 15, because F is 1531
0xFF15×16 + 15255, the largest value one byte holds
One int, two byte orders · change the value

The warm byte is the least significant one, worth 1. Watch which end of the four bytes it sits at.

microdb, x86 and ARM are little-endian, so the small end goes first14. Get it wrong in one direction only and the bytes still round-trip perfectly on your machine, which is precisely why the bug survives until someone else reads your file.

Recap & next time

Three ideas from today carry the whole course; if you remember nothing else, remember these.

  • A database is a layered machine: front end → operators → records → buffer pool → file manager, with the write-ahead log as the crash-safety rail. You now know what each layer is for, and you will build all of them.
  • Storage pays by the trip, so engines move whole blocks and count block touches, and every speed technique in this course is a way to touch fewer.
  • Declarative SQL hands the "how" to the planner: same query, strategies 1000× apart, chosen by machinery, not by phrasing.

250× · 1000× one disk trip costs 250 memory reads; two correct plans for one query can differ by 1000×

FAQ

Do I need a systems or databases background?

No, that's the point of the course. You need comfortable Python and basic SQL (SELECT/JOIN/GROUP BY). Everything below the SQL line is built, not assumed.

My SQL is rusty. Will that sink me?

Week 1 uses only single-table SELECT … WHERE. Skim any SQL tutorial's first chapter before Thursday and you're current; the sophisticated SQL in this course is SQL we implement, not SQL we write.

What do I need installed for Thursday?

See the setup checklist above: Python 3.11+, an editor, the three starter files, and nothing else. Windows users: everything works natively; if os.fsync misbehaves under OneDrive-synced folders, work in a local directory like C:\dev\microdb.

Can I use Copilot / Claude / ChatGPT on labs?

For understanding, yes. For code, the course rule is the project rule: anything you submit, you must be able to explain line by line when asked. The labs are small enough that outsourcing them mostly costs you the midterm.

Is there a textbook to buy?

No purchase required. We follow the spirit (and sometimes the letter) of Sciore's Database Design and Implementation; UVA's library has electronic access if you want the deep version of any week.
