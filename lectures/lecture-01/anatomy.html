Anatomy of a Database

What actually happens underneath a query, and the engine you're about to build.
Daniel G. Graham · UVA School of Data Science

You have run thousands of queries. Today we open the box they disappeared into. This lecture walks one SELECT through every layer of a database engine: parser, planner, operators, buffer pool, disk. Then it lays out the plan for the rest of Act I: over the next seven Thursdays, you will build each of those layers yourself, in Python, until you have a working engine called microdb.

Why not just pandas?

You already know a tool that answers questions about tables. It's called pandas, it's excellent, and this course is not here to talk you out of it. It's here to show you exactly where it stops.

Four ways the CSV dies

Four failures matter enough to name, because each one maps to machinery we build this semester:

The contract a database signs

Those four fixes aren't features; they're a contract. When a database says a write is committed, it is promising the write is atomic, consistent, isolated, and durable: all-or-nothing, rule-preserving, safe from concurrent readers, and crash-proof. Everything heavy inside an engine exists to keep that promise while staying fast. pandas never signed it, which is exactly why pandas is light.

The relational model, fast

You've written SQL, so this is a refresher with sharpened definitions; we'll need them precise later. A relation is a set of rows (tuples) sharing a schema: named fields with types. Our pinned example for the next seven weeks is this six-row table:

The toy table · students(id int, name varchar, gpa int)

Six rows, pinned. You will meet these exact values in every widget from here to the midterm: gpa is stored ×10 as an int (3.9 → 39) because microdb won't grow floats until Lab 3.

Rows 1–3 live in block 0 of students.tbl; rows 4–6 in block 1. That placement is real: Thursday you write the code that puts them there.

Keys: a promise about the future

A key is a minimal set of fields that uniquely identifies a row: id here. The subtlety students miss: a key is not a fact about the rows you have, it's a promise about every row you will ever have. name works until the second ada enrolls; id exists precisely to be meaningless and immortal.

Exercise

The registrar proposes (name, gpa) as the key for students. Give two distinct reasons this is a bad key, using only the six pinned rows and common sense about future rows.

Show answer

(1) Nothing prevents two students named ada with gpa 39; uniqueness isn't guaranteed by the meaning of the data, and a key is a promise about all future rows, not the current six. (2) Both fields change (name changes, gpa changes every term); a key that mutates forces every reference to it to be rewritten.

Declarative means the engine chooses

SQL is declarative: the query names the rows you want, never the steps to find them. That one design decision creates the entire middle of a database engine, because someone still has to choose the steps, and that someone is the planner, not you:

Strategy A: read everything
Scan all blocks of students
→ test every row against gpa > 3.5
→ keep 3
cost ≈ every block (fine for 2, fatal for 2 million)
Strategy B: jump straight there
Walk a gpa index to 3.5
→ follow pointers to just the matching rows
→ keep 3
cost ≈ 3–4 blocks, almost regardless of table size

Same query, same answer, and on a table of a few thousand blocks Strategy A does 1000× the work. The freedom to pick B without you rewriting anything is what "declarative" buys, and why I dedicated two lectures to the planner (week 5, week 9).

The catalog: tables about tables

One more idea completes the model. The schema itself (which tables exist, their columns, types, and file locations) has to live somewhere, and the relational answer is pleasingly circular: in tables. This is the system catalog, and microdb's will look almost exactly like this:

field_catalog: one row per column in the database

In Postgres, \dt and \d students are just queries against the catalog; in microdb, you build it in Lab 3, and notice those offsets: they're the exact bytes you'll place by hand on Thursday.

The five layers of every database

Now the box itself. Postgres, SQLite, DuckDB, Oracle: radically different engines, same five layers. Before you tour them, decide what they must be.

Show the answer

Five layers, and most lists come back with four. A SQL front end turns text into a plan; an execution engine turns the plan into rows; a records and catalog layer turns bytes into rows and back; a file manager moves whole blocks to and from disk. The one that usually goes missing is the buffer pool, whose only job is deciding which blocks are worth keeping in memory. It is easy to skip because it changes no answer, only how long the answer takes, which is exactly why it gets a week of its own. The write-ahead log is the sixth component, and it sits beside the stack rather than in it.

The rail beside the stack: the write-ahead log

One component sits beside the stack rather than in it, touching everything: the write-ahead log. Before any layer changes a page, it writes a note ("I am about to change X from a to b") to an append-only file. After a crash, replaying and undoing those notes restores a clean database.

The kill -9 test

In Lab 7 you will kill -9 microdb halfway through a transaction, restart it, and watch recovery put back exactly the committed work, no more, no less. That demo is the whole reason COMMIT means something, and the fsync price you measure Thursday is the reason the log exists at all.

Why disks shaped everything

One design decision explains more of database architecture than any other: storage is brutally slower than memory, and it pays by the trip, not by the byte. First, calibrate your intuition.

Think · Pair · Share · the latency ladder
  • Think · 2 minRank these and guess each gap as a multiplier: reading from CPU cache, from RAM, from an SSD, one disk seek on a spinning drive, one network round-trip inside a datacenter. Write your multipliers down; out loud, most people are off by 100× somewhere.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare ladders, then check against the real one on the next slide. Which rung surprised each of you most?
  • Share · 2 minAgree on one sentence: what should a system that lives on the slow rungs do differently from one that lives in RAM?
Show the answer

Getting the order right is the easy half; the gaps are where almost everyone is wrong. An L1 hit is about 1 ns, RAM about 100 ns (100× slower), an NVMe SSD about 25 µs (another 250×), a datacenter round trip about 500 µs, and a spinning-disk seek about 10 ms, which is ten million times the L1 hit. For the Share prompt: a system living on the slow rungs stops counting instructions and starts counting trips. It moves data in large chunks, because a trip costs the same either way, and it keeps whatever it fetched, because the next request is cheap only if the bytes are already there. Those two moves are the buffer pool and the block, and they are the next two weeks.

The ladder, measured

The latency ladder

Log scale: every gridline is 10× the one to its left, so bar length counts decades, not multiples: the disk bar is three times the L1 bar and ten million times the latency. That is why the true ratio is printed on the right. Toggle human scale to feel it: if one L1 cache hit took one second, a spinning-disk seek would take four months.

Figures are representative, after Colin Scott's interactive latency page; your hardware varies. The ratios are what to remember.

Consequence 1: move whole blocks

Because each trip to storage costs the same whether it fetches 8 bytes or 8 KB, databases never read a value; they read a whole block and keep it around, betting that nearby bytes will be wanted next.

The arithmetic of a wasted trip

One trip to an NVMe SSD (Non-Volatile Memory express, the interface modern solid-state drives speak) costs about 25 µs whether it moves 8 bytes or 4096. Take two rows of the pinned students table: fetching ada (row 1) on its own and then coming back for ben (row 2) means paying 25 µs twice for neighbors whose bytes sit 15 apart on disk. Fetch the block once and ben arrives with it; that second read is served from memory at 100 ns, a 250× discount for one design decision.

Consequence 2: count the disk trips, nothing else

A query reads every block it needs from one of two places: from disk, or from memory because some earlier read left it there. The first costs hundreds to hundreds of thousands of times more than the second, so a query's time is decided almost entirely by how many blocks it has to fetch from disk. That is the course's first cost model, crude and genuinely useful:

T(query)  ≈  blocks_from_disk × t_disk  +  blocks_from_memory × t_mem

     t_disk  ≈   25 µs    one NVMe trip
     t_mem   ≈  100 ns    one buffer-pool hit
     one disk trip therefore costs what 250 memory reads cost
     (100,000 of them, if the disk spins)

students lives in 2 blocks, so the demo's two runs of the same query cost:

     cold run   2 × 25 µs  +  0 × 100 ns  =  50 µs    both blocks from disk
     warm run   0 × 25 µs  +  2 × 100 ns  =  0.2 µs   both already in memory

The warm run is 250× faster. The query did not change; only the first term did.

So the first term is the only one worth attacking, and every speed technique in this course (the buffer pool, B+ trees, column stores, even the vector indexes in Act II) is one strategy for shrinking it: touch fewer blocks.

Check yourself · the only arithmetic that matters

A table occupies 500 blocks. Query A scans all of them. Query B uses an index that reads 4 index blocks, then jumps to the 3 blocks holding matching rows. With a disk trip at ~25 µs and a memory read effectively free: how much faster is B, and what happens to that ratio when the table grows to 500,000 blocks?

Show answer

A costs 500 trips ≈ 12.5 ms; B costs 7 trips ≈ 0.18 ms, about 70× faster. Grow the table 1000× and A pays 1000× more while B pays almost the same (the index gets one level deeper at most); the ratio balloons toward 70,000×. That scaling behavior, not any single number, is why indexes exist; you'll measure a real 4,091× in Lab 6.

Little-endian, and why you care

set_int(0, 1) has to put four bytes somewhere, and the order it puts them in is a decision, not a fact. Both answers are in use: your laptop's CPU is little-endian, every integer that crosses a network is big-endian, and SQLite's file header is big-endian inside files your little-endian machine wrote. Thursday's spec picks one, struct '<i', and the tests enforce it literally.

One int, two byte orders · change the value

The warm byte is the least significant one, worth 1. Watch which end of the four bytes it sits at.

microdb, x86 and ARM are little-endian, so the small end goes first. Get it wrong in one direction only and the bytes still round-trip perfectly on your machine, which is precisely why the bug survives until someone else reads your file.

Recap & next time

Three ideas from today carry the whole course; if you remember nothing else, remember these.

  • A database is a layered machine: front end → operators → records → buffer pool → file manager, with the write-ahead log as the crash-safety rail. You now know what each layer is for, and you will build all of them.
  • Storage pays by the trip, so engines move whole blocks and count block touches, and every speed technique in this course is a way to touch fewer.
  • Declarative SQL hands the "how" to the planner: same query, strategies 1000× apart, chosen by machinery, not by phrasing.

FAQ

Do I need a systems or databases background?

No, that's the point of the course. You need comfortable Python and basic SQL (SELECT/JOIN/GROUP BY). Everything below the SQL line is built, not assumed.

My SQL is rusty. Will that sink me?

Week 1 uses only single-table SELECT … WHERE. Skim any SQL tutorial's first chapter before Thursday and you're current; the sophisticated SQL in this course is SQL we implement, not SQL we write.

What do I need installed for Thursday?

See the setup checklist above: Python 3.11+, an editor, the three starter files, and nothing else. Windows users: everything works natively; if os.fsync misbehaves under OneDrive-synced folders, work in a local directory like C:\dev\microdb.

Can I use Copilot / Claude / ChatGPT on labs?

For understanding, yes. For code, the course rule is the project rule: anything you submit, you must be able to explain line by line when asked. The labs are small enough that outsourcing them mostly costs you the midterm.

Is there a textbook to buy?

No purchase required. We follow the spirit (and sometimes the letter) of Sciore's Database Design and Implementation; UVA's library has electronic access if you want the deep version of any week.
