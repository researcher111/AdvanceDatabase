Record Layout & the Catalog

How can a database locate and update fields without shifting neighboring rows?
Daniel G. Graham · UVA School of Data Science

A fictional classroom investigation

Maya saves the byte position where cyd begins. She then renames ben to benjamin in a packed page. The later bytes shift. Noor taps the saved address: Does this still point to cyd? They try again with reserved slots so a longer name can stay inside its own row.

The record layer locates a row’s fields within a block. A Layout computes field offsets. A RecordPage interprets one pinned block. A TableScan visits occupied slots. The catalog saves the rules needed to interpret those rows after restart.

Companion reading: Sciore, Database Design and Implementation, ch. 6 (record management) & ch. 7 (metadata)2 · how a production engine does it: PostgreSQL's page layout docs and system catalogs.

Start with what you already know

In the 128-byte toy block, each student slot occupies 24 bytes and GPA begins at offset 20. Where does slot 3’s GPA begin? Would deleting slot 1 move it?

Check your explanation

Its address is 3 × 24 + 20 = 92. Deletion changes slot 1’s status flag. Fixed-size slots keep slot 3 at the same position. The layout is required to interpret the bytes there.

We begin with Quiz 2 (the buffer pool, 10 min), then add the record layer that interprets cached bytes as rows and fields.

Suppose variable-length rows are packed end to end. Renaming ben to benjamin needs five extra bytes, so later data must move. Saved byte positions then become invalid. Without a directory of row locations, finding row 4 also requires reading the lengths of earlier rows.

In microdb, a table has a heap file containing fixed-size record slots and catalog entries describing its columns and layout. Together, they let the engine find a row’s bytes and interpret their values.

Fixed-size slots make all three operations arithmetic

microdb uses fixed-size slots. Each slot reserves the space its schema requires, including the maximum permitted string capacity. This makes the position of every field predictable:

OperationSlotted answerCost
Find slot kseek to k × slot_size\(O(1)\), no parsing
Update a fieldoverwrite within the reserved capacity\(O(1)\), nothing moves
Delete a rowset the slot’s deletion marker\(O(1)\), nothing moves
 
CREATE TABLE students (
    id    INT,
    name  VARCHAR(8),   -- capacity reserved here, before any row exists
    gpa   INT
);

UPDATE students SET name = 'benjamin' WHERE id = 2;   -- 8 chars: fits, overwritten in place

In microdb, declaring VARCHAR(8) reserves eight UTF-8 bytes plus a four-byte length prefix in every record. A name that fits can be updated within that reserved area. The next section explains how this choice determines field offsets.

Fixed-size slots keep neighboring rows in place

This 128-byte demonstration block holds five 24-byte student slots. Each slot contains [flag][id][name][gpa]. Insert a row. Delete a row. Rename a row. After each operation, compare the changed bytes with the bytes that retain their positions.

A record page, slot by slot · students(id int, name varchar(8), gpa int)

Each row is one slot: the flag (green, 4 bytes) then fields at computed offsets. Click a slot to select it. Hover over a segment to see its byte arithmetic.

A fresh block is all zeros: five EMPTY slots in this widget. Insert the first student.

Delete ada. Then insert a row to reuse her slot. Rename ben to benjamin: its eight ASCII characters occupy eight UTF-8 bytes, so it fits. Bartholomew exceeds that capacity and is rejected. Other slots keep their positions throughout.

Calculate an address from the slot number and field offset

\[ \text{start}(k) \;=\; k \cdot \text{slot\_size} \] \[ \text{addr}(k, f) \;=\; k \cdot \text{slot\_size} + \text{offset}(f) \]

For students: slot_size = 24, offset(id) = 4, offset(name) = 8, offset(gpa) = 20, so

\[ \text{addr}(3, \text{gpa}) \;=\; 3 \cdot 24 + 20 \;=\; 92 \]

The GPA in slot 3 begins at byte 92: 3 × 24 + 20. No earlier row needs to be parsed.

For this fixed-size layout, a field’s byte address is slot number × slot size + field offset.

Compute field offsets from the schema

Think of a tray with equally sized compartments. A slot reserves one compartment, and field offsets locate items inside it. Map compartment number to slot number and the tray to a block. Actual capacity is measured in bytes, including string length prefixes. A character count alone is insufficient.

CREATE TABLE students (
    id    INT,
    name  VARCHAR(8),
    gpa   INT
);

In microdb, an INT always occupies four bytes. A VARCHAR field also needs a declared byte capacity so the layout can reserve a fixed amount of space. The declaration above reserves eight bytes for each name’s contents.

To read GPA in slot 3, the engine computes 3 × slot_size + offset(gpa). That works because every slot uses the same field offsets. The name field reserves twelve bytes: four for its length and eight for its contents. GPA therefore begins at offset 20 whether the name is ada or benjamin. This reservation is a microdb design choice. Production SQL engines can use variable-length layouts.

Check yourself · drop the 8

Suppose the packed layout stored each name using only the bytes it needed. Which field offset could no longer be computed once for the whole table? What would a GPA lookup need to read first? What would happen if ada were renamed to adelaide?

Show answer

offset(gpa) would depend on the name length in each row, so a lookup would first read that length. Renaming ada to adelaide would require five additional bytes and shift later fields in a packed layout. In microdb’s fixed layout, both names fit within the eight-byte reservation, so the update can happen in place. A name exceeding eight UTF-8 bytes must be rejected.

NumPy’s dtype='U8' makes a related choice by reserving space for eight Unicode characters per element, rather than microdb’s eight UTF-8 bytes. Variable-length layouts avoid reserving every value’s maximum capacity but require other ways to locate fields. PostgreSQL uses variable-length tuples and can move large values to TOAST storage, described below.

Schema records field types. Layout calculates positions.

schema = Schema().add_int_field("id").add_string_field("name", 8).add_int_field("gpa")
layout = Layout(schema) # computes offsets + slot_size
layout.offset("gpa") # 20 layout.slot_size # 24

Reserved string capacity can leave unused space

Internal fragmentation, quantified

Ada’s name occupies three UTF-8 bytes in an eight-byte reservation, leaving five bytes unused. This unused space within an allocated record is internal fragmentation. The reservation makes field addresses predictable but reduces the number of rows that fit in a block. With a 200-byte string capacity, the example schema fits only 19 rows per block3.

A null bitmap records which fields have no value

microdbmicrodb has no NULL. Every field holds a value, initially 0 for an integer or "" for a string. Real datasets can contain missing values. A missing value differs from 0 or "".
Real enginesMany engines use a null bitmap to record which fields have no value. When a null bitmap is present, PostgreSQL stores one bit per column, plus layout and alignment overhead. A null field has no ordinary stored value.4
The DS connectionNULL represents a missing or unknown value. It differs from an integer zero or an empty string, which are present values with their own meanings.5

Store large values outside the main row

Reserved capacity makes updates easy but can waste space. For a very large value, reserving room in every row becomes impractical. The main row can instead hold a reference to bytes stored elsewhere.

Reserving the maximum size in every row becomes impractical for large values such as a two-megabyte essay. PostgreSQL can compress such values and store them separately, leaving a small reference in the main row.

The problemReserving space for a 2 MB essay in every slot would waste substantial space. Fixed reservations suit modest maximum sizes.
Postgres's answerTOAST can compress values or store them in a side table. An external value leaves an 18-byte reference in the main tuple. PostgreSQL’s tuples still have variable lengths.6
The patternReserve fixed space when the maximum value is small. For larger values, store a small reference to external data. Column stores (week 10) and vector storage (week 11) also use this approach.

Follow an essay from inline to external storage

PostgreSQL leaves the value unchanged until the row exceeds about 2 KB. It then tries compression within the row. If the row remains too large, it moves the value to the table's pg_toast side table. The value occupies chunks of about 2,000 bytes, with four chunks per page. A unique index on (chunk_id, chunk_seq) locates these chunks6.

An externally stored PostgreSQL value is represented by an 18-byte reference in the main row. This keeps the main row smaller while allowing a value of up to about 1 GB. PostgreSQL’s variable-length tuple layout differs from microdb’s fixed-size slots6.

RecordPage works one pinned block at a time

RecordPage combines a pinned block from the buffer pool with the table’s Layout. It reads and writes field values by calculating their byte addresses within that block. Its methods also find empty or occupied slots and change their status flags.

What it isRecordPage combines one pinned block with the table's Layout. It translates rp.get_int(3, "gpa") into a read at byte 3 × 24 + 20 = 92.
JobAll record operations within ONE block: read/write a field of slot k, find free slots, flip flags.
Runs onyour Lab 2 pool: it pins its block on construction and unpins on close(). This follows the week 2 pin/unpin contract. The pool cannot evict a block while RecordPage holds its pin.
Key methodsget/set_int, get/set_string (arithmetic + Lab 1 page calls), insert_after / next_after (find EMPTY / find USED), delete (flip to EMPTY).

Mark changed pages dirty so the buffer manager writes them

One ruleEnd every write with set_modified() to mark the buffer dirty. Without this call, the pool treats the page as unchanged. Eviction can then discard the update without writing it to disk.

Deletion marks the slot EMPTY

Deleting a microdb row changes its flag to EMPTY without erasing its field bytes or shrinking the file. Scans skip that slot, and a later insertion can reuse it. Stored bytes may therefore remain recoverable until overwritten. PostgreSQL’s vacuum also reclaims space, but it manages obsolete row versions under MVCC rather than microdb’s single EMPTY flag78.

Scan a table one block at a time

RecordPage finds occupied slots within one block. TableScan extends the search across the file. After the last occupied slot in a block, it releases that block. It opens the next block and continues searching. The scan ends only after it exhausts the last block.

slot = rp.next_after(current_slot) # next USED slot here?
while slot == -1: # exhausted this block
if at_last_block: return False
move_to_block(next); slot = rp.next_after(-1)
current_slot = slot; return True
Hover a line to follow the scan’s transition from one block to the next.

insert() searches for an empty slot before appending a block

First choiceSearch forward from the current slot with insert_after. Reuse an EMPTY slot encountered in this search. Call before_first() first when you want to search from the beginning of the table.
Last resortIf the search reaches the end without finding space, fm.append() adds a zeroed block containing block_size // slot_size empty slots. Zero is the EMPTY flag, so these slots are ready for insertion.
The invariantThe file grows by whole blocks at its end. This simple insertion search does not return to slots before the current position, so it may append even if an earlier slot is empty.

Every row now has an address: the RID

A RID identifies a record’s physical location as (block number, slot number). In this five-slot demonstration, ada is at (0, 0) and the twelfth row is at (2, 1). A live microdb row keeps its location when updated in place. After deletion, another row can reuse that slot, so a RID is not a permanent identity. Lab 6’s index maps field values to RIDs910.

The catalog stores the offsets calculated by Layout. A TableScan can read those catalog rows and reconstruct a layout later. The provided catalog.py is an early test of your record layer because it reads and writes catalog tables through your RecordPage and TableScan.

Define catalog layouts in code to avoid a circular dependency

Reading a table requires its layout, but table layouts are stored in the catalog. To avoid needing the catalog before it can be read, microdb defines the catalog tables’ own schemas in code. This bootstrapping step lets the engine open the catalog and look up layouts for other tables.

Postgres does the same: \d students is a catalog query

Postgrespg_class describes tables and other relations such as indexes and views. pg_attribute describes their columns. The \d students command queries this metadata.11
Catalog rowsCatalog rows describe indexes, views, functions, permissions, and even the catalog tables themselves12.
Why it matters to DSDatabase schema browsers, ORMs such as SQLAlchemy, and database-connected reporting tools obtain metadata from catalogs or metadata APIs. A pandas df.info() call instead describes a DataFrame already in memory.

Return to the opening question

Explain it to a teammate

A row is deleted at RID (0, 1), and another row reuses that slot. Has the address changed? Does it still identify the original student?

Check your explanation

The physical address is unchanged, but its occupant can change. A RID identifies the block and slot that hold a row. A student ID identifies the student. Keep index entries consistent when rows are deleted or moved.

Return to the saved address. Fixed slots locate a row. The layout locates its fields. The scan skips empty slots. The catalog stores the rules for interpreting those bytes. Stable byte positions do not make a RID a permanent identity.

Four points to remember:

  • Fixed-size slots make addresses predictable. The cost is unused reserved space, and values that exceed their field capacity must be rejected.
  • Deletion changes a slot’s flag. Live-row addresses stay fixed. A deleted slot can be reused for another row, so indexes must be updated when rows are deleted or replaced.
  • Large values can be stored separately. PostgreSQL can compress a large value or move it to TOAST storage, leaving a reference in the main row.
  • The catalog stores schemas as data. Its own layouts are defined in code so the engine can open it without first looking up those layouts.

FAQ

Why 4 whole bytes for a flag that stores 0 or 1?

microdb uses an integer flag because Page already reads and writes four-byte integers. Production engines combine flags, null bitmaps, and metadata in page headers and a compact slot directory4. This reduces space for some metadata. PostgreSQL also uses about 23 header bytes per row, compared with microdb’s four-byte flag4.

Does reserving maximum capacity for every varchar waste space?

Yes. Reserving the full capacity makes microdb’s field offsets constant and allows in-place updates within that capacity. PostgreSQL stores variable-length tuples and uses a slot directory to locate them. TOAST handles large values. These designs make different tradeoffs among space use, addressing, and update work4.

What if a table needs more rows than one file can hold?

microdb uses one file per table and does not need to split files at the lab’s scale. PostgreSQL splits a large table into segment files, normally 1 GB each. Its storage layer translates logical block numbers into the appropriate segment and position13.

Does the catalog slow everything down? Every query needs layouts!

Catalog lookups have a cost. Production engines cache metadata. PostgreSQL’s relcache is one example. microdb scans the catalog for each get_layout call to keep the implementation simple. If the catalog blocks remain in the buffer pool, those scans avoid additional disk reads14.
