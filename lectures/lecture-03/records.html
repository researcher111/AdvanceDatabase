Record Layout & the Catalog

Bytes become rows, files become tables, and the database starts describing itself.
Daniel G. Graham · UVA School of Data Science

Two weeks ago you placed the ada row into a page by hand, byte by byte. Today we make that placement systematic: a schema computes every field's offset, rows live in fixed-size slots inside the heap file, a scan walks every row of a table through your buffer pool, and the layout rules themselves get stored in tables, because in a relational system even the schema is data. Thursday, microdb learns what a row is.

Bytes don't know they're rows

What tight packing costs

Worked out in bytes: renaming ben in a packed page shifts every later byte in the block, and anything that remembered where those bytes lived is now lying.

OperationPacked (Lab 1 style)What breaks
Update ben → benjaminshift cyd, dee… 5 bytes rightevery saved position after byte 30; a full-block rewrite
Delete adaeither shift everything left, or leave a 15-byte hole no one trackscompaction cost, or unusable fragments
Find row #4walk from byte 0, parsing every record on the wayO(row number) just to address a row

The three operations a layout must survive

The fix every row store converges on: fixed-size slots. Reserve the maximum bytes each record could need, all records identical, and the three cursed operations become arithmetic:

OperationSlotted answerCost
Find slot kseek to k × slot_sizeO(1), no parsing
Update a fieldoverwrite in place; capacity was pre-reservedO(1), nothing moves
Delete a rowflip the slot's in-use flagO(1), nothing moves

Drive a record page

Here is one 128-byte block wearing the students schema: five 24-byte slots, each [flag][id][name][gpa]. Insert the pinned students, delete one, rename one, and watch that nothing ever moves.

A record page, slot by slot · students(id int, name varchar(8), gpa int)

Each row is one slot: the flag (green, 4 bytes) then fields at computed offsets. Click a slot to select it; hover any segment to see its byte arithmetic.

A fresh block is all zeros: five EMPTY slots. Insert the first student.

Delete ada, then insert again: the new row lands in her old slot. Rename ben to benjamin: exactly 8 chars, fits his reserved capacity. Try bartholomew and the layout says no. That refusal is the price of O(1).

The arithmetic underneath

slot k starts at            k × slot_size
field f of slot k lives at  k × slot_size + offset(f)

students: slot_size = 24,  offset(id) = 4,  offset(name) = 8,  offset(gpa) = 20

  → gpa of slot 3  =  3 × 24 + 20  =  byte 92.   No parsing. No searching.

Every address in this layer is one multiply and one add. That's what "structured" means to a storage engine.

Schema → Layout

Two small classes carry it all

schema = Schema().add_int_field("id").add_string_field("name", 8).add_int_field("gpa")
layout = Layout(schema) # computes offsets + slot_size
layout.offset("gpa") # 20 layout.slot_size # 24
Hover a line: this split (declared schema vs computed layout) recurs in every engine.

The worked map, byte by byte

BytesHoldsWhy there

slot_size = 24 → a 4 KB block holds 170 students, with 16 bytes left over. Thursday's measurement makes you compute (then prove) this for three different schemas.

Check yourself · a fresh schema

Run the same arithmetic on courses(cid int, title varchar(12), credits int): the offset of each field, the slot size, and rows per 4 KB block. (Same rules: 4-byte flag first, ints are 4 bytes, a varchar reserves 4 + capacity.)

Show answer

Offsets: cid at 4 (after the flag), title at 8, credits at 8 + (4 + 12) = 24. Slot size 4 + 4 + 16 + 4 = 28 bytes; ⌊4096 / 28⌋ = 146 rows per block (8 bytes left over). If you got 150, you forgot the flag; the most common Thursday bug, and the tests check offsets before anything else.

The price: air in every slot

Internal fragmentation, quantified

ada's name is 3 chars in a 8-char reservation: 5 bytes of air. Every varchar carries its worst case everywhere. That waste inside allocated space is internal fragmentation: the deliberate rent paid for O(1) addressing. A bio varchar(200) schema fits only 19 rows per block; whether that rent is fair depends entirely on how full a typical value runs.

the rent calculator · schema (id int, name varchar(?), gpa int), 4 KB block

You are the schema designer. Drag the capacity you reserve and how long a typical value actually runs; the block responds. Every number is the offset arithmetic from the slide above.

Drag capacity to 200 with short typical values and the block is mostly air: 170 rows per block collapses toward 19, and Thursday's measurement (59 vs 527 blocks for the same 10,000 rows) is this slider, felt through a table scan. Rent is fair only when typical fill is high.

What about NULL?

microdbducks the question: every field always has a value (0, ""). Honest for a teaching engine; real data isn't so tidy.
Real enginesa null bitmap per record: one bit per column, stored beside the flag. NULL costs a bit, not a field's bytes, and reading a field first checks its bit.
The DS connectionthis is why NULL and 0 and "" are genuinely different things in SQL: the bitmap distinguishes "absent" from any value your bytes could spell.

And truly variable data? TOAST

The problema 2 MB essay can't reserve worst-case capacity in every slot; reservation only works when maxima are modest.
Postgres's answerTOAST: big values move to a side table (compressed, chunked); the slot keeps an 18-byte pointer. The row stays fixed-ish; the elephant lives elsewhere.
The patternfixed where you can, indirection where you must, the same trick you'll see again in column stores (week 10) and vector storage (week 11).

Deletion is a bit flip

A deleted row's bytes are still on disk; the slot is a tombstone waiting for reuse, not a hole. Nothing compacts, nothing shifts, scans simply skip EMPTY flags. This is why "deleted" data is recoverable in forensics, why DELETE doesn't shrink files, and why real engines need a vacuum process: all one design decision, visible in your 24-byte slots.

TableScan: the whole table

next(), annotated

slot = rp.next_after(current_slot) # next USED slot here?
while slot == -1: # exhausted this block
if at_last_block: return False
move_to_block(next); slot = rp.next_after(-1)
current_slot = slot; return True
Hover a line: this dozen lines is most of Thursday's thinking.

insert(): when every slot is full

First choicereuse: insert_after hunts forward for any EMPTY slot; tombstones get recycled before the file grows.
Last resortgrowth: every block full → fm.append() hands back a fresh zeroed block, which is five EMPTY slots by construction. Lab 1's zero-fill was load-bearing all along.
The invariantfiles grow by whole blocks, only at the end, only when truly full; Thursday's harness counts your blocks to check exactly this.

Every row now has an address: the RID

A row's identity in the storage engine is its RID: (block #, slot #): ada is (0, 0), row twelve is (2, 1). Fixed slots make RIDs stable: updates and deletes move nothing, so the address keeps working. File this away carefully: an index (week 6) is nothing but a map from values to RIDs.

Recap & next time

Three ideas from today, all of which the rest of the engine will lean on.

  • Fixed slots buy O(1) with wasted air. Find/update/delete became one multiply and one add, paid for by internal fragmentation and a refusal to store "bartholomew" in an 8-char field.
  • Deletion is a flag, addresses are stable. Tombstones recycle, nothing shifts, and every row keeps a permanent RID, the hook indexes will hang from in week 6.
  • The schema is data. Layouts round-trip through ordinary tables, one hardcoded bootstrap breaks the chicken-and-egg, and your scan's first customer is the database's own self-description.

FAQ

Why 4 whole bytes for a flag that stores 0 or 1?

Alignment and honesty: microdb's Page speaks ints, so the flag is an int. Real engines pack flags, null bitmaps, and bookkeeping into a per-page header plus a compact slot directory; same idea, tighter belt. (Postgres spends ~23 bytes per row on headers; our 4 is shy.)

Isn't reserving max capacity for every varchar wasteful?

Yes, deliberately. It's the rent for in-place updates and stable addresses. Postgres actually stores varchars variably within the page (via a slot directory) and pays with extra indirection; TOAST handles the truly huge. The tradeoff triangle (space, address stability, update cost) has no free corner.

What if a table needs more rows than one file can hold?

microdb: one file per table, and Python's file size limit is nobody's problem at our scale. Postgres: tables are split into 1 GB segment files, invisible above the storage layer; the block abstraction doesn't care how many OS files stand behind it.

Does the catalog slow everything down? Every query needs layouts!

It would, so real engines cache catalog entries in memory aggressively (Postgres's "relcache"). microdb re-scans the catalog on each get_layout, which is honest, measurable, and exactly the kind of thing the buffer pool quietly rescues.
