Record Layout & the Catalog

Lab 1 packed rows end to end, so one rename shifts every byte after it: how does a database find, update, and delete rows without ever moving one?
Daniel G. Graham · UVA School of Data Science

Two weeks ago you placed the ada row into a page by hand, byte by byte, and that packing breaks the moment ben becomes benjamin: every byte after him shifts, and every saved position behind him points at the wrong data. Today we make that placement systematic: a schema computes every field's offset, rows live in fixed-size slots inside the heap file, a scan walks every row of a table through your buffer pool, and the layout rules themselves get stored in tables, because in a relational system even the schema is data1. Thursday, microdb learns what a row is.

Companion reading: Sciore, Database Design and Implementation, ch. 6 (record management) & ch. 7 (metadata)2 · how a production engine does it: PostgreSQL's page layout docs and system catalogs.

Today's plan

Quiz 2 first (the buffer pool, 10 min), then the layer that turns last week's cache of anonymous bytes into tables.

Lab 1 packed rows end to end. Rename ben to benjamin and every byte after him shifts, every saved position behind him is wrong, and finding row 4 means parsing rows 1 to 3 first. SQL never mentioned any of this.

Today's claim: a table is two things. A file on disk, cut into fixed-size slots that each hold one row. And a few rows in a special table, the catalog, that record the table's name, its columns, and where each column's bytes sit inside a slot. Nothing else.

Packed rows break the moment one row changes

Worked out in bytes: renaming ben in a packed page shifts every later byte in the block, and any saved position that pointed at those bytes now points at the wrong data.

OperationPacked (Lab 1 style)What breaks
Update ben → benjaminshift cyd, dee… 5 bytes rightevery saved position after byte 30 is now wrong, and the whole rest of the block has to be rewritten to make room for 5 extra bytes
Delete adaeither shift everything left, or leave a 15-byte hole no one tracksshifting means rewriting the rest of the block (compaction) and invalidating every saved position; leaving the hole means those 15 bytes are lost, because nothing records that they are free
Find row #4walk from byte 0, parsing every record on the waythe cost of reaching a row grows with its row number: there is no way to know where row 4 starts without reading rows 1 to 3 first

Fixed-size slots make all three operations arithmetic

The fix every row store converges on: fixed-size slots. Reserve the maximum bytes each record could need, all records identical, and the three operations from the table above become arithmetic:

OperationSlotted answerCost
Find slot kseek to k × slot_size\(O(1)\), no parsing
Update a fieldoverwrite in place; capacity was pre-reserved\(O(1)\), nothing moves
Delete a rowflip the slot's in-use flag\(O(1)\), nothing moves

In a slotted page, nothing ever moves

Here is one 128-byte block wearing the students schema: five 24-byte slots, each [flag][id][name][gpa]. Insert the pinned students, delete one, rename one, and watch that nothing ever moves.

A record page, slot by slot · students(id int, name varchar(8), gpa int)

Each row is one slot: the flag (green, 4 bytes) then fields at computed offsets. Click a slot to select it; hover any segment to see its byte arithmetic.

A fresh block is all zeros: five EMPTY slots. Insert the first student.

Delete ada, then insert again: the new row lands in her old slot. Rename ben to benjamin: exactly 8 chars, fits his reserved capacity. Try bartholomew and the layout says no. That refusal is the price of \(O(1)\).

Every address is one multiply and one add

\[ \text{start}(k) \;=\; k \cdot \text{slot\_size} \] \[ \text{addr}(k, f) \;=\; k \cdot \text{slot\_size} + \text{offset}(f) \]

For students: slot_size = 24, offset(id) = 4, offset(name) = 8, offset(gpa) = 20, so

\[ \text{addr}(3, \text{gpa}) \;=\; 3 \cdot 24 + 20 \;=\; 92 \]

The gpa of slot 3 is at byte 92. No parsing. No searching.

Every address in this layer is one multiply and one add. That's what "structured" means to a storage engine.

The schema fixes every offset before any row exists

CREATE TABLE students (
    id    INT,
    name  VARCHAR(8),
    gpa   INT
);

You have typed a statement like this many times, and the 8 was probably a number you picked so the database would stop complaining. Notice what SQL does not ask for: INT comes with no size, and neither does gpa. Only the string demands a number. Why would a database need to know, before a single row exists, the longest name it will ever store?

The answer is the arithmetic on the previous slide. To find gpa in slot 3 the engine computes 3 × slot_size + offset(gpa), and it can only do that if offset(gpa) is one fixed number for every row. An INT is always 4 bytes, so the engine already knows how far to step over it. A name could be any length, so the engine makes you promise one: reserve 8 bytes for every name, and now gpa starts at byte 20 in every slot, whether the name is ada or benjamin. The 8 is not a rule about names. It is a promise to the layout.

Check yourself · drop the 8

Suppose SQL let you write name VARCHAR with no length, and the engine stored each name using exactly as many bytes as it needed. Which number in today's layout could no longer be computed once for the whole table? What would every gpa lookup have to do instead, and what would happen to the row when ada was renamed to adelaide?

Show answer

offset(gpa) stops being a constant: it becomes 8 plus the length of whatever name is in that slot. So every gpa read would first have to read the name's length and add it, per row, which is the parsing this lecture set out to eliminate. And renaming ada to adelaide would need five more bytes in the middle of the slot, pushing gpa and every later field to the right: the shift-everything update from the opening table. The length in VARCHAR(8) is what lets the engine refuse that rename cheaply instead of rewriting the block.

You have met this trade before. NumPy's fixed-width string dtype, dtype='U8', reserves 8 characters per element for exactly the same reason, and pandas' object columns are the variable-length alternative: flexible, and slower to scan. Postgres offers both: VARCHAR(n) and a plain TEXT type with no limit, which it can afford because its pages do not use fixed slots; the TOAST slide at the end of this section shows what it pays instead.

Schema declares, Layout computes: one place to be right

schema = Schema().add_int_field("id").add_string_field("name", 8).add_int_field("gpa")
layout = Layout(schema) # computes offsets + slot_size
layout.offset("gpa") # 20 layout.slot_size # 24
Hover a line: this split (declared schema vs computed layout) recurs in every engine.

Four fields, 24 bytes, 170 students per block

BytesHoldsWhy there
0–3in-use flag (0 empty / 1 used)every slot needs a marker saying whether it holds a live row, so that deleting a row can be a single write to this flag (see the flag lifecycle below)
4–7id (int)the first field in the schema goes right after the flag, so its offset is 4
8–19name (4-byte len + 8 capacity)4 bytes record the actual length, then 8 bytes are reserved for the longest allowed name; the field takes 12 bytes no matter how short the name is
20–23gpa (int)name starts at 8 and takes 12 bytes, so the next field starts at 8 + 12 = 20

170 students per 4 KB block: slot_size = 24, with 16 bytes left over. Thursday's measurement makes you compute (then prove) this for three different schemas.

Check yourself · a fresh schema

Run the same arithmetic on courses(cid int, title varchar(12), credits int): the offset of each field, the slot size, and rows per 4 KB block. (Same rules: 4-byte flag first, ints are 4 bytes, a varchar reserves 4 + capacity.)

Show answer

Offsets: cid at 4 (after the flag), title at 8, credits at 8 + (4 + 12) = 24. Slot size 4 + 4 + 16 + 4 = 28 bytes; ⌊4096 / 28⌋ = 146 rows per block (8 bytes left over). If you got 150, you forgot the flag; the most common Thursday bug, and the tests check offsets before anything else.

Every varchar carries its worst case in every slot

Internal fragmentation, quantified

ada's name is 3 chars in a 8-char reservation: 5 bytes of air. Every varchar carries its worst case everywhere. That waste inside allocated space is internal fragmentation: the deliberate rent paid for \(O(1)\) addressing3. A bio varchar(200) schema fits only 19 rows per block; whether that rent is fair depends entirely on how full a typical value runs.

Rent is fair only when typical fill is high

the rent calculator · schema (id int, name varchar(?), gpa int), 4 KB block

You are the schema designer. Drag the capacity you reserve and how long a typical value actually runs; the block responds. Every number is the offset arithmetic from the slide above.

Drag capacity to 200 with short typical values and the block is mostly air: 170 rows per block collapses toward 19, and Thursday's measurement (59 vs 527 blocks for the same 10,000 rows) is this slider, felt through a table scan. Rent is fair only when typical fill is high.

NULL costs a bit, not a field's bytes

microdbhas no NULL at all: every field always holds a value (0 for an int, "" for a string). That is acceptable for a teaching engine, but real data has missing values, and "missing" is not the same as 0 or "".
Real enginesa null bitmap per record: one bit per column, stored beside the flag. NULL costs a bit, not a field's bytes, and reading a field first checks its bit4.
The DS connectionthis is why NULL and 0 and "" are genuinely different things in SQL: the bitmap distinguishes "absent" from any value your bytes could spell5.

Huge values move out; the slot keeps a pointer

The problema 2 MB essay can't reserve worst-case capacity in every slot; reservation only works when maxima are modest.
Postgres's answerTOAST: big values move to a side table (compressed, chunked); the slot keeps an 18-byte pointer6. The row itself stays small and close to fixed-size; the big value lives in the side table.
The patternreserve fixed space when the maximum is modest, and store a small pointer to data kept elsewhere when it is not; the same trick appears again in column stores (week 10) and vector storage (week 11).

RecordPage works one pinned block at a time

JobAll record operations within ONE block: read/write a field of slot k, find free slots, flip flags.
Runs onyour Lab 2 pool: it pins its block on construction and unpins on close(). This is the pin/unpin contract from week 2, now used by real code: while a RecordPage is working on a block, the pool cannot evict it.
Key methodsget/set_int, get/set_string (arithmetic + Lab 1 page calls), insert_after / next_after (find EMPTY / find USED), delete (flip to EMPTY).

Every write ends with set_modified() or it is lost

One ruleevery write ends with set_modified(), which marks the buffer dirty. Skip it and the pool believes the frame is unchanged, evicts it without writing it to disk, and the write is lost.

One flag per slot tracks EMPTY and USED

StateFlagField bytes holdWho moves it
Fresh block0 (EMPTY)all zeros: append hands you a zeroed block, and 0 is the EMPTY flag, so a fresh block is already a valid page of empty slots with no setupnobody; the zero-fill does it
After insert_after1 (USED)whatever bytes were in the slot before; the caller must write every field nextinsert_after writes 1 to the flag, then the caller sets the fields
After delete0 (EMPTY)the old data, untouched; only the flag changeddelete writes 0 to the flag and touches nothing else
After re-insert1 (USED)the previous row's bytes, until the caller overwrites them; this is why insert marks the slot first and the caller writes the fields secondinsert_after finds the EMPTY slot and reuses it

Deletion is a bit flip

A deleted row's bytes are still on disk; the slot is a tombstone waiting for reuse, not a hole. Nothing compacts, nothing shifts, scans simply skip EMPTY flags7. This is why "deleted" data is recoverable in forensics, why DELETE doesn't shrink files, and why real engines need a vacuum process: all one design decision, visible in your 24-byte slots8.

TableScan walks the whole table through one frame

slot = rp.next_after(current_slot) # next USED slot here?
while slot == -1: # exhausted this block
if at_last_block: return False
move_to_block(next); slot = rp.next_after(-1)
current_slot = slot; return True
Hover a line: this dozen lines is most of Thursday's thinking.

insert() recycles tombstones before it grows the file

First choicereuse: insert_after hunts forward for any EMPTY slot; tombstones get recycled before the file grows.
Last resortgrowth: every block full → fm.append() hands back a fresh zeroed block, which is five EMPTY slots by construction. This is why Lab 1's append had to zero-fill new blocks: 0 is the EMPTY flag, so a zeroed block reads as five empty slots with no extra setup.
The invariantfiles grow by whole blocks, only at the end, only when truly full; Thursday's harness counts your blocks to check exactly this.

Every row now has an address: the RID

A row's identity in the storage engine is its RID: (block #, slot #): ada is (0, 0), row twelve is (2, 1). Fixed slots make RIDs stable: updates and deletes move nothing, so the address keeps working9. File this away carefully: an index (week 6) is nothing but a map from values to RIDs10.

The offsets are the ones you computed in Layout, stored as data, readable by a TableScan, reconstructable into a Layout. The catalog is the first user of your record layer: in the lab catalog.py is provided complete, and it reads and writes its own tables through your RecordPage and TableScan, so it works exactly when your code does.

The catalog reads itself through hardcoded layouts

There is a loop hiding here. To read any table you need its layout, and layouts live in field_catalog. But field_catalog is itself a table, so to read it you would need its layout, which is stored in field_catalog. The way out is a small bootstrap: the layouts of the catalog tables themselves are computed in code, never read from disk. That handful of hardcoded offsets is enough to open the catalog, and everything else is read from it.

Postgres does the same: \d students is a catalog query

Postgrespg_class (one row per table) and pg_attribute (one per column); \d students is a catalog query, not magic11.
Everything is a rowindexes, views, functions, permissions, even the catalog's own tables: all rows in catalog tables12. One mechanism, everywhere.
Why it matters to DSevery schema-introspection tool you've used (df.info()-style table explorers, ORMs such as SQLAlchemy that map tables to Python classes, business-intelligence dashboards) is reading these tables. Now you know what they're reading.

Recap & next time

Three ideas from today, all of which the rest of the engine will lean on.

  • Fixed slots buy \(O(1)\) with wasted air. Find/update/delete became one multiply and one add, paid for by internal fragmentation and a refusal to store "bartholomew" in an 8-char field.
  • Deletion is a flag, addresses are stable. Tombstones recycle, nothing shifts, and every row keeps a permanent RID, the address that indexes will point to in week 6.
  • The schema is data. A table's layout is written to the catalog as ordinary rows and read back into a Layout; the catalog's own layouts are hardcoded so that reading the catalog does not first require reading the catalog; and the first code to use your scan is the catalog itself.

FAQ

Why 4 whole bytes for a flag that stores 0 or 1?

Simplicity: microdb's Page reads and writes whole 4-byte ints, so the flag is stored as an int. Real engines pack flags, null bitmaps, and bookkeeping into a per-page header plus a compact slot directory4; the same idea with less waste. (Postgres spends ~23 bytes per row on headers, so our 4 bytes is modest by comparison4.)

Isn't reserving max capacity for every varchar wasteful?

Yes, deliberately. It's the rent for in-place updates and stable addresses. Postgres actually stores varchars variably within the page (via a slot directory) and pays with extra indirection; TOAST handles the truly huge4. No layout gets all three of compact space, stable addresses, and cheap updates; every design gives up part of one.

What if a table needs more rows than one file can hold?

microdb: one file per table, and Python's file size limit is nobody's problem at our scale. Postgres: tables are split into 1 GB segment files, invisible above the storage layer13; the block abstraction doesn't care how many OS files stand behind it.

Does the catalog slow everything down? Every query needs layouts!

It would, so real engines cache catalog entries in memory aggressively (Postgres's "relcache"). microdb re-scans the catalog on each get_layout, which is slow but simple, and in practice the catalog blocks stay resident in the buffer pool, so the re-scan costs a few pins and no disk reads14.
