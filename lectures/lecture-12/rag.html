RAG as a Systems Problem

Finding a passage is only the start. Can you give the model that passage and check which claims it supports?

How to give a model access to your data

Consider an open-book exam. A retriever selects pages. A generator writes an answer from those pages. Page references make the answer checkable, but selected pages do not guarantee a correct explanation. RAG supplies selected evidence at question time. Compare this approach with training on documents or sending all documents in every prompt.

Retrieval turns the problem into a database workload

Retrieval lets you update source documents and their index without retraining the model. Each question sends only selected passages to the generator. Retaining source identifiers also gives the answer a citation trail that can be checked.

Build a vector with hashed words

Lecture 11 introduced models that use surrounding words to create embeddings. Lab 10 uses a simpler method: hashed bag-of-words. It counts words without keeping their order. A hash function maps each word to a repeatable number. The remainder after division by the vector width selects a position, called a bucket.

Think of the vector as a row of numbered boxes. Each word’s hash chooses a box for its contribution. Different words can choose the same box. This is a hash collision, and it can make unrelated texts appear similar.

Predict whether the two texts will have similar vectors. Then try the collision and synonym examples. This demonstration uses the lab’s actual hash, word filtering, weighting, and normalization rules. Eight buckets make the mechanism visible. The lab uses 2,048 buckets.

Words → counts → hash buckets → normalized vector → comparison

Worked example: compare database log with database log replay using eight buckets.

WordHash remainder modulo 8Count in each text where it occursContribution
database411
log711
replay311

The query puts 1 in buckets 4 and 7. The passage also puts 1 in bucket 3. Normalize each vector by dividing every coordinate by its magnitude. Their dot product is approximately 0.816.

The lab uses 1 / (1 + ln(count)) once per distinct word. Here, ln is the natural logarithm. A word that occurs twice contributes about 0.591, not 2. Contributions from different words add when their hashes select the same bucket.

With eight buckets, car and banana both select bucket 1. Their one-word vectors have similarity 1 despite their different meanings. With sixteen buckets, they select buckets 9 and 1, so similarity becomes 0.

Enable JavaScript to edit the texts and step through each calculation.

Eight-bucket example: database log gives weights of 1 in buckets 4 and 7. The normalized values are approximately 0.707 each. database log replay gives weights of 1 in buckets 3, 4, and 7. Its normalized values are approximately 0.577 each. The dot product is approximately 0.816.

Collision: car and banana both hash to bucket 1 with eight buckets. Their similarity is 1. With sixteen buckets, their positions differ and similarity is 0. More buckets can separate collisions. They do not teach the system that car and automobile are synonyms.

Lab rule: lowercase the text, keep ASCII letter sequences, and remove the supplied stop words. Count each retained word. Add 1 / (1 + ln(count)) to the bucket selected by MD5(word) % DIM. Normalize a nonzero vector. Empty input produces a zero vector.

Keep this idea: hashing groups words by a numeric rule, not by meaning. More buckets can reduce collisions, but they do not resolve different words with the same meaning.

Missing evidence limits the answer



Retrieval determines which source passages the model can use. If a passage is missing from the prompt, a better prompt cannot make the model quote it. Generation still needs evaluation: a model can misread, ignore, or misrepresent passages that were retrieved correctly.

Retrieval quality is measurable: two numbers, twelve questions



Maya compares retrieval settings with the same questions. First, check whether each result contains a labeled relevant source. Then record the first relevant source’s rank. These measurements describe different parts of retrieval quality.




  Count a small example before using the formula
  
Three questions have their first relevant source at rank 1, rank 3, and outside the top 3. Predict each question’s hit and reciprocal-rank score. Suppose the second question’s relevant source moves from rank 3 to rank 1. Do both metrics change?

  
Check your explanation
The hit scores are 1, 1, 0, giving hit@3 = 2/3. Reciprocal ranks are 1, 1/3, 0, giving MRR@3 = 4/9 ≈ 0.44. Moving the second relevant source to rank 1 improves MRR but leaves hit@3 unchanged. This is a toy three-question example, separate from the twelve-question measurements below.





Two numbers from one hand-labeled set





The evaluation set has 12 questions. Each question has manually labeled relevant document IDs. This set produces hit@k and MRR, the mean reciprocal rank.8

\[ \text{hit@}k \;=\; \frac{\#\{\text{questions with a relevant doc in the top } k\}}{\#\text{questions}} \qquad \text{(did it come back?)} \]
\[ \text{MRR} \;=\; \frac{1}{|Q|} \sum_{q \in Q} \frac{1}{\text{rank}_q} \qquad \text{(how high?)} \]

Here, rankq is the position of the first relevant source among returned chunks. Ranks 1, 2, and 3 score 1.0, 0.5, and approximately 0.33. The lab retrieves three chunks, so it measures MRR@3. A relevant source outside those chunks scores 0. Average all question scores, including misses. Multiple chunks from one source do not give a question multiple hits.

Vocabulary mismatchTwo questions can ask for the same information while using different words. A bag-of-words embedder cannot reliably recognize that relationship.

  
Why it happensThe buffer-pool document shares few content words with “popular pages in memory.” Its low score reflects limited word overlap rather than whether it answers the question.

  
The fixA learned embedding model can place paraphrases near one another. In the lab design, you replace the embed() function and rebuild the vectors. Evaluate the new model to check which failures it fixes.





A retrieved passage may still be ranked or used poorly




  
Lost in the middleLiu et al. tested evidence use at different prompt positions. The tested models used relevant evidence less reliably in the middle of a long context. Try fewer chunks or a different order. Evaluate whether the change improves results.1011

  
Right doc, wrong rankA relevant chunk at rank 3 counts as a hit@3, just as one at rank 1 does. MRR distinguishes them: rank 3 contributes 0.33, while rank 1 contributes 1.0. A reranker can change a poor ranking by scoring the question and chunk together.





Keep the index current and check answer support




  
Stale indexRetrieval can return outdated information when a document changes but its chunks or vectors remain unchanged. Rebuild affected records after an update. Record document and index versions to detect stale entries.

  
Confident grounding failureA model may give a confident answer even when the retrieved chunks do not support it. Evaluate unsupported answers. Calibrate score thresholds with your data. Allow the generator to state that the sources do not answer the question.

  
Embedding driftQuery and document vectors must use a compatible embedding model. When changing models, record the new model version. Rebuild the corpus vectors. Switch queries to the compatible new index. Do not compare vectors from incompatible embedding spaces.

Three additions can improve the lab pipeline. Each adds work. Use evaluation results to decide whether an addition helps your corpus.

Hybrid searchRun BM25 keyword search. Run vector search. Merge the ranked results.13The methods search the same corpus. Keyword search can find exact identifiers, such as error codes. Vector search can find paraphrases. Evaluate whether merging the results improves retrieval.

FAQ



Context windows keep growing: will long context kill RAG?


A longer context window lets you send more text, but does not guarantee that the model will use every passage effectively. Cost, latency, and evidence selection still matter. Compare full-context and retrieval approaches on your own corpus when both are practical.11



Why not fine-tune on our documents instead?


Fine-tuning can change model behavior. It does not provide dependable passage lookup or source citations. Retrieval helps answers reflect changing documents. A system can combine fine-tuning for behavior with retrieval of current evidence.3



Is the hashed bag-of-words embedder just a toy?


It uses the same feature-hashing idea as scikit-learn’s HashingVectorizer. Its vocabulary limitation is intentional: the lab makes that failure visible and measurable. Replacing embed() with a learned model keeps the pipeline interfaces, but requires rebuilding the index and rerunning the evaluation.9



What should our project's eval set look like?


Write at least 25 questions that users of your corpus would ask. Label each question with the source passages that answer it. Compare at least two configurations. Report retrieval quality and answer quality. Exclude the partner team’s questions from tuning. Report their results alongside your own.
