The Analytics Stack

Analytics reads a few columns of every row, and everything you built assumes the opposite: why the layout flips, and what the flip buys.
Daniel G. Graham · UVA School of Data Science

The engine you built reads and writes one whole row at a time, and an analyst's query touches two columns of every row: Act II opens with the confession that everything in microdb assumed a workload (many small reads and writes, each of one whole row) that analytics simply doesn't have. For that shape, storing rows together is the wrong bet. Flip the layout ninety degrees and a cascade follows: columns compress absurdly well, scans vectorize, filters push into file formats, and the modern stack (DuckDB on your laptop, warehouses in the cloud, Parquet as the lingua franca) falls out of one decision. Thursday you measure all of it.

Neither layout wins; the industry runs both

Neither layout is "better"; they're answers to different questions. The industry's standard architecture is both: OLTP systems run the business, and their data flows into columnar systems that analyze it.

Columns unlock three tricks, and they compound

Storing columns together is not the speedup by itself. It makes three further tricks possible, and they compound. Each one fails in row storage, where a row's mixed types (an integer, then a string, then a float) sit next to each other every few bytes:

TrickNeedsBuys
compressionruns of same-typed, similar valuesfewer blocks to read, which is the cost measure from week 1
vectorized executioncontiguous arrays of one typemore values processed per CPU second, because the engine runs a tight loop over an array instead of interpreting one row at a time
stats-based skippingper-chunk min/maxwhole chunks never read: if a chunk's stored min and max show that no row in it can match the filter, its blocks are skipped

Columns are boring, so they compress: compression is performance

a column is a run of SAME-TYPED, often-similar values, a compressor's dream:

  month:    1 1 1 1 2 2 2 ...        run-length:  (1×4)(2×3)...      ~50x smaller
  payment:  card card cash card...   dictionary:  {card:0, cash:1} + bits
  ride_id:  0 1 2 3 4...             delta:       start + (+1 +1 +1...)

row storage interleaves types every few bytes; none of these tricks survive it.
smaller files = fewer blocks = faster scans: compression IS performance here.

The pattern in the data picks the encoding

compress one column · 24 rides, three encodings

Pick a column; the widget shows its raw values, applies the encoding that fits its shape, and counts the bytes. The encoding is chosen by the pattern in the data: sorted-and-runny, low-cardinality, or sequential.

These three cover most real columns, and they compound: Parquet dictionary-encodes then run-length-encodes the dictionary codes2. A 20-column fact table routinely shrinks 10–20×, and every saved byte is a block the scan never reads3.

Vectorized execution pays interpreter overhead once per 2048 rows

microdb (Volcano)DuckDB (vectorized)
Unit of workone row per next()a vector of ~2048 values per call
Interpreter overheadpaid per rowpaid once per 2048 rows, so the cost per row is close to nothing4
CPU behaviorone branch per row and scattered memory accesses, so the CPU's caches and branch predictor help littletight loops over arrays, which CPUs run fastest and which SIMD instructions (one instruction applied to several values at once) speed up further1
The modelthe same: before_first/next/get, except that each next() returns a batch of values instead of one row. The iterator model you built in microdb still applies.

Check yourself · predict Thursday's number

rides: 60,000 rows, 12 columns, ~8 bytes per value. Compute the bytes that must move for SELECT avg(fare) FROM rides under (a) row layout, (b) column layout, and (c) column layout with a month = 12 filter over 12 equal hive partitions (one folder per month). What's the (a)-to-(c) ratio?

Show answer

(a) all of it: \(60{,}000 \times 12 \times 8 \approx\) 5.8 MB. (b) one column: \(60{,}000 \times 8 \approx\) 0.48 MB, 12× less. (c) one column of one partition: \(0.48\ \text{MB} / 12 \approx\) 40 KB, roughly 96× less than (a), before compression shrinks it further. Thursday's measured 100×+ is this arithmetic with real files and real codecs; you can now predict a benchmark before running it, which is the whole point of a cost model.

The analyst's whole stack is one pip install

DuckDBa full columnar OLAP engine in a Python library, "SQLite for analytics." No server, queries CSV/Parquet/pandas frames in place5. Thursday's lab engine.
Parquetthe columnar file format everyone reads and writes: column chunks + per-chunk stats + dictionary/RLE compression, self-describing schema6. It plays the role CSV once played as the universal exchange format, but with types, compression, and per-chunk statistics built in.

A partition folder per month lets a filter open one folder, not twelve

Partitioningthe rows for each value of a column stored in their own folder (month=12/…), so a WHERE month = 12 clause means the engine opens one folder and never touches the other eleven7; you'll watch EXPLAIN say Scanning Files: 1/12.

SQL and pandas hand the same dataframe back and forth

DuckDB and pandasDuckDB can run SQL directly against a pandas dataframe and hand the result back as a dataframe8. A pipeline can therefore use SQL for one step and pandas for the next, passing the same data between them.

The cloud separates where data rests from where queries run

Everything DuckDB does on your laptop, the cloud does on rented hardware over shared storage; same columnar bones, plus one architectural move DuckDB doesn't need: separating where data rests from where queries run.

Warehouse, lake, lakehouse: the same columnar bones, resized

SystemWhat it isThe defining trick
Snowflake / BigQuery / Redshiftcloud data warehouses: columnar engines, elastic compute9separation of storage and compute: the data rests permanently in object storage, and a separate cluster of machines is started when queries arrive, billed for the work it does, and shut down when it is idle10
The data lakea collection of Parquet files sitting in S3-style object storage, with no database engine attached to themthe storage is as cheap as storage gets, and because the files are in an open format, any engine (DuckDB, Spark, a warehouse) can read them
The lakehouse (Delta, Iceberg)the same lake files plus a transactional metadata layer on topACID commits, schema evolution, and time travel over plain Parquet files11. All three rest on a manifest: a small metadata file that lists exactly which Parquet files make up the table right now, so a commit is just a new manifest and readers never see a half-written table12

A lakehouse is your catalog plus WAL over plain files

The lakehouse's manifest-plus-files design is a small transactional layer that turns a folder of plain files into a table. You built the same shape in Act I: the catalog from Lab 3 recorded which file and which columns make up a table, and the WAL from Lab 7 made changes to that record atomic and durable. The lakehouse manifest does both jobs, at cloud scale.

FAQ

Should I stop using pandas?

No: aim DuckDB at the loading/filtering/joining that pandas does slowly and memory-hungrily, and keep pandas for what it's brilliant at (transformation, modeling glue). duckdb.sql("...").df() hands you a dataframe; the two compose in14 one line.

Why did CSV lose by more than 100×, when it's also just a file?

Two separate sins: CSV must be parsed (every byte inspected, every number decoded from text), and it has no column structure, so the whole file moves even for one column. Parquet stores typed binary columns with stats; most bytes3 never move, and none need parsing.

Is DuckDB replacing Postgres?

Different workload, different tool: DuckDB has no concurrent writers, no WAL-grade durability story for hot OLTP, on purpose15. The modern pattern is Postgres running the app, Parquet snapshots in a lake, and DuckDB or a warehouse reading them.

What's "time travel" in the lakehouse pitch?

Old manifests are kept: query the table as of last Tuesday by reading last Tuesday's file list. It's MVCC's keep-old-versions idea (Lecture 8) applied to whole files; same trade too: history costs storage until vacuumed16.
