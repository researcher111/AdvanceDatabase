Same rides, two storage layouts

What is Parquet?

Parquet is a file format for storing table data by column. A file format defines how values are stored in a file. Our three rides could be saved in rides.parquet. Inside each row group, Parquet keeps pickup values, payment values, and fare values in separate column chunks. Metadata describes the field types and where those chunks start.6

Parquet stores the data. DuckDB runs the query. To calculate average fare, DuckDB can read the fare chunk and skip pickup and payment. The answer remains $30. A larger file can contain many row groups. Look inside the example file →

How do slots change?

In microdb’s row pages, each slot contains a complete record. Suppose Ride 2 occupies block 7, slot 1. The RID (7, 1) locates its pickup, payment, and fare together.

In this simple column layout, every column uses the same row order. Reconstruct Ride 2 from position 1 in each column. The values are LGA, card, and $24. Positions start at zero.

Step through the slot comparison →

Parquet organizes a batch of rows as a row group. Each column has a separate chunk in that group. Each chunk contains encoded pages. A position identifies a row within the group. Locating its value can require decoding, rather than a fixed byte offset.23

The starting principle is: read less data, then process it efficiently. DuckDB and Parquet illustrate this principle. The lecture connects it to cloud databases and model training with SQL.

Main idea: choose a storage layout that fits the queries you run.

One ride or many rides?

A workload is the mix of queries a database runs. A complete Ride 2 lookup needs its pickup, payment, and fare. Average fare needs the fare from every ride. Row storage groups the values for the first query. Column storage groups the values for the second query. Both layouts can answer both queries.

Many systems use both layouts

A taxi service can record rides in a row-based database. It can copy the rides into a column-based database for reports. Each layout serves a different task.

Row storage keeps a complete ride’s fields together. Column storage gathers those fields from separate columns. This is a simplified model. Actual disk reads also depend on page size, caching, and indexes.

Why columns help

Imagine copying each fare into a separate list without changing ride order. Fare positions still match the pickup and payment positions. These positions let us reconstruct a ride. Grouping one field’s values helps the engine read only that field and encode repeated patterns. Compression, chunk metadata, and execution determine the actual work.

Reading only the fare column saves work immediately. Storing similar values together also helps the engine do three things:

TechniqueIdeaWhat it saves
Compress valuesStore repeated values or patterns in less space.Fewer bytes to read.
Process batchesApply an operation to an array of values. This is vectorized execution.Fewer operator calls.
Skip chunksCheck a chunk's minimum and maximum before reading it.No read when the chunk cannot match the filter.

1. Store patterns in less space

Repeated values → store the value and its count
  month:    1 1 1 1 2 2 2       → (1 × 4), (2 × 3)

Repeated labels → store a small dictionary and codes
  payment:  card card cash card  → {card: 0, cash: 1} + 0 0 1 0

Nearby numbers → store the first value and the changes
  ride_id:  4000 4001 4002 4003  → 4000, then +1 +1 +1

These are run-length, dictionary, and delta encoding. Each uses a pattern in the values to reduce storage. The savings depend on the data.

An engine can combine encodings. Parquet can dictionary-encode labels and then compress runs of their codes.2 The displayed byte counts are examples. Actual file sizes vary.

2. Process a batch at a time

Recall the Lecture 4 scans. TableScan finds a row. SelectScan checks its condition. ProjectScan exposes the requested fields. The caller repeats plan.next(). After each successful call, it reads fields with plan.get_val(...).

Consider SELECT fare FROM rides WHERE fare > 25 with fares 36, 24, and 30 in that order. The first successful call selects 36. The next call skips 24 and selects 30. A batch can send [36, 24, 30] to the filter at once and return both matching fares together. The condition and answer stay the same. Each transfer between operators contains more rows. Step through the comparison →

microdb (Volcano)DuckDB (vectorized)

Batching reduces calls between operators. The filter must still check each fare. Microdb already reads disk pages into buffers. A scan call that returns one row does not imply one disk read. An execution batch groups values for processing in memory. Array loops can also use the CPU efficiently.1

3. Skip data that cannot match

Suppose a chunk’s fares range from $5 to $20. A query for fare > 100 can skip that chunk. Its minimum and maximum prove that no fare can match. The engine does not need to check individual fares.

Are partitions folders?

A partition groups rows by a rule. For one year of rides, we can group all January rides together, all February rides together, and so on. In this example, each month's group lives in a folder of Parquet files:

rides/
  month=01/data.parquet   ← January rides
  month=02/data.parquet   ← February rides
  ...
  month=12/data.parquet   ← December rides

For December’s average fare, folder labels let the engine skip eleven months. It can then read only fare chunks in December’s files. This folder convention is Hive partitioning. A partition can contain several files, although this example has one file per month. Folders are one way to store partitions. Other database systems manage partitions internally.24

How much data can we skip?

Fewer bytes is a prediction. Faster execution is something we measure.

Check yourself · keep fewer columns and fewer months

Our question is “What is the average fare for December?” Imagine a toy year with 60,000 rides, split evenly into 12 months. Each month has 5,000 rides. Each ride has 12 stored fields, including fare, and each value uses 8 bytes. The folder name supplies the month.

Draw a grid with 12 columns and 12 months. Each square represents one month’s values for one column. It contains 5,000 values × 8 bytes = 40 KB. These are equal groups of value data, not disk pages.

Start with all 144 squares. Keep only the fare column. Then keep only December. What fraction of the full table’s value data remains? Step through the grid →

Show answer
  1. All table values: 60,000 × 12 × 8 = 5,760,000 bytes, or 5.76 MB. This is our full-table baseline.
  2. Keep only fare: 60,000 × 1 × 8 = 480,000 bytes, or 480 KB. Twelve squares remain. Divide the starting bytes by 12.
  3. Keep only December fares: 5,000 × 1 × 8 = 40,000 bytes, or 40 KB. One square remains. Divide by 12 again.

One of 144 equal squares remains: 1/144 of the full value data. The two savings multiply because one removes columns and the other removes months. Using the same units, 5,760 KB ÷ 40 KB = 144.

This model uses decimal units: 1 KB = 1,000 bytes. It excludes metadata, encoding, and compression. It compares value bytes, not query speed or measured disk reads. Actual months can have different row counts. If December held half the rides, selecting December would divide by 2. The remaining data would be 1/24 of all value data.

From trips to running totals

Storage layout can help a query read fewer bytes. Now follow the operations on those values. First, group trips into monthly totals. Then add a running total to each monthly row. Check what one result row represents at each stage.

A window function lets each row use other rows in its calculation while keeping a result for each row. Move through a four-ride visual to see which rows contribute →

Here, start with one row per trip. GROUP BY month produces one row per month. A running total then shows how much revenue we have collected by the end of each month. Its frame includes the rows from the first month through the current month: January alone, then January plus February.

At each step, ask: what does one row represent now? This is the table’s grain. The WITH clause names the monthly result for the next step. This named result is a common table expression (CTE).

The same ideas in the cloud

DuckDB can run on your laptop. Cloud systems can spread queries across many machines. They use the same basic ideas: read selected columns, compress values, and skip data.

Storage keeps the data. Compute runs the queries. Separating them lets a system change query capacity without moving all the data.

Which files belong to the table?

Suppose an update replaces three data files. A reader should see the complete old version or the complete new version. Lakehouse metadata records which files belong to each committed version, so a query does not mix the two.

Bytes scanned can affect query cost

BigQuery's on-demand query pricing is based on data processed. Selecting fewer columns and filtering partitions can reduce that amount.13

Train a model with SQL

The engine can summarize fares. Training uses rides to estimate a relationship and save a model. Prediction applies that model to separate test rides. Data preparation, training, and prediction are different operations.

Can trip distance help predict fare? SQL will fit a line and save its slope and intercept in a table. Another query will predict a fare. DuckDB performs the calculations. This is in-database machine learning.

1. Keep training and test rows separate

distance is the feature: the input to the model. fare is the label: the outcome we want to predict. The split column marks each row for training or testing.

A test ride is a recorded taxi trip we reserve before training to check the model afterward. Four rides help the model learn its line. The other two rides check its predictions on data it did not learn from. Their recorded fares become the answers we compare the predictions with.

CREATE TABLE ml_rides (
    ride_id INTEGER, distance DOUBLE, fare DOUBLE, split VARCHAR
);
INSERT INTO ml_rides VALUES
    (1, 1.0,  6.0, 'train'),
    (2, 2.0,  6.0, 'train'),
    (3, 3.0,  8.0, 'train'),
    (4, 4.0, 12.0, 'train'),
    (5, 2.5,  9.0, 'test'),
    (6, 4.5, 11.0, 'test');

CREATE VIEW fare_features AS
SELECT ride_id, distance, fare, split
FROM ml_rides
WHERE distance > 0 AND fare >= 0;

The filter keeps positive distances and nonnegative fares. It excludes nulls. Only distance predicts fare. ride_id identifies the row. split identifies training and test rows.

For real data: avoid leaking test information

For forecasting, train on earlier data. Test on later data. Fit preprocessing means, scales, or category mappings with training rows only. Exclude test data from every fitting step.

2. Fit the line with an aggregate query

CREATE TABLE fare_model AS
SELECT regr_intercept(fare, distance) AS intercept,
       regr_slope(fare, distance) AS slope,
       count(*) AS training_rows
FROM fare_features
WHERE split = 'train';

SELECT * FROM fare_model;
-- intercept | slope | training_rows
--       3.0 |   2.0 |             4

The regression functions take (fare, distance): outcome first, input second. They find the line that minimizes squared errors on the training rows.17 The result is predicted fare = 3 + 2 × distance. SQL learned 3 and 2 from the four training rides and saved them in fare_model.

Why does regr_intercept(fare, distance) need both columns? It must learn how fare changes with distance to locate the fitted line's crossing at distance zero. Each training row supplies a pair: a known fare and its distance. The aggregate uses all four pairs and returns one number, the intercept. regr_slope(fare, distance) uses those same pairs and returns the slope of the same line.

For this fit, intercept = average fare − slope × average distance. Training averages are $8 and 2.5 miles. The learned slope is $2 per mile. Thus, the intercept is $8 − ($2 per mile × 2.5 miles) = $3. No training ride traveled zero miles, so the model estimates that crossing. The estimate does not establish the taxi’s actual base fare.

Training:  scan feature columns → filter split = 'train' → aggregate → model row
Scoring:   scan new distances   → combine with model row → project predictions

These queries use familiar operations: scan, filter, aggregate, and join. One aggregate query trains this simple model. More complex models can require many passes through the data.

3. Check the line on the test rides

CROSS JOIN pairs each test ride with the one model row. We then calculate its predicted fare and compare it with the actual fare.

CREATE VIEW held_out_predictions AS
SELECT r.ride_id, r.distance, r.fare,
       m.intercept + m.slope * r.distance AS predicted_fare
FROM fare_features AS r
CROSS JOIN fare_model AS m
WHERE r.split = 'test';

SELECT * FROM held_out_predictions ORDER BY ride_id;
-- ride_id | distance | fare | predicted_fare
--       5 |      2.5 |  9.0 |            8.0
--       6 |      4.5 | 11.0 |           12.0

SELECT count(*) AS test_rows,
       avg(abs(fare - predicted_fare)) AS mae,
       sqrt(avg(pow(fare - predicted_fare, 2))) AS rmse
FROM held_out_predictions;
-- test_rows | mae | rmse
--         2 | 1.0 |  1.0

For the reserved 2.5-mile ride, the model predicts $8 and the recorded fare is $9. The absolute error is $1. For the 4.5-mile ride, the prediction is $12 and the recorded fare is $11. Its absolute error is also $1. Therefore, MAE (mean absolute error) is $1. Here, RMSE (root mean squared error) is also $1.

Why use separate test rows? Evaluation checks predictions on data that did not train the model. Two made-up rows demonstrate this procedure. An actual evaluation needs representative test data and a comparison baseline.

4. Predict the fare for a new ride

SELECT r.ride_id, r.distance,
       m.intercept + m.slope * r.distance AS predicted_fare
FROM (VALUES (7, 3.5)) AS r(ride_id, distance)
CROSS JOIN fare_model AS m;
-- ride_id | distance | predicted_fare
--       7 |      3.5 |           10.0

For 3.5 miles, the saved model predicts 3 + 2 × 3.5 = $10. We need the distance, not the actual fare. This query uses the saved model without training it again.

Optional BigQuery SQL: the same stages with a managed model

This optional example uses a paid cloud service. It is not required for the lab.22

Use a Google Cloud project with billing and the BigQuery API enabled. You need permission to run jobs and create and read models.21 Create a dataset named demo. Load the six rides into demo.ml_rides with types INT64, FLOAT64, FLOAT64, STRING. Replace YOUR_PROJECT with your project ID.

-- BigQuery GoogleSQL; these statements do not run in DuckDB.
CREATE MODEL `YOUR_PROJECT.demo.fare_model`
OPTIONS (
    model_type = 'linear_reg',
    input_label_cols = ['fare'],
    data_split_method = 'NO_SPLIT',
    optimize_strategy = 'NORMAL_EQUATION',
    l2_reg = 0.0
) AS
SELECT distance, fare
FROM `YOUR_PROJECT.demo.ml_rides`
WHERE split = 'train' AND distance > 0 AND fare >= 0;

SELECT mean_absolute_error, mean_squared_error
FROM ML.EVALUATE(
    MODEL `YOUR_PROJECT.demo.fare_model`,
    (SELECT distance, fare
     FROM `YOUR_PROJECT.demo.ml_rides`
     WHERE split = 'test' AND distance > 0 AND fare >= 0)
);

SELECT ride_id, distance, predicted_fare
FROM ML.PREDICT(
    MODEL `YOUR_PROJECT.demo.fare_model`,
    (SELECT 7 AS ride_id, 3.5 AS distance)
);

NO_SPLIT uses every row from the training query. That query selects only split = 'train'. The evaluation query selects test rows separately. The other options request the same type of least-squares fit as the DuckDB example. ride_id labels prediction output. It is not a feature.

Why keep the work in the database? We can train where the rows already live and use the predictions in another query. We avoid exporting the training table. The available models and compute costs depend on the engine.

FAQ

Should I stop using pandas?

Use SQL and pandas together when useful. For example, summarize rides with SQL. Then plot the result with Python. duckdb.sql("...").df() returns a pandas dataframe.14

Why can Parquet be faster than CSV?

CSV stores rows as text. The reader must scan the text to find the fields it needs. Parquet stores columns separately, so the engine can skip unused columns and some chunks. Reading less can be faster, but the speedup depends on the query and data.3

Is DuckDB replacing Postgres?

They serve different needs. DuckDB runs inside an application and focuses on analytics. Postgres runs as a server that many clients can read and update. Choose based on the work and how the application is deployed.15

Where does our model training happen?

DuckDB trains the regression model in this lecture. Python sends SQL and prints results. Exporting rows to a Python library for fitting would move training outside the database.

What does “time travel” mean for a lakehouse table?

It means querying an earlier version of the table. Metadata identifies the files for that version. It works only while those files and their metadata are still retained.16
