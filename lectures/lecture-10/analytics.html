The Analytics Stack

Column storage supports analytical scans. Those same scans can prepare features, fit a model, and score new rows inside the database.
Daniel G. Graham · UVA School of Data Science

microdb stores the fields of each row together. That layout suits small record lookups and updates. Many analytical queries instead read a few columns across a large number of rows. Column storage lets them skip unused columns, compress similar values, and process batches efficiently. Today we will connect those choices to vectorized execution, DuckDB, Parquet, and cloud warehouses, then use SQL to train and evaluate a small machine-learning model without exporting its training rows. Tuesday’s lab measures the effects of file format, column selection, and partition pruning.

Companion reading: Abadi et al., The Design and Implementation of Modern Column-Oriented Database Systems1 · the Why DuckDB page · Parquet's file-format docs.

A query for average fare needs the fare values from every matching ride. With a row layout, those values share pages with fields the query does not use. A column layout can read the fare column separately.

Today's claim: layout follows workload. Analytics and model training both benefit from scanning selected columns near where the data lives.

Match the storage layout to the workload

Row and column layouts serve different access patterns. Many systems use both: transactional databases handle operational reads and updates, while pipelines copy data into analytical stores for reporting and large scans.

Column storage supports three related optimizations

Column storage first reduces I/O by letting a query skip unused columns. It also makes the following optimizations easier to apply: compressing similar values, processing batches of one type, and skipping chunks whose statistics rule out a match.

TechniqueNeedsBenefit
compressionruns of same-typed, similar valuesfewer blocks to read, which is the cost measure from week 1
vectorized executioncontiguous arrays of one typemore values processed per CPU second, because the engine runs a tight loop over an array instead of interpreting one row at a time
stats-based skippingper-chunk min/maxwhole chunks never read: if a chunk's stored min and max show that no row in it can match the filter, its blocks are skipped

Repeated values and patterns enable compression

a column is a run of SAME-TYPED, often-similar values, a compressor's dream:

  month:    1 1 1 1 2 2 2 ...        run-length:  (1×4)(2×3)...      ~50x smaller
  payment:  card card cash card...   dictionary:  {card:0, cash:1} + bits
  ride_id:  0 1 2 3 4...             delta:       start + (+1 +1 +1...)

row storage interleaves types every few bytes; these column-specific encodings are less straightforward, though row stores can also compress data.
smaller files = fewer blocks = faster scans: compression IS performance here.

The pattern in the data picks the encoding

compress one column · 24 rides, three encodings

Pick a column; the widget shows its raw values, applies the encoding that fits its shape, and counts the bytes. The encoding is chosen by the pattern in the data: long runs of repeated values, a small number of distinct values, or a numeric sequence.

These encodings suit different patterns and can be combined. For example, Parquet dictionary-encodes then run-length-encodes the dictionary codes2. A 20-column fact table can shrink substantially, depending on values, encodings, and codecs, and a smaller encoded column generally requires fewer blocks to read3.

Vectorized execution processes batches of values

microdb (Volcano)DuckDB (vectorized)
Unit of workone row per next()a vector of ~2048 values per call
Operator-call overheadpaid per rowshared across a batch of up to 2048 values, reducing per-row overhead4
CPU behaviorrepeated calls through the operator tree can add overhead; memory locality depends on the implementationtight loops over arrays can improve locality and use SIMD instructions, which apply one instruction to several values at once1
The modelthe same compositional idea as microdb: operators pass data to other operators. The unit of work becomes a batch. Production engines can use different interfaces and scheduling models.

Estimate bytes read before measuring elapsed time

Measure the speedup for the same query over CSV and Parquet. The result depends on the data, selected columns, cache state, and machine.

Check yourself · compare the bytes read

rides: 60,000 rows, 12 columns, ~8 bytes per value. Compute the bytes that must move for SELECT avg(fare) FROM rides under (a) row layout, (b) column layout, and (c) column layout with a month = 12 filter over 12 equal hive partitions (one folder per month). What's the (a)-to-(c) ratio?

Show answer

(a) all of it: \(60{,}000 \times 12 \times 8 \approx\) 5.8 MB. (b) one column: \(60{,}000 \times 8 \approx\) 0.48 MB, 12× less. (c) one column of one partition: \(0.48\ \text{MB} / 12 \approx\) 40 KB, 144× less than (a), before compression shrinks it further. This is a prediction about bytes read, not a guaranteed 144× reduction in elapsed time. Compression, decoding, caching, and query overhead affect the measured runtime.

Use DuckDB to query Parquet directly

DuckDBa full columnar OLAP engine in a Python library, "SQLite for analytics." No server, queries CSV/Parquet/pandas frames in place5. Tuesday's lab engine.
Parqueta widely supported columnar file format: column chunks + per-chunk stats + dictionary/RLE compression, self-describing schema6. It plays the role CSV once played as the universal exchange format, but with types, compression, and per-chunk statistics built in.

A partition folder per month lets a filter open one folder, not twelve

Partitioningrows grouped into folders by a partition column’s value (month=12/…), so a WHERE month = 12 clause lets the engine exclude data files in the other eleven month folders7; you'll watch EXPLAIN say Scanning Files: 1/12.

SQL and pandas hand the same dataframe back and forth

DuckDB and pandasDuckDB can run SQL directly against a pandas dataframe and hand the result back as a dataframe8. A pipeline can therefore use SQL for one step and pandas for the next, passing the same data between them.

The cloud separates where data rests from where queries run

Cloud analytical engines use many of the same columnar techniques, then add distributed execution and managed storage. A common architectural choice is separating durable storage from the compute resources that run queries.

Compare warehouses, data lakes, and lakehouses

SystemWhat it isKey design choice
Snowflake / BigQuery / Redshiftcloud data warehouses: columnar engines, elastic compute9separation of storage and compute: the data rests permanently in object storage, and a separate cluster of machines is started when queries arrive, billed for the work it does, and shut down when it is idle10
The data lakea collection of Parquet files sitting in S3-style object storage, with no database engine attached to themobject storage provides durable storage without a permanently running query cluster. Open file formats let compatible engines such as DuckDB and Spark read the data
The lakehouse (Delta, Iceberg)the same lake files plus a transactional metadata layer on topACID commits, schema evolution, and time travel over plain Parquet files11. The metadata layer records the files belonging to each committed table version. Delta Lake uses a transaction log; Iceberg uses snapshots and manifests. Readers select a committed version instead of discovering a partially updated table from directory contents12

Table metadata gives lakehouse files transactional structure

A lakehouse needs both data files and metadata describing committed table versions. This extends ideas from your catalog and transaction log: the engine must know which data belongs to a table and expose changes atomically. Delta Lake and Iceberg implement those requirements differently; neither is simply microdb’s WAL applied to a directory.

Train and score a model inside the database

In-database machine learning puts model fitting or prediction in the database's execution environment. A query that prepares features for an external Python model is useful, but feature preparation alone does not train an in-database model. Here we will fit a line, store its learned coefficients in a table, and use another query to make predictions.

StageQuestionDatabase work in this example
Feature preparationWhich inputs and known outcomes describe each example?Filter rows; select distance as the feature and fare as the label.
TrainingWhich coefficients fit the training rows?Aggregate training rows into one model row: intercept and slope.
EvaluationHow far are predictions from outcomes on rows held out of training?Score held-out rows, then aggregate their errors.
InferenceWhat fare does the saved model predict for a new distance?Combine new rows with the model row and compute a predicted value.

We use six hand-chosen synthetic rides so every result can be checked by hand. Distance is in miles; fare is in dollars. The four training rows determine the model. The two test rows remain outside that calculation. This is an execution example, not evidence that distance alone predicts real taxi fares accurately.

Run locally: download in_database_ml.py, install DuckDB with python3 -m pip install duckdb, then run python3 in_database_ml.py. Add --explain to inspect the training and scoring plans. Python submits SQL and displays results; DuckDB performs the calculations. The script uses an in-memory database and needs no cloud account or dataset download.

1. Prepare the feature and label, with the split already assigned

CREATE TABLE ml_rides (
    ride_id INTEGER, distance DOUBLE, fare DOUBLE, split VARCHAR
);
INSERT INTO ml_rides VALUES
    (1, 1.0,  6.0, 'train'),
    (2, 2.0,  6.0, 'train'),
    (3, 3.0,  8.0, 'train'),
    (4, 4.0, 12.0, 'train'),
    (5, 2.5,  9.0, 'test'),
    (6, 4.5, 11.0, 'test');

CREATE VIEW fare_features AS
SELECT ride_id, distance, fare, split
FROM ml_rides
WHERE distance > 0 AND fare >= 0;

The filter is a fixed validity rule; comparisons also exclude null distances and fares. The split field controls which rows reach training. Neither it nor ride_id is a predictive feature. In a real forecasting task, choose a split that respects time; if preprocessing learns a mean, scale, or category mapping, fit that preprocessing on training data too. Otherwise information from the held-out data can leak into training.

2. Training can be an aggregate query

CREATE TABLE fare_model AS
SELECT regr_intercept(fare, distance) AS intercept,
       regr_slope(fare, distance) AS slope,
       count(*) AS training_rows
FROM fare_features
WHERE split = 'train';

SELECT * FROM fare_model;
-- intercept | slope | training_rows
--       3.0 |   2.0 |             4

DuckDB's regression aggregates take (y, x): the label first, the feature second. They compute the ordinary least-squares line with one input feature.17 The model is now data in a one-row table: predicted fare = 3 + 2 × distance. The coefficients are learned from the training rows, rather than supplied as constants in the prediction query.

Training:  scan feature columns → filter split = 'train' → aggregate → model row
Scoring:   scan new distances   → combine with model row → project predictions

This connects to your scan operators: fitting this model is a scan and aggregation; scoring is a scan, a cross product with one row, and arithmetic. The --explain output shows DuckDB's actual plan, including pushed-down filters. More complex models may require iterative training or specialized operators. These regression aggregates are a small complete example, not a general ML framework.

3. Evaluate using rows that did not fit the model

CREATE VIEW held_out_predictions AS
SELECT r.ride_id, r.distance, r.fare,
       m.intercept + m.slope * r.distance AS predicted_fare
FROM fare_features AS r
CROSS JOIN fare_model AS m
WHERE r.split = 'test';

SELECT * FROM held_out_predictions ORDER BY ride_id;
-- ride_id | distance | fare | predicted_fare
--       5 |      2.5 |  9.0 |            8.0
--       6 |      4.5 | 11.0 |           12.0

SELECT count(*) AS test_rows,
       avg(abs(fare - predicted_fare)) AS mae,
       sqrt(avg(pow(fare - predicted_fare, 2))) AS rmse
FROM held_out_predictions;
-- test_rows | mae | rmse
--         2 | 1.0 |  1.0

MAE is the mean absolute error: both predictions miss by $1, so MAE is $1. RMSE is the square root of mean squared error; it is also $1 here. Evaluating the training rows would measure fit on data the model already used. Two synthetic test rows demonstrate the separation but cannot establish useful predictive accuracy; a real project needs representative held-out data and a baseline to compare against.

4. Inference uses the saved coefficients and needs no label

SELECT r.ride_id, r.distance,
       m.intercept + m.slope * r.distance AS predicted_fare
FROM (VALUES (7, 3.5)) AS r(ride_id, distance)
CROSS JOIN fare_model AS m;
-- ride_id | distance | predicted_fare
--       7 |      3.5 |           10.0

The new ride has a distance but no observed fare. The query uses the existing model; it does not retrain it. The model table contains exactly one row, so each input ride produces exactly one prediction. A system that stores many model versions must select one version before this join.

A warehouse can expose training as CREATE MODEL

BigQuery ML offers the same train → evaluate → predict workflow through model objects and SQL functions. For linear regression, CREATE MODEL fits the model, ML.EVALUATE measures its errors, and ML.PREDICT returns predictions.181920

Optional BigQuery SQL: the same stages with a managed model

Cloud setup: this example requires a Google Cloud project with billing enabled, the BigQuery API, a dataset named demo, and permission to run jobs and create/read models. Replace YOUR_PROJECT with your project ID and load the six rows above into demo.ml_rides with BigQuery types INT64, FLOAT64, FLOAT64, STRING. Training, storage, evaluation, and prediction may incur charges; this is an optional illustration, not required lab setup.2122

-- BigQuery GoogleSQL; these statements do not run in DuckDB.
CREATE MODEL `YOUR_PROJECT.demo.fare_model`
OPTIONS (
    model_type = 'linear_reg',
    input_label_cols = ['fare'],
    data_split_method = 'NO_SPLIT',
    optimize_strategy = 'NORMAL_EQUATION',
    l2_reg = 0.0
) AS
SELECT distance, fare
FROM `YOUR_PROJECT.demo.ml_rides`
WHERE split = 'train' AND distance > 0 AND fare >= 0;

SELECT mean_absolute_error, mean_squared_error
FROM ML.EVALUATE(
    MODEL `YOUR_PROJECT.demo.fare_model`,
    (SELECT distance, fare
     FROM `YOUR_PROJECT.demo.ml_rides`
     WHERE split = 'test' AND distance > 0 AND fare >= 0)
);

SELECT ride_id, distance, predicted_fare
FROM ML.PREDICT(
    MODEL `YOUR_PROJECT.demo.fare_model`,
    (SELECT 7 AS ride_id, 3.5 AS distance)
);

NO_SPLIT tells BigQuery to use all rows supplied to CREATE MODEL for training; our query has already restricted those rows to split = 'train'. We supply the test query explicitly to ML.EVALUATE. Omitting it would not measure our held-out rows. The normal-equation strategy and zero L2 regularization make this a comparable least-squares fit; actual cloud results are not required for the local exercise. ride_id is passed through prediction output, not learned as a feature.

Why keep the work in the database? A training query can filter, join, and aggregate where the data already lives, avoiding an application-side export of all training rows. Predictions can feed another SQL query. This uses database compute, and the choice of available models depends on the engine. SQL syntax alone does not tell you where a model runs: a remote-model call can invoke an external service. Decide based on the model, data movement, resources, and evaluation needs.

Recap & next time

  • Layout follows workload. Rows for fetch-and-update, columns for scan-and-aggregate; the industry runs both, connected by pipelines.

FAQ

Should I stop using pandas?

Use the tool that fits each step. DuckDB can query and aggregate large tabular inputs, while pandas provides convenient dataframe transformations and integrates with modeling libraries. duckdb.sql("...").df() returns a pandas dataframe, so a pipeline can use both.14

Why can a Parquet query be much faster than the same CSV query?

CSV stores rows as text, so the reader must locate fields and parse values. It generally scans the input even when the query uses only one column. Parquet stores typed column chunks and statistics, allowing the engine to skip unused columns and some nonmatching chunks. Values still require decoding and often decompression, and the measured speedup depends on the query and data.3

Is DuckDB replacing Postgres?

DuckDB supports transactions, WAL, and concurrent writers within one process. Its embedded concurrency model and analytical execution differ from PostgreSQL’s server model. Choose based on the workload and deployment requirements. DuckDB’s concurrency guide explains the boundary.

Does querying features in SQL make a Python model “in-database ML”?

It makes feature preparation a database operation. If you export those features and fit an external model, training happens outside the database. In our example DuckDB computes the coefficients and predictions. Python only submits the SQL and displays results. A production workflow can mix these approaches deliberately.

What does “time travel” mean for a lakehouse table?

A table can retain metadata for earlier committed versions. To query an earlier version, the engine uses that version’s metadata to find the required data files. This resembles MVCC’s use of old row versions, but the unit being tracked is a file set. Time travel is available only while the needed metadata and data files are retained.16
