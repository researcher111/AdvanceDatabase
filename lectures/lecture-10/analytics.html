The Analytics Stack

Row storage was the wrong default for analysis all along: columns, compression, warehouses, and the lakehouse.
Daniel G. Graham · UVA School of Data Science

Act II opens with a confession: everything you built assumed a workload (many small reads and writes of whole rows) that analytics simply doesn't have. An analyst's query touches two columns of every row, and for that shape, storing rows together is the wrong bet. Flip the layout ninety degrees and a cascade follows: columns compress absurdly well, scans vectorize, filters push into file formats, and the modern stack (DuckDB on your laptop, warehouses in the cloud, Parquet as the lingua franca) falls out of one decision. Thursday you measure all of it.

The workload flip

OLTP vs OLAP, finally formal

OLTP (microdb's world)OLAP (this week's)
Typical queryfetch/update one ride by idaggregate two columns of all rides
Touchesa few rows, all columnsall rows, a few columns
Right layoutrows together (one block has your whole record)columns together (one read has only what you need)
Writesconstant small ones: WAL, locks, the worksbulk appends; datasets are mostly immutable
EnginesPostgres, MySQL, your microdbDuckDB, Snowflake, BigQuery, Spark

Neither layout is "better"; they're answers to different questions. The industry's standard architecture is both: OLTP systems run the business, and their data flows into columnar systems that analyze it.

Inside a column store

Turning the layout ninety degrees isn't the speedup by itself; it's the license for three compounding tricks, each impossible while types interleave:

TrickNeedsBuys
compressionruns of same-typed, similar valuesfewer blocks (week 1's currency)
vectorized executioncontiguous arrays of one typeCPU throughput
stats-based skippingper-chunk min/maxblocks never read at all

Compression: columns are boring, thankfully

a column is a run of SAME-TYPED, often-similar values, a compressor's dream:

  month:    1 1 1 1 2 2 2 ...        run-length:  (1×4)(2×3)...      ~50x smaller
  payment:  card card cash card...   dictionary:  {card:0, cash:1} + bits
  ride_id:  0 1 2 3 4...             delta:       start + (+1 +1 +1...)

row storage interleaves types every few bytes; none of these tricks survive it.
smaller files = fewer blocks = faster scans: compression IS performance here.

Run the encodings yourself

compress one column · 24 rides, three encodings

Pick a column; the widget shows its raw values, applies the encoding that fits its shape, and counts the bytes. The encoding is chosen by the pattern in the data: sorted-and-runny, low-cardinality, or sequential.

These three cover most real columns, and they compound: Parquet dictionary-encodes then run-length-encodes the dictionary codes. A 20-column fact table routinely shrinks 10–20×, and every saved byte is a block the scan never reads.

Vectorized execution: amortize everything

microdb (Volcano)DuckDB (vectorized)
Unit of workone row per next()a vector of ~2048 values per call
Interpreter overheadpaid per rowpaid per 2048 rows, amortized to dust
CPU behaviorbranchy, cache-hostiletight loops over arrays, SIMD-friendly, the thing CPUs love
The modelidentical! before_first/next/get, just bigger sips. Your mental model survives intact.

Columnar layout + vectorized execution is why Thursday's measurement shows Parquet beating CSV 89× on the same rows on the same laptop.

Check yourself · predict Thursday's number

rides: 60,000 rows, 8 columns, ~8 bytes per value. Compute the bytes that must move for SELECT avg(fare) FROM rides under (a) row layout, (b) column layout, and (c) column layout with a month = 12 filter over 12 equal hive partitions. What's the (a)-to-(c) ratio?

Show answer

(a) all of it: 60,000 × 8 × 8 ≈ 3.8 MB. (b) one column: 60,000 × 8 ≈ 0.48 MB, 8× less. (c) one column of one partition: ≈ 40 KB, roughly 96× less than (a), before compression shrinks it further. Thursday's measured 89× is this arithmetic with real files and real codecs; you can now predict a benchmark before running it, which is the whole point of a cost model.

DuckDB & Parquet

The analyst's stack, one pip install

DuckDBa full columnar OLAP engine in a Python library, "SQLite for analytics." No server, queries CSV/Parquet/pandas frames in place. Thursday's lab engine.
Parquetthe columnar file format everyone reads and writes: column chunks + per-chunk stats + dictionary/RLE compression, self-describing schema. The CSV of the 2020s, minus the regrets.
Partitioningfolder-per-value layout (month=12/…) that turns WHERE clauses into skipped directories; you'll watch EXPLAIN say Scanning Files: 1/12.
The pandas peace treatyDuckDB queries dataframes directly and returns them; SQL and pandas stop being rivals and become stages of one pipeline.

Warehouses & the lakehouse

Everything DuckDB does on your laptop, the cloud does on rented hardware over shared storage; same columnar bones, plus one architectural move DuckDB doesn't need: separating where data rests from where queries run.

The same ideas, industrial size

SystemWhat it isThe defining trick
Snowflake / BigQuery / Redshiftcloud data warehouses: columnar engines, elastic computeseparation of storage and compute: data lives in object storage; query clusters spin up, bill by the scan, vanish
The data lakeParquet files in S3-style object storage, no engine attachedcheapest possible storage; any engine may read it
The lakehouse (Delta, Iceberg)lake files + a transactional metadata layerACID commits, schema evolution, and time travel, over plain Parquet, via a manifest that says which files ARE the table

Look closely at the lakehouse's manifest-plus-files trick: a small transactional layer conferring table-hood on dumb storage. You built that exact shape; it's the catalog (Lab 3) plus the WAL (Lab 7), wearing a warehouse badge. Act I keeps paying rent.

FAQ

Should I stop using pandas?

No: aim DuckDB at the loading/filtering/joining that pandas does slowly and memory-hungrily, and keep pandas for what it's brilliant at (transformation, modeling glue). duckdb.sql("...").df() hands you a dataframe; the two compose in one line.

Why did CSV lose by 89×, when it's also just a file?

Two separate sins: CSV must be parsed (every byte inspected, every number decoded from text), and it has no column structure, so the whole file moves even for one column. Parquet stores typed binary columns with stats; most bytes never move, and none need parsing. Thursday's question 1, spoiled.

Is DuckDB replacing Postgres?

Different workload, different tool: DuckDB has no concurrent writers, no WAL-grade durability story for hot OLTP, on purpose. The modern pattern is Postgres running the app, Parquet snapshots in a lake, DuckDB/warehouse reading them. Each piece you can now name from the inside.

What's "time travel" in the lakehouse pitch?

Old manifests are kept: query the table as of last Tuesday by reading last Tuesday's file list. It's MVCC's keep-old-versions idea (Lecture 8) applied to whole files; same trade too: history costs storage until vacuumed.
