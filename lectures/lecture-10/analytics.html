The Analytics Stack

Ask a question about many rows. Read the columns you need. Use SQL to find patterns and make predictions.
Daniel G. Graham · UVA School of Data Science

Imagine a table with one row per taxi ride and columns for pickup location, payment type, and fare. What is the average fare across all rides? To answer, we need only the fare column.

With row storage, each ride's fields are stored together. Reading fares can also bring in pickup locations and payment types. With column storage, fares are stored together, so the query can read just that column.

Same rides, two storage layouts

What is Parquet?

Parquet is a file format for storing table data by column. A file format defines how values are stored in a file. Our three rides could be saved in rides.parquet. Inside each row group, Parquet keeps pickup values, payment values, and fare values in separate column chunks. Metadata describes the field types and where those chunks start.6

Parquet stores the data; DuckDB runs the query. To calculate the average fare, DuckDB can read the fare chunk and skip pickup and payment. The answer is still $30. A larger file can contain many row groups. Look inside the example file →

How do slots change?

In microdb's row pages, each slot holds a complete record. If Ride 2 is in block 7, slot 1, the RID (7, 1) locates its pickup, payment, and fare together.

In a simple column layout, each column keeps the same row order. To rebuild Ride 2, read position 1 from each column: LGA from pickup, card from payment, and $24 from fare. We count positions from zero.

Step through the slot comparison →

For Parquet, a batch of rows is a row group. Each column has its own chunk within that group, and each chunk contains encoded pages. A position identifies a row within the group; locating its value may require decoding. It is not necessarily a fixed byte offset.23

That is today's starting point: read less data, then process it efficiently. We will use DuckDB and Parquet to explore this idea, connect it to cloud databases, and finish by training a small model with SQL.

Main idea: choose a storage layout that fits the queries you run.

One ride or many rides?

A workload is the mix of queries a database runs. Showing all of Ride 2 needs its pickup, payment, and fare. Calculating the average fare needs just the fare from every ride. Row storage keeps the first set together; column storage keeps the second set together. Both layouts can answer both questions.

Many systems use both layouts

A taxi service might record each ride in a row-based database, then copy the rides into a column-based database for reports. Each layout serves a different job.

Why columns help

Reading only the fare column saves work immediately. Storing similar values together also helps the engine do three things:

TechniqueIdeaWhat it saves
Compress valuesStore repeated values or patterns in less space.Fewer bytes to read.
Process batchesApply an operation to an array of values. This is vectorized execution.Fewer operator calls.
Skip chunksCheck a chunk's minimum and maximum before reading it.No read when the chunk cannot match the filter.

1. Store patterns in less space

Repeated values → store the value and its count
  month:    1 1 1 1 2 2 2       → (1 × 4), (2 × 3)

Repeated labels → store a small dictionary and codes
  payment:  card card cash card  → {card: 0, cash: 1} + 0 0 1 0

Nearby numbers → store the first value and the changes
  ride_id:  4000 4001 4002 4003  → 4000, then +1 +1 +1

These are run-length, dictionary, and delta encoding. Each uses a pattern in the values to reduce storage. The savings depend on the data.

Try three encodings

Compress one column from 24 rides

Pick a column. Compare the original values, the encoded values, and the bytes used. Which pattern makes each encoding work?

Encodings can be combined. Parquet can dictionary-encode labels, then compress runs of their codes.2 The byte counts here illustrate the idea; actual file sizes vary.

2. Process a batch at a time

Recall the scans from Lecture 4: TableScan finds a row, SelectScan checks the condition, and ProjectScan exposes the requested fields. The caller repeats plan.next(), then reads the current result with plan.get_val(...).

For SELECT fare FROM rides WHERE fare > 25, use the toy fares 36, 24, and 30 in that scan order. The first successful call selects 36. The next call skips 24 and selects 30. A batch version could pass [36, 24, 30] to the filter at once, then pass the two matching fares onward together. Same condition, same answer; more rows per handoff. Step through the comparison →

microdb (Volcano)DuckDB (vectorized)
Unit of workOne current row per successful next(); get_val() reads its fields.A batch of values; the standard vector size is 2,048.4
Example: filter faresAdvance until one row matches, then read its fare.Test the fares in a batch, then pass matching positions onward.
Call overheadPaid for each row.Shared across the batch.

Batching reduces repeated calls between operators; each fare still needs its condition checked. Microdb already reads disk pages into buffers, so one row per successful scan call does not mean one disk read per row. An execution batch groups values for processing in memory. Loops over arrays can also use the CPU efficiently.1

3. Skip data that cannot match

Suppose a chunk's fares range from $5 to $20. A query for fare > 100 can skip it. The minimum and maximum are enough to rule it out; the engine need not check every fare.

Are partitions folders?

A partition groups rows by a rule. For one year of rides, we can group all January rides together, all February rides together, and so on. In this example, each month's group lives in a folder of Parquet files:

rides/
  month=01/data.parquet   ← January rides
  month=02/data.parquet   ← February rides
  ...
  month=12/data.parquet   ← December rides

For December's average fare, the engine can use the folder labels to skip the other eleven months. Then it can read only fare chunks inside December's files. This folder convention is called Hive partitioning. One partition can contain several files; the example shows one per month. A folder is one way to store a partition; other database systems manage partitions internally.24

How much data can we skip?

Fewer bytes is a prediction. Faster execution is something we measure.

Check yourself · keep fewer columns and fewer months

Our question is “What is the average fare for December?” Imagine a toy year with 60,000 rides, split evenly into 12 months. Each month has 5,000 rides. Each ride has 12 stored fields, including fare, and each value uses 8 bytes. The folder name supplies the month.

Draw a grid with 12 columns and 12 months. Each square represents one month's values for one column: 5,000 values × 8 bytes = 40 KB. These are equal pieces of value data, not disk pages.

Start with all 144 squares. Keep only the fare column, then only December. What fraction of the full table's value data remains? Step through the grid →

Show answer
  1. All table values: 60,000 × 12 × 8 = 5,760,000 bytes, or 5.76 MB. This is our full-table baseline.
  2. Keep only fare: 60,000 × 1 × 8 = 480,000 bytes, or 480 KB. Twelve squares remain. Divide the starting bytes by 12.
  3. Keep only December fares: 5,000 × 1 × 8 = 40,000 bytes, or 40 KB. One square remains. Divide by 12 again.

One of 144 equal squares remains: 1/144 of the full value data. The two savings multiply because one removes columns and the other removes months. Using the same units, 5,760 KB ÷ 40 KB = 144.

This model uses decimal units (1 KB = 1,000 bytes) and excludes metadata, encoding, and compression. It compares value bytes, not query speed or measured disk reads. Real months need not be equal: if December held half the rides, keeping that month would divide by 2, leaving 1/24 of the full value data.

From trips to running totals

Start with one row per trip. GROUP BY month produces one row per month. A running total then shows how much revenue we have collected by the end of each month. For each calculation, the window includes the rows from the first month through the current month: January alone, then January plus February.

At each step, ask: what does one row represent now? This is the table's grain. The WITH clause names the monthly result so the next step can use it; that named result is a common table expression (CTE).

Worked result: Four toy trips become monthly revenues 20 and 30. The window preserves two monthly rows and adds running totals 20 and 50.

The same ideas in the cloud

DuckDB can run on your laptop. Cloud systems can spread queries across many machines. They use the same basic ideas: read selected columns, compress values, and skip data.

Storage keeps the data; compute runs the queries. Separating them lets a system change its query capacity without moving all the data.

Which files belong to the table?

Suppose an update replaces three data files. A reader should see the complete old version or the complete new version. Lakehouse metadata records which files belong to each committed version, so a query does not mix the two.

Bytes scanned can affect query cost

BigQuery's on-demand query pricing is based on data processed. Selecting fewer columns and filtering partitions can reduce that amount.13

All rides, all fields   → read all columns
All rides, average fare → read the fare column
December, average fare → read fares in December's partition

Read less, pay less can apply when billing is based on data processed. Other plans charge for compute capacity.

Train a model with SQL

Can trip distance help predict fare? We will use SQL to fit a line, save its slope and intercept in a table, and predict a new fare. DuckDB does the calculations. This is in-database machine learning.

StageWhat we doResult
PrepareChoose distance as the input and fare as the known outcome.Training rows and separate test rows.
TrainFit a line to the training rows.One model row: intercept and slope.
EvaluatePredict fares for the test rows and compare with their actual fares.Prediction errors.
Predict (inference)Apply the saved line to a new distance.A predicted fare.

Use six made-up rides so we can check the math: four for training and two for testing. Distance is in miles; fare is in dollars. These rows illustrate the workflow, not real taxi-fare accuracy.

Run it: download in_database_ml.py, install DuckDB with python3 -m pip install duckdb, then run python3 in_database_ml.py. Add --explain to see the query plans. No cloud account or data download is needed.

1. Keep training and test rows separate

distance is the feature: the input to the model. fare is the label: the outcome we want to predict. The split column marks each row for training or testing.

CREATE TABLE ml_rides (
    ride_id INTEGER, distance DOUBLE, fare DOUBLE, split VARCHAR
);
INSERT INTO ml_rides VALUES
    (1, 1.0,  6.0, 'train'),
    (2, 2.0,  6.0, 'train'),
    (3, 3.0,  8.0, 'train'),
    (4, 4.0, 12.0, 'train'),
    (5, 2.5,  9.0, 'test'),
    (6, 4.5, 11.0, 'test');

CREATE VIEW fare_features AS
SELECT ride_id, distance, fare, split
FROM ml_rides
WHERE distance > 0 AND fare >= 0;

The filter keeps positive distances and nonnegative fares; it also excludes nulls. Only distance is used to predict fare. ride_id identifies the row, and split controls when we use it.

For real data: avoid leaking test information

For a forecasting task, train on earlier data and test on later data. If preprocessing learns a mean, scale, or category mapping, learn it from training rows only. Keep test data out of every fitting step.

2. Fit the line with an aggregate query

CREATE TABLE fare_model AS
SELECT regr_intercept(fare, distance) AS intercept,
       regr_slope(fare, distance) AS slope,
       count(*) AS training_rows
FROM fare_features
WHERE split = 'train';

SELECT * FROM fare_model;
-- intercept | slope | training_rows
--       3.0 |   2.0 |             4

The regression functions take (fare, distance): outcome first, input second. They find the line that minimizes squared errors on the training rows.17 The result is predicted fare = 3 + 2 × distance. SQL learned 3 and 2 from the four training rides and saved them in fare_model.

Training:  scan feature columns → filter split = 'train' → aggregate → model row
Scoring:   scan new distances   → combine with model row → project predictions

These are familiar query operations: scan, filter, aggregate, and join. This simple model can be trained with one aggregate query; more complex models may need many passes through the data.

3. Check the line on the test rides

CROSS JOIN pairs each test ride with the one model row. We then calculate its predicted fare and compare it with the actual fare.

CREATE VIEW held_out_predictions AS
SELECT r.ride_id, r.distance, r.fare,
       m.intercept + m.slope * r.distance AS predicted_fare
FROM fare_features AS r
CROSS JOIN fare_model AS m
WHERE r.split = 'test';

SELECT * FROM held_out_predictions ORDER BY ride_id;
-- ride_id | distance | fare | predicted_fare
--       5 |      2.5 |  9.0 |            8.0
--       6 |      4.5 | 11.0 |           12.0

SELECT count(*) AS test_rows,
       avg(abs(fare - predicted_fare)) AS mae,
       sqrt(avg(pow(fare - predicted_fare, 2))) AS rmse
FROM held_out_predictions;
-- test_rows | mae | rmse
--         2 | 1.0 |  1.0

The predictions are $8 and $12. The actual fares are $9 and $11, so both miss by $1. MAE (mean absolute error) is therefore $1. RMSE (root mean squared error) is also $1 here.

Why use separate test rows? We want to check predictions on data the model did not learn from. Two made-up rows show how this works; a real evaluation needs representative test data and a baseline for comparison.

4. Predict the fare for a new ride

SELECT r.ride_id, r.distance,
       m.intercept + m.slope * r.distance AS predicted_fare
FROM (VALUES (7, 3.5)) AS r(ride_id, distance)
CROSS JOIN fare_model AS m;
-- ride_id | distance | predicted_fare
--       7 |      3.5 |           10.0

For 3.5 miles, the saved model predicts 3 + 2 × 3.5 = $10. We need the distance, not the actual fare. This query uses the saved model without training it again.

Optional BigQuery SQL: the same stages with a managed model

This optional example uses a paid cloud service. It is not required for the lab.22

To run it, use a Google Cloud project with billing and the BigQuery API enabled, plus permission to run jobs and create/read models.21 Create a dataset named demo and load the six rides into demo.ml_rides using types INT64, FLOAT64, FLOAT64, STRING. Replace YOUR_PROJECT below with your project ID.

-- BigQuery GoogleSQL; these statements do not run in DuckDB.
CREATE MODEL `YOUR_PROJECT.demo.fare_model`
OPTIONS (
    model_type = 'linear_reg',
    input_label_cols = ['fare'],
    data_split_method = 'NO_SPLIT',
    optimize_strategy = 'NORMAL_EQUATION',
    l2_reg = 0.0
) AS
SELECT distance, fare
FROM `YOUR_PROJECT.demo.ml_rides`
WHERE split = 'train' AND distance > 0 AND fare >= 0;

SELECT mean_absolute_error, mean_squared_error
FROM ML.EVALUATE(
    MODEL `YOUR_PROJECT.demo.fare_model`,
    (SELECT distance, fare
     FROM `YOUR_PROJECT.demo.ml_rides`
     WHERE split = 'test' AND distance > 0 AND fare >= 0)
);

SELECT ride_id, distance, predicted_fare
FROM ML.PREDICT(
    MODEL `YOUR_PROJECT.demo.fare_model`,
    (SELECT 7 AS ride_id, 3.5 AS distance)
);

NO_SPLIT uses all rows passed to training; the query already selects only split = 'train'. The evaluation query separately selects the test rows. The other options request the same kind of least-squares fit as our DuckDB example. ride_id labels the prediction output; it is not a feature.

Why keep the work in the database? We can train where the rows already live and use the predictions in another query. We avoid exporting the training table. The available models and compute costs depend on the engine.

Recap & next time

  • Match the layout to the query. Rows keep one record together. Columns keep one field's values together.
  • Do less work. Read fewer columns, compress values, process batches, and skip data that cannot match.
  • Separate the roles. DuckDB runs queries. Parquet stores column data. Lakehouse metadata tracks table versions.
  • SQL can train and use a model. Keep training and test rows separate, then predict with the saved model.

FAQ

Should I stop using pandas?

Use both when it helps. For example, summarize rides with SQL, then plot the result with Python. duckdb.sql("...").df() returns a pandas dataframe.14

Why can Parquet be faster than CSV?

CSV stores rows as text. The reader must scan the text to find the fields it needs. Parquet stores columns separately, so the engine can skip unused columns and some chunks. Reading less can be faster, but the speedup depends on the query and data.3

Is DuckDB replacing Postgres?

They serve different needs. DuckDB runs inside an application and focuses on analytics. Postgres runs as a server that many clients can read and update. Choose based on the work and how the application is deployed.15

Where does our model training happen?

Inside DuckDB. Python sends the SQL and prints the results. If we exported the rows and fitted a model in a Python library, that training would happen outside the database.

What does “time travel” mean for a lakehouse table?

It means querying an earlier version of the table. Metadata identifies the files for that version. It works only while those files and their metadata are still retained.16
