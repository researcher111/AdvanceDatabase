Concurrency: Locks, Isolation & MVCC

How do two individually correct transactions share one row and lose money with no crash anywhere, and what does each way of stopping it cost?
Daniel G. Graham · UVA School of Data Science

Two cashiers each add $10 to the same $100 account, both commit cleanly, and the balance reads $110: no crash, no error, and one deposit gone. Thursday's log made one transaction crash-proof; today two of them meet, and interleaving a pair of correct transactions carelessly is all it takes to lose money with no failure anywhere. The anomalies have names, the fixes have prices, and every engine picks its trade. We build up from two-phase locking (the classic textbook algorithm, and the one you build in lab) to MVCC, the keep-every-version trick that lets Postgres run reports and updates through the same rows without either waiting1.

Companion reading: Sciore, Database Design and Implementation, ch. 5 · the anomaly zoo: Berenson et al., A Critique of ANSI SQL Isolation Levels2 · Postgres's isolation docs.

Today's claim: isolation is purchased: every level pays for its safety with one of three things: transactions waiting on locks, transactions aborted and retried, or old row versions kept on disk. There is no free level.

Correct alone is not correct together

The gold standard is serializability: the result equals some serial order. Everything else on today's menu is a named, priced deviation from it.

Five anomalies, each with a name and a recipe

AnomalyThe story in one lineNeeds
Lost updatetwo transactions each read the same row, compute a new value, and write it back; the second write overwrites the first without ever having seen it, so one change silently disappearstwo transactions that both write the same row, where the second writer read the row before the first writer's change landed
Dirty readyou read a value that another transaction has written but not yet committed; that transaction later rolls back, so you acted on data that never officially existeda transaction that is allowed to read another transaction's uncommitted write
Non-repeatable readread a row twice in one transaction (tx) and get two different answers, because someone else updated the row and committed between your two readsone transaction reads a row; a second transaction updates that row and commits; the first transaction reads the row again
Phantomrun WHERE gpa > 35 twice in one transaction; the second run finds a row that another transaction inserted in between. Row locks cannot stop this, because a lock can only be placed on a row that already exists, and the new row did not exist when the first query ranone transaction runs the same WHERE condition twice while another transaction inserts a row that matches it
Write skewtwo transactions each check a condition, then write different rows; both checks pass, the combined result violates the ruletwo transactions that read overlapping rows but write different rows, so no write-write conflict is ever detected; the full example is in the FAQ

One lost update closed an exchange

War story · the lost update that closed a bank, 2014

The anomaly zoo is not academic. In 2014 the Bitcoin exchange Flexcoin was destroyed by the first row of that table: attackers fired thousands of simultaneous transfers between accounts they controlled, and the transfer code did read-balance → check → write-balance with no isolation3. Concurrent reads saw the same balance, the debits overwrote each other (a textbook lost update), and the attackers withdrew about 896 BTC the exchange didn't have3. Flexcoin announced its closure within days. The two-cashier demo in the next section is the same exploit with smaller numbers. Preventing it is what the rest of today's lecture is about.

2PL buys serializability with waiting

The classic prevention: make conflicting access impossible by fencing rows with locks. Every serious engine shipped it for decades; yours ships it Thursday in 40 lines.

S lock (shared / read):     many holders welcome, readers coexist
X lock (exclusive / write): one holder, no readers, no exceptions

conflict table:        S      X
                 S    ok    WAIT
                 X   WAIT   WAIT        ← every anomaly dies in these three WAITs4

Lock first, grow then shrink, hold to commit

RuleStatementWhy
Lock before touchingS (shared) lock to read, many holders; X (exclusive) to write, one holder, no readerstwo transactions can never both write the same row at the same time, and no transaction can read a row while another is writing it, because the lock table refuses the second request; that removes every write-write and read-write overlap
Two phasesa transaction acquires locks in a growing phase, then releases them in a shrinking phase; once it has released any lock, it never acquires another5at the instant a transaction holds its full set of locks, every other transaction that conflicts with it has either already released its conflicting locks or must wait until this one releases them; that ordering is what makes the schedule provably equivalent to some serial order
Strict varianthold every lock until commit or rollbackno other transaction can read or write a row you changed until your change is final, so a dirty read of an uncommitted write becomes impossible as well; this is the variant your lab (and most engines) implement4

The bill is waiting, and sometimes deadlock

Waitinga conflicting lock means someone sits idle: a long report holding shared locks makes an update wait for its exclusive lock, and the next report then waits behind that update. Every transaction that is waiting is one that could have been doing work, so throughput falls even though nothing has gone wrong.
Deadlocktx1 holds A wants B; tx2 holds B wants A, forever. Engines detect the cycle and shoot one participant (your app must retry)6.
microdb's versionmicrodb runs one transaction at a time on a single thread, so a transaction that waited for a lock would be waiting for a holder that cannot run to release it. Instead, a conflicting request raises LockAbortError immediately and that transaction rolls back. The lock rules are the same as a real engine's; only the response to a conflict differs.
The open questionmost conflicts involve a reader, and readers don't change anything. Must a report really block a deposit? The MVCC section below answers no.

Climb from bottom to top and watch the order the anomalies die in; that order IS the standard's definition of the levels7.

REPEATABLE READ has a gray zone the standard never named

Set it per transaction: SET TRANSACTION ISOLATION LEVEL SERIALIZABLE8. The gray zone the explorer shows at REPEATABLE READ is why the Berenson paper in the citations exists. The ANSI standard defines each level only by which of the anomalies above it forbids, and those definitions were written before snapshot isolation existed. Snapshot isolation forbids everything the standard lists for REPEATABLE READ, yet still allows write skew (see the FAQ), an anomaly the standard never names2.

MVCC moved the cost, it didn't erase it

Readers never block writers; writers never block readers. Writers still block writers (locks live on)6, and a transaction that holds its snapshot open for a long time forces the engine to keep every old version that snapshot might still read, so vacuum cannot reclaim them and the table grows: MVCC moved the cost, it didn't erase it13. No free level, ever.

No locks appear anywhere in this test; it's pure arithmetic on two stamps, which is why a 10-minute report and a write flood coexist. The versions the slider leaves behind are VACUUM's job; a reader parked at the leftmost snapshot is exactly the "long-lived snapshot" that makes vacuum's job harder.

FAQ

What exactly is write skew?

The on-call rule: at least one doctor rostered. Two doctors each run "if the OTHER is on call, I can leave". Under snapshot isolation both transactions read the old roster, in which both doctors are on call, so both checks pass; each then updates only its own row, both commit, and zero doctors remain11. No row was written by both transactions, so no write-write conflict fired and neither was blocked or aborted. Only true serializability catches it. Postgres implements that as SSI, Serializable Snapshot Isolation, which tracks which transactions read rows that other transactions then wrote, and aborts one of them when that pattern could produce a result no serial order would give. Write skew is the reason SERIALIZABLE still exists as a level above snapshot isolation.

Why doesn't microdb's Lab 7 implement MVCC?

Locks are 40 lines and teach the protocol; MVCC is version chains, snapshot bookkeeping, and vacuum: several weeks of work, not one lab session. You now know both designs and, more importantly, the trade they're making. Sciore's SimpleDB stops at locks too, though his chapter 5 does sketch multiversion locking15.

How often do real deadlocks happen?

Constantly, at scale: check pg_stat_database.deadlocks14 on any busy system. The standard defenses are ordering (all code touches accounts in id order, no cycles possible) and retry loops6. "Transactions may be shot; write retryable code" is professional-grade advice you now understand.

Does the buffer pool's pin count relate to these locks?

Different layer, different lifetime. A pin protects a frame of the buffer pool for microseconds, just long enough to read or write the bytes in it (week 2; Lab 3's FAQ calls this kind of short-term protection a latch). A lock protects the meaning of a row or block for the transaction's whole life, which can be seconds or minutes. The two APIs look alike, acquire then use then release, but they differ by three orders of magnitude in how long they hold, and they are easy to confuse for exactly that reason.
