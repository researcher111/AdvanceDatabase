Concurrency: Locks, Isolation & MVCC

Two transactions can each be correct when run alone but lose an update when run together. How do locks and row versions prevent these conflicts?
Daniel G. Graham · UVA School of Data Science

A fictional classroom investigation

Maya and Noor each deposit $10 into the same account. The starting balance is $100. Both read 100, calculate 110, and write 110. Maya points to the completed deposits: Why is the balance missing ten? Their operations overlapped. No crash occurred.

Concurrency adds an ordering problem to otherwise correct transactions. Create a schedule that loses an update. Find the conflicting lock request. Compare the row versions that reads can see under different snapshot rules. Locks, MVCC, and crash recovery solve different problems.

Companion reading: Sciore, Database Design and Implementation, ch. 5 · a detailed analysis of isolation levels: Berenson et al., A Critique of ANSI SQL Isolation Levels2 · Postgres's isolation docs.

Start with what you already know

Check your explanation

Serial execution gives 120. Durability can preserve the incorrect final value of 110. It does not provide isolation. The order of reads, calculations, and writes must prevent a lost update.

Optional exploration: create a schedule that produces an incorrect result. Explain how locks or snapshots change that result.

Account A holds $100. Both cashiers read 100 before either writes, then each adds 10 and stores 110. Both transactions commit, but the balance should be $120. This is a lost update.

Isolation controls how concurrent transactions interact. Stronger guarantees can require lock waits, aborts and retries, or storage for older row versions. We will compare those costs with the anomalies each design prevents.

Correct alone is not correct together

Serializability means concurrent execution has the same effect as some serial execution. In serial execution, transactions run one at a time. Weaker isolation levels can permit results that no serial execution produces.

Five concurrency anomalies and how they arise

Two-phase locking orders conflicting operations

A lock is like a reservation on an item. Several readers can hold compatible shared locks. A writer needs an exclusive lock, which conflicts with another transaction’s lock. A buffer pin keeps a frame in memory. A transaction lock controls conflicting access.

A lock table prevents transactions from taking incompatible locks on the same item. Two-phase locking adds a rule about when those locks may be released. The provided Lab 7 lock table applies this approach to blocks.

S lock (shared / read):     many holders welcome, readers coexist
X lock (exclusive / write): one holder, no readers, no exceptions

conflict table:        S      X
                 S    ok    WAIT
                 X   WAIT   WAIT        ← conflicting accesses cannot proceed together; range predicates also need protection4

Acquire locks before access and keep them until completion

RuleStatementWhy
Lock before touchingReading requires an S (shared) lock, which permits multiple readers. Writing requires an X (exclusive) lock, which excludes other readers and writers.The lock table rejects incompatible requests. Two transactions cannot write the same row at the same time. One transaction cannot read a row while another holds its write lock. These rules prevent conflicting read-write and write-write operations from overlapping.
Two phasesA transaction acquires locks during its growing phase. It releases locks during its shrinking phase. After releasing any lock, it cannot acquire another.5Consider the point when a transaction holds all its locks. A conflicting transaction has already released its conflicting locks or must wait. This ordering makes the schedule provably equivalent to a serial order.
Strict varianthold every lock until commit or rollbackOther transactions cannot read or write a changed row until the writer finishes. This prevents dirty reads. The lab holds both shared and exclusive locks until completion. This stronger variant is also called rigorous two-phase locking.4

Lock conflicts cause waits or aborts

Waitinga transaction requesting an incompatible lock must wait or abort. For example, a report holding a shared lock can delay an update that needs an exclusive lock. Long waits can reduce throughput.
Deadlocktx1 holds A and waits for B. tx2 holds B and waits for A. Neither can proceed. An engine can detect this cycle and abort one transaction. The application must retry the aborted transaction.6
microdb's versionThe lab interleaves transactions on one thread. Waiting on that thread would prevent the other transaction from releasing its lock. A conflicting request therefore raises LockAbortError immediately. The caller must roll back that transaction. The lock compatibility rules match an actual engine. The response to a conflict differs.
The open questioncan a report read a consistent version of a row while another transaction updates it? MVCC provides this capability without requiring ordinary reads to hold conflicting row locks.

Isolation levels provide different guarantees

Multi-version concurrency control (MVCC) keeps multiple row versions. MVCC alone does not specify which anomalies an isolation level prevents. Check the isolation rules. A reader can have a consistent snapshot while concurrent transactions produce a result that no serial execution permits.

Snapshot isolation can still allow write skew

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE requests the serializable level. SQL-92 classifies levels with a limited set of anomalies. Snapshot isolation prevents dirty and non-repeatable reads, as REPEATABLE READ requires. It can still allow write skew. PostgreSQL uses snapshot isolation for REPEATABLE READ. Its SERIALIZABLE level adds checks for results that no serial execution permits.82

Postgres keeps row versions for snapshot reads

Waiting for locks is one way to coordinate access. Another is to keep older versions: a snapshot acts like a dated view of the data. The actual visibility rules, transaction status, and snapshot membership determine what a reader sees.

MVCC trades read-write lock conflicts for version storage

The payoffordinary snapshot reads avoid row-level conflicts with writes: a report and an update pass through the same rows without waiting on each other.
Writers still waitWriters can still block other writers. Locks control write-write conflicts6.
Storage costA long transaction snapshot can require many old versions. Vacuum cannot reclaim those versions while the snapshot needs them. The table can therefore grow13. This reduces read-write lock conflicts but adds storage and cleanup work.

FAQ

What exactly is write skew?

The rule requires at least one doctor on call. Each doctor applies this condition: "if the OTHER is on call, I can leave". Under snapshot isolation, both transactions read the old roster with both doctors on call. Both checks pass. Each transaction changes only its own row. Both commit, leaving no doctor on call.11

The transactions wrote different rows, so no write-write conflict blocked or aborted them. Serializability prevents this result. PostgreSQL implements Serializable Snapshot Isolation (SSI). SSI tracks dependencies between transactions that read and write overlapping data. It aborts a transaction when those dependencies could permit a result that no serial order produces. This is why SERIALIZABLE provides stronger guarantees than snapshot isolation.

Why does microdb’s Lab 7 omit MVCC?

The provided lock table is small enough to inspect in one lab. MVCC would also require row-version storage, snapshot tracking, visibility checks, and safe cleanup. The lecture compares those designs, while the lab focuses on locking and recovery. Sciore’s chapter 5 also discusses multiversion locking.15

How often do real deadlocks happen?

Deadlock frequency depends on the workload and access order. PostgreSQL exposes a count in pg_stat_database.deadlocks. Acquiring locks in a consistent order, such as account ID order, helps avoid cycles. Applications should also be able to retry transactions the database aborts.146

Does the buffer pool's pin count relate to these locks?

A pin prevents eviction of a buffer frame. A latch protects a shared memory structure during a short operation. A transaction lock protects logical access to a row, block, or key range. A pin alone does not prevent another client from changing a page.
