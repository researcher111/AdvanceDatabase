Two transactions, one row, and every way that can go wrong, named, priced, and prevented.

Ways to be wrong together

Think · Pair · Share · break the bank yourselves
  • Think · 2 minAccount A holds $100. Two cashiers each run: read A; add $10; write A back. Both transactions are individually perfect. Find the interleaving of their four steps where a deposit vanishes, and say exactly which step destroyed it.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare interleavings: both read 100 → both write 110 → one $10 is gone. No crash, no error, no log entry: which of last Thursday's machinery even noticed?
  • Share · 2 minOne sentence: what property did the serial (one-then-the-other) schedule have that the interleaved one lost?
Show the answer

The killing interleaving is: T1 reads 100, T2 reads 100, T1 writes 110, T2 writes 110. The step that destroys the deposit is T2's read, not its write: it read a value that was already stale-in-waiting, because T1 was going to change it. The write merely carries out the damage. Final balance $110 where it should be $120, and one customer's $10 has vanished.

What noticed? Nothing. No crash, no error, no rollback, and the log is perfectly happy, because both transactions committed and every write it recorded did land on disk. Last Thursday's machinery guarantees durability and atomicity, and neither was violated. That is the point: this is a new category of bug. The property the serial schedule had and the interleaved one lost is that each transaction saw the whole effect of every transaction before it and none of any transaction after it. Restoring that property is what isolation means, and it is the I this whole lecture is about.

War story · the lost update that closed a bank, 2014

The anomaly zoo is not academic. In 2014 the Bitcoin exchange Flexcoin was destroyed by the first row of that table: attackers fired thousands of simultaneous transfers between accounts they controlled, and the transfer code did read-balance → check → write-balance with no isolation. Concurrent reads saw the same balance, the debits overwrote each other (a textbook lost update), and the attackers withdrew about 896 BTC the exchange didn't have. Flexcoin announced its closure within days. The two-cashier TPS you just did is that exploit with smaller numbers; the fix is today's entire lecture.

Two-phase locking

The classic prevention: make conflicting access impossible by fencing rows with locks. Every serious engine shipped it for decades; yours ships it Thursday in 40 lines.

S lock (shared / read):     many holders welcome, readers coexist
X lock (exclusive / write): one holder, no readers, no exceptions

conflict table:        S      X
                 S    ok    WAIT
                 X   WAIT   WAIT        ← every anomaly dies in these three WAITs

The protocol

RuleStatementWhy
Lock before touchingS (shared) lock to read, many holders; X (exclusive) to write, one holder, no readerswrite-write and read-write overlaps become impossible
Two phasesacquire locks growing, never after the first releasethe growing/shrinking split is what makes schedules provably serializable
Strict varianthold everything until commit/rollbackalso kills dirty reads; what your lab (and most engines) implement

The bill: waiting, and worse

Waitinga conflicting lock means someone sits idle: the report blocks the update blocks the report. Throughput dies of politeness.
Deadlocktx1 holds A wants B; tx2 holds B wants A, forever. Engines detect the cycle and shoot one participant (your app must retry).
microdb's dodgesingle-threaded, so waiting would be waiting on nobody: conflicts raise LockAbortError immediately. Same protocol, honest scale.
The itchmost conflicts involve a reader, and readers don't change anything. Must a report really block a deposit? Hold that thought two sections.

Isolation levels

Think · Pair · Share · price the safety
  • Think · 2 minYour dashboard runs a 10-minute analytics query over the orders table while checkouts commit constantly. Full serializability would block or abort someone for 10 minutes. Which anomalies from the zoo could you TOLERATE in a dashboard, in exchange for never blocking checkouts? Which could a bank transfer tolerate?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minDashboards shrug at non-repeatable reads; transfers cannot shrug at lost updates. Different queries deserve different contracts; that's why levels exist per-transaction, not per-database.
  • Share · 2 minGuess before the next slide: which level is Postgres's default?
Show the answer

A dashboard can shrug at almost all of them. A non-repeatable read or a phantom just means the ten-minute report reflects a slightly different instant in different places, which for a revenue chart is noise next to the fact that it is ten minutes stale by the time anyone reads it. Even a dirty read is often survivable there. A bank transfer can tolerate none of it, and least of all the lost update, which is the one that silently destroys money.

That asymmetry is why isolation is set per transaction rather than per database: SET TRANSACTION ISOLATION LEVEL …. The same database serves both, and each query buys only the safety it needs.

The guess: Postgres's default is READ COMMITTED, not SERIALIZABLE. Most people assume the strongest is the default, and the fact that it is not is the whole economics of this lecture: safety is bought with waiting, and databases sell it by the transaction.

MVCC: readers don't block

Think · Pair · Share · the reader who wants yesterday
  • Think · 2 minThe 10-minute report doesn't need the latest data; it needs a consistent view, as of its start. Design a scheme where writers never wait for it and it never waits for writers. Hint from Lab 3: what if UPDATE didn't overwrite the row?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minConverge on: keep old versions; stamp each with its creator; let each reader see the versions current at its snapshot. What new chore does this create? (Someone must take out the trash.)
  • Share · 2 minName a Lab 3 design decision that made "just keep the old row" cheap.
Show the answer

Do not overwrite. An UPDATE writes a new version of the row and leaves the old one in place, each version stamped with the transaction that created it and the one that deleted it. Every reader carries a snapshot, the set of transactions committed when it started, and sees exactly the versions that were current then. Readers never block writers and writers never block readers, because neither takes a lock to do it: visibility is a two-field arithmetic test on the stamps, which is really just a Predicate from Lab 4.

The new chore is garbage. Old versions accumulate forever unless someone reclaims the ones no living snapshot can still see, which is what VACUUM does, and why a long-running report makes vacuum's job harder: its snapshot keeps old versions alive. The Lab 3 decision that made "just keep the old row" cheap is deletion as a bit flip with tombstone slots that get recycled. Superseding a row is the same move as deleting it, and reclaiming a dead version is the same move as reusing a tombstone. MVCC is that idea, industrialized.

How Postgres actually does it

PieceMechanismYou already built the bones
VersionsUPDATE = insert a new row version; the old one stays, stamped (xmin, xmax) with creator/deleter tx idsLab 3: inserts into free slots; tombstones linger
Snapshotseach tx knows which tx ids were committed at its start; it sees exactly those versions 
Visibility checkper row: xmin committed-before-me AND xmax not, a two-field test, no locksa Predicate, really (Lab 4)
The trashVACUUM reclaims versions no living snapshot can seeLab 3's tombstone reuse, industrialized

Readers never block writers; writers never block readers. Writers still block writers (locks live on), and long-lived snapshots make vacuum's job harder: MVCC moved the cost, it didn't erase it. No free level, ever.

History: tx 100 inserted the row at 120, tx 103 updated it to 70, tx 107 updated it to 50. Each version's test: visible if xmin committed before my snapshot AND xmax was not. Green = the version this reader sees; every other reader, concurrently, sees its own.

No locks appear anywhere in this test; it's pure arithmetic on two stamps, which is why a 10-minute report and a write flood coexist. The versions the slider leaves behind are VACUUM's job; a reader parked at the leftmost snapshot is exactly the "long-lived snapshot" that makes vacuum's job harder.

FAQ

What exactly is write skew? The table teased it.

The on-call rule: at least one doctor rostered. Two doctors each run "if the OTHER is on call, I can leave": under snapshot isolation both reads see the old roster, both commit, zero doctors remain. No row was written by both, so no write conflict fired. Only true serializability (Postgres's SSI) catches it; the reason SERIALIZABLE still exists as a level above snapshot.

Why doesn't microdb's Lab 7 implement MVCC?

Locks are 40 lines and teach the protocol; MVCC is version chains, snapshot bookkeeping, and vacuum, a semester garnish, not a Thursday. You now know both designs and, more importantly, the trade they're making. Sciore stops at locks too.

How often do real deadlocks happen?

Constantly, at scale: check pg_stat_database.deadlocks on any busy system. The standard defenses are ordering (all code touches accounts in id order, no cycles possible) and retry loops. "Transactions may be shot; write retryable code" is professional-grade advice you now understand.

Does the buffer pool's pin count relate to these locks?

Different layer, different lifetime: a pin protects a frame for microseconds (week 2, and the latch world of Lab 3's FAQ); a lock protects a row/block's meaning for the transaction's whole life. Same shaped API, three orders of magnitude apart in duration; confusing them is a classic systems interview trap you're now immune to.
