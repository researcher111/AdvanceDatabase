Concurrency: Locks, Isolation & MVCC

Two transactions can each be correct when run alone but lose an update when run together. How do locks and row versions prevent these conflicts?
Daniel G. Graham · UVA School of Data Science

Two cashiers each add $10 to a $100 account. If both read $100 before either writes, both store $110, leaving one deposit unrecorded. Crash recovery does not prevent this: the problem is the order of concurrent operations. Today we will examine common concurrency anomalies, then compare two-phase locking with MVCC. MVCC keeps row versions so ordinary snapshot reads can proceed without conflicting with row updates.1

Companion reading: Sciore, Database Design and Implementation, ch. 5 · a detailed analysis of isolation levels: Berenson et al., A Critique of ANSI SQL Isolation Levels2 · Postgres's isolation docs.

Account A holds $100. Both cashiers read 100 before either writes, then each adds 10 and stores 110. Both transactions commit, but the balance should be $120. This is a lost update.

Isolation controls how concurrent transactions interact. Stronger guarantees can require lock waits, aborts and retries, or storage for older row versions. We will compare those costs with the anomalies each design prevents.

Correct alone is not correct together

Serializability means that concurrent execution has the same effect as running the transactions one at a time in some order. Weaker isolation levels permit specific results that no serial execution would produce.

Five concurrency anomalies and how they arise

AnomalyWhat happensNeeds
Lost updatetwo transactions each read the same row, compute a new value, and write it back; the second write overwrites the first without ever having seen it, so one change silently disappearstwo transactions that both write the same row, where the second writer read the row before the first writer’s change was visible
Dirty readyou read a value that another transaction has written but not yet committed; that transaction later rolls back, so you acted on a change that was later undonea transaction that is allowed to read another transaction's uncommitted write
Non-repeatable readread a row twice in one transaction (tx) and get two different answers, because someone else updated the row and committed between your two readsone transaction reads a row; a second transaction updates that row and commits; the first transaction reads the row again
Phantomrun WHERE gpa > 35 twice in one transaction; the second run finds a row that another transaction inserted in between. Row locks cannot stop this, because a lock can only be placed on a row that already exists, and the new row did not exist when the first query ranone transaction runs the same WHERE condition twice while another transaction inserts a row that matches it
Write skewtwo transactions each check a condition, then write different rows; both checks pass, the combined result violates the ruletwo transactions that read overlapping rows but write different rows, so no write-write conflict is ever detected; the full example is in the FAQ

Two-phase locking orders conflicting operations

A lock table prevents transactions from taking incompatible locks on the same item. Two-phase locking adds a rule about when those locks may be released. The provided Lab 7 lock table applies this approach to blocks.

S lock (shared / read):     many holders welcome, readers coexist
X lock (exclusive / write): one holder, no readers, no exceptions

conflict table:        S      X
                 S    ok    WAIT
                 X   WAIT   WAIT        ← conflicting accesses cannot proceed together; range predicates also need protection4

Acquire locks before access and keep them until completion

RuleStatementWhy
Lock before touchingS (shared) lock to read, many holders; X (exclusive) to write, one holder, no readerstwo transactions can never both write the same row at the same time, and no transaction can read a row while another is writing it, because the lock table refuses the second request; that removes every write-write and read-write overlap
Two phasesa transaction acquires locks in a growing phase, then releases them in a shrinking phase; once it has released any lock, it never acquires another5at the instant a transaction holds its full set of locks, every other transaction that conflicts with it has either already released its conflicting locks or must wait until this one releases them; that ordering is what makes the schedule provably equivalent to some serial order
Strict varianthold every lock until commit or rollbackno other transaction can read or write a row you changed until your change is final, so a dirty read of an uncommitted write becomes impossible as well; the lab holds both shared and exclusive locks until completion; this stronger variant is also called rigorous two-phase locking4

Lock conflicts cause waits or aborts

Waitinga transaction requesting an incompatible lock must wait or abort. For example, a report holding a shared lock can delay an update that needs an exclusive lock. Long waits can reduce throughput.
Deadlocktx1 holds A and waits for B, while tx2 holds B and waits for A. Neither can proceed. An engine can detect this cycle and abort one transaction; the application must retry it6.
microdb's versionthe lab interleaves transaction operations on one thread. Blocking that thread on a lock would prevent the other transaction from running and releasing it. Instead, a conflicting request raises LockAbortError immediately and the caller must roll that transaction back. The lock rules are the same as a real engine's; only the response to a conflict differs.
The open questioncan a report read a consistent version of a row while another transaction updates it? MVCC provides this capability without requiring ordinary reads to hold conflicting row locks.

Snapshot isolation can still allow write skew

Choose a level with SET TRANSACTION ISOLATION LEVEL SERIALIZABLE. The SQL-92 definitions classify levels using a limited set of anomalies. Snapshot isolation prevents the dirty and non-repeatable reads forbidden by REPEATABLE READ, but can still allow write skew. PostgreSQL uses snapshot isolation for REPEATABLE READ; its SERIALIZABLE level adds checks for outcomes that are not serializable.82

MVCC trades read-write lock conflicts for version storage

The payoffordinary snapshot reads avoid row-level conflicts with writes: a report and an update pass through the same rows without waiting on each other.
Writers still waitwriters still block writers; locks live on for write-write conflicts6.
Storage costa transaction that holds its snapshot open for a long time forces the engine to keep every old version that snapshot might still read, so vacuum cannot reclaim them and the table grows13. This reduces read-write lock conflicts but adds storage and cleanup work.

Recap & next time

  • Correct alone ≠ correct together. Recognizing these anomalies helps you interpret an engine’s isolation guarantees.
  • Two-phase locking orders conflicting operations. The lab holds all locks until commit or rollback and aborts conflicting requests. Engines that wait for locks must also handle deadlocks.
  • MVCC lets snapshot readers use older row versions: updates create versions, snapshots determine visibility, and cleanup waits until the old versions are no longer needed.

FAQ

What exactly is write skew?

The on-call rule: at least one doctor rostered. Two doctors each run "if the OTHER is on call, I can leave". Under snapshot isolation both transactions read the old roster, in which both doctors are on call, so both checks pass; each then updates only its own row, both commit, and zero doctors remain11. No row was written by both transactions, so no write-write conflict fired and neither was blocked or aborted. Only true serializability catches it. Postgres implements that as SSI, Serializable Snapshot Isolation, which tracks which transactions read rows that other transactions then wrote, and aborts one of them when that pattern could produce a result no serial order would give. Write skew is the reason SERIALIZABLE still exists as a level above snapshot isolation.

Why doesn't microdb's Lab 7 implement MVCC?

The provided lock table is small enough to inspect in one lab. MVCC would also require row-version storage, snapshot tracking, visibility checks, and safe cleanup. The lecture compares those designs, while the lab focuses on locking and recovery. Sciore’s chapter 5 also discusses multiversion locking.15

How often do real deadlocks happen?

Deadlock frequency depends on the workload and access order. PostgreSQL exposes a count in pg_stat_database.deadlocks. Acquiring locks in a consistent order, such as account ID order, helps avoid cycles. Applications should also be able to retry transactions the database aborts.146

Does the buffer pool's pin count relate to these locks?

A pin prevents a buffer frame from being evicted. A latch protects a shared in-memory structure during a short operation. A transaction lock protects logical access to a row, block, or key range. These are separate mechanisms; a pin alone does not stop another client from changing a page.
