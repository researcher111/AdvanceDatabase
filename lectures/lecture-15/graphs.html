Graph Databases & Course Synthesis

Who does Ada follow?
Daniel G. Graham · UVA School of Data Science

A fictional classroom investigation

Maya opens Ada’s profile in the student club directory. Under “Following,” she sees Ben. She writes ada → ben on the board.

Noor asks, Does Ben follow Ada too? What can Maya tell from the one entry she has seen?

Companion reading: Kuzu's documentation (archived version with setup and Cypher examples) · Robinson, Webber & Eifrem, Graph Databases (free O'Reilly text) · Microsoft's From Local to Global: GraphRAG paper.

Learning goals

  • A directed relationship records who follows whom. A fact about one person belongs to that person. A fact about a particular follow belongs to the relationship.
  • Storing a person’s neighbors together makes their list easier to find. A query still has to inspect the neighbors it needs, and each new follow must update the list.
  • A route records the steps taken. Two routes can end at one person. The question determines whether both routes belong in the answer.
  • Searching one hop at a time discovers people in order of hop count. Marking each person on arrival avoids repeated searches. Saving who led there preserves a route with the fewest hops.
  • Two queries can return the same names and do different work. Comparing their speed requires the same question, including which routes and repetitions count.
  • Following a link can uncover a new source of evidence. Whether it helps depends on what that source supports and what the extra search costs.

2 · Put a fact on the person or the relationship

Open slide 2 ↗

Keep the same two people and the same arrow. The directory records Ada’s grade point average (GPA) as 3.9. Maya also wants to record that Ada began following Ben in 2026. Which fact would still describe Ada if she stopped following Ben?

Put the GPA on Ada’s node. Put the year on the arrow from Ada to Ben. Each named value is a property. A property graph can store properties on both nodes and edges.

The notation gives Ada the label Student and the arrow the relationship type Follows. Parentheses enclose a node. Brackets enclose the relationship. Values in braces describe the item they belong to.

node   (:Student {name: 'ada', gpa: 39})       a labeled record with properties
edge   (ada)-[:Follows {since: 2026}]->(ben)   a typed, directed relationship

The Kuzu demo stores GPA in tenths, so 39 means 3.9. The year illustrates a property we could add to its edge. [3]

3 · Store Ada’s neighbors for the next lookup

Open slide 3 ↗

Ada also follows Cyd. In an edge table, Maya now has two rows starting with Ada. The src column holds the source and dst holds the destination. Which rows should the directory fetch each time someone opens Ada’s “Following” list?

The directory needs the rows with src = 'ada'. As more students join, a scan can pass many unrelated rows. An index on src helps the engine locate Ada’s rows.

Another option is to store the destinations together as ada → [ben, cyd]. Ben and Cyd are Ada’s outgoing neighbors. An adjacency list stores references to those neighbors or to the edges that lead to them.

Adding Cyd costs a write to Ada’s list. In return, later queries can go straight to her neighbors. Like an index, the list must stay up to date when a relationship changes. Engines store the references in different ways, and reading a list can require storage access. [4]

6 · Explore distance layers with a visited set

Open slide 6 ↗

Now Ada wants everyone she can reach in up to three outgoing hops. This question asks about reachability. Two walks led to Dee. If we want names, what could we gain by remembering the first time we saw her?

Start a visited set with Ada. Add Ben and Cyd when you first reach them. They form the next frontier, the group whose outgoing arrows you will inspect next.

Ben leads to Dee and back to Ada. Add Dee to the next group. Ada is already in the set. Now Cyd leads to Dee and Eli. Which person still needs a place in the group?

Only Eli is new. Expanding Dee and Eli once each finds Fay. Searching in these distance layers is breadth-first search (BFS). The three-hop limit is a depth bound. At the bound we record Fay and stop.

Distance from AdaNew frontierVisited after discovery
0[ada]{ada}
1[ben, cyd]{ada, ben, cyd}
2[dee, eli]{ada, ben, cyd, dee, eli}
3[fay]All six students

The return ada → ben → ada is a cycle. Remembering Ada also prevents this cycle from starting her search again. With both a cycle and two ways to Dee, how much work would it take to list every walk instead?

7 · Count walks and distinct people separately

Open slide 7 ↗

Keep the same six students, nine follow edges, and three-hop bound. This time the club asks for all walks from Ada. Both routes to Dee count, and each can continue along dee → eli.

One way to generate the walks is to join the edge table to itself. Match each destination from the first edge with the source of the second. This is a self-join. Repeating that match builds a join chain. Each walk produces a separate row.

DepthWalk endpoints at exactly this depthNew distinct peopleOutgoing edges examined by BFS in this round
1[ben, cyd] · 2 rows[ben, cyd]2 from Ada
2[dee, ada, dee, eli] · 4 rows[dee, eli]4 from Ben and Cyd
3[eli, ben, cyd, eli, fay] · 5 rows[fay]2 from Dee and Eli

The walk enumeration produces 2 + 4 + 5 = 11 rows, excluding the starting row. BFS examines 2 + 4 + 2 = 8 outgoing edges and finds 5 other people.

The ninth edge, fay → ada, is beyond this BFS expansion bound. Fay is first discovered at depth 3, so the search does not expand Fay.

Worked result: At depth two, walk endpoints are [dee, ada, dee, eli]. Visited-set reachability adds only [dee, eli]. Through depth three, BFS examines eight outgoing edges and finds five other people. Bounded walk enumeration produces eleven rows before exclusions.

Start at ada and step to depth 3. The reached students match query 3 of the Kuzu demo. The cycle ada → cyd → eli → fay → ada shows why traversal needs a stopping rule. The example queries use a depth bound. Their DISTINCT operation keeps one copy of each returned name.2

These counters measure different things. One counts rows and the other counts inspected edges. SQL can implement visited-set logic, and a graph engine can enumerate walks. The counters alone cannot establish which engine finishes first.

Compare work for the same result

Ada’s two outgoing edges gave the join two choices for its first step. The number of outgoing edges is a node’s out-degree. Let d be the average out-degree and k the requested walk length. With roughly d choices at each expansion, the number of length-k walks can grow approximately as dk.

This branching estimate assumes repeated expansion without pruning or deduplication. Uneven degrees and query restrictions can change it. Count one edge-table join per expansion from the starting row.

For visited-set traversal, Vr counts reached vertices, including the start. Er counts examined outgoing edges under the bound. Big-O notation describes how work grows with those counts, rather than a measured runtime.

\[ \text{join chain: } k \text{ joins, about } d^{k} \text{ intermediate rows before dedup} \] \[ \text{visited-set traversal: } O(V_r + E_r) \text{ over reached vertices and examined edges} \]

The traversal bound assumes efficient neighbor access and visited-set membership checks. A cache keeps reusable data in memory to avoid repeated storage reads. Storage access and query planning also affect runtime. Compare the same required result before timing either engine.

8 · Express the same question in SQL and Cypher

Open slide 8 ↗

Use the five names from the search as an answer you can check. Ask two engines for everyone Ada can reach within three outgoing hops. Exclude Ada and return each other name once, in alphabetical order.

Cypher lets us write a query that looks like Maya’s drawing. The pattern (a)-[:Follows]->(b) describes one outgoing follow. In MATCH, changing that relationship to [:Follows*1..3] allows one to three hops. Which part of this query makes Dee appear just once?

// Cypher: the pattern IS the query, draw the arrow, star the depth
MATCH (a:Student {name: 'ada'})-[:Follows*1..3]->(b)
WHERE b.name <> 'ada'
RETURN DISTINCT b.name ORDER BY b.name

In SQL, start with Ada at depth zero. Match the outgoing edges of each endpoint to advance one hop. A common table expression (CTE) names a temporary query result. A recursive CTE uses one round’s result to produce the next. Its starting row is the seed.

SQL partRole in this example
SELECT 'ada', 0Seed the computation with Ada at depth 0.
JOIN follows f ON f.src = r.nameExpand each earlier endpoint through its outgoing relationships.
r.depth + 1 and r.depth < 3Count each hop and stop expanding after depth 3.
UNION ALLRetain repeated rows produced by different walks.
WHERE name <> 'ada'Exclude the starting person.
DISTINCT and ORDER BYRemove repeated names and sort the final output.
 
-- DuckDB / Postgres: a loop, spelled as algebra
WITH RECURSIVE reach(name, depth) AS (
    SELECT 'ada', 0
  UNION ALL
    SELECT f.dst, r.depth + 1
    FROM reach r JOIN follows f ON f.src = r.name
    WHERE r.depth < 3
)
SELECT DISTINCT name FROM reach WHERE name <> 'ada' ORDER BY name;

The SQL recursion generates 11 walk rows across depths 1–3, plus the seed. Final exclusion and DISTINCT return [ben, cyd, dee, eli, fay]. The Kuzu query returns the same five names on this fixture.

In the SQL query, both walks to Dee can expand to Eli. The final DISTINCT removes repeated names after those rows exist. In section 6 the visited set let the search skip the second expansion of Dee.

Replacing UNION ALL with UNION removes duplicate whole rows. It does not merge (ada, 0) with (ada, 2), because their depths differ. Keep an explicit stopping or cycle rule. [2] [5]

Kuzu’s default variable-length relationship semantics are WALK: nodes and edges can repeat. Other engines or options can use different rules. Kuzu MATCH documentation.

Both languages compile the request into an execution plan. Each operation in a plan, such as following an edge or removing duplicates, is an operator. The five names check the answer. To compare speed, measure the plans on the same task.

9 · Reconstruct a shortest route

Open slide 9 ↗

Both queries returned Fay’s name. Now Ada wants the shortest chain of follows that connects her to Fay. The list of five names gives her no directions. What could the search save when it first reaches each person?

When BFS discovers Cyd from Ada, it records Ada as Cyd’s predecessor. It records Cyd when it first reaches Eli, then Eli when it first reaches Fay. Starting with Fay, which name would you read next?

Reading backward gives Fay, Eli, Cyd, Ada. Reverse that list to get ada → cyd → eli → fay. Fay first appeared in the third BFS layer. Since BFS had already checked every shorter distance, this three-hop route is a shortest path.

For Dee, Ben and Cyd both offer a two-hop route. Saving the first predecessor gives one shortest route. Finding all shortest routes would also require keeping the other equally short choice.

Here each edge costs one hop. If each edge instead records the time a message takes, that time is its weight. Finding the fastest route would require accounting for those weights.

Kuzu’s SHORTEST query asks the engine for a minimum-hop route. The diagram shows one way to produce that result. [6]

10 · Account for nodes with many neighbors

Open slide 10 ↗

Finding Fay took little work because each student on the way had few outgoing edges. Now imagine a larger club. In the diagram one member follows 5 people, then 30. Finding the start of that member’s list still leaves 30 entries to inspect.

When one member has far more connections than most, that node is a supernode. The uneven work that results is skew. Suppose the system inspects just the first 8 neighbors of this member. Could it still promise to find every reachable person?

That limit is an expansion budget. In this illustration it leaves 22 outgoing edges unchecked. An unexamined edge might be the only way to reach a person within the allowed depth.

If the question asks only for relationships formed this year, an index on the year can help locate the qualifying edges. If every neighbor counts, workers can share a long list, at the cost of coordinating their work.

11 · Choose a system for the required query

Open slide 11 ↗

Which work does the club actually need? Consider three requests on the same follow records. The first asks whom Ada follows directly. A SQL query can look up rows for Ada and join each destination to a student. The destination can be a foreign key that references the student table.

The second request asks how Ada can reach Fay. The route length is unknown when the query starts. A graph query language can express that search directly. The recursive SQL query in section 8 also followed successive relationships.

The third request asks which students are influential across the club. An algorithm such as PageRank repeatedly uses links across the graph to update importance scores. This is whole-graph analytics. Another example is community detection, which looks for groups with strong internal connections.

Required workReasonable starting pointWhat to check
Fixed, shallow relationships, often 1–2 hopsSQL joinsInspect the join plan and indexes. Measure the workload before adding another store.
Variable-depth connections or route-shaped resultsA graph query engineConfirm depth, direction, repeat rules, and shortest-path behavior. Kuzu supplies our teaching example. Neo4j is another graph engine.
Whole-graph scores or communitiesA graph analytics tool or database analytics featureCompare dataset size and algorithm support in tools such as NetworkX and Spark GraphFrames. [8]
Relationships already handled well by foreign keys and SQLThe existing relational systemA second graph copy adds synchronization and maintenance work.

The club’s workload includes how often each request runs and how often follow records change. Compare systems on that mix, including any work needed to keep a second copy of the edges current.

12 · Use relationships to connect source passages

Open slide 12 ↗

Following ada → ben gave us a name. Suppose we use the same one-hop operation to find a source for an answer. This time the nodes represent concepts in course notes. Each concept links back to a passage where it appears.

Why must logging happen before a dirty page is written? Consider a system that retrieves passages before a language model answers. This is retrieval-augmented generation (RAG). Each stored passage is a chunk from the document collection, or corpus.

Vector retrieval ranks passages by how similar their numeric representations are to the question’s representation. Suppose it returns log-notes. This passage explains the write-ahead log (WAL). Which passage could help a reader understand what changes in memory?

Source IDIllustrative passageNamed concept
log-notesWAL records recovery information before a changed page reaches storage.WAL
buffer-notesA dirty page has changes not yet written to storage.Buffer pool

The buffer pool holds working copies of storage pages. A page becomes dirty when the engine changes its memory copy. The write-ahead log stores the information the engine needs to recover that change.

WAL and the buffer pool each name a concept, or entity. A knowledge graph stores such entities and the named relationships between them. In the illustration, an edge labeled protects page writes leads from WAL to the buffer pool.

Following that edge leads to buffer-notes. Combine it with log-notes to form an evidence union. If both routes retrieve the same chunk, include it once. Keep each chunk’s source ID so the reader can check which passage supports which claim.

These links take work to build. During ingestion, the system identifies entities, records relationships supported by the sources, and links the entities to passages. If it links the wrong concepts, a search can follow the arrow correctly and still bring back an irrelevant passage.

Our experiment follows one edge. Microsoft’s GraphRAG paper also groups related entities into communities and builds summaries for broad questions about the corpus. [12]

14 · Recognize five recurring database mechanisms

Open slide 14 ↗

Suppose the second run of a relationship query finishes sooner than the first. Did the engine reuse a page, examine fewer edges, or choose another plan? Return to the club’s simplest query, “Whom does Ada follow?” Follow one lookup to see what each explanation would predict.

MechanismWhat to look for in Ada’s graphCourse connections
Blocks and cachingAfter one lookup loads the block containing Ada’s edges, a second lookup can reuse its copy in memory. This saves storage input/output (I/O).The file manager and buffer pool. Bigtable’s sorted-file blocks, Parquet’s groups of column data, and temporary shuffle files.
Sorting and indexesAn index on the source finds Ada’s edge rows. A stored adjacency list also gives the query a way to skip other students’ edges.B+ trees, graph adjacency, and Bloom filters. Inverted file (IVF) vector indexes group vectors into searchable lists.
Logs and recoverySuppose the club saves a follow and gets a success reply. If the engine uses a WAL, its durable log record can help recover that change after a crash.WAL and Bigtable recovery. Spark’s lineage records transformations for recomputation. Table-format metadata records committed data-file versions.
Declarative queries and plansAsk for every other student within three hops. The plan determines when the engine expands edges and removes duplicates to produce the five names.SQL parsing and execution, Spark plans, and Cypher MATCH.
PartitioningA system can assign different students’ edges to different workers. One worker may still receive the busiest member’s entire list.Shuffle destinations, Bigtable’s row ranges, data folders, and IVF lists.

Each mechanism has a contract, the behavior it promises. Caching Ada’s list can save a read. Recovering a confirmed change requires information that survives a crash. Spark lineage records how to recompute lost data. A transaction WAL records changes needed for database recovery.

15 · Ask how an unfamiliar system does the work

Open slide 15 ↗

A database promises faster relationship queries for the club. Give its designers a request with a known answer. On the original graph, the query must return five other people within three outgoing hops of Ada. How could the engine produce that answer faster?

  1. Which block holds Ada’s edges? Does a second query read it from storage again?
  2. Which access path finds Ben and Cyd? What does it cost to maintain that index or neighbor list when a follow changes?
  3. What durability does a success reply promise? Which failures can the recorded change survive?
  4. Does the plan expand Dee twice or mark her visited on the first discovery? Which counters show the difference?
  5. Who expands a member with 30 outgoing edges? Does sharing that list save time once the workers exchange results?

Test a proposed explanation with a benchmark, a measurement of a defined workload. Run both configurations on the same graph with the same depth, exclusions, and resource limits. Check the returned names before comparing response times. If the proposed benefit is caching, record storage reads on the first and second runs.

FAQ

Is Kuzu a real engine or a teaching toy?

Kuzu is an embedded graph engine with Cypher support. It stores data by column and processes batches of values, a technique called vectorized execution.

The original kuzudb/kuzu repository became read-only in October 2025. Its last release was 0.11.3. The archive supports this course example. Check maintenance and compatibility before choosing an engine for a new project. [13] [14] [19]

Why did we not cover [Mongo/Redis/Elasticsearch/…]?

The course emphasizes mechanisms used across products. MongoDB’s WiredTiger engine uses B-trees and a write-ahead log. Redis provides memory data structures and optional persistence. [15] [16]

Elasticsearch uses an inverted index, which maps terms to matching documents. Its immutable index segments remain unchanged while newer segments record later data. These mechanisms connect to indexes, version handling, and compaction studied earlier. [17]

What should I study next?

Choose a topic that interests you. For research depth, read Readings in Database Systems, followed by the Spanner and Aurora papers. For a broader view, read Kleppmann’s Designing Data-Intensive Applications. [18]

For implementation practice, extend microdb with versioned concurrency, a log-structured merge-tree (LSM) engine, or query-optimizer rules. Multiversion concurrency control, or MVCC, keeps versions so transactions can use appropriate read views. These are optional extensions. Measure their results.

Will the project rubric reward a GraphRAG attempt?

The rubric rewards evidence for design choices. Compare graph-based retrieval with the baseline. Report improvements, unchanged results, and regressions. Adding a graph without evaluating its effect does not demonstrate improvement.
