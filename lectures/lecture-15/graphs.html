The question we will trace

Start with what you already know

An edge table contains src and dst. How would a join find Ada’s outgoing neighbors? If two routes end at Dee, does a query for distinct people need two copies of Dee?

Quiz 11 first (Bigtable, LSM & NoSQL, 10 min, the last quiz), then graph storage, traversal queries, and the course review.

A one-hop relationship query finds a node’s immediate neighbors. Repeating that operation finds longer paths. Joins, recursive CTEs, and graph query operators can all express these expansions, but may produce different intermediate results. We will distinguish finding reachable nodes from enumerating paths.3

Today’s main idea: storing adjacency makes repeated neighbor lookup cheaper. Graph databases combine that storage choice with query operators for paths and relationships.

Compare repeated joins with graph traversal

Path enumeration and reachability do different work

A join matches a person’s key to relationship rows. Stored adjacency retains neighbor references for later expansion. On a campus map, intersections represent nodes and directed paths represent edges. Listing routes and listing distinct destinations are different queries. The map alone does not select an algorithm.

Count paths and reachable people separately

Distinguish walks from distinct people before comparing costs. A walk follows directed edges and can revisit a person. Predict the endpoints after two hops. Compare them with the frontier of previously unvisited people. A repeated endpoint does not add a person.

Worked result: At depth two, walk endpoints are [dee, ada, dee, eli]. Visited-set reachability adds only [dee, eli]. Through depth three, BFS examines eight outgoing edges and finds five other people. Bounded walk enumeration produces eleven rows before exclusions.

Compare work for the same result

The small graph shows why counting paths and counting reached people can require different amounts of work. Now generalize those counts. Require both algorithms to return the same kind of result before comparing their work estimates.

A relational join finds neighbors by matching keys, often with a hash table or index. An adjacency-oriented graph store uses stored neighbor references. With average degree d, paths of length k can produce approximately dk rows before deduplication. Reachability with a visited set has a different bound:

\[ \text{join chain: } k \text{ joins, about } d^{k} \text{ intermediate rows before dedup} \] \[ \text{visited-set traversal: } O(V_r + E_r) \text{ over reached vertices and examined edges} \]

Adjacency storage can reduce neighbor-lookup costs, but the algorithm and query semantics determine how many edges or paths must be explored. Benchmark the same result requirement in both engines.

Distinguish neighbor lookup from path enumeration

For reachability, a breadth-first traversal with a visited set expands each reached node once and examines its outgoing edges. A bounded path query may instead enumerate multiple paths to the same node. Those are different amounts of work, whether the query is written in SQL or Cypher.

Count edges and paths separately. A visited-set traversal and a query enumerating all bounded paths need not perform the same work.

Graph-oriented storage and path operators can reduce work, but writing a query in SQL or Cypher does not by itself guarantee a faster plan.

Store nodes, edges, and their properties

A person is a node. A follows relationship is a directed edge. Names and dates are properties. Stored adjacency lets a query read neighbor references directly. Adding or removing an edge must also update those references.

The property-graph model used by many graph databases (Neo4j, Kuzu, Neptune, Memgraph):3

node   (:Student {name: 'ada', gpa: 39})       a labeled record with properties
edge   (ada)-[:Follows {since: 2026}]->(ben)   a typed, directed relationship

ada’s neighbors: outgoing [ben, cyd]; incoming [ben, fay]
adjacency storage keeps references for locating these neighbors

Adjacency speeds lookup but adds storage and update work

AdjacencyStoring adjacency records the connection when an edge is added. A later traversal can use the stored neighbor reference instead of matching the endpoints’ keys again.4
Update costAs with an index, writes maintain extra structure so reads can do less lookup work. The benefit depends on how often the application traverses those relationships.
The failure modeA supernode has far more edges than other nodes. Traversing it may require inspecting a large neighbor list. This is a form of skew: a small part of the graph accounts for much of the work.

Express paths with SQL or Cypher

Noor asks Maya to express the same bounded question in two languages. Keep the starting person, edge direction, depth, exclusions, and duplicate handling identical. Compare those rules before comparing the plans.

In Cypher, *1..3 means a path of one to three edges

-- DuckDB / Postgres: a loop, spelled as algebra
WITH RECURSIVE reach(name, depth) AS (
    SELECT 'ada', 0
  UNION ALL
    SELECT f.dst, r.depth + 1
    FROM reach r JOIN follows f ON f.src = r.name
    WHERE r.depth < 3
)
SELECT DISTINCT name FROM reach WHERE name <> 'ada' ORDER BY name;
// Cypher: the pattern IS the query, draw the arrow, star the depth
MATCH (a:Student {name: 'ada'})-[:Follows*1..3]->(b)
WHERE b.name <> 'ada'
RETURN DISTINCT b.name ORDER BY b.name

The Cypher pattern ( )-[ ]->( ) represents nodes, a relationship, and its direction. The *1..3 range specifies path lengths directly. Both SQL and Cypher compile to execution plans, but Cypher gives path queries dedicated syntax. Kuzu also provides * SHORTEST for the shortest-path query in the demo.

Use a shortest-path query to return the connecting route

Query 4 requests a shortest path from ada to fay. Kuzu uses a path operator in MATCH. A SQL implementation must express the search and stopping rules. Graph query languages can help express routes, dependency chains, and connections between entities.6

Case study: investigating relationships in the Panama Papers

Case study · the Panama Papers, 2016

The Panama Papers investigation examined 11.5 million leaked documents from Mossack Fonseca. Investigators connected people, companies, and intermediaries across records. ICIJ used Neo4j and a visual interface to help reporters inspect these relationships. The investigation later won a Pulitzer Prize. Reporters needed to follow connections without knowing their depth in advance. A graph interface supported that work.91011

Combine text similarity with entity relationships

The blind spotVector retrieval ranks chunks by similarity to the question. A question that requires evidence from several documents may need connections that do not appear in any single highly ranked chunk.
Graph-based retrievalDuring ingestion, extract or label entities and relationships. Link them to source chunks. Graph-based retrieval can use those links to select additional evidence. The cited GraphRAG paper also builds community summaries for questions about the complete corpus. Its method extends beyond one-hop expansion.12
Combining methodsVector search and graph-based retrieval select evidence using different signals. Combining them may recover useful passages that either method misses alone. Evaluate that benefit on questions with labeled sources.

FAQ

Is Kuzu real enough to use, or a teaching toy?

Kuzu is an embedded graph engine with columnar storage, vectorized execution, and Cypher support. It supports this local demonstration. The original kuzudb/kuzu repository became read-only in October 2025. Its last release was 0.11.3. Check maintenance and compatibility before selecting it for a new project. The archive remains available for this course example.131419

Why did we not cover [Mongo/Redis/Elasticsearch/…]?

This course emphasizes mechanisms used across products. MongoDB’s WiredTiger engine uses B-trees and a write-ahead log. Redis provides memory data structures and optional persistence. Elasticsearch uses inverted indexes and immutable segments. Their architecture documentation connects these systems to the mechanisms covered here.151617

What should I learn next after this course?

Choose a topic that interests you. For research depth, read Readings in Database Systems, followed by the Spanner and Aurora papers. For a broader view, read Kleppmann’s Designing Data-Intensive Applications. For implementation practice, add MVCC, an LSM engine, or optimizer rules to microdb. Measure the results.18

Will the project rubric reward a GraphRAG attempt?

The rubric rewards evidence for design choices. Compare graph-based retrieval with the baseline. Report improvements, unchanged results, and regressions. Adding a graph without evaluating its effect does not demonstrate improvement.
