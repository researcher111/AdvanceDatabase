Graph Databases & Course Synthesis

How do graph databases store relationships, and when does traversal make a query easier to express or faster to run?
Daniel G. Graham · UVA School of Data Science

Relationship queries can require repeated expansion: “Who follows ada?” asks for immediate neighbors, while “Who is within three hops of ada?” explores several levels. SQL can express these queries with joins or recursive CTEs. Graph databases provide adjacency-oriented storage and path operators designed for this work. We will compare the approaches using a small Kuzu demo, then review five database ideas that recur across the course.1

Companion reading: Kuzu's documentation (setup and Cypher examples) · Robinson, Webber & Eifrem, Graph Databases (free O'Reilly text) · Microsoft's From Local to Global: GraphRAG paper.

A one-hop relationship query finds a node’s immediate neighbors. Repeating that operation finds longer paths. Joins, recursive CTEs, and graph query operators can all express these expansions, but may produce different intermediate results. We will distinguish finding reachable nodes from enumerating paths.3

Today’s main idea: storing adjacency makes repeated neighbor lookup cheaper. Graph databases combine that storage choice with query operators for paths and relationships.

Compare repeated joins with graph traversal

A relational join finds neighbors by matching keys, often through a hash table or index. An adjacency-oriented graph store finds them through stored neighbor references. With average degree d, enumerating paths of length k can generate roughly dk rows before duplicate nodes are removed. A reachability traversal with a visited set has a different bound:

\[ \text{join chain: } k \text{ joins, about } d^{k} \text{ intermediate rows before dedup} \] \[ \text{visited-set traversal: } O(V_r + E_r) \text{ over reached vertices and examined edges} \]

Adjacency storage can reduce neighbor-lookup costs, but the algorithm and query semantics determine how many edges or paths must be explored. Benchmark the same result requirement in both engines.

Distinguish neighbor lookup from path enumeration

For reachability, a breadth-first traversal with a visited set expands each reached node once and examines its outgoing edges. A bounded path query may instead enumerate multiple paths to the same node. Those are different amounts of work, whether the query is written in SQL or Cypher.

how a row's neighbors are foundby matching the frontier’s keys to relationship rows, using the join plan selected by the engineby reading stored neighbor references. The physical access may still require cache or storage reads
a node reachable by several routesa path-enumerating join chain can produce several rows for the same node; intermediate or final deduplication changes that workcan be marked visited once in a reachability algorithm; path enumeration may revisit it

Count edges and paths separately. A visited-set traversal and a query enumerating all bounded paths need not perform the same work.

Graph-oriented storage and path operators can reduce work, but neither notation guarantees a faster plan.

Store nodes, edges, and their properties

The property-graph model used by many graph databases (Neo4j, Kuzu, Neptune, Memgraph):3

node   (:Student {name: 'ada', gpa: 39})       a labeled record with properties
edge   (ada)-[:Follows {since: 2026}]->(ben)   a typed, directed relationship

ada’s neighbors: outgoing [ben, cyd]; incoming [ben, fay]
adjacency storage keeps references for locating these neighbors

Adjacency speeds lookup but adds storage and update work

AdjacencyStoring adjacency records the connection when an edge is added. A later traversal can use the stored neighbor reference instead of matching the endpoints’ keys again.4
Update costAs with an index, writes maintain extra structure so reads can do less lookup work. The benefit depends on how often the application traverses those relationships.
The failure modeA supernode has far more edges than other nodes. Traversing it may require inspecting a large neighbor list. This is a form of skew: a small part of the graph accounts for much of the work.

Express paths with SQL or Cypher

SQL’s WITH RECURSIVE defines a query that repeatedly uses one iteration’s results to produce the next. A depth condition or cycle-handling rule bounds the traversal. Below, a recursive SQL query and a Cypher query answer the same question on the six-student dataset; both return ben cyd dee eli fay.5

In Cypher, *1..3 means a path of one to three edges

-- DuckDB / Postgres: a loop, spelled as algebra
WITH RECURSIVE reach(name, depth) AS (
    SELECT 'ada', 0
  UNION ALL
    SELECT f.dst, r.depth + 1
    FROM reach r JOIN follows f ON f.src = r.name
    WHERE r.depth < 3
)
SELECT DISTINCT name FROM reach WHERE name <> 'ada' ORDER BY name;
// Cypher: the pattern IS the query, draw the arrow, star the depth
MATCH (a:Student {name: 'ada'})-[:Follows*1..3]->(b)
WHERE b.name <> 'ada'
RETURN DISTINCT b.name ORDER BY b.name

The Cypher pattern ( )-[ ]->( ) represents nodes, a relationship, and its direction. The *1..3 range specifies path lengths directly. Both SQL and Cypher compile to execution plans, but Cypher gives path queries dedicated syntax. Kuzu also provides * SHORTEST for the shortest-path query in the demo.

Use a shortest-path query to return the connecting route

Query 4 asks for a shortest path from ada to fay. Kuzu expresses it with a path operator in MATCH; a SQL implementation would need to express the search and stopping rules. Queries that return routes, dependency chains, or connections between entities are good candidates for a graph query language.6

Case study: investigating relationships in the Panama Papers

Case study · the Panama Papers, 2016

The Panama Papers investigation examined 11.5 million leaked documents from Mossack Fonseca. Investigators needed to connect people, companies, and intermediaries across records. ICIJ used Neo4j and a visual interface to help reporters explore those relationships. The investigation later won a Pulitzer Prize. The example shows the value of matching the query interface to the work: reporters needed to follow and inspect connections whose depth was not known in advance.91011

Combine text similarity with entity relationships

The blind spotVector retrieval ranks chunks by similarity to the question. A question that requires evidence from several documents may need connections that do not appear in any single highly ranked chunk.
Graph-based retrievalDuring ingestion, extract or label entities and relationships, then link them to the source chunks. Graph-based retrieval can use those links to select additional evidence. The cited GraphRAG paper also builds community summaries for questions about the corpus as a whole; it is more than a one-hop expansion.12
Combining methodsVector search and graph-based retrieval select evidence using different signals. Combining them may recover useful passages that either method misses alone. Evaluate that benefit on questions with labeled sources.

Try a limited one-hop entity expansion

GraphRAG is an optional project extension. A limited experiment is to tag chunks with entities and record selected relationships between those entities. When a question names an entity, add chunks associated with its direct neighbors to the vector-search results. Compare the combined retrieval with the baseline on the same evaluation questions.

Use these ideas to understand an unfamiliar system

These five ideas give you useful questions to ask about a new system: How is data stored? What does it cache? Which indexes does it maintain? How does it recover? How is work planned and partitioned? The answers will not explain every feature, but they provide a starting point for evaluating the system’s design and tradeoffs.

Final recap

  • Adjacency-oriented storage records relationships so traversal can avoid repeated key matching. Graph query operators are useful when paths or variable-depth connections are central to the workload.
  • Cypher provides direct path syntax. SQL recursive CTEs can also traverse relationships; compare queries with the same result requirements and cycle rules.
  • Blocks and caching, indexes, recovery, query plans, and partitioning recur throughout the course. Use them to explain how a system processes a workload.

FAQ

Is Kuzu real enough to use, or a teaching toy?

Kuzu is an embedded graph engine with columnar storage, vectorized execution, and Cypher support. It is useful for this local demonstration. The original kuzudb/kuzu repository was archived read-only in October 2025, with 0.11.3 as its last release. Check maintenance and compatibility before choosing it for a new project; the archive remains available for the course example.131419

Why did we not cover [Mongo/Redis/Elasticsearch/…]?

The course emphasizes mechanisms that transfer across products. MongoDB’s WiredTiger engine uses B-trees and a write-ahead log; Redis offers in-memory data structures and optional persistence; Elasticsearch uses inverted indexes and immutable segments. Their architecture documentation will let you connect those systems to the ideas covered here.151617

What should I learn next after this course?

Choose a direction that interests you. For research depth, read Readings in Database Systems and the Spanner and Aurora papers. For a broader systems view, read Kleppmann’s Designing Data-Intensive Applications. For implementation practice, extend microdb with MVCC, an LSM engine, or more optimizer rules, and measure the results.18

Will the project rubric reward a GraphRAG attempt?

The rubric rewards evidence for your design choices. If you add graph-based retrieval, compare it with the baseline and report where it helps, has no effect, or makes results worse. Adding a graph without evaluating its effect does not demonstrate an improvement.
