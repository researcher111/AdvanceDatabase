Graph Databases & the Course, Closed

When relationships are the data, plus the five ideas you actually learned this semester, wearing fifteen different costumes.
Daniel G. Graham · UVA School of Data Science

One data shape has quietly resisted everything we've built: deep relationships. "Who follows ada?" is a join; "who's within three hops of ada?" is a join chained onto a join onto a join, with SQL getting longer and the plan getting worse at every depth. Graph databases store the relationships as pointers on the data itself and replace join chains with traversal; you'll watch it live in Kuzu, an embeddable graph engine that is to Neo4j what DuckDB is to Postgres. Then the real last act: the whole semester compressed to five ideas, and the argument that every system you'll meet for the rest of your career is a remix of them.

Companion reading: Kuzu's documentation (install to Cypher in ten minutes) · Robinson, Webber & Eifrem, Graph Databases (free O'Reilly text) · Microsoft's From Local to Global: GraphRAG paper.

Show the answer

One self-join per hop. The text grows linearly, one more JOIN follows per level, and the intermediate result grows like dk for average degree d and depth k, since the middle of the plan must materialise every path before the final filter thins it. Three hops on a graph with average degree 100 is a million-row intermediate to answer a question whose answer might be twelve names. And nobody writes the 5-hop version by hand; there is a WITH RECURSIVE answer, but you had to reach for it, which is itself the lesson about notation.

The waste is that every hop re-discovers the neighbours by matching keys, even though the neighbours never changed between queries. So the fix is to store the answer with the row: keep on each node a list of pointers to its actual neighbours, an adjacency list. Then a hop is a pointer-follow instead of an index probe, and the key matching is paid once at insert rather than once per query per hop. That is a graph database, and it is the same trade as an index in Lab 6: pay organisation on write, skip work forever after.

The two cost models

relational:  each hop = a JOIN     · find neighbors by MATCHING KEYS (hash/index probe per row)
graph:       each hop = a WALK     · find neighbors by FOLLOWING POINTERS stored on the node

k hops from one start node, average degree d:
    join chain:  k joins; intermediates ~ d^k rows before dedup; planner sweats at every step
    traversal:   visit ~ d^k nodes, each neighbor list one pointer-follow away, no matching

same asymptotics, wildly different constants, and the constant is the product.

The property graph

The data model every mainstream graph database shares (Neo4j, Kuzu, Neptune, Memgraph):

node   (:Student {name: 'ada', gpa: 39})          a record with a label + properties
edge   (ada)-[:Follows {since: 2026}]->(ben)      ALSO a record: typed, directed, with properties

storage:  each node keeps its adjacency lists, Follows-out: [ben, cyd], Follows-in: [fay]
          neighbors are reachable without consulting any index: index-free adjacency

Say it in this course's vocabulary: a graph database materializes the join at write time. Adding the edge does the key-matching once; every future traversal follows the stored pointer. The trade should feel familiar by now: it's the index trade (Lab 6) with the cost moved to a different operation: writes pay, reads ride. Even the failure mode is familiar: a supernode is skew (Lecture 13) wearing a graph costume.

Cypher vs recursive SQL

SQL can traverse: WITH RECURSIVE is a loop in the algebra, and it's genuinely how you should do shallow graph work in Postgres or DuckDB. The same question, both notations, both verified against their engines on the six-student data (both return ben cyd dee eli fay):

"Everyone within 3 hops of ada"

-- DuckDB / Postgres: a loop, spelled as algebra
WITH RECURSIVE reach(name, depth) AS (
    SELECT 'ada', 0
  UNION ALL
    SELECT f.dst, r.depth + 1
    FROM reach r JOIN follows f ON f.src = r.name
    WHERE r.depth < 3
)
SELECT DISTINCT name FROM reach WHERE name <> 'ada' ORDER BY name;
// Cypher: the pattern IS the query, draw the arrow, star the depth
MATCH (a:Student {name: 'ada'})-[:Follows*1..3]->(b)
WHERE b.name <> 'ada'
RETURN DISTINCT b.name ORDER BY b.name

The Cypher pattern ( )-[ ]->( ) is ASCII art of the graph itself: nodes in parens, edges in brackets, direction as an arrow. Notation matters here the way it did in week 5: both compile to plans; one keeps the human honest about what's being asked. *1..3 replaced the entire recursive CTE, and * SHORTEST (in the demo) replaces an algorithm SQL can't comfortably spell at all.

Live demo: Kuzu

Kuzu is the DuckDB of graph databases: pip install kuzu, embedded in your process, no server. The demo script loads the six students and runs four queries; outputs below are the real thing, so the demo survives a typo-prone instructor:

    ['cyd']

--- 2 · two hops: friends-of-friends (not ada, not already followed)
    ['dee']
    ['eli']

--- 3 · variable length: everyone within 3 hops of ada
    ['ben'] ['cyd'] ['dee'] ['eli'] ['fay']

--- 4 · shortest path: how does ada reach fay?

Query 4 is the one to savor: how does ada reach fay is a shortest-path search (BFS under the hood) expressed in one MATCH. Ask it of the SQL version and you're implementing Dijkstra in a CTE; ask it of Kuzu and it's Tuesday. When the path itself is the answer (recommendations, fraud rings, lineage, dependency chains) that's the graph database's home turf.

War story · the Panama Papers, 2016

The second row of that table won a Pulitzer. When 11.5 million leaked documents from the law firm Mossack Fonseca reached the International Consortium of Investigative Journalists, the questions that mattered were pure traversal: which officers connect to which shell companies, through which intermediaries, to which real owners: paths of unknown depth through millions of entities. ICIJ loaded the extracted entities and relationships into Neo4j and gave hundreds of reporters a visual graph-query front end; reporters with no database training followed edges to prime ministers. The relational version of that investigation is a self-join per hop with the hops unknown in advance; possible, and nobody would have finished it. Data model chosen to match the question: that's the course's thesis, holding up under journalism's brightest spotlight.

GraphRAG

Your project retrieves by similarity: question vector → nearest chunks. Its known blind spot is questions whose answer is spread across documents ("how do the WAL and the buffer pool interact?"; no single chunk says it). GraphRAG's move: extract an entity graph from the corpus at ingest (WAL constrains→ page flushing; buffer pool defers→ writes), retrieve by traversing from mentioned entities, and hand the LLM connected subgraphs instead of disconnected paragraphs. Similarity finds what a question sounds like; traversal finds what it's connected to; knowledge-graph retrieval and vector retrieval compose, and hybrid is the production pattern. An optional extension in the project spec; one past-team-sized bite is entity-tagging your chunks and adding a 1-hop expansion to retrieval.

The five the course keeps re-using: block I/O and caching (file manager and buffer pool, then SSTable blocks, Parquet row groups, shuffle spill files); sorting and indexes (B+ tree, then IVF lists, Bloom-filtered SSTables, Hive partitions, adjacency lists); log first, reorganise later (the WAL, then LSM trees, Delta and Iceberg commit logs, Spark lineage); declarative query, plan, execute (parser and planner and iterators, then EXPLAIN, Spark's DAG, Cypher's MATCH); and partition to scale (the shuffle you hand-wrote, then tablets, IVF lists, Hive folders).

Two tests for a candidate. Does it appear in at least three separate weeks, and is it an idea rather than a technology? "SQL" fails the second test; it is a notation, and the idea underneath it is the declarative one. A defensible sixth exists and tables often nominate it: keep the old version rather than overwriting, which links tombstones, MVCC, LSM compaction and time travel in Iceberg. Whether that is its own idea or a corollary of log-first is exactly the argument worth having in the room.

FAQ

Is Kuzu real enough to use, or a teaching toy?

Real: columnar storage, a vectorized query processor, full Cypher, active development, and it holds its own on benchmarks against Neo4j for embedded analytics. Like DuckDB, its niche is in-process work rather than serving a fleet of concurrent clients. For a server deployment with users and auth, Neo4j or Neptune; for "I have a graph problem in a notebook," Kuzu is exactly right.

Why did we not cover [Mongo/Redis/Elasticsearch/…]?

Deliberate: those are products, and products rotate. Mongo is a document store over a B+ tree engine (WiredTiger) with a WAL; Redis is a data-structure server with an append-only log; Elasticsearch is inverted indexes (BM25, Lecture 12) over segment files that behave like SSTables. You have the parts list. An afternoon with any of their architecture pages will slot them into the five-ideas table; try it; it's the best exam this course doesn't give.

What should I learn next after this course?

Three worthy directions, pick by taste: depth, read the Red Book (Bailis, Hellerstein, Stonebraker's Readings in Database Systems) and the Spanner and Aurora papers; breadth, Kleppmann's Designing Data-Intensive Applications, which is this course's Act II at production scale; craft, extend microdb (MVCC, an LSM engine, the optimizer); nothing teaches like the engine you already own.

Will the project rubric reward a GraphRAG attempt?

Only the measured kind. A 1-hop entity expansion with an eval table showing where it helped (and where it hurt; it will, on some questions) earns real credit; a bolted-on graph with no measurement earns sympathy. The rubric's spine all semester has been the same sentence: show the numbers that made you decide.
