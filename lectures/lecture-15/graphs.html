1 · Decide whether the answer is routes or people

Open slide 1 ↗

A graph represents things and their connections. A node, also called a vertex, represents one thing. An edge represents one connection.

A directed edge has a source and destination. The arrow ada → ben means Ada follows Ben. It does not by itself mean Ben follows Ada.

A hop follows one edge. A route with two edges has two hops. Distinct means each person appears once in the result, even when several routes reach that person.

Think of a campus map with one-way routes. Intersections represent nodes and arrows represent edges. Listing routes and listing destinations answer different questions.

The map explains connections and direction. It does not specify file layout, query cost, or which routes an algorithm should explore.

Our graph has 6 students and 9 directed follows edges. We use lowercase names as identifiers throughout the code and diagrams.

QuestionRequired resultWhat repeated routes mean
Which people can Ada reach?Distinct student namesDee appears once.
Which routes connect Ada to Dee?Sequences of connected studentsada → ben → dee and ada → cyd → dee are different routes.
How can Ada reach Fay with the fewest hops?A shortest routeThe answer includes the connecting students, not only Fay’s name.

State the result before choosing the algorithm. SQL and graph query languages can both express relationship questions. Their query rules and the operations chosen by the engine determine the work.

2 · Represent people and relationships as a graph

Open slide 2 ↗

A property is a named value attached to a node or edge. A label, such as Student, identifies a node category. A relationship type, such as Follows, identifies an edge category.

A property graph combines these nodes, typed edges, and properties. Ada’s GPA belongs to her node. The year a follow relationship began belongs to that edge.

The notation below draws nodes with parentheses and edges with brackets and arrows. Named values appear inside braces. The integer gpa: 39 stores GPA in tenths, so it represents 3.9.

An outgoing neighbor is a destination reached by following an arrow from a node. An incoming neighbor has an arrow pointing to that node. Adjacency means the direct connections between nodes.

node   (:Student {name: 'ada', gpa: 39})       a labeled record with properties
edge   (ada)-[:Follows {since: 2026}]->(ben)   a typed, directed relationship

ada’s neighbors: outgoing [ben, cyd]; incoming [ben, fay]
adjacency storage keeps references for locating these neighbors

The since: 2026 property illustrates the model. The supplied Kuzu script stores student GPA values but does not add that edge property. The physical storage can differ across graph engines. [3]

Predict, then explain

Where should we store the year Ada began following Ben: Ada’s node, Ben’s node, or their Follows edge?

Check your explanation

Store it on their Follows edge because the year describes that particular relationship. Ada can begin following another student in a different year.

3 · Store neighbor references for later queries

Open slide 3 ↗

An edge table stores one row per relationship. Its src column names the source, and dst names the destination.

To find Ada’s outgoing neighbors, select rows where src = 'ada'. An index is a maintained search structure for locating data. An index on src can locate those rows. Without a suitable access structure, the engine may scan more rows.

An adjacency list stores a node’s neighbor references or incident edges. A reference identifies where to find the connected node. Ada’s outgoing list contains [ben, cyd].

A traversal follows relationships through a graph. To expand a node means inspect its relevant neighbor list. Stored adjacency lets a traversal reuse connections established when edges were written.

The engine must maintain that structure when an edge changes. This resembles an index: extra write work can reduce later lookup work. [4]

References need not be raw memory pointers. Engines use different stored representations, and accessing them can still require storage reads.

Adjacency can reduce neighbor-lookup work. It does not remove the work of inspecting many neighbors or enumerating many routes.

4 · Follow one outgoing relationship

Open slide 4 ↗

The first question is: Who does Ada follow? One hop follows each outgoing edge once. The destinations are ben and cyd.

A result set contains each answer once, so we write {ben, cyd}. An ordered list can contain repeated values. The difference becomes visible after two hops.

Predict, then explain

Reverse the question: who follows Ada? Which arrows and result should the query use?

Check your explanation

Use incoming arrows. Ben and Fay follow Ada, so the result is {ben, fay}. This differs from Ada’s outgoing neighbors.

5 · Find new contacts through two relationships

Open slide 5 ↗

The second question is: Which new contacts can Ada reach through exactly two follows relationships? Exclude Ada and people she already follows directly.

A walk is a sequence that follows edges and can revisit nodes or edges. Its endpoint is the final node. Here are all four two-hop walks from Ada.

Two-hop walkEndpointEffect on the distinct-person result
ada → ben → deedeeKeep Dee.
ada → ben → adaadaExclude the starting person.
ada → cyd → deedeeDee is already included.
ada → cyd → elieliKeep Eli.

Deduplication removes repeated result values. Applying the exclusions and deduplicating endpoints gives {dee, eli}. Neither remaining student is already Ada’s outgoing neighbor.

The term path can carry stricter repeat rules in graph theory or a query language. We use walk when repeats are allowed. Check an engine’s path rules before assuming the same syntax returns the same routes.

Predict, then explain

If the question asks for both routes to Dee, should deduplication keep only one route?

Check your explanation

No. The two sequences are different answers. Removing a repeated endpoint is appropriate only when the query asks for distinct people.

6 · Explore distance layers with a visited set

Open slide 6 ↗

Reachability asks which nodes can be reached from a start under the chosen direction and depth limit. Breadth-first search, or BFS, explores nodes in increasing hop distance.

The frontier contains newly discovered nodes waiting for the next expansion. The visited set records every node already discovered. A discovered node enters the frontier only once.

A depth bound limits how many edges a route may use. Starting at Ada, the algorithm expands frontiers through depth 3. Nodes first discovered at depth 3 are returned but are not expanded further.

Distance from AdaNew frontierVisited after discovery
0[ada]{ada}
1[ben, cyd]{ada, ben, cyd}
2[dee, eli]{ada, ben, cyd, dee, eli}
3[fay]All six students

A cycle follows directed edges back to an earlier node. For example, ada → ben → ada returns to the start. The visited set prevents that return from restarting the same expansion.

BFS tracks people already reached, not every route to them. This saves repeated expansion when the required answer is distinct reachability.

Predict, then explain

Ben and Cyd both lead to Dee. How many times should a visited-set BFS add Dee to the frontier?

Check your explanation

Once. The first discovery records Dee as visited. The second route does not create another person or require another expansion of Dee.

7 · Count walks and distinct people separately

Open slide 7 ↗

A self-join matches a table with another use of that same table. A join chain repeatedly matches relationship sources to the previous endpoints.

Without intermediate deduplication, each walk contributes another result row. Repeated people can therefore appear many times. This can be correct when the question requires walks.

DepthWalk endpoints at exactly this depthNew distinct peopleOutgoing edges examined by BFS in this round
1[ben, cyd] · 2 rows[ben, cyd]2 from Ada
2[dee, ada, dee, eli] · 4 rows[dee, eli]4 from Ben and Cyd
3[eli, ben, cyd, eli, fay] · 5 rows[fay]2 from Dee and Eli

The walk enumeration produces 2 + 4 + 5 = 11 rows, excluding the starting row. BFS examines 2 + 4 + 2 = 8 outgoing edges and finds 5 other people.

The ninth edge, fay → ada, is beyond this BFS expansion bound. Fay is first discovered at depth 3, so the search does not expand Fay.

Worked result: At depth two, walk endpoints are [dee, ada, dee, eli]. Visited-set reachability adds only [dee, eli]. Through depth three, BFS examines eight outgoing edges and finds five other people. Bounded walk enumeration produces eleven rows before exclusions.

Compare work for the same result

The out-degree of a node is its number of outgoing edges. Let d be average out-degree and k the requested walk length. With roughly d choices at each expansion, the number of length-k walks can grow approximately as dk.

This branching estimate assumes repeated expansion without pruning or deduplication. Uneven degrees and query restrictions can change it. Count one edge-table join per expansion from the starting row.

For visited-set traversal, Vr counts reached vertices, including the start. Er counts examined outgoing edges under the bound. Big-O notation describes how work grows with those counts, rather than a measured runtime.

\[ \text{join chain: } k \text{ joins, about } d^{k} \text{ intermediate rows before dedup} \] \[ \text{visited-set traversal: } O(V_r + E_r) \text{ over reached vertices and examined edges} \]

The traversal bound assumes efficient neighbor access and visited-set membership checks. A cache keeps reusable data in memory to avoid repeated storage reads. Storage access and query planning also affect runtime. Compare the same required result before timing either engine.

8 · Express the same question in SQL and Cypher

Open slide 8 ↗

Cypher is a graph query language that describes relationship patterns. MATCH selects matching patterns. An operator is a query operation, such as following edges or removing duplicates.

The pattern (a)-[:Follows]->(b) names a source, relationship type, direction, and destination. The pattern [:Follows*1..3] allows one to three edges.

A common table expression, or CTE, names a temporary query result. A recursive CTE uses earlier results to produce another round. Its seed supplies the starting rows.

Both queries below ask for distinct students reachable from Ada within three outgoing hops, excluding Ada. Read the query parts before comparing their results.

SQL partRole in this example
SELECT 'ada', 0Seed the computation with Ada at depth 0.
JOIN follows f ON f.src = r.nameExpand each earlier endpoint through its outgoing relationships.
r.depth + 1 and r.depth < 3Count each hop and stop expanding after depth 3.
UNION ALLRetain repeated rows produced by different walks.
WHERE name <> 'ada'Exclude the starting person.
DISTINCT and ORDER BYRemove repeated names and sort the final output.
 
-- DuckDB / Postgres: a loop, spelled as algebra
WITH RECURSIVE reach(name, depth) AS (
    SELECT 'ada', 0
  UNION ALL
    SELECT f.dst, r.depth + 1
    FROM reach r JOIN follows f ON f.src = r.name
    WHERE r.depth < 3
)
SELECT DISTINCT name FROM reach WHERE name <> 'ada' ORDER BY name;
// Cypher: the pattern IS the query, draw the arrow, star the depth
MATCH (a:Student {name: 'ada'})-[:Follows*1..3]->(b)
WHERE b.name <> 'ada'
RETURN DISTINCT b.name ORDER BY b.name

The SQL recursion generates 11 walk rows across depths 1–3, plus the seed. Final exclusion and DISTINCT return [ben, cyd, dee, eli, fay]. The Kuzu query returns the same five names on this fixture.

Final deduplication is different from preventing repeated expansion. Here, the engine may generate repeated endpoints before the final DISTINCT. That is not the visited-set BFS from section 6.

Replacing UNION ALL with UNION removes duplicate whole rows. It does not merge (ada, 0) with (ada, 2), because their depths differ. Keep an explicit stopping or cycle rule. [2] [5]

Kuzu’s default variable-length relationship semantics are WALK: nodes and edges can repeat. Other engines or options can use different rules. Kuzu MATCH documentation.

An execution plan is the sequence of operations the engine chooses to run a query. Both languages compile to plans. Syntax alone does not guarantee a faster plan.

9 · Reconstruct a shortest route

Open slide 9 ↗

A shortest path here is a directed route with the fewest edges. Each edge has the same cost: one hop. BFS reaches nodes in increasing hop count, so its first discovery of Fay has minimum hop distance.

A predecessor records which node led to a new discovery. The first discoveries on the route to Fay record cyd ← ada, eli ← cyd, and fay ← eli.

Follow predecessor records backward from Fay, then reverse that sequence. The route is ada → cyd → eli → fay, with three edges.

This diagram explains one BFS reconstruction. It does not claim that Kuzu uses exactly this internal implementation. Its query interface provides SHORTEST for requesting the route. [6]

A weight is an edge’s cost, such as travel time. With unequal weights, the fewest hops need not give the lowest total cost. That question needs a search that accounts for weights.

Predict, then explain

Does the visited set alone tell us how to travel from Ada to Fay?

Check your explanation

No. It tells us Fay was reached. Predecessor records, or another route representation, are needed to reconstruct the connecting sequence.

10 · Account for nodes with many neighbors

Open slide 10 ↗

A supernode has far more incident edges than most other nodes. Skew means work is distributed unevenly, so a small part of the data accounts for much of the cost.

Locating a neighbor list quickly does not make a long list cheap to inspect. The diagram changes from 5 neighbors to 30. An expansion budget limits how many neighbors the query examines.

The hypothetical budget examines only 8 of the 30 neighbors. It saves work but can omit valid answers. This is a teaching example, not a recommended engine setting.

A more selective query can reduce the required neighbors. Specialized indexes can help locate those matches. Dividing a large list across workers can spread work, but communication and coordination also cost time.

Predict, then explain

The query requires every reachable person. Can a 30-to-8 neighbor cap preserve that guarantee without further evidence?

Check your explanation

No. An omitted neighbor can lead to a required person. State any limit and measure missing results before claiming the same answer.

11 · Choose a system for the required query

Open slide 11 ↗

Start with the required query, then consider its data size, update pattern, and response time. A graph-shaped drawing alone does not justify another database.

A foreign key references a key in another table. A fixed department lookup can use a join between student and department tables.

Whole-graph analytics repeatedly processes large portions of a graph. PageRank computes link-based importance scores. Community detection identifies groups with strong internal connections.

Required workReasonable starting pointWhat to check
Fixed, shallow relationships, often 1–2 hopsSQL joinsInspect the join plan and indexes. Measure the workload before adding another store.
Variable-depth connections or route-shaped resultsA graph query engineConfirm depth, direction, repeat rules, and shortest-path behavior. Kuzu supplies our teaching example. Neo4j is another graph engine.
Whole-graph scores or communitiesA graph analytics tool or database analytics featureCompare dataset size and algorithm support in tools such as NetworkX and Spark GraphFrames. [8]
Relationships already handled well by foreign keys and SQLThe existing relational systemA second graph copy adds synchronization and maintenance work.

These are starting choices, not performance guarantees. Compare equivalent results and include the cost of keeping stored relationships current.

12 · Use relationships to connect source passages

Open slide 12 ↗

Retrieval-augmented generation, or RAG, retrieves source passages before a language model writes an answer. A chunk is one stored passage. A corpus is the document collection.

Vector retrieval ranks chunks using similarity between their numeric representations and the question’s representation. Useful evidence can be spread across passages that do not all rank highly.

Consider the teaching question: Why must logging happen before a dirty page is written? A write-ahead log, or WAL, stores recovery information. A dirty page has changes not yet written to storage.

Source IDIllustrative passageNamed concept
log-notesWAL records recovery information before a changed page reaches storage.WAL
buffer-notesA dirty page has changes not yet written to storage.Buffer pool

The buffer pool holds working copies of storage pages. An entity is an identified person, object, or concept. Here, WAL and the buffer pool are entities linked to their source passages.

A knowledge graph stores entities and named relationships. Our illustrative edge says WAL protects page writes from the buffer pool. The edge must be justified by source evidence.

Start with the retrieved log-notes passage. Follow the relationship to the buffer-pool entity. Add its buffer-notes passage while retaining both source IDs.

An evidence union combines the selected passages from both retrieval methods. It can remove repeated chunk IDs, but it must preserve each retained chunk’s source identity.

This one-hop extension can supply related evidence. It does not prove that every added passage is relevant or that the generated answer is correct.

During ingestion, the system prepares documents for later queries. It can extract entities, record relationships, and link them to chunks. Wrong entity matches or unsupported edges can lead retrieval toward irrelevant evidence.

The cited Microsoft GraphRAG paper also groups related entities into communities and builds summaries for broad questions about the corpus. Our one-hop experiment illustrates only a smaller graph-based retrieval step. [12]

14 · Recognize five recurring database mechanisms

Open slide 14 ↗

The same questions connect graph storage to the earlier course. The table briefly restates each mechanism before naming its earlier examples.

MechanismWhat it doesCourse connections
Blocks and cachingRead stored data in chunks and keep useful copies in memory. I/O means input/output, including storage reads and writes.The file manager and buffer pool. Bigtable’s sorted-file blocks, Parquet’s groups of column data, and temporary shuffle files.
Sorting and indexesMaintain structures that help locate required data or skip irrelevant data.B+ trees, graph adjacency, and Bloom filters. Inverted file (IVF) vector indexes group vectors into searchable lists.
Logs and recoveryPreserve changes or instructions needed to recover work after failure.WAL and Bigtable recovery. Spark’s lineage records transformations for recomputation. Table-format metadata records committed data-file versions.
Declarative queries and plansDescribe the result, then let the engine plan operations that produce it.SQL parsing and execution, Spark plans, and Cypher MATCH.
PartitioningDivide data and work into portions while monitoring uneven load.Shuffle destinations, Bigtable’s row ranges, data folders, and IVF lists. Supernodes show why equal data portions can still have unequal work.

A contract states the behavior or guarantee a mechanism promises. A cached copy saves reads but does not by itself make a write durable. Spark lineage can recompute lost data but is not a transaction WAL.

Recognize the mechanism and its limits. Similar shapes in two systems can support different guarantees.

15 · Ask how an unfamiliar system does the work

Open slide 15 ↗

An access path is a way to find data, such as an index or adjacency list. Durability states which acknowledged writes survive the failures covered by the storage protocol.

Imagine a new database brochure promises fast relationship queries. Turn that promise into five concrete questions before choosing a benchmark.

  1. Which records share a stored block, and which blocks can the cache reuse?
  2. How does the engine find neighbors, and what must an edge update maintain?
  3. What information survives a crash after the caller receives success?
  4. Does the plan enumerate walks or avoid repeated expansion of visited nodes?
  5. How are data and work divided when one node has many neighbors?

A benchmark measures a defined workload under stated conditions. Test the required result, dataset, updates, and resource limits. These questions help investigate the design, but they do not explain every feature.

FAQ

Is Kuzu a real engine or a teaching toy?

Kuzu is an embedded graph engine with Cypher support. It stores data by column and processes batches of values, a technique called vectorized execution.

The original kuzudb/kuzu repository became read-only in October 2025. Its last release was 0.11.3. The archive supports this course example. Check maintenance and compatibility before choosing an engine for a new project. [13] [14] [19]

Why did we not cover [Mongo/Redis/Elasticsearch/…]?

The course emphasizes mechanisms used across products. MongoDB’s WiredTiger engine uses B-trees and a write-ahead log. Redis provides memory data structures and optional persistence. [15] [16]

Elasticsearch uses an inverted index, which maps terms to matching documents. Its immutable index segments remain unchanged while newer segments record later data. These mechanisms connect to indexes, version handling, and compaction studied earlier. [17]

What should I study next?

Choose a topic that interests you. For research depth, read Readings in Database Systems, followed by the Spanner and Aurora papers. For a broader view, read Kleppmann’s Designing Data-Intensive Applications. [18]

For implementation practice, extend microdb with versioned concurrency, a log-structured merge-tree (LSM) engine, or query-optimizer rules. Multiversion concurrency control, or MVCC, keeps versions so transactions can use appropriate read views. These are optional extensions. Measure their results.

Will the project rubric reward a GraphRAG attempt?

The rubric rewards evidence for design choices. Compare graph-based retrieval with the baseline. Report improvements, unchanged results, and regressions. Adding a graph without evaluating its effect does not demonstrate improvement.
