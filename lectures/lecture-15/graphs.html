Graph Databases & the Course, Closed

Why does every extra hop of "who's within three hops of ada?" cost SQL another join and a worse plan, and what does a database that stores the relationship as a pointer give up to fix it?
Daniel G. Graham · UVA School of Data Science

One data shape has quietly resisted everything we've built: deep relationships. "Who follows ada?" is a join; "who's within three hops of ada?" is a join chained onto a join onto a join, with SQL getting longer and the plan getting worse at every depth. Graph databases store the relationships as pointers on the data itself and replace join chains with traversal; you'll watch it live in Kuzu, an embeddable graph engine that is to1 Neo4j what DuckDB is to Postgres. Then the real last act: the whole semester compressed to five ideas, and the argument that every system you'll meet for the rest of your career is a remix of them.

Companion reading: Kuzu's documentation (install to Cypher in ten minutes) · Robinson, Webber & Eifrem, Graph Databases (free O'Reilly text) · Microsoft's From Local to Global: GraphRAG paper.

Today's claim: a graph database is an index decision, not a new kind of database: it pre-joins your relationships at write time, exactly the way an index pre-sorts your rows.

Every extra hop costs SQL another join and a worse plan

Relational: each hop is a JOIN, and neighbors are found by matching keys (a hash or index probe per row). Graph: each hop is a WALK, and neighbors are found by following pointers stored on the node. For k hops from one start node with average degree d:

\[ \text{join chain: } k \text{ joins, about } d^{k} \text{ intermediate rows before dedup} \] \[ \text{traversal: about } d^{k} \text{ nodes visited, each one pointer-follow away, nothing to match} \]

Same asymptotics, wildly different constants, and the constant is the product.

Same number of touches, far less paid per touch

In words: to find everyone within k hops of a start node, both approaches touch on the order of \(d^{k}\) neighbors, where \(d\) is the average number of edges leaving a node. What differs is the cost of each touch.

Same growth rate, much smaller cost per step; that smaller constant is what a graph database sells.

Start at ada and step to depth 3: the reached set matches query 3 of the Kuzu demo below. The fay→ada edge closes a loop (ada → cyd → eli → fay → ada), which is why "within 3 hops" needs cycle handling in either notation: a walk with no stopping rule would circle forever, so both the Cypher pattern and the recursive CTE carry an explicit depth bound, and both end with DISTINCT so a node reached by two routes is listed once2.

A graph database materializes the join at write time

The data model every mainstream graph database shares (Neo4j, Kuzu, Neptune, Memgraph):3

node   (:Student {name: 'ada', gpa: 39})          a record with a label + properties
edge   (ada)-[:Follows {since: 2026}]->(ben)      ALSO a record: typed, directed, with properties

storage:  each node keeps its adjacency lists, Follows-out: [ben, cyd], Follows-in: [fay]
          neighbors are reachable without consulting any index: index-free adjacency

Lab 6's index trade and Lecture 13's skew, in graph form

Say it in this course's vocabulary: a graph database materializes the join at write time. Adding the edge does the key-matching once; every future traversal follows the stored pointer4. The trade should feel familiar by now: it's the index trade (Lab 6) with the cost moved to a different operation: every write pays a little extra to store the pointer, and every read gets its neighbors without a lookup. Even the failure mode is familiar: a supernode, a node with far more edges than the rest, is the skew problem from Lecture 13 in graph form: one key that carries most of the work, so any traversal through it does far more work than the average node.

SQL can traverse; Cypher draws the question's shape

SQL can traverse: WITH RECURSIVE defines a recursive CTE, a query that feeds its own output back in as input until no new rows appear, which is a loop written in the algebra, and it's genuinely how you should do shallow graph work in Postgres or5 DuckDB. The same question, both notations, both verified against their engines on the six-student data (both return ben cyd dee eli fay):

A star range, *1..3, replaces the whole recursive CTE

-- DuckDB / Postgres: a loop, spelled as algebra
WITH RECURSIVE reach(name, depth) AS (
    SELECT 'ada', 0
  UNION ALL
    SELECT f.dst, r.depth + 1
    FROM reach r JOIN follows f ON f.src = r.name
    WHERE r.depth < 3
)
SELECT DISTINCT name FROM reach WHERE name <> 'ada' ORDER BY name;
// Cypher: the pattern IS the query, draw the arrow, star the depth
MATCH (a:Student {name: 'ada'})-[:Follows*1..3]->(b)
WHERE b.name <> 'ada'
RETURN DISTINCT b.name ORDER BY b.name

The Cypher pattern ( )-[ ]->( ) is ASCII art of the graph itself: nodes in parens, edges in brackets, direction as an arrow. Notation matters here the way it did in week 5: both compile to query plans, but the Cypher pattern shows the shape of the question on the page, while the recursive CTE hides it inside a loop over rows. *1..3 (any path of one to three edges) replaced the entire recursive CTE, and * SHORTEST (in the demo) replaces a shortest-path algorithm that SQL has no direct way to express.

When the path itself is the answer, it is one MATCH

Query 4 is the important one: how does ada reach fay is a shortest-path search (BFS, breadth-first search, under the hood) expressed in one6 MATCH. Ask it of the SQL version and you're writing a shortest-path algorithm such as Dijkstra's by hand inside a recursive CTE; ask it of Kuzu and it's one ordinary query. When the path itself is the answer (recommendations, fraud rings, lineage, dependency chains) that's the graph database's home turf.

A graph database is built for the second; a graph compute framework is built for the first8
relationships that are really just foreign keysstay relationala schema with foreign keys is a graph on paper, but if every query follows one or two of them it is not a graph workload. Path-shaped questions through 11.5 million documents won a Pulitzer

War story · the Panama Papers, 2016

The second row of that table (variable depth, path-shaped answers) won a Pulitzer9. When 11.5 million leaked documents from the law firm Mossack Fonseca reached the International Consortium of10 Investigative Journalists, the questions that mattered were pure traversal: which officers connect to which shell companies, through which intermediaries, to which real owners: paths of unknown depth through millions of entities. ICIJ loaded the extracted entities and relationships into Neo4j and gave hundreds of reporters a visual graph-query front end11; reporters with no database training followed edges to prime ministers11. The relational version of that investigation is a self-join per hop with the hops unknown in advance; possible, and nobody would have finished it. Choosing the data model to match the question is the course's thesis, and this is the clearest real-world case of it.

Vector retrieval finds sound-alikes; graph traversal finds connections

Your project retrieves by similarity: question vector → nearest chunks. Its known blind spot is questions whose answer is spread across documents ("how do the WAL and the buffer pool interact?"; no single chunk says it). GraphRAG's move: extract an entity graph from the corpus at ingest12 (nodes for entities such as the WAL, the buffer pool, and a page; typed edges for the relationships the text states between them, such as “WAL constrains page flushing” and “buffer pool defers writes”), retrieve by traversing from mentioned entities, and hand the LLM connected subgraphs instead of disconnected paragraphs. Similarity finds what a question sounds like; traversal finds what it's connected to; knowledge-graph retrieval and vector retrieval compose, and hybrid is the production pattern.

A 1-hop entity expansion is a GraphRAG you can finish

GraphRAG is an optional extension in the project spec. A version one team can finish in the time left: tag each chunk with the entities it mentions, and when a question names an entity, add the chunks tagged with that entity's direct neighbors in the graph (a 1-hop expansion) to what similarity retrieval already returned.

FAQ

Is Kuzu real enough to use, or a teaching toy?

Real: columnar storage, a vectorized query processor, full13 Cypher, and it holds its own on benchmarks against Neo4j for embedded14 analytics. Like DuckDB, its niche is in-process work rather than serving a fleet of concurrent clients. For a server deployment with users and auth, Neo4j or Neptune; for "I have a graph problem in a notebook," Kuzu is exactly right. One caveat: the original kuzudb/kuzu repository was archived read-only in October 2025 (last release 0.11.3), so pip install kuzu still works but development has moved to community forks19.

Why did we not cover [Mongo/Redis/Elasticsearch/…]?

Deliberate: those are products, and products rotate. Mongo is a document store over a B+ tree engine (WiredTiger) with a WAL15; Redis is a data-structure server with an append-only log16; Elasticsearch is inverted indexes (BM25, Lecture 12) over segment files that behave like SSTables17. You have the parts list. An afternoon with any of their architecture pages will slot them into the five-ideas table; try it.

What should I learn next after this course?

Three worthy directions, pick by taste: depth, read the Red Book (Bailis, Hellerstein, Stonebraker's18 Readings in Database Systems) and the Spanner and Aurora papers; breadth, Kleppmann's Designing Data-Intensive Applications, which covers the second half of this course at production scale; craft, extend microdb (MVCC, an LSM engine, the optimizer); nothing teaches like the engine you already own.

Will the project rubric reward a GraphRAG attempt?

Only the measured kind. A 1-hop entity expansion with an eval table showing where it helped (and where it hurt; it will, on some questions) earns real credit; a bolted-on graph with no measurement earns sympathy. The rubric's spine all semester has been the same sentence: show the numbers that made you decide.
