Memory & the Buffer Pool

Your data has to live on a disk 250× to 100,000× slower than RAM, so which blocks get to be in memory decides whether a query answers in milliseconds or minutes.
Daniel G. Graham · UVA School of Data Science

Thursday you measured the gap: your SSD absorbs hundreds of thousands of buffered writes a second and a fraction of that when honesty is required, and every block your microdb reads still comes off that disk, even one it read a moment ago. Today we build the layer that lives in that gap. The buffer pool is a cache the database runs for itself (not the OS page cache, its own), and its hit rate, more than any other number, decides whether your query answers in milliseconds or minutes. On Thursday you write one; today you learn why every design choice in it is forced.

Companion reading: Sciore, Database Design and Implementation1, ch. 4 (SimpleDB's buffer manager) · Hellerstein et al., Architecture of a Database System, §5.3 · the case against mmap: Crotty et al., Are You Sure You Want to Use MMAP in Your DBMS?2 (CIDR 2022).

Today's plan

Quiz first, then one arc: from the number you measured Thursday to the cache that exists because of it.

The problem: your data must live on disk (it does not fit in RAM, and it must survive power loss), and disk is 250× to 100,000× slower than RAM. Unless something decides which blocks stay in memory, every query pays the disk price.

  1. Quiz 1: files, blocks & pages (10 min, first thing).
  2. Why a cache is not optional: your data lives on disk, your code runs on RAM, and every trip between them costs 250× or worse.
  3. Watch one pool run two workloads: a full-table scan scores 0% hits, a hot-set workload scores about 70%, and explaining that gap is the whole lecture.
  4. What the gap proves: a cache helps only when the rows you reuse fit inside it; merely touching a lot of data earns nothing.
  5. How the buffer pool works: a fixed set of frames, pin and unpin, LRU eviction, and dirty pages written back before their frame is reused.
  6. Why the hit rate is everything: even at 90% hits the average access is still 26× slower than RAM, because the rare misses dominate the average.
  7. Thursday: you build all of it, in four methods.

Today's claim: a database is fast exactly when its buffer pool is winning.

Data must live on disk; only RAM is fast enough

The two resources at hand have opposite virtues, and the buffer pool's whole job is arbitraging between them:

DRAMSSD / diskRatio
Access time~100 ns~25 µs – 10 msdisk is 250× – 100,000× slower3
Capacity (a laptop)16–32 GB0.5–4 TBdisk holds ~50× more
Survives power lossnoyes 
Cost per GBhighlowDRAM costs ~50–100× more13

The data must live on disk (it's big, and it must survive). The data must be read in RAM (nothing else is fast enough). Something has to manage the shuttle between them, deliberately, not accidentally.

OLTP reuses a small hot set; OLAP touches everything once

How hard the shuttle job is depends entirely on the access pattern, and database access patterns cluster into two families you'll meet all semester:

Caches reward reuse that fits, not size

Two workloads, same pool, wildly different outcomes; that contrast is the whole point of the lecture:

WorkloadPatternHit rate (3 frames)Why
Scan ×20,1,2,…,7 then again0%the pool evicts by LRU, least recently used: when all three frames are full, the block that has gone longest without being touched is thrown out to make room. In a scan that is always the block the scan will want next time around: block 0 is evicted to load block 3, block 1 to load block 4, and so on. By the time a block is needed again, LRU has evicted it, every time
Hot setmostly blocks 0–1, occasional others~70%the working set fits in the pool, so repeats are free

0% vs ~70% the same three-frame pool: a scan that doesn't fit against a hot set that does

Caches don't reward size of data touched; they reward reuse that fits.

The pool: fixed frames, and pin/unpin are the only doors

The poolN fixed frames, allocated once at startup; Postgres calls the setting4 shared_buffers. Each frame holds exactly one block's page.
The lookup"is block b already here?": microdb scans its handful of frames; real engines keep a hash table from BlockId → frame so the answer costs \(O(1)\).
The bookkeepingper frame: which block · a pin count · a dirty flag · a last-used tick. Twelve bytes of metadata that decide everything.
The interfacetwo verbs only: pin(block) and unpin(buffer). Every read and write in the rest of microdb goes through them, forever.

A hash table makes "is it here?" cost O(1)

Every pin starts with the same question (is block b already here?), and how fast you can answer it decides whether the pool itself becomes the bottleneck:

ApproachCost per pinWho uses it
Scan every frame\(O(\text{frames})\)microdb: scanning 3 frames is instant, and even at the lab's 50-frame pool the scan is still cheap; a real pool has hundreds of thousands of frames, where it would not be
Hash table: BlockId → frame\(O(1)\)every real engine (Postgres: the "buffer mapping table")5

This is why Lab 1 made BlockId immutable and hashable: a design decision two weeks old pays off as a dict key today. Interfaces are promises to your future layers.

A pinned frame is never evicted, no matter how old

Why do the verbs exist at all? Because a cache that can evict at any moment is a cache that can evict the page you are currently reading. Pinning is the fix, a promise with two sides:

buf = bm.pin(BlockId("students.tbl", 0)) # "hold this in memory"; 0 = block number
value = buf.contents().get_int(0) # a different 0: byte offset in the page
bm.unpin(buf) # "you may evict it now"

Pin counts nest: two readers of one block means pins == 2, and the frame survives until both release. And a frame with pins > 0 is never evicted, no matter how old.

The OS cache can't pin, order writes, or see ahead

PinningThe OS offers no "don't evict this, I'm using it."6 A database must be able to hold a page mid-operation; that alone forces its own pool.
Write orderingRecovery (week 7) requires the log to reach disk before the data page it describes. The OS flushes whenever it likes; the database must control the order7.
Smarter evictionThe database knows its own future ("this is a one-pass scan, don't cache it"), and can pick policies per workload8. The OS sees anonymous bytes.
The mmap trapMapping the file into memory looks like a free buffer pool; the CIDR 2022 paper in the citations is titled "Are you sure?" for a reason: no pinning, no write ordering, surprise stalls6.

The OS cache still exists underneath, doing its best. The database pool isn't instead of it; it's the layer that adds the guarantees correctness needs.

LRU: evict the unpinned frame used longest ago

The pool is full and a new block is needed: someone must go. The policy that picks the victim is the pool's personality, and Thursday you implement the classic one.

microdb's rule, exactly as Thursday's tests check it: the pool keeps one ever-growing counter, stamps a frame every time it is pinned, and evicts the unpinned frame with the oldest stamp.

state
  tick = 0                     one global counter; goes up forever, never resets
  frame.last_used              per frame: the tick when this frame was last pinned

on EVERY successful pin(block), hit or miss
  tick = tick + 1
  frame.last_used = tick       stamped on hits as well as misses

on a miss, when no frame is free
  candidates = frames with pins == 0        a pinned frame is never a candidate,
                                            no matter how old its stamp is
  if candidates is empty:
      raise BufferAbortError                every frame is in use; some caller
                                            must unpin before anyone can pin
  victim = the candidate with the SMALLEST last_used
                                            smallest stamp = pinned longest ago
  flush victim if dirty, then reuse its frame for the new block

Hits refresh recency too, not just misses

Trace it once by hand and the tests in Thursday's lab will hold no surprises. Three frames, access sequence A B C A D:

AccessResultFrame 0Frame 1Frame 2Victim logic
AmissA¹  empty frame
BmissA¹B² empty frame
CmissA¹B²C³empty frame
AhitA⁴B²C³re-stamp A's tick; this is the step people forget
DmissA⁴D⁵C³victim = min tick among unpinned = B²

The superscript is last_used. If your code evicts A instead of B, you stamped the tick only on misses; hits refresh recency too.

Pins outrank recency, always

Pick up where the table stops (frames: A⁴, D⁵, C³) and run two more accesses: E, then B. Who gets evicted each time, and would either answer change if a client still held a pin on A?

Show answer

E misses; victim is the min tick, C³ → frames A⁴, D⁵, E⁶. B also misses; it was evicted back at step 5, which is the quiet lesson: eviction has a memory-shaped cost later. Victim is now A⁴, so the once-hot page finally leaves → B⁷, D⁵, E⁶. With A pinned, A is untouchable regardless of its tick, so B would evict D⁵ instead; pins outrank recency, always.

Recency predicts reuse, so LRU is the default choice

PolicyRuleCostWeakness
FIFOevict the oldest loadtrivialignores re-use entirely: a hot page ages out mid-popularity
Randomevict anyone unpinnedtrivialsurprisingly decent on average; no protection for the working set
LRUevict the coldest usea timestamp per accessone full-table scan evicts the whole working set and the hit rate collapses to zero (the scan workload you just watched)9
ClockLRU's cheap approximation: one bit + a sweeping hand10nearly freefails the same way under a scan: each page's bit is cleared before the scan comes back for it, so one big scan still flushes the working set. And because the bit only records "touched since the hand last passed," not when, it ranks recency more coarsely than true LRU

LRU is the default choice because recency predicts re-use for most workloads, and Thursday you implement the full version, tick and all.

Real engines stop scans from evicting the working set

Postgresclock-sweep (an LRU approximation with a usage counter), plus ring buffers: a big sequential scan gets a tiny private ring so it can't flood the shared pool5.
MySQL/InnoDBmidpoint LRU: new pages enter the middle of the list, not the head; a page must be touched again to reach the protected young region11.
DuckDBanalytics engines take a different route. DuckDB still caches storage pages while memory lasts, but a big scan streams through in fixed-size chunks instead of flooding that cache. Everything that wants memory, cached pages and the hash table a join is building alike, shares one memory budget. When the budget runs out, the operator writes its own half-finished results to disk and the cached pages survive14.
The shared ideadetect "this access pattern won't reuse" and refuse to let it evict what will.

Dirty pages reach disk on eviction or flush, not commit

Reads were the easy half. Once queries modify pages, the pool holds data the disk doesn't have yet, and must never lose track of that fact.

MomentWho triggers itWhy
Evictionthe pool, inside pin()a miss with no free frame means a victim page is thrown out so its frame can hold the new block. If that victim is dirty, the pool writes it to disk first, then overwrites the frame; skip that write and the change exists nowhere
flush_all()shutdown / checkpointwrites every dirty page in the pool to disk in one sweep. At shutdown that is how the changes outlive the process; at a checkpoint it puts a ceiling on how much work recovery has to redo after a crash, since everything before the checkpoint is already on disk
Never on unpin unpin only says the caller is done with the page, not that it should be written. A hot page that many transactions touch stays dirty in memory for a long time, on purpose: writing it on every unpin would turn each small change into a disk trip
Not at COMMITthe log insteadcommit does not write the data pages. It forces the write-ahead log to disk instead, one sequential fsync of a small record, and the pages follow later at their own pace. That is the week-7 escape from the fsync ratio you measured in Lab 17

The miss term owns the average

\[ T_{\text{avg}} \;=\; h \cdot t_{\text{mem}} \;+\; (1 - h) \cdot t_{\text{disk}} \qquad (h = \text{hit rate}) \]

with tmem = 100 ns and tdisk = 25 µs:

hTavgrelative to RAM
90%2,590 nsabout 26× slower
99%349 nsabout 3.5× slower
99.6%200 ns2× RAM: the target

26× slower than RAM at 90% hits: the 10% of misses are 96% of the time

The miss term owns the average: at 90% hits, the 10% of misses12 contribute 96% of the total time. Caches aren't good until they're absurdly good; this is why the scan's 0% hit rate hurts so much.

Size the pool to the working set, not a percentage

Postgresshared_buffers: the classic starting rule is ~25% of RAM, leaving the OS cache to serve as a fuzzy second tier underneath4.
Why not 100%?double-caching (every page would live in both tiers), and everything else on the machine still needs memory; a pool that causes swapping is a pool that made things worse: thrashing.
The real targetnot a percentage, the working set. If the pages a workload actually re-touches fit in the pool, hit rates go asymptotic; if not, no tuning saves you.

Recap & next time

Three ideas from today, each one load-bearing for the rest of the course.

  • The pool is deliberate memory. Fixed frames, pin/unpin as the only doors, its own eviction policy, because correctness needs guarantees (pinning, write ordering) that a general-purpose cache can't give.
  • LRU is great until it's catastrophic. Recency wins on hot sets and earns exactly 0% on scans one block too big; real engines detect and special-case the scan.
  • The miss term owns the average. T = h·t_mem + (1−h)·t_disk means 90% is 26× slower than RAM and "good" starts past 99%; the working set fitting the pool is the whole ballgame.

FAQ

Is the buffer pool the same thing as the OS page cache?

Same idea, different owner and different guarantees. The OS caches anonymous file bytes opportunistically; the database pool adds pinning, controlled write-back ordering, and workload-aware eviction: the three things correctness and predictability need. On a Postgres box both are active at once, stacked.

Why LRU and not something smarter?

Lab 2 uses true LRU because it's the canonical policy and its failure mode (a scan scoring 0%) is the best systems lesson in the course. Real engines use cheaper approximations (clock, usage counters) that behave almost identically, and then bolt on scan-resistance, which is the actual smartness.

What happens if I forget to unpin?

The frame stays ineligible for eviction forever; enough leaks and pin() raises BufferAbortError with every frame pinned. Real engines have the same bug class; it's why their buffer code is written with the paranoia of a bank vault.

Does a bigger pool always help?

Up to the working set, enormously; past it, almost not at all, and past available RAM it actively hurts (the machine swaps, which is disk again with extra steps). The measurement you run Thursday shows the first two regimes on real code.
