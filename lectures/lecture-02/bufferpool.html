Memory & the Buffer Pool

The layer that decides which bytes deserve to be in RAM, and why that one decision is most of database performance.
Daniel G. Graham · UVA School of Data Science

Thursday you measured the gap: your SSD absorbs hundreds of thousands of buffered writes a second and a fraction of that when honesty is required. Today we build the layer that lives in that gap. The buffer pool is a cache the database runs for itself (not the OS page cache, its own), and its hit rate, more than any other number, decides whether your query answers in milliseconds or minutes. On Thursday you write one; today you learn why every design choice in it is forced.

Companion reading: Sciore, Database Design and Implementation, ch. 4 (SimpleDB's buffer manager) · Hellerstein et al., Architecture of a Database System, §4 · the case against mmap: Crotty et al., Are You Sure You Want to Use MMAP in Your DBMS? (CIDR 2022).

The gap you measured

The problem

The two resources at hand have opposite virtues, and the buffer pool's whole job is arbitraging between them:

DRAMSSD / diskRatio
Access time~100 ns~25 µs – 10 msdisk is 250× – 100,000× slower
Capacity (a laptop)16–32 GB0.5–4 TBdisk holds ~50× more
Survives power lossnoyes 
Cost per GBhighlowDRAM costs ~10–20× more

The data must live on disk (it's big, and it must survive). The data must be read in RAM (nothing else is fast enough). Something has to manage the shuttle between them, deliberately, not accidentally.

Two workloads, two worlds

How hard the shuttle job is depends entirely on the access pattern, and database access patterns cluster into two families you'll meet all semester:

Transactional (OLTP)Analytical (OLAP)
What it isOnline Transaction Processing: the many small reads and writes that run the business, one login, one order, one balance update at a timeOnline Analytical Processing: a few large read-only questions asked of the whole history, a total, a trend, a report
Typical querySELECT * FROM students WHERE id = 42SELECT major, AVG(gpa) FROM students GROUP BY major
Typical accessthe same hot rows, over and overone pass over everything
Re-useconstant: small working setalmost none: each block once
What a cache can donearly everythingnearly nothing
In today's lecturethe "hot set" workloadthe "scan" workload

Keep this split in mind; the simulator you're about to drive runs one workload from each family, and they will behave like different machines.

What just happened

Two workloads, same pool, wildly different outcomes; that contrast is the whole point of the lecture:

WorkloadPatternHit rate (3 frames)Why
Scan ×20,1,2,…,7 then again0%the pool evicts by LRU, least recently used: when all three frames are full, the block that has gone longest without being touched is thrown out to make room. In a scan that is always the block the scan will want next time around: block 0 is evicted to load block 3, block 1 to load block 4, and so on. By the time a block is needed again, LRU has evicted it, every time

Caches don't reward size of data touched; they reward reuse that fits. Hold that thought: it comes back as a cliff.

Frames, pin & unpin

Anatomy of the pool

The poolN fixed frames, allocated once at startup; Postgres calls the setting shared_buffers. Each frame holds exactly one block's page.
The lookup"is block b already here?": microdb scans its handful of frames; real engines keep a hash table from BlockId → frame so the answer costs O(1).
The bookkeepingper frame: which block · a pin count · a dirty flag · a last-used tick. Twelve bytes of metadata that decide everything.
The interfacetwo verbs only: pin(block) and unpin(buffer). Every read and write in the rest of microdb goes through them, forever.

The lookup: a page table

Every pin starts with the same question (is block b already here?), and how fast you can answer it decides whether the pool itself becomes the bottleneck:

ApproachCost per pinWho uses it
Scan every frameO(frames)microdb: fine at 3 frames, honest at 50
Hash table: BlockId → frameO(1)every real engine (Postgres: the "buffer mapping table")

This is why Lab 1 made BlockId immutable and hashable: a design decision two weeks old pays off as a dict key today. Interfaces are promises to your future layers.

Pin & unpin: the contract

Why do the verbs exist at all? Because a cache that can evict at any moment is a cache that can evict the page you are currently reading. Pinning is the fix, a promise with two sides:

buf = bm.pin(BlockId("students.tbl", 0)) # "hold this in memory for me"
value = buf.contents().get_int(0) # safe: the frame cannot vanish
bm.unpin(buf) # "you may evict it now"

Pin counts nest: two readers of one block means pins == 2, and the frame survives until both release. And a frame with pins > 0 is never evicted, no matter how old.

Why not just use the OS cache?

PinningThe OS offers no "don't evict this, I'm using it." A database must be able to hold a page mid-operation; that alone forces its own pool.
Write orderingRecovery (week 7) requires the log to reach disk before the data page it describes. The OS flushes whenever it likes; the database must control the order.
Smarter evictionThe database knows its own future ("this is a one-pass scan, don't cache it"), and can pick policies per workload. The OS sees anonymous bytes.
The mmap trapMapping the file into memory looks like a free buffer pool; the CIDR 2022 paper in the citations is titled "Are you sure?" for a reason: no pinning, no write ordering, surprise stalls.

The OS cache still exists underneath, doing its best. The database pool isn't instead of it; it's the layer that adds the guarantees correctness needs.

Eviction: who leaves?

The pool is full and a new block is needed: someone must go. The policy that picks the victim is the pool's personality, and Thursday you implement the classic one.

LRU (least recently used), microdb's spec:

  every successful pin stamps the frame:   last_used ← next tick
  victim = the UNPINNED frame with the smallest last_used
  no unpinned frame?  →  BufferAbortError

LRU by hand: the pinned trace

Trace it once by hand and the tests in Thursday's lab will hold no surprises. Three frames, access sequence A B C A D:

AccessResultFrame 0Frame 1Frame 2Victim logic
AmissA¹  empty frame
BmissA¹B² empty frame
CmissA¹B²C³empty frame
AhitA⁴B²C³re-stamp A's tick; this is the step people forget
DmissA⁴D⁵C³victim = min tick among unpinned = B²

The superscript is last_used. If your code evicts A instead of B, you stamped the tick only on misses; hits refresh recency too.

Pick up where the table stops (frames: A⁴, D⁵, C³) and run two more accesses: E, then B. Who gets evicted each time, and would either answer change if a client still held a pin on A?

Show answer

E misses; victim is the min tick, C³ → frames A⁴, D⁵, E⁶. B also misses; it was evicted back at step 5, which is the quiet lesson: eviction has a memory-shaped cost later. Victim is now A⁴, so the once-hot page finally leaves → B⁷, D⁵, E⁶. With A pinned, A is untouchable regardless of its tick, so B would evict D⁵ instead; pins outrank recency, always.

Why LRU? The policy menu

PolicyRuleCostWeakness
FIFOevict the oldest loadtrivialignores re-use entirely: a hot page ages out mid-popularity
Randomevict anyone unpinnedtrivialsurprisingly decent on average; no protection for the working set
LRUevict the coldest usea timestamp per accessthe scan cliff you're about to see
ClockLRU's cheap approximation: one bit + a sweeping handnearly freesame cliff, coarser recency

LRU wins the textbook seat because recency predicts re-use for most workloads, and Thursday you implement the honest version, tick and all.

The sequential-flooding cliff

Now the dark side of LRU, measured for real by Thursday's lab code: a 50-block file, two workloads, pool sizes from 5 to 55:

Measured hit rate vs pool size · Lab 2's measure_hits.py

Sequential scan (two passes over all 50 blocks) vs a hot-set workload (90% of accesses to 5 blocks). Same file, same LRU pool.

The scan earns exactly 0% at 49 frames (one frame short of the file), and jumps to 50% at 50. LRU + scan is a perfect anti-pattern: each block is evicted precisely one step before it's needed again.

What real engines do about it

Postgresclock-sweep (an LRU approximation with a usage counter), plus ring buffers: a big sequential scan gets a tiny private ring so it can't flood the shared pool.
MySQL/InnoDBmidpoint LRU: new pages enter the middle of the list, not the head; a page must be touched again to reach the protected young region.
DuckDB & friendsanalytics engines mostly don't fight it: scans stream, and the pool is reserved for what genuinely re-reads (metadata, hash tables, hot columns).
The shared ideadetect "this access pattern won't reuse" and refuse to let it evict what will. Your Going-Further in Lab 2 builds a taste of it.

Dirty pages & write-back

Reads were the easy half. Once queries modify pages, the pool holds data the disk doesn't have yet, and must never lose track of that fact.

When do bytes actually reach disk?

MomentWho triggers itWhy
Evictionthe pool, inside pin()the frame is being reused: flush-if-dirty first, or the modification is lost
flush_all()shutdown / checkpointbound how much replay recovery needs
Never on unpin unpin means "not using it", not "write it"; hot pages stay dirty in memory for ages, on purpose
Not at COMMITthe log insteadcommit forces the WAL to disk (one sequential fsync), not the data pages; that's the week-7 escape from your fsync ratio

Surprise worth savoring: on the day you commit a transaction, the table's pages are usually not written. One cheap log write stands in for many expensive page writes; the buffer pool and the WAL are two halves of one design.

A preview of week 7: force & steal

Two yes/no questions define every engine's write-back personality, and the quadrant every serious engine picks is the one that requires a recovery log:

Force (flush dirty pages at commit)No-force (flush whenever)
No-steal (never flush uncommitted)slow but simple, no log neededneeds redo after a crash
Steal (may flush uncommitted)needs undo after a crashneeds both, and it's what everyone builds, because it's the only fast quadrant

No-force + steal means: commits don't wait for data pages, and the pool evicts whatever it likes, maximum freedom for the cache, paid for by ARIES-style recovery. Week 7 builds the payment.

The arithmetic of a cache

Effective access time

T_avg  =  h · t_mem  +  (1 − h) · t_disk        (h = hit rate)

with t_mem = 100 ns, t_disk = 25 µs:

  h = 90%   →  T_avg = 2,590 ns    ≈ 26× slower than RAM
  h = 99%   →  T_avg =   349 ns    ≈ 3.5× slower than RAM
  h = 99.6% →  T_avg =   200 ns    =  2× RAM  ← the TPS answer

The miss term owns the average: at 90% hits, the 10% of misses contribute 96% of the total time. Caches aren't good until they're absurdly good; this is why the cliff matters.

Sizing pools in the wild

Postgresshared_buffers: the classic starting rule is ~25% of RAM, leaving the OS cache to serve as a fuzzy second tier underneath.
Why not 100%?double-caching (every page would live in both tiers), and everything else on the machine still needs memory; a pool that causes swapping is a pool that made things worse: thrashing.
The real targetnot a percentage, the working set. If the pages a workload actually re-touches fit in the pool, hit rates go asymptotic; if not, no tuning saves you.

Recap & next time

Three ideas from today, each one load-bearing for the rest of the course.

  • The pool is deliberate memory. Fixed frames, pin/unpin as the only doors, its own eviction policy, because correctness needs guarantees (pinning, write ordering) that a general-purpose cache can't give.
  • LRU is great until it's catastrophic. Recency wins on hot sets and earns exactly 0% on scans one block too big; real engines detect and special-case the scan.
  • The miss term owns the average. T = h·t_mem + (1−h)·t_disk means 90% is 26× slower than RAM and "good" starts past 99%; the working set fitting the pool is the whole ballgame.

FAQ

Is the buffer pool the same thing as the OS page cache?

Same idea, different owner and different guarantees. The OS caches anonymous file bytes opportunistically; the database pool adds pinning, controlled write-back ordering, and workload-aware eviction: the three things correctness and predictability need. On a Postgres box both are active at once, stacked.

Why LRU and not something smarter?

Lab 2 uses true LRU because it's the canonical policy and its failure mode (the cliff) is the best systems lesson in the course. Real engines use cheaper approximations (clock, usage counters) that behave almost identically, and then bolt on scan-resistance, which is the actual smartness.

What happens if I forget to unpin?

The frame stays ineligible for eviction forever; enough leaks and pin() raises BufferAbortError with every frame pinned. Real engines have the same bug class; it's why their buffer code is written with the paranoia of a bank vault.

Does a bigger pool always help?

Up to the working set, enormously; past it, almost not at all, and past available RAM it actively hurts (the machine swaps, which is disk again with extra steps). The measurement you run Thursday shows the first two regimes on real code.
