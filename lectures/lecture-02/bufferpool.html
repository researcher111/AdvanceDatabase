Memory & the Buffer Pool

How does a database keep frequently used blocks in memory while preserving changes on disk?
Daniel G. Graham · UVA School of Data Science

In Lab 1 you measured how fsync changes write throughput. You also built a file manager that issues a read whenever it is asked for a block. Today we add a buffer pool: a cache managed by the database that keeps selected blocks in memory. It works alongside the OS page cache. We will study how pinning, eviction, and dirty-page tracking make that cache safe to use, then implement it in Lab 2.

Companion reading: Sciore, Database Design and Implementation1, ch. 4 (SimpleDB's buffer manager) · Hellerstein et al., Architecture of a Database System, §5.3 · the case against mmap: Crotty et al., Are You Sure You Want to Use MMAP in Your DBMS?2 (CIDR 2022).

Today's plan

We begin with Quiz 1 (files, blocks, and pages, 10 min), then use your Lab 1 measurements to motivate the buffer pool.

Persistent data must be stored on disk, and a dataset may be larger than RAM. Keeping frequently reused blocks in memory can reduce the cost of accessing that data.

Today's claim: a high buffer-pool hit rate can remove a major source of query latency.

Disk provides persistence; RAM provides faster access

A buffer pool uses a limited amount of RAM to cache data stored on disk:

DRAMSSD / diskRatio

Disk keeps the database persistent. RAM holds the blocks currently in use. The buffer manager decides which blocks to retain and which to replace when memory is full.

Repeated lookups and sequential scans have different caching needs

Database workloads often combine short transactions and larger analytical queries. These two examples have different opportunities for reusing cached blocks:

Caching helps when blocks are reused before eviction

The memory capacity is the same in both runs. The difference is how soon each workload requests a block again:

WorkloadPatternHit rate (3 frames)Why
Scan ×20,1,2,…,7 then again0%LRU replaces the unpinned block used longest ago. In this sequential scan, each block is evicted before the next pass reaches it. Block 0 is replaced when block 3 arrives, block 1 when block 4 arrives, and so on. Every request therefore misses.
Hot setmostly blocks 0–1, occasional others~70%blocks 0–1 are reused frequently enough to remain cached for many requests

0% vs ~70% the same three-frame pool: a scan that doesn't fit against a hot set that does

Cache hits depend on reuse: a block helps only if another request arrives before it is evicted.

Frames hold blocks; pin and unpin track their users

The poolN fixed frames, allocated once at startup; Postgres calls the setting4 shared_buffers. Each frame holds exactly one block's page.
The lookup"is block b already here?": microdb scans its handful of frames; real engines keep a hash table from BlockId → frame so the answer costs \(O(1)\).
The bookkeepingper frame: which block · a pin count · a dirty flag · a last-used tick. A small set of metadata; Python object overhead is larger than these logical fields.
The interfacepin(block) obtains a frame and records an active user; unpin(buffer) releases that use. Higher record layers access pages while holding a pin.

A hash table makes "is it here?" cost O(1)

Each pin call first checks whether the requested block is already in a frame. The lookup cost matters more as the pool grows:

ApproachCost per pinWho uses it
Scan every frame\(O(\text{frames})\)microdb scans its small frame list; scanning hundreds of thousands of frames on every request would be costly
Hash table: BlockId → frame\(O(1)\)a common production approach; PostgreSQL calls it the buffer mapping table5

BlockId is immutable and hashable, so it can be used as a dictionary key in a block-to-frame lookup table. Lab 2 keeps the implementation simpler by scanning its small frame list.

A pinned frame is never evicted, no matter how old

A caller needs the page to remain in its frame while it reads or changes the page. Pinning records that active use and prevents the frame from being chosen for eviction.

buf = bm.pin(BlockId("students.tbl", 0)) # "hold this in memory"; 0 = block number
value = buf.contents().get_int(0) # a different 0: byte offset in the page
bm.unpin(buf) # "you may evict it now"
NestingPin counts nest: two readers of one block means pins == 2, and the frame survives until both release.
Never evicteda frame with pins > 0 is never evicted, no matter how old its last-used stamp is.

A database needs more control than an ordinary OS file cache provides

PinningThe database needs a complete protocol for protecting pages in use and ordering writes. OS memory locking alone does not provide that protocol.6
Write orderingRecovery (week 7) requires the log to reach disk before the data page it describes. The OS flushes whenever it likes; the database must control the order7.
Smarter evictionThe database can recognize access patterns, such as a large sequential scan, and adjust its replacement policy. The OS has less information about the query’s purpose.8
The mmap trapMemory mapping delegates page movement to the OS. The cited CIDR paper explains the resulting challenges for eviction, write ordering, and unexpected page-fault delays.6

The OS page cache can still operate underneath the database. The buffer pool adds its own pin counts, replacement policy, and control over when dirty pages are submitted for writing.

LRU: evict the unpinned frame used longest ago

When a requested block is absent and every frame is occupied, the pool must select an unpinned frame to reuse. Lab 2 uses least recently used (LRU) replacement.

microdb's rule, exactly as Thursday's tests check it: the pool keeps one ever-growing counter, stamps a frame every time it is pinned, and evicts the unpinned frame with the oldest stamp.

state
  tick = 0                     one global counter; goes up forever, never resets
  frame.last_used              per frame: the tick when this frame was last pinned

on EVERY successful pin(block), hit or miss
  tick = tick + 1
  frame.last_used = tick       stamped on hits as well as misses

on a miss, when no frame is free
  candidates = frames with pins == 0        a pinned frame is never a candidate,
                                            no matter how old its stamp is
  if candidates is empty:
      raise BufferAbortError                every frame is in use; some caller
                                            must unpin before anyone can pin
  victim = the candidate with the SMALLEST last_used
                                            smallest stamp = pinned longest ago
  flush victim if dirty, then reuse its frame for the new block

The superscript is last_used. If your code evicts A instead of B, you stamped the tick only on misses; hits refresh recency too.

E misses and replaces C³, leaving A⁴, D⁵, E⁶. B then misses and replaces A⁴, leaving B⁷, D⁵, E⁶. If A remains pinned, E still replaces C, but B must replace D instead. A pinned frame is excluded from the candidate set regardless of its timestamp.

LRU uses recent access to predict future reuse

PolicyRuleCostWeakness
FIFOevict the oldest loadlow bookkeeping costignores repeated use: a frequently accessed page can still be the oldest loaded page
Randomevict anyone unpinnedlow bookkeeping costsimple, but does not favor recently reused blocks
LRUevict the unpinned frame used longest agoa timestamp per accessa large sequential scan can replace the cached working set, as in the scan workload above9
Clockapproximate recency with a reference bit and a rotating pointer10low per-access costfails the same way under a scan: each page's bit is cleared before the scan comes back for it, so one big scan still flushes the working set. And because the bit only records "touched since the hand last passed," not when, it ranks recency more coarsely than true LRU

Lab 2 implements exact LRU with a timestamp on every pin. Recency is a useful predictor for many workloads, but the scan example shows that it is not always effective.

Production systems can protect reusable blocks from large scans

PostgresPostgreSQL uses clock-sweep replacement with usage counters. Large sequential scans can reuse a small ring of shared-buffer slots to limit disruption to the rest of the cache.5
MySQL/InnoDBmidpoint LRU: new pages enter the middle of the list, not the head; a page must be touched again to reach the protected young region11.
DuckDBanalytics engines take a different route. DuckDB still caches storage pages while memory lasts, but a big scan streams through in fixed-size chunks instead of flooding that cache. The cache shares one memory budget with running queries, so a join building a big hash table competes with the cached pages for space. When the budget runs out, the buffer manager may evict cached storage pages or spill temporary query data to disk14.
The shared ideaLimit how much one-pass data displaces blocks that other requests are likely to reuse.

Dirty pages reach disk on eviction or an explicit flush

When a query changes a cached page, its contents differ from the stored copy. The buffer manager marks the page dirty so it knows a write is required before that frame can be reused.

MomentWho triggers itWhy
Evictionthe pool, inside pin()on a cache miss, the pool may reuse an occupied frame. If the old page is dirty, it writes that page first. Otherwise overwriting the frame would discard the change.
flush_all()shutdown / checkpointwrites all dirty pages currently in the pool. Shutdown and checkpoint procedures use page flushing as part of preserving changes and limiting recovery work; their durability and log-ordering requirements are covered in Lab 7.
Never on unpin unpin means the caller has finished using the page. It does not request a write. Deferring the write lets several updates to the same cached page share a later flush.
At COMMIT: policy-dependentFORCE or NO-FORCELab 7 uses FORCE: data pages are durable before COMMIT is logged. With NO-FORCE, commit can force the log and defer data-page writes, so recovery also needs redo information.

A small fraction of misses can dominate average access time

\[ T_{\text{avg}} \;=\; h \cdot t_{\text{mem}} \;+\; (1 - h) \cdot t_{\text{disk}} \qquad (h = \text{hit rate}) \]

with tmem = 100 ns and tdisk = 25 µs:

hTavgrelative to RAM
90%2,590 nsabout 26× slower
99%349 nsabout 3.5× slower
99.6%200 ns2× RAM: the target

26× slower than RAM at 90% hits: the 10% of misses are 96% of the time

At a 90% hit rate, misses account for about 96% of access time in this model. Disk reads are much slower than memory accesses, so even a small miss rate has a large effect on the average12.

Size the pool to the working set, not a percentage

PostgresA common initial setting for shared_buffers is about 25% of RAM. The OS cache and other processes also need memory; measure your workload before tuning further.4
Why not 100%?The OS cache, queries, and other processes also consume memory. Excessive allocation can cause swapping, which adds disk I/O and can produce thrashing.
The real targetConsider which pages the workload reuses and whether the pool can retain them between requests. The access pattern and replacement policy matter as well as capacity.

Recap & next time

Three points to remember:

  • The buffer pool manages a fixed set of frames. Pin counts protect pages in use; dirty flags track changes that still need to be written.
  • LRU favors recently accessed blocks. It can work well for repeated access to a small set, but a sequential scan larger than the pool can miss on every request.
  • Misses can dominate average access time. With today’s latency assumptions, a 90% hit rate still gives an average about 26× slower than a memory access.

FAQ

Is the buffer pool the same thing as the OS page cache?

Both keep file data in memory, but they are managed by different software. The database pool tracks its own active users, dirty pages, and replacement decisions. PostgreSQL normally uses both its buffer pool and the OS page cache.

Why LRU and not something smarter?

Exact LRU is straightforward to implement and trace, including its poor behavior on a repeated scan larger than the pool. Production engines often use cheaper approximations, such as clock or usage counters, and additional policies to protect useful cached data from large scans.

What happens if I forget to unpin?

A leaked pin keeps its frame unavailable for eviction. If all frames remain pinned, pin() raises BufferAbortError. Match every successful pin with an unpin when the caller finishes using the page.

Does a bigger pool always help?

A larger pool helps when it retains blocks that later requests reuse. Once the working set fits, additional frames may add little benefit. Allocating so much memory that the OS starts swapping can make performance worse. Lab 2 measures the first two cases.
