B+ Trees from First Principles

How does a B+ tree locate a row without scanning the whole table?1
Daniel G. Graham · UVA School of Data Science

Your engine currently finds rows by scanning the table. A B+ tree adds a sorted map from values to RIDs, so a lookup can go directly to the matching records. Its internal nodes can have hundreds of children, keeping the tree shallow even when the table is large. When an insertion overfills a node, the tree splits that node and updates its parent. These local changes keep every leaf at the same depth. In Thursday’s lab, you will implement searches, inserts, splits, and range scans.

Companion reading: Sciore, Database Design and Implementation, ch. 12 · the classic survey: Comer, The Ubiquitous B-Tree (1979) · Postgres's btree docs.

B+ trees support equality lookups, ordered scans, and updates in one structure. This makes them a common default index type, including in PostgreSQL.3

An index locates rows in the heap

The heapremains an unordered collection of rows, as in Lab 3. Adding this index does not rearrange the heap.
The indexstores (value, RID) pairs in sorted order, providing another way to locate the same heap rows.
The hand-offthe index returns the matching RIDs. move_to_rid on the reference TableScan uses each RID to reach its heap row. A RID stays valid while that record occupies its slot; deleting or replacing the record requires updating any index entries that refer to it.
Many indexesuid, name, and gpa can each have a separate index over the same heap. Inserts and deletes must update each index; an update must maintain the entries affected by the changed fields.

Every leaf remains at the same depth after each insertion. Splitting nodes and updating their parents maintains that property; insertion needs no separate pass over the whole tree.

Leaves hold entries; internal nodes route searches

Leaveshold the actual index entries, (key, RID) pairs in sorted order, and a next pointer to the right-hand sibling. Every index entry is stored in a leaf.
Internal nodeshold routing keys and child pointers. k keys separate k+1 child ranges. For example, a separator of 10 sends keys below 10 left and keys at least 10 right. Internal keys do not carry RIDs.
The leaf chainlinked leaves support range scans: descend once to lo, then follow next until a key passes hi. B+ trees keep the entries in leaves and link those leaves for ordered traversal2.
The invariantevery leaf is the same distance from the root. The next section shows how splitting preserves this property.

An index search visits one node per level

after inserting gpas 39, 31, 37, 28, 36, 34:        [ 36 ]            ← root (internal)
                                                   /      \
search(37):                            [28 31 34] → [36 37 39]        ← leaves, chained
  at [36]:      37 >= 36 → go right
  at leaf:      find 37 → its RIDs                 2 nodes touched, n = 6

Compare 37 with the root’s separator, follow the right child, and search that leaf. This example visits two index nodes. Larger trees use the same process at each level.

Ranges: descend once, then walk the chain

range(31, 37) on the pinned tree:

  descend once to 31's leaf ......... [28 31 34] → collect 31, 34
  follow next → sibling ............. [36 37 39] → collect 36, 37; 39 > hi → stop

  one descent + a walk.  Without a leaf chain, an ordered tree can still traverse successors using a stack or parent links; the chain makes the scan simpler.

The sorted leaf chain can serve BETWEEN, ORDER BY, and date-range queries without scanning unrelated index entries. Whether an index is faster than a heap scan depends on how many rows match and how they are stored. A hash index does not provide this ordered traversal.

Splits preserve equal leaf depth

After an insertion overfills a node, split it and add a separator to its parent. If the parent also overflows, repeat the process upward. If the root splits, create a new root. Each step preserves equal leaf depth.

Leaves copy the middle key up; internal nodes move it

Also fixthe leaf chain: the new sibling's next takes the old node's next, and the old node's next now points at the sibling, so a range scan still walks every leaf in order 
No parent?make a new root of one key and two children: the tree grows at the top, height increases by one, and every leaf is one level farther from the root

A root split adds one level above every existing leaf. A non-root split divides a node at its current level. Neither operation changes one leaf’s depth relative to another’s, so the tree remains balanced.1

Splits cascade upward, and a root split adds a level

insert 5 into a full tree of 1..4:                 root [3] appears
[1 2 3 4] + 5  →  split at mid=2  →   [1 2]  →  [3 4 5]      height 1 → 2

keep inserting 6, 7:   [3 4 5] fills, splits at 5 → root becomes [3 5]
insert 8, 9:           [5 6 7] fills... root [3 5 7] → root gains its fourth key at 11 and overflows at 13
                       → the ROOT splits → new root, height 2 → 3

Splits occur when insertions exceed a node’s capacity. Each split creates space for more keys and changes only the affected node, its new sibling, and any ancestors that also split. Thursday’s harness inserts 25 scattered keys and checks the resulting tree invariants.

A skewed split can preserve key order and equal leaf depth while violating minimum occupancy. Searches may still return correct results, but the tree uses extra space and can become taller. The lab’s 500-key height check tests this efficiency requirement alongside the correctness checks.

Fan-out 200 makes a billion rows a four-level tree

4 levels hold a billion rows when every node has 200 children, so a lookup reads four nodes

In this simplified full-node model, a billion keys need four index levels. Fetching one heap row adds a page access, and cached pages may avoid disk I/O.

Large fan-out keeps the height small. Page-sized nodes hold many keys and child pointers, so each page read narrows the search substantially. The exact fan-out depends on page size, entry size, and occupancy.4

Fan-out 2 costs 27 levels; fan-out 200 costs four

fan-out vs height · compare the number of levels

Pick a table size, then drag the fan-out from binary-tree territory (2) to page-sized nodes (~200). Each bar is a tree level, labeled with its node count; the height is how many bars you must descend.

With 100 million rows, fan-out 2 gives about 27 levels in this model. Increasing fan-out to about 200 reduces that to four. Each level is an index-page access; only uncached accesses require a disk read.

Caching can reduce the disk reads per lookup

Tree level (fan-out 200, 100M rows)NodesWhere it lives
root1usually cached because every lookup accesses it; memory pressure can still evict it
level 2~200often cached: 200 pages can fit in a modest buffer pool and are accessed frequently
level 3~40,000may be cached if the buffer pool has room for these pages and the workload reuses them
leaves~10⁶may exceed the cache capacity, making leaf accesses more likely to require disk I/O

The buffer pool reduces the I/O cost of index traversal by caching frequently used upper levels. A point lookup may then need one leaf read plus heap reads. A full table scan still visits every heap page, though those pages can also be cached.

Indexes add write and storage costs

Maintaining an index requires additional work when table data changes. This is a form of write amplification: one logical table change can cause writes to several structures.

You payWhenHow much
Maintenanceevery INSERT/UPDATE/DELETEone \(O(\log n)\) tree update per index on the table: five indexes mean six structures to update for an insert; the number of physical writes varies5
Spacealwaysroughly another copy of the indexed column + RIDs, often 10–30% of the table, each

Add indexes for queries that benefit enough to justify their maintenance and storage costs. Check actual query plans and usage before adding or dropping an index. The optimizer, covered in Lecture 9, estimates whether a particular query should use an available index.

Recap & next time

Three ideas to carry into the lab and later lectures.

  • An index is a map from values to RIDs: sorted entries provide direct access to heap rows and must be maintained when those rows change.
  • One move keeps it balanced: split the full node, push the middle up, grow at the root. Splits preserve equal leaf depth.
  • Fan-out is what makes the tree fast. With about 200 entries per leaf and 200 children per internal node, a billion keys fit in roughly four index levels; a heap fetch adds a page access8. The file, buffer, and record layers support those accesses.

FAQ

Why not a hash index? O(1) beats O(log n).

Hash indexes support efficient equality lookups, and PostgreSQL provides them. They do not preserve key order for range scans or sorted output. B+ trees support both equality and ordered access, making them useful for a wider range of queries. Bigtable, covered in Lecture 14, also preserves key order but uses write-optimized log-structured storage.91011

Is the binary search tree from my algorithms class the same thing?

Both structures route searches by comparing keys. A binary tree has at most two children per node, so even a balanced tree needs about 27 levels for 100 million entries. A B+ tree packs many keys into each disk page and branches to many children, reducing the number of page accesses. The design optimizes page I/O as well as comparisons.2

How does deletion affect node occupancy?

Deletion can leave nodes underfull. Textbook B+ trees redistribute keys or merge nodes to restore minimum occupancy. Production policies differ: PostgreSQL reclaims empty index pages but does not merge partly full pages, while other engines may merge them. The lab does not require deletion; Sciore ch. 12 covers the fuller algorithm.1213

Does Postgres really rebuild indexes at startup like ours?14

No. Persistent indexes store nodes in disk pages and represent child links with page identifiers, so the tree survives a restart. The lab keeps its index in memory to focus on search and splitting. Persisting it would also require page allocation, recovery, and careful updates to links; Going Further outlines the storage mapping.
