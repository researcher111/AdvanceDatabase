B+ Trees from First Principles

The forty-year-old data structure that finds one row in a billion by reading four nodes.
Daniel G. Graham · UVA School of Data Science

Your engine can answer any query, by reading everything. Today we fix that. The B+ tree is a map from values to RIDs whose height grows logarithmically-with-a-huge-base, so a point lookup touches a handful of nodes where a scan touches them all. One structural move (split the full node, push the middle key up) keeps it perfectly balanced through any insert order, forever. It is the single most consequential data structure in systems, and Thursday you build one.

Companion reading: Sciore, Database Design and Implementation, ch. 12 · the classic survey: Comer, The Ubiquitous B-Tree (1979) · Postgres's btree docs.

Finding one row in a million

Think · Pair · Share · the waste, quantified
  • Think · 2 minA million-row users table, WHERE uid = 77777, exactly one match. Your Lab 4 SelectScan answers it. Count its waste precisely: rows examined, rows returned, and the fraction of work that accomplished nothing. Then propose ANY scheme that does better: sorted file? Python dict? Something else? What does your scheme cost to maintain?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare schemes. A sorted file gives binary search but inserts shift everything (Lab 3's nightmare). A dict is O(1) but lives in RAM and can't do ranges. What would a structure need to dodge both traps?
  • Share · 2 minList the three requirements on the board: fast lookup, cheap insert, range-friendly. Today's structure hits all three.
Show the answer

One million rows examined, one returned: 99.9999% of the work accomplished nothing, and it gets worse linearly as the table grows. That is the cost of having only one access path.

Every scheme people propose trades one trap for another. A sorted file gives binary search, but every insert shifts the rows after it, which is exactly the nightmare Lab 3 abolished. A Python dict is O(1), but it lives in RAM, dies with the process, and hashing destroys order, so it cannot answer gpa BETWEEN 30 AND 35 at all. The three requirements are therefore fast lookup, cheap insert, and range-friendly, and a structure hits all three only by being shallow and sorted rather than flat: keep the keys in order, but reach them through a few levels of signposts instead of by shifting bytes. That is the B+ tree, and it is why it has been the default since 1979.

The B+ tree is the structure that refuses to be bad at anything, which is why every relational engine defaults to it.

An index is a second road

The heapstays exactly as Lab 3 left it: dumb, unordered, insert-friendly. Nothing about the table changes.
The indexa separate structure holding (value, RID) pairs in sorted order: a second road into the same rows, organized by a different principle.
The handshakethe index ends every journey with a RID; move_to_rid (three new lines on the reference TableScan) finishes the trip. Stable RIDs (Lab 3's quiet promise) are what make the handshake safe.
The pluralroads are independent: index uid AND name AND gpa if you like, each a separate tree over the same heap, each billed separately on every write.

Anatomy of the tree

Leaveshold the actual index entries, (key, RID) pairs in sorted order, and a next pointer to the right-hand sibling. All data lives at the bottom.
Internal nodeshold routing keys only: k keys fence k+1 children; "keys < 10 go left, ≥ 10 go right." Pure directions, no data.
The leaf chainsiblings linked left-to-right make ranges a walk: descend once to lo, then follow next until a key passes hi. This chain is the "+" in B+.
The invariantevery leaf is the same distance from the root, always. Not by luck: the split maintains it, as the next section shows.

A search, traced on the pinned tree

after inserting gpas 39, 31, 37, 28, 36, 34:        [ 36 ]            ← root (internal)
                                                   /      \
search(37):                            [28 31 34] → [36 37 39]        ← leaves, chained
  at [36]:      37 >= 36 → go right
  at leaf:      find 37 → its RIDs                 2 nodes touched, n = 6

Two comparisons at the root's routing key, one leaf, done. The same two-step dance at every scale; only the height changes, and the height barely changes.

Ranges: the chain pays off

range(31, 37) on the pinned tree:

  descend once to 31's leaf ......... [28 31 34] → collect 31, 34
  follow next → sibling ............. [36 37 39] → collect 36, 37; 39 > hi → stop

  one descent + a walk.  A sorted structure with NO chain would descend per key.

This is why BETWEEN, ORDER BY on an indexed column, and "the last 30 days" queries are cheap, and why hash indexes, orderless, can never serve them.

The split: one move, repeated

Think · Pair · Share · the full node
  • Think · 2 minA leaf holds [28, 31, 34, 36] (full at ORDER 4) and key 39 arrives. You must keep: sorted order, the every-leaf-same-depth invariant, and the leaf chain. Design the repair. What goes where, and what does the parent need to learn?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare repairs against: split at the middle, right half moves out, middle key goes up as the parent's new signpost. Now the hard case: what if the PARENT was also full?
  • Share · 2 minAnd if the splitting continues all the way to the root? Say aloud what happens to the tree's height, and to the same-depth invariant.
Show the answer

Split at the middle. The right sibling takes the upper half of the keys, the leaf chain is repaired so the node points at its new sibling and the sibling at the old next, and the middle key goes up to the parent as a signpost. In a leaf split the middle key is copied up, because leaves must keep all the data; in an internal split it is moved up, because internal keys are only directions. So [28, 31, 34, 36] plus 39 becomes [28, 31] and [34, 36, 39], with 34 copied into the parent.

If the parent is full too, it splits by the same move, and the repair walks upward. If it reaches the root, a new root is made holding one key and two children, and the height grows by one. That is the deep trick: the tree grows at the top, so every leaf gets one level deeper at the same instant and the same-depth invariant cannot break. Binary search trees grow at the leaves, which is exactly why they go lopsided and need rebalancing passes. This one never does.

Growing at the root is the deep trick: every leaf gets one level deeper at the same instant, so the same-depth invariant can't break. Trees that grow at the leaves (like binary search trees) can go lopsided; this one structurally cannot.

The cascade, hand-traced

insert 5 into a full tree of 1..4:                 root [3] appears
[1 2 3 4] + 5  →  split at mid=2  →   [1 2]  →  [3 4 5]      height 1 → 2

keep inserting 6, 7:   [3 4 5] fills, splits at 5 → root becomes [3 5]
insert 8, 9:           [5 6 7] fills... root [3 5 7] → root fills next split
                       → the ROOT splits → new root, height 2 → 3

Splits are rare (one per ~ORDER/2 inserts at each level) and local (the path, nothing else). Thursday's harness inserts 25 scattered keys and checks every invariant after the dust settles.

Why the middle key?

mid = len // 2two half-full nodes≥ 50% guaranteed; the height bound holds

Every invariant still holds under a skewed split; only quality dies. Thursday's harness includes a 500-key height check that exists to catch exactly this: correctness tests plus a quality bound.

Fan-out is the superpower

Think · Pair · Share · guess the height
  • Think · 2 minA real engine fits ~200 keys per page-sized node (fan-out 200). Guess the height of a B+ tree indexing 100 million rows. Then compute it: log₂₀₀(10⁸). Most people guess high, by a lot.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCheck: 200³ = 8 million, 200⁴ = 1.6 billion. So 10⁸ rows → height 4. What does the buffer pool do to the top 2–3 of those levels on a busy system?
  • Share · 2 minFinish the thought: how many actual disk reads does a point lookup on 100M rows cost, steady-state?
Show the answer

Height 4, and almost everyone guesses far higher. 200³ is 8 million and 200⁴ is 1.6 billion, so 10⁸ rows sits comfortably at four levels. A billion-row table is five.

The buffer pool then takes most of that away. The root is touched by every single lookup and the second level by nearly all of them, so on any busy system the top two or three levels are permanently resident. Steady state, a point lookup on 100 million rows costs about one or two actual disk reads: the leaf, and then the heap block holding the row. That is the whole reason databases feel instant. Not magic, just a logarithm with base 200, and the base is 200 because a node is sized to one of Lab 1's blocks.

The height table to remember

height ≈ log_fanout(n)

  rows        fan-out 4 (lab)     fan-out 200 (real page)
  100                4                    2
  100,000           11 (you'll measure)   3
  100,000,000       ~14                   4        ← a billion-row table is FIVE reads
                                                     and the top levels live in the pool

This is why databases feel instant: not magic, just a logarithm with base 200. And the base is 200 because nodes are sized to Lab 1's blocks: the tree is shaped by the disk it lives on.

Check yourself · run the cascade

The hand-traced tree stands at root [3] over leaves [1 2] and [3 4 5] (capacity 4 per node). Insert 6, then 7. For each: does a split happen, what moves up, and what does the root hold afterward?

Show answer

Insert 6: the right leaf becomes [3 4 5 6], full but legal, no split. Insert 7: now it overflows; split at the middle key 5 into [3 4] and [5 6 7], and a copy of 5 goes up: root [3 5], three leaves, height unchanged. If you moved 5 up without leaving it in a leaf, key 5 just became unfindable by a range scan; the copy-vs-move distinction is Thursday's subtlest test.

What indexes cost

Nothing in an engine is free, and the index bill arrives on every write; the polite name is write amplification:

You payWhenHow much
Maintenanceevery INSERT/UPDATE/DELETEone O(log n) tree update per index on the table: five indexes, six writes per insert
Spacealwaysroughly another copy of the indexed column + RIDs, often 10–30% of the table, each
Build timeCREATE INDEXone full scan + n inserts (you'll measure ~0.5s per 100k rows)
Planner riskquery timean index used on a low-selectivity predicate is slower than the scan it replaced (random hops vs one smooth read)

The DBA's proverb, now yours: index the columns you filter on constantly; resent every index you can't justify. The optimizer's job (week 9) is deciding per-query whether the index you built is actually worth using.

When the index loses

WHERE score > 10        keeps ~99% of rows (low selectivity)

  via index:  ~99,000 tree walks + 99,000 RANDOM heap jumps      ← disaster
  via scan:   294 blocks, read once, in order                    ← boring, correct, faster

An index on an unselective predicate is a longcut. Deciding, per query, from estimated selectivity, is precisely the optimizer's job, and week 9 builds that judgment.

The flip side: the covering index

The trickstore the columns a hot query needs inside the index entries, then answer from the index alone, zero heap visits.
The namea covering index; Postgres calls the resulting plan an index-only scan and offers INCLUDE to build one deliberately.
The pricefatter entries → lower fan-out → the write bill grows again. Every index decision is the same triangle: read speed, write cost, space.

Recap & next time

Three ideas from today, all load-bearing for the rest of the course.

  • An index is a map from values to RIDs: a second, sorted road into the same heap rows, paid for on every write.
  • One move keeps it balanced: split the full node, push the middle up, grow at the root. Same-depth leaves are structural, not lucky.
  • Fan-out beats cleverness. log base 200 makes a billion rows five reads, and the base is 200 because nodes are disk blocks. Every layer you've built shows up in this one structure.

FAQ

Why not a hash index? O(1) beats O(log n).

For pure equality it does, and Postgres offers one. But hashing destroys order: no ranges, no prefix matches, no sorted output for free. The B+ tree is two comparisons slower and infinitely more versatile; the default for a reason. (Bigtable's world, week 14, makes the opposite bet and pays with different machinery.)

Is the binary search tree from my algorithms class the same thing?

Same idea, wrong constants for disks: fan-out 2 means height 27 for 100M rows, 27 disk reads. The B+ tree is a BST re-engineered for Lab 1's block economics: one node = one block = one trip = 200 decisions. Data structures change when I/O is the currency.

What about deletes? Nodes can get too empty.

Textbook trees rebalance by merging underfull nodes, the split's mirror. Real engines mostly… don't: they tolerate thin nodes and reclaim lazily (vacuum), because merges cost writes and thin nodes only cost a little height. The lab follows the engines; Sciore ch. 12 has the full ritual if you want it.

Does Postgres really rebuild indexes at startup like ours?

No: real trees live in pages on disk (each Node a block, child pointers as block numbers) and survive restarts; that's the part we traded for a 75-minute lab. The algorithm you write is byte-for-byte the same logic; persistence is Lab 1 plumbing plus care. Going Further sketches the mapping.
