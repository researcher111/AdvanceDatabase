Vector Databases

How do we find vectors closest to a question, and how much search quality do we lose when we examine only part of the dataset?
Daniel G. Graham · UVA School of Data Science

Your project retrieves chunks whose embeddings are closest to the question vector. The B+ tree and hash indexes you built support equality and range queries, but they do not directly rank high-dimensional vectors by similarity to a new query. Approximate nearest-neighbor indexes reduce the number of vectors searched. They may miss some of the exact nearest neighbors, so you must measure recall as well as speed. In Thursday’s lab, you will build an IVF index and compare its search settings with brute-force search.

Companion reading: pgvector's README (index types and search settings) · the HNSW paper: Malkov & Yashunin, Efficient and robust ANN search using Hierarchical Navigable Small World graphs1 · FAISS's index-choosing guide.

Why similarity search needs a different index

A B+ tree stores a fixed key order; a hash index groups equal keys. In similarity search, the ranking depends on the query vector. A key order that works for one query generally does not give the nearest neighbors for another.

Exact search costs n × d multiplications per query

Store n vectors of d dimensions (n in the millions; d from 384 to 3072 for real embedding models2). A query asks for the top k by similarity, and for unit vectors cosine similarity is just the dot product2:

\[ \text{sim}(q, v) \;=\; q \cdot v \;=\; \sum_{i=1}^{d} q_i\, v_i \]

Normalize each stored vector once by dividing it by its length, and normalize each query vector before searching. The exact search then computes n dot products per query:

\[ \text{exact cost} \;=\; n \cdot d \text{ multiplications} \]

At one million vectors and 1536 dimensions, each query requires about 1.5 billion multiplications, before accounting for additions and result selection.2

Measure exact search before adding an index

Exact search scores all n vectors and keeps the top k. This gives the reference result for the chosen similarity metric. The dot products are independent, so they can run in parallel. Total work grows with the number of stored vectors, their dimensions, and the query rate.

Brute force may be sufficient for a small corpus

Brute-force search is simple and gives exact results. It may already meet your project’s latency target. The project requires this baseline so you can show whether an index improves performance enough to justify its build cost, memory use, and recall loss.

IVF and HNSW: search work versus recall

IVF and HNSW avoid comparing the query with every vector. Each provides a search setting that controls how much of the index is explored. Increasing that setting usually improves recall while increasing query cost.

IVFHNSW
Buildcluster the vectors with k-means and store one list per clustera layered graph: a few long-range links on top, near-neighbor links at the bottom
Searchscore the centroids, brute-force inside the best P listsnavigate upper graph layers, then explore a candidate set at the bottom layer
Search settingprobe (P)ef_search
Why a neighbor is misseda true neighbor in a list that was not probedthe graph search stops before exploring the true neighbor

IVF probes a few clusters and skips the rest

Build: group the vectors into C clusters with k-means. The number of clusters is a build setting; values on the order of √n are a starting heuristic, not a universal optimum. Search: score all C centroids and search only the P closest lists. If the lists are roughly equal in size, the number of vector comparisons is approximately:34

\[ \text{cost} \;\approx\; C + P \cdot \frac{n}{C} \qquad \text{instead of } n \]
4,000 vectors, C = 20, P = 4about 920 vs 4,0004.3×
1M vectors, C = 1000, P = 10about 11,000 vs 1,000,00090×4

A true neighbor is missed if its cluster is not among the P lists searched. Increasing P adds candidate vectors and increases the work per query.4

HNSW searches through a layered graph

HNSW illustration · long-range links above, local links below

Twelve vectors are arranged in two layers. The top layer contains a subset of the nodes; the bottom layer contains them all. This simplified animation follows the closest neighbor from the current node. When no neighbor is closer to the query ★, it moves down a layer. A full HNSW search keeps multiple candidates at the bottom layer.1

In this example, graph navigation finds the nearest neighbor after inspecting only part of the graph. HNSW does not guarantee that every query finds the exact nearest neighbors. The ef_search setting controls the size of the search candidate list: a larger value permits more exploration and usually improves recall at the cost of more distance calculations.5

HNSW trades memory and build cost for search performance

Search settingef_search controls the search candidate list. Larger values allow more exploration before the search returns its result. Measure recall and query time to choose a setting.3
The priceHNSW stores graph links as well as vectors and generally uses more memory and takes longer to build than IVFFlat. Search performance also depends on how much of the index is cached. Compare memory use, build time, recall, and query time for your workload.3

Measure agreement with exact search using recall@k

\[ \text{recall@}k \;=\; \frac{\bigl|\, \text{approximate top-}k \;\cap\; \text{true top-}k \,\bigr|}{k} \]

1.0 means the index found everything the exact search would have; 0.75 means it missed a quarter of the real neighbors, on that measured query set6.

Choose a recall target for the application

There is no recall target that suits every application. A missed neighbor may remove a useful recommendation or omit the passage needed to answer a question. Evaluate those effects with representative queries. Geometric recall measures agreement with exact vector search; it does not by itself show whether the results answer the user’s question.

Seven true neighbors appear: {1, 2, 3, 5, 6, 8, 9}, so recall@10 = 0.7. In this lab’s IVF search, ids 4, 7, and 10 must be in unsearched lists: vectors in the searched lists are scored exactly. Increasing probe adds lists without removing previous candidates. With fixed scores and consistent tie handling, recall therefore cannot decrease. Thursday’s harness checks that property.4

Where to run a vector index

Vector-search products often include IVF, HNSW, or related structures. They also differ in filtering, compression methods such as quantization, durability, and operations. One practical decision is whether the index belongs in your existing database, a library inside your application, or a separate service.

Compare database extensions, libraries, and services

ShapeExamplesWhen
Inside your databasepgvector (Postgres), DuckDB's VSSvectors are stored beside the rows they describe. This can simplify joins, filtering, and updates; check the extension’s supported queries and index limitations7
A libraryFAISS, hnswlibyour application loads the index, serves queries, and coordinates updates. This provides control over the implementation but requires you to build the surrounding service8
A dedicated servicePinecone, Weaviate, Milvus, Qdranta separate system stores and queries the vectors. A managed deployment can handle scaling and operations, but updates must stay consistent with the source data9

FAQ

Why cosine instead of Euclidean distance?

For unit vectors, cosine similarity and Euclidean distance give equivalent rankings because ‖q−v‖² = 2−2q·v. Cosine compares direction and ignores vector length. Use the metric recommended for the embedding model, and normalize consistently when using dot products as cosine scores.2

Is recall the only quality metric that matters?

Recall measures whether an approximate index finds the exact geometric neighbors. It does not tell you whether those neighbors are useful evidence. Next lecture separates retrieval evaluation from answer evaluation so that you can measure both.

When is a dedicated vector service useful?

A dedicated service can be useful for a large vector workload that needs managed scaling, tenant isolation, or specialized search features. Compare those benefits with the cost of operating a second datastore and keeping it synchronized. An index in your existing database is also worth evaluating.10

Could microdb have a vector index?

Yes. An IVF list could store (centroid_id, RID) entries. A search would choose lists, score their vectors, and return RIDs for the matching table rows. Lab 6’s IndexSelectScan illustrates the index-to-table lookup pattern, though similarity ranking would require additional logic. This is a possible project extension for a team continuing microdb.3
