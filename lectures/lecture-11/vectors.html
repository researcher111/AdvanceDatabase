Vector Databases

When the column is an embedding and the query is "what's similar?": indexes for a world without equality.
Daniel G. Graham · UVA School of Data Science

You already trust embeddings, vectors whose geometry encodes meaning. The database question they raise is new: every index you've met accelerates equality and order (uid = 7, gpa > 35), but "the 10 chunks most similar to this question" has no equality anywhere. B+ trees are useless here; hashing is worse. The answer is a new index family (approximate nearest neighbor) that buys speed by giving up a small, measured amount of correctness: the index may miss a few true neighbors, you measure how many it misses, and one setting lets you choose the trade. Thursday you build IVF and set that dial yourself; your project's retrieval layer will sit on it.

Companion reading: pgvector's README (the whole design in one page) · the HNSW paper: Malkov & Yashunin, Efficient and robust ANN search using Hierarchical Navigable Small World graphs1 · FAISS's index-choosing guide.

The similarity query

The setup, precisely

store:   n vectors, d dims (n = millions, d = 384-3072 for real embedding models2)
query:   top-k by similarity, cosine for unit vectors, which is just the dot product2:

    sim(q, v) = q · v = Σ qᵢvᵢ          (after normalizing: divide by length once, at insert)

exact answer:  n dot products per query = n·d multiplications.
             1M vectors × 1536 dims × every user question = the wall2.

Exact search and its wall

Before approximating anything, price the exact thing: score all n vectors, keep the top k. It is always correct, because it looks at every vector. It splits across cores trivially, because each dot product is independent of the others. And its cost grows in step with the number of vectors, the dimensions, and the queries, which is why it is the right baseline and why, at some scale, it stops finishing in time.

What brute force costs, and when it's fine

ScaleExact cost per queryVerdict
4k × 32-d (Thursday's lab)128k mults, sub-millisecondfine: brute force is the right choice at this size, but measure its cost anyway so the IVF speedup has something to be compared against
100k × 768-d (a real project corpus)77M mults, tens of msacceptable for one user at a time; tens of milliseconds per query becomes a problem once many queries arrive at once
10M × 1536-d, 100 queries per second (production RAG)1.5 × 10¹² mults/secthe wall: 1.5 trillion multiplications every second is more than a server can sustain, so exact search stops being an option

Honest advice your project should hear: at small scale, brute force is the right answer: exact, simple, zero recall anxiety. The project spec requires the brute-force baseline for exactly this reason. Indexes earn their keep at scale, like always.

ANN: IVF and HNSW

IVF: cluster, then probe

build:   k-means into C lists (C ≈ √n is folklore)3      once, offline
search:  score C centroids → take the best P ("probe")  → brute-force inside those lists4

cost ≈ C + P·(n/C) instead of n:   4,000 vectors, C=20, P=4  →  ~880 vs 4,000  (4.5×)
                                   1M vectors, C=1000, P=10  →  ~11k vs 1M     (90×)4

the miss: a true neighbor in an unprobed list. P is the dial4.

HNSW: navigate, don't partition

HNSW's greedy walk · highways to get close, streets to finish

Twelve vectors, two layers. The top layer keeps a few nodes with long-range links (the highways); the bottom layer links every node to its near neighbors (the streets). Step the walk: from the entry point, always hop to whichever neighbor is closest to the query ★; when no neighbor improves, drop a layer and keep walking1.

The walk reaches the true nearest neighbor in a handful of hops, computing distances only along the path; that near-logarithmic hop count is why HNSW usually wins the recall-at-speed benchmarks5. Its dial is ef_search, the number of candidate nodes the walk keeps track of at once instead of only the single best one: same contract as IVF's probe, since a wider candidate set finds more true neighbors and costs more distance computations.

The dialef_search sets how many candidate nodes the walk carries at once. With a larger set the walk explores more branches before settling, so it is less likely to stop at a node that is close but not closest. Same trade as probe: a bigger value gives better recall and does more work3.
The pricethe whole graph must sit in RAM, and each insert has to search for its neighbors and link to them, which costs more than IVF's append to one list. Choose HNSW when recall at a given speed matters most; choose IVF when memory is tight or the index has to build quickly3.

Recall: the honesty metric

recall@k  =  |approximate top-k  ∩  true top-k|  /  k6

  1.0  = found everything the exact search would have
  0.75 = missed a quarter of the real neighbors - and told you so

Read it like an engineer: at probe 1 you're wrong about 1 in 4 neighbors and 17× faster; at probe 4 you're wrong about 1 in 20 and still 4.5× faster. Neither is "right". A recommender can tolerate 0.76, because a user never notices that one suggestion in four was not the mathematically closest. Retrieved evidence for a RAG answer cannot, because the missed neighbor may be the one passage that held the answer. The dial is yours, and "what recall does this application need?" is now a question you ask out loud.

Check yourself · score an index by hand

Exact search says the true top-10 for a query is ids {1…10}. Your IVF at probe 2 returns, in order: 1, 2, 3, 5, 6, 8, 9, 11, 14, 20. Compute recall@10, and then explain where ids 4, 7, and 10 must be, physically, for this result to have happened.

Show answer

Seven of the true ten appear ({1,2,3,5,6,8,9}), so recall@10 = 0.7. Ids 4, 7, and 10 sit in cluster lists the two probes didn't visit; they were never compared, not out-scored; 11, 14, 20 filled their seats. Raising probe can only add candidate lists, so recall can only rise, which is exactly the monotonicity Thursday's harness tests, and the reason a "probe more, recall drops" bug always means the probe isn't selecting what you think4.

The landscape

Every product in the vector-database gold rush is some packaging of the two structures you just met, plus the dial. What varies is where it lives relative to the rest of your data:

Three ways to ship a vector index

ShapeExamplesWhen
Inside your databasepgvector (Postgres), DuckDB's VSSthe vectors sit in a column beside the rows they describe, so joins, WHERE filters, and transactions work on them with no extra machinery. This is the unexciting default, and it is usually the right one7
A libraryFAISS, hnswlibthe library gives you the index data structure and nothing else: you write the process that loads it, answers queries, and keeps it in step with your data. Maximal control and speed, at the cost of building that plumbing yourself8
A dedicated servicePinecone, Weaviate, Milvus, Qdranta vendor runs the index for you and handles scaling and operations. The price is a second copy of your data living outside your database, which you must keep in sync with the first (see FAQ)9

For the project: microvector or pgvector or FAISS all satisfy the spec; what's graded is that your retrieval layer is a real index and you can defend its dial setting with your own measurements.

FAQ

Why cosine instead of Euclidean distance?

On unit vectors they induce the same ranking (‖q−v‖² = 2−2q·v), so the argument is moot once you normalize, which embedding models mostly assume2. Cosine's virtue is that it ignores a vector's length and compares direction only. For embeddings, direction carries what a text is about, while length tends to reflect how much or how emphatically it says it, which is not what a similarity query is asking.

Is recall the only quality metric that matters?

It's the index's metric: did the structure find the true geometric neighbors? Whether those neighbors are useful is the embedding model's burden and the pipeline's (next lecture: end-to-end evaluation, where retrieval hit-rate and answer quality get separated on purpose).

The dedicated vector databases advertise hard: when do they earn it?

When vectors are your primary workload at serious scale: billions of vectors (usually quantized), filtered ANN, multi-tenant serving10. Below that, a second datastore means a second copy of truth, sync jobs, and consistency questions you now know by name. The boring answer (vectors in the database you already run) wins more often than the marketing implies.

Could microdb have a vector index?

Structurally yes: IVF lists are just tables (centroid_id, RID), and Lab 6's IndexSelectScan pattern applies verbatim: the index scan hands back RIDs and the table fetches those rows. That is, in fact, roughly what pgvector is to Postgres: a new index type that returns RIDs the same way every other index does3. A good final-project appendix for teams that keep building on microdb.
