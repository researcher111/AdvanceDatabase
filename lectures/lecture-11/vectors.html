Vector Databases

The passage you need is in the database. Can you find it without searching everything?
Daniel G. Graham · UVA School of Data Science

A fictional project rehearsal

Maya sits at a lab desk, turns her laptop toward her teammate Noor, and types: How does a database recover after a crash? Their notes contain a passage about replaying a durable log. She searches for her question as an exact string. No match.

She scrolls back to the passage and taps the screen. It’s right here. Why can’t the search find it? Noor reads the two sentences aloud. They describe the same idea with different words.

Maya thinks, Our search needs to find the passage that answers the question, even when the wording is different. She turns back to the keyboard. Let’s trace the search to see why it missed the passage.

We will follow that question through three decisions: how to compare meaning, how to reduce search work, and how to notice what the shortcut misses. Your project represents questions and chunks with embeddings. An approximate nearest-neighbor index searches those vectors while risking some missed neighbors. In Lab 9 on October 29, you will build an IVF index and measure that trade.

Companion reading: pgvector's README (index types and search settings) · the HNSW paper: Malkov & Yashunin, Efficient and robust ANN search using Hierarchical Navigable Small World graphs1 · FAISS's index-choosing guide.

The question we will follow

Given a question vector, return the 10 most similar chunk vectors. Scoring every stored vector gives the exact result. Today we examine how an index can reduce that work, and how to measure the neighbors it misses.

Start with what you already know

Before following Maya’s question, explain what a B+ tree does for uid = 7. Would the same exact-key lookup find a sentence with different wording? If you already know dot products, compute (0.8, 0.6) · (0.6, 0.8); otherwise, trace the two products with a partner.

Check the starting point

A B+ tree locates the requested key in a fixed ordering. Matching a paraphrase requires a different comparison. The dot product is 0.8 × 0.6 + 0.6 × 0.8 = 0.96. We will reuse that score when a nearby vector is skipped.

Quiz 7 first (columnar & the analytics stack, 10 min), then the index your project depends on.

Today’s main idea: searching fewer candidates can miss true neighbors; measure that loss against exact search. Choose search settings by measuring work and recall on queries representative of your application.

Keep Maya’s question in view. First, find the nearest vectors with exact search. Then take a shortcut, catch a missed neighbor, and choose how much work to spend getting it back. Finally, read the returned passage: being nearby does not guarantee that it answers the question.

The passage is there but the words differ

Could we use the B+ tree we already built? Maya asks. It can find an exact key or walk a range. But her next question will need a different ranking of the same passages. The index needs to answer near this question, with “near” defined by the embedding model.

A B+ tree stores a fixed key order; a hash index groups equal keys. In similarity search, the ranking depends on the query vector. A key order that works for one query generally does not give the nearest neighbors for another.

Turn the question and passage into comparable vectors

Noor sends the question and the stored chunks through a compatible embedding model. It maps each to coordinates. Those coordinates can place a paraphrase near the question even when the strings differ. Use compatible model versions, dimensions, and preprocessing for both sides; equal dimensions alone do not make two models’ spaces compatible.

Store n vectors of d dimensions. A query asks for the top k by similarity. Follow the model’s recommended metric. For unit vectors cosine similarity is just the dot product2:

\[ \text{sim}(q, v) \;=\; q \cdot v \;=\; \sum_{i=1}^{d} q_i\, v_i \]

Normalize each stored vector once by dividing it by its length, and normalize each query vector before searching. The exact search then computes n dot products per query:

\[ \text{exact cost} \;=\; n \cdot d \text{ multiplications} \]

At one million vectors and 1536 dimensions, each query requires about 1.5 billion multiplications, before accounting for additions and result selection.2

Find the neighbors before taking a shortcut

Maya writes a loop: score every stored vector, then keep the ten highest scores. Noor points to the result IDs. Save that list. When we try an index, how else will we know what it missed? This is their exact baseline. They still have to open the passages and check whether they answer the question.

Exact search scores all n vectors and keeps the top k. This gives the reference result for the chosen similarity metric. The dot products are independent, so they can run in parallel. Total work grows with the number of stored vectors, their dimensions, and the query rate.

Brute force may be sufficient for a small corpus

Brute-force search is simple and gives exact results. It may already meet your project’s latency target. The project requires this baseline so you can show whether an index improves performance enough to justify its build cost, memory use, and recall loss.

The rehearsal now has a way to rank passages. Then the team adds more documents and more users. Maya watches the timer as a query runs. Do we have to score every vector every time? Before changing the search, measure elapsed time. The operation counts explain the growing work; they do not tell you how long it takes on your hardware.

Search less and risk missing a neighbor

Noor sketches groups of vectors on paper. What if we search only a few groups? Maya starts to nod, then stops. What happens to a good passage in a group we skip? Searching fewer groups saves comparisons, but it can leave a useful passage out of the results.

IVF and HNSW avoid comparing the query with every vector. Each provides a search setting that controls how much of the index is explored. Increasing that setting usually improves recall while increasing query cost.

Choose shelves before checking their contents

Imagine books grouped onto shelves. You choose a few promising shelves from their labels, then check the books on those shelves. A useful book on another shelf is never examined. IVF uses the same kind of shortcut: a centroid represents a group, a list holds its vectors, and probe says how many lists to search.

Noor draws a shelf label above each list. The label helps us choose where to look. It doesn’t tell us every book that’s inside. In an actual index, distances between vectors determine the assignments and the chosen lists. The shelf analogy explains the grouping; it does not guarantee which passages are relevant.

Build: choose centroids and assign each stored vector to a list. Search: score the centroids, choose a few lists, and score their vectors. Before counting the savings, watch what this choice can miss.

Find the missing neighbor by hand

Maya puts four unit vectors on the whiteboard. The query is q = (0.8, 0.6). The query’s highest centroid score is for c0, whose list contains only v0. Then v0 is our best result? Noor asks her to score v1 = (0.6, 0.8) before advancing. Its dot product is 0.96, higher than v0’s 0.80. But v1 belongs to the other list.

Predict the next step: what will probe 1 return, and what changes at probe 2? At build time, each stored vector joins its closest centroid’s list. At query time, choosing the closest centroid to the query can skip the query’s closest stored vector. These are toy coordinates, separate from the fictional project’s passages.

Worked result: At probe 1, the query searches only vector 0 and misses vector 1, whose score is 0.96. Recall@2 is 0.5. At probe 2 it finds both exact neighbors but pays six dot products, compared with four for exact search.

Count the work and compare another route

The four-vector example makes the consequence visible: the best vector can be in another list. Now count the work when there are many vectors. The estimate below generalizes the same two operations you just traced: score the centroids, then score the vectors in the chosen lists.

IVF probes a few clusters and skips the rest

Build once: group the vectors into C clusters with k-means and store each vector in its closest centroid’s list. For each query: score all C centroids and search only the P closest lists. The closest centroid does not necessarily own the closest vector. If lists are roughly equal in size, the count of distance evaluations, including centroids, is approximately:34

\[ \text{cost} \;\approx\; C + P \cdot \frac{n}{C} \qquad \text{instead of } n \]
4,000 vectors, C = 20, P = 4about 820 vs 4,0004.9× fewer evaluations
1M vectors, C = 1000, P = 10about 11,000 vs 1,000,00090×4

A true neighbor is missed if its cluster is not among the P lists searched. Increasing P adds candidate vectors and increases the work per query.4

The cluster count is a build choice. Values on the order of √n are a starting heuristic; choose with measurements. The balanced-list estimate above is separate from the measured Lab 9 results below.

HNSW searches through a layered graph

IVF chooses lists. HNSW follows links between vectors. Noor traces a long link across the page, drops to a denser layer, and checks nearby candidates. We can change how widely we explore here, too. The setting changes, but the experiment stays the same: compare the result with exact search and count the work.

HNSW illustration · long-range links above, local links below

Twelve vectors are arranged in two layers. The top layer contains a subset of the nodes; the bottom layer contains them all. This simplified animation follows the closest neighbor from the current node. When no neighbor is closer to the query ★, it moves down a layer. A full HNSW search keeps multiple candidates at the bottom layer.1

In this example, graph navigation finds the nearest neighbor after inspecting only part of the graph. HNSW does not guarantee that every query finds the exact nearest neighbors. The ef_search setting controls the size of the search candidate list: a larger value permits more exploration and usually improves recall at the cost of more distance calculations.5

HNSW trades memory and build cost for search performance

Search settingef_search controls the search candidate list. Larger values allow more exploration before the search returns its result. Measure recall and query time to choose a setting.3
The priceHNSW stores graph links as well as vectors and generally uses more memory and takes longer to build than IVFFlat. Search performance also depends on how much of the index is cached. Compare memory use, build time, recall, and query time for your workload.3

Decide how much search is enough

Maya opens the saved exact result beside the IVF result. How many exact neighbors are missing from the IVF result? Count the shared IDs. Recall measures that overlap so you can assess the missed neighbors alongside the reduction in search work.

\[ \text{recall@}k \;=\; \frac{\bigl|\, \text{approximate top-}k \;\cap\; \text{true top-}k \,\bigr|}{k} \]

1.0 means the index found everything the exact search would have; 0.75 means it missed a quarter of the real neighbors, on that measured query set6.

Choose a recall target for the application

There is no recall target that suits every application. A missed neighbor may remove a useful recommendation or omit the passage needed to answer a question. Evaluate those effects with representative queries. Geometric recall measures agreement with exact vector search; it does not by itself show whether the results answer the user’s question.

Maya leans back when the missing vector returns. Noor opens its passage. Does it actually explain recovery? If exact search finds useful evidence that IVF misses, investigate the index’s search budget. If even the exact neighbors are unhelpful, inspect chunking, embeddings, metadata, or ranking. Increasing the probe count searches more vectors; it does not change their similarity scores or the text stored in each chunk.

Check yourself: recall is a count you can do by hand

Exact search says the true top-10 for a query is ids {1…10}. Your IVF at probe 2 returns, in order: 1, 2, 3, 5, 6, 8, 9, 11, 14, 20. Compute recall@10, and then explain where ids 4, 7, and 10 must be, physically, for this result to have happened.

Show answer

Seven true neighbors appear: {1, 2, 3, 5, 6, 8, 9}, so recall@10 = 0.7. In this lab’s IVF search, ids 4, 7, and 10 must be in unsearched lists: vectors in the searched lists are scored exactly. Increasing probe adds lists without removing previous candidates. With fixed scores and consistent tie handling, recall therefore cannot decrease. Lab 9’s harness checks that property.4

Where to run a vector index

With a search setting to test, Maya reaches for a database diagram. Where do the vectors go when we update a document? Now the decision concerns who stores the index, applies filters, and keeps it connected to the source rows.

Vector-search products often include IVF, HNSW, or related structures. They also differ in filtering, compression methods such as quantization, durability, and operations. One practical decision is whether the index belongs in your existing database, a library inside your application, or a separate service.

Compare database extensions, libraries, and services

ShapeExamplesWhen
Inside your databasepgvector (Postgres), DuckDB's VSSvectors are stored beside the rows they describe. This can simplify joins, filtering, and updates; check the extension’s supported queries and index limitations7

FAQ

Why cosine instead of Euclidean distance?

For unit vectors, cosine similarity and Euclidean distance give equivalent rankings because ‖q−v‖² = 2−2q·v. Cosine compares direction and ignores vector length. Use the metric recommended for the embedding model, and normalize consistently when using dot products as cosine scores.2

Is recall the only quality metric that matters?

Recall measures whether an approximate index finds the exact geometric neighbors. It does not tell you whether those neighbors are useful evidence. Next lecture separates retrieval evaluation from answer evaluation so that you can measure both.

When is a dedicated vector service useful?

A dedicated service can be useful for a large vector workload that needs managed scaling, tenant isolation, or specialized search features. Compare those benefits with the cost of operating a second datastore and keeping it synchronized. An index in your existing database is also worth evaluating.10

Could microdb have a vector index?

Yes. An IVF list could store (centroid_id, RID) entries. A search would choose lists, score their vectors, and return RIDs for the matching table rows. Lab 6’s IndexSelectScan illustrates the index-to-table lookup pattern, though similarity ranking would require additional logic. This is a possible project extension for a team continuing microdb.3
