Vector Databases

A chunk can answer a question even when the words differ. Vector search compares their embedding vectors.
Daniel G. Graham · UVA School of Data Science

Fictional project example

Maya and Noor test their project at a lab desk. Maya types: How does a database recover after a crash? Their notes contain a passage about replaying a durable log. An exact string search for the question returns no match.

The question and the passage use different words for the same idea. The search must find a passage that answers the question.

Maya and Noor will use vector comparison instead of string matching. They will then check whether each result answers the question.

A chunk is a passage of text that the system stores for retrieval. The project represents each question and chunk with an embedding vector. The question embedding is the query vector. We will compare vectors, reduce search work, and measure missed neighbors.

An approximate nearest-neighbor index searches these vectors. It can miss some exact neighbors. In Lab 9 on October 29, you will build an inverted file (IVF) index. You will measure its search work and missed neighbors.

Find chunks that answer a question

Find a chunk with different words

A B+ tree on chunk IDs can find chunk 7 or chunks with IDs from 7 to 12. This ID order stays the same for every question.

For the crash-recovery question, Maya wants a chunk about replaying a log. For a question about faster queries, Maya wants a chunk about indexes. The required order of chunks changes with each question.

An embedding model converts each question and chunk to a vector. Search ranks chunk vectors by their similarity to the query vector.

A B+ tree stores a fixed key order. A hash index groups equal keys. In similarity search, the ranking depends on the query vector. A key order for one query generally does not give the nearest neighbors for another query.

Convert the question and chunks to comparable vectors

Noor sends the question and each stored chunk through a compatible embedding model. For each input, the model returns an embedding vector: a list of numbers with a fixed length. This vector identifies a position in the embedding space. The recovery question and a log-replay chunk can have similar vectors, even when their words differ.

A typical transformer embedding model splits text into tokens. A token can be a word or part of a word. The model uses surrounding tokens to update each token vector. It then combines the token vectors into one vector.

The example below uses mean pooling and normalization. Mean pooling calculates the average of the token vectors. Normalization divides the resulting vector by its magnitude. Other models can use different pooling methods.1112

Compare the vectors with a similarity score

The dataset has n vectors with d dimensions. A query requests the top k vectors by similarity. Use the metric that the model recommends. For unit vectors, cosine similarity equals the dot product2:

\[ \text{sim}(q, v) \;=\; q \cdot v \;=\; \sum_{i=1}^{d} q_i\, v_i \]

Normalize each stored vector once: divide each coordinate by the vector magnitude, or Euclidean norm. Before each search, normalize the query vector. Exact search then calculates n dot products per query:

\[ \text{exact cost} \;=\; n \cdot d \text{ multiplications} \]

For one million vectors with 1536 dimensions, each query requires about 1.5 billion multiplications. Additions and result selection require additional work.2

Save the exact search results

Maya compares the query vector with every stored chunk vector. She keeps the ten results with the highest scores. Noor saves the result IDs. These IDs identify the exact search baseline for the chosen similarity metric. They will compare approximate results with this baseline.

Maya and Noor must still read the returned chunks. An exact neighbor does not necessarily answer the question.

Each dot product is independent, so the comparisons can run in parallel. Every query still scores all n stored vectors and uses all d coordinates. More vectors, more dimensions, or more queries per second increase the total work.

Exact search can be sufficient for a small dataset

Exact search, also called brute-force search, scores every stored vector. It can meet your project latency target. The project requires this baseline. Use the baseline to evaluate the benefits and costs of an index. Compare query time, build cost, memory use, and recall loss.

More documents and more users increase the search workload. Before changing the search method, measure elapsed time. Operation counts explain the work. They do not establish query time on your hardware.

Search fewer vectors

Noor groups the stored vectors and searches only some groups. This method reduces comparisons. However, a skipped group can contain a useful chunk. The search can therefore miss an exact neighbor.

IVF and HNSW can search without a comparison between the query vector and every stored vector. A candidate vector is a stored vector that the search selects for scoring. Each index has a setting that controls search effort. A larger setting usually improves recall and increases query cost.

Select lists before scoring their vectors

Consider books grouped on shelves. You use shelf labels to select some shelves. You check only the books on those shelves. You can miss a useful book on another shelf.

In IVF, a centroid represents a group of vectors. A list contains the vectors assigned to that centroid. The probe count specifies how many lists to search.

A shelf label helps you select a shelf, but it does not identify every book. Similarly, a centroid helps search select a list. Distances between vectors determine their list assignments and which lists the search selects. The shelf comparison explains grouping. It does not establish which chunks answer the question.

During index construction, the system selects centroids and assigns each stored vector to a list. During search, the system scores the centroids, selects lists, and scores the vectors in those lists. The next example shows how list selection can miss an exact neighbor.

Calculate the missed neighbor

The example has four unit vectors and query vector q = (0.8, 0.6). Centroid c0 has the highest score for this query. This centroid has only v0 in its list. The dot product of the query vector and v0 is 0.80.

Now compare the query vector with v1 = (0.6, 0.8). Their dot product is 0.96. This score is higher than the score for v0. However, v1 belongs to the other list.

What will probe 1 return? What changes at probe 2? During index construction, each stored vector joins the list of its closest centroid. During search, selecting the closest centroid can miss the closest stored vector. These illustrative coordinates are separate from the chunks in the fictional project.

Worked result: At probe 1, the query searches only vector 0. It misses vector 1, whose score is 0.96. Recall@2 is 0.5. At probe 2, the search finds both exact neighbors. It calculates six dot products, compared with four for exact search.

Compare the work for IVF and HNSW

The four-vector example shows that the nearest vector can be in a skipped list. We now estimate work for a larger dataset. IVF scores the centroids first. It then scores the vectors in the selected lists.

IVF searches selected lists

During index construction, k-means groups the vectors into C clusters. The system stores each vector in the list of its closest centroid. For each query, IVF scores all C centroids. It then searches the P lists with the closest centroids. The list of the closest centroid does not necessarily contain the closest vector.

If the lists have approximately equal sizes, this formula estimates distance evaluations. The count includes centroid evaluations.34

\[ \text{cost} \;\approx\; C + P \cdot \frac{n}{C} \qquad \text{instead of } n \]
4,000 vectors, C = 20, P = 4about 820 vs 4,0004.9× fewer evaluations
1M vectors, C = 1000, P = 10about 11,000 vs 1,000,00090×4

If the search skips a list, it misses any exact neighbors in that list. A larger P adds candidate vectors and increases the work per query.4

The cluster count is a setting for index construction. A count proportional to √n is a starting estimate. Use measurements to select a count. The estimate above assumes balanced lists. The measured Lab 9 results below come from a separate experiment.

HNSW searches through a layered graph

IVF selects lists. HNSW follows links between stored vectors. HNSW means Hierarchical Navigable Small World. Search starts in a sparse upper layer and continues in denser lower layers. The search setting controls how many candidate vectors the search can explore.

Choose a search setting

Compare the IVF result IDs with the saved exact result IDs. Count the IDs that occur in both results. Recall measures this overlap. Compare recall with search work to select a setting.

\[ \text{recall@}k \;=\; \frac{\bigl|\, \text{approximate top-}k \;\cap\; \text{true top-}k \,\bigr|}{k} \]

Recall of 1.0 means that the index found all exact neighbors. Average recall of 0.75 means that the index missed one quarter of the exact neighbors across the measured query set.6

Choose a recall target for the application

No recall target suits every application. A missed neighbor can remove a useful recommendation or a chunk needed to answer a question. Evaluate these effects with representative queries. Geometric recall measures agreement with exact vector search. It does not establish whether the results answer the question.

After a search finds a missed neighbor, read its chunk. If exact search finds useful evidence that IVF misses, examine the search setting. If exact neighbors are also unhelpful, examine chunking, embeddings, metadata, or ranking. A larger probe count searches more vectors. It does not change their similarity scores or chunk text.

Where to run a vector index

A vector index can run inside a database, inside an application, or in a separate service. A separate service is optional. In each case, the system must connect vectors to their source chunks.

For example, Maya edits chunk 42. Vector 42 still represents the old text. The application must create a new embedding and update index entry 42. An index inside the database does not automatically create a new embedding.

Vector-search products often provide IVF, HNSW, or related indexes. Products also differ in filtering, durability, and operations. Some provide compression methods such as quantization. Compare these features when selecting where to run the index.

FAQ

Why cosine instead of Euclidean distance?

For unit vectors, cosine similarity and Euclidean distance give equivalent rankings because ‖q−v‖² = 2−2q·v. Cosine compares direction and ignores vector length. Use the metric that the embedding model recommends. If you use dot products as cosine scores, normalize vectors consistently.2

Is recall the only quality metric that matters?

Recall measures whether an approximate index finds the exact geometric neighbors. It does not establish whether those neighbors provide useful evidence. The next lecture separates retrieval evaluation from answer evaluation. You can then measure both.

When is a separate vector service useful?

A separate service can support large vector workloads that need managed scaling, tenant isolation, or specialized search features. It also adds another data store and an update process. Compare these benefits and costs with an index in your existing database.10

Could microdb have a vector index?

Yes. An IVF list could store (centroid_id, RID) entries. Search would select lists and score their vectors. It would return RIDs for matching table rows. Lab 6 IndexSelectScan shows this index-to-table lookup pattern.

Similarity ranking would require additional logic. A team that continues microdb could implement this project extension.3
