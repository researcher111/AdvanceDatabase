The discovery bureau

From city streets to distant worlds.

Your team is a tiny research bureau. A surprising chart arrives on your desk. Your job is to find out what it actually means—and explain the discovery so someone else can reproduce it.

Open a browser and start investigating. The live examples use databases operated by ClickHouse, NASA’s Exoplanet Archive, and Wikidata. No student database server or new account is required for these public queries. Saved evidence below works without contacting those services.

One story, five cases

Each case unlocks the next question. The city teaches us to count fairly. The weather teaches us to doubt a field. Planets teach us to ask what could be observed. A knowledge graph teaches us to follow a source. The final case is the team’s own discovery.

Instructor preparation · about 15 minutes, no server administration
  1. Open each hosted service from the teaching network. Run one case query and inspect its schema and row count.
  2. Use the dated JSON/CSV snapshots on this page for a common class baseline. Live results may change; record the retrieval time.
  3. To refresh them, run python3 lectures/discovery/refresh.py from the course repo. It uses Python’s standard library and four small read-only requests. Run it during preparation, not on every student page load.
  4. Have students download the evidence before class if internet access is uncertain. The page itself draws the saved charts without a network call.
  5. Keep a copy of the query, result, source URL, retrieval date, row definition, and any exclusions with each conclusion.
When would we build a database together?

Only if we want private uploads, persistent student tables, or dedicated capacity for everyone to experiment at once. Then a small managed ClickHouse Cloud classroom database is a natural continuation of the same SQL. We would choose a budget and account owner together, load a bounded taxi/weather subset, and give students read-only access. The provider runs the infrastructure; we still own the classroom data and access choices. Nothing has been provisioned or billed for this outline.

For the current public lessons, there is nothing for you to create. The optional local DuckDB loader already demonstrates schema creation, import, keys, and views without a cloud account.

Case 1 · Thursday November 19 · Minutes 0–25

The city that never sleeps?

“More taxi trips happen on weekdays, so New Yorkers go out less on weekends.” The editor wants to publish. Do we sign off?

Predict: which hours would change most if we divided by the number of observed weekdays or weekend days? Sketch the two curves before seeing the result.

Data: filtered yellow-cab trips in the hosted July 2015 table. This is a different extract from the bundled 2024 teaching sample. We compare day types within this extract, not counts between the two datasets. One result row is an hour/day-type pair; keep its observed-date count beside the total.

  1. 0–5 · The headline. Recall the taxi sample: why were all months equally busy?
  2. 5–10 · Meet the witnesses. Inspect dates, cab type, filters, and observed-date counts. Predict a weekend curve.
  3. 10–20 · Follow the query. Filter trips → group by day type/hour → count distinct dates → divide. Reveal totals, then switch to trips per observed day.
  4. 20–25 · File the case. Pairs state one finding and one limitation. Propose changing a month or distance band as a follow-up; then turn to the weather clue.
Teaching reveal and visual plan

Animate one trip entering an hour bucket, then reveal the calendar tiles supplying its denominator. The saved chart switches between totals and per-observed-day rates. In July 2015 the weekday groups contain 23 dates and weekend groups 8; an hour with no records would disappear from this denominator, so audit coverage before describing calendar-day rates. A taxi ride is not a person, and activity is not happiness.

Systems link: column scans, filter pushdown, aggregation, and the difference between elapsed time and work done. Ask which columns the engine needs to read.

Cliffhanger: perhaps weather explains the pattern. Can we trust the weather table?

Case 2 · Thursday November 19 · Minutes 25–55, then question swap

The July that froze?

The next chart says Central Park’s average temperature was zero every day in July. Did the city freeze—or did something happen between the observations and our database?

Predict: list two explanations for zero. Which extra field or source document could distinguish them?

Data: NOAA GHCN-Daily observations mirrored by ClickHouse, station USW00094728, July 2015. One row is a station/date. Temperature fields are stored in tenths of °C; the query converts units while preserving the encoded zeros.

  1. 25–30 · The impossible chart. Reveal only encoded_avg_c. Students predict two explanations.
  2. 30–40 · A second witness. Reveal minimum and maximum; inspect the schema and source preparation.
  3. 40–50 · Reconstruct the pipeline. Draw observation rows → quality filtering → pivot → station/date row. Explain how an absent element can become a numeric default.
  4. 50–55 · Design the next test. Before joining to daily taxi aggregates, name the key, date-coverage, and time-convention checks needed.
  5. 55–75 · Project question swap. Exchange the ten evaluation questions already due today; label which need numeric evidence, retrieved text, or an explicit “unknown.”
Teaching reveal and visual plan

The saved chart first draws the suspicious average, then adds the recorded minimum and maximum. Compare the original NOAA missing-value and flag definitions with the mirror’s pivot using anyIf. Its numeric default can lose the distinction between an absent observation and a real zero. Do not fix all zeros with NULLIF: zero °C and zero precipitation can be real observations.

Systems link: sparse observations, wide rows, schema design, defaults, and joins that preserve the intended row unit. An optional taxi/weather scatterplot is a follow-up design, not a causal finding or a chart already computed here. Use the same 2015 dates; never attach this mirror to the 2024 sample by month/day alone.

Cliffhanger: if observation rules can change a weather chart, what might they do to a census of planets?

Case 3 · Tuesday November 24 · 75 minutes

The planet census

A catalog contains many more planets found by one method than another. Have we discovered what the universe mostly contains—or what our instruments are good at finding?

Predict: should every discovery method have the same proportion of planets with a radius value? What does COUNT(column) leave out?

Data: the NASA Exoplanet Archive’s pscomppars table, discovery years 1990–2024. It offers one composite row per planet. Values in a row can come from different references or calculations; a non-null radius is not necessarily a direct measurement. A discovery-year cutoff does not freeze later catalog revisions.

  1. 0–10 · Choose the headline. Teams predict the most common recorded method and the weakest conclusion one might draw from it.
  2. 10–25 · Choose the row. Compare the composite table’s planet grain with the ps table’s multiple parameter sets.
  3. 25–40 · Make a census. Run the grouped count. Switch the saved visual from catalog counts to radius-value coverage.
  4. 40–60 · Change the lens. In the hosted query, change the year band, or examine one method and its missing values. Outline a period–radius plot with log axes and an explicit eligibility filter.
  5. 60–75 · Peer review. Trade a claim and an alternative explanation. Name the detection-efficiency information needed before estimating the underlying population.
Teaching reveal and visual plan

Start with a full catalog bar. Split it into rows with and without a radius value, then change to percentages. Never fill missing radii with zero. The proposed scatterplot is an extension: state excluded nulls, uncertainty, upper/lower-limit flags, and whether a radius was calculated. Counts in a detected catalog do not estimate the frequency of planets in the universe without a selection model.

Systems link: table grain, null-aware aggregation, metadata catalogs, and reproducible snapshots. Composite-table documentation and column definitions are part of the evidence.

Cliffhanger: a name such as TESS appears in our research. How do we connect it to organizations and sources without trusting a name match?

Case 4 · Tuesday December 1 · 30 minutes + 45-minute project rehearsal

Who says so?

Our research assistant produces a fluent sentence about TESS. Can we trace each part of the sentence to an identifiable statement and a source?

Predict: if a graph lists two operators, is that a contradiction? If one statement has no attached reference, is it false?

Data: Wikidata’s TESS entity Q1323537, its operator statements, and attached references. One output row is a statement/reference combination, not a distinct mission. An optional URL may be empty even when another kind of reference is present.

  1. 0–10 · Follow one edge. Query mission → operator by entity ID and draw the returned organizations.
  2. 10–20 · Open the envelope. Reveal statement IDs and reference nodes. Compare one claim with an official mission page; a graph edge is a lead to investigate.
  3. 20–30 · Audit the answer. Write a sourced sentence and an unanswered question. Explain how optional references can multiply rows.
  4. 30–75 · Rehearse the project. Show one supported answer and one retrieval failure. Peers follow the citations and propose a better question.
Teaching reveal and visual plan

Draw mission → operator first. Then inspect statement IDs and reveal attached-reference presence. Follow any source or import URL in the result table. The Wikimedia import URL records where a statement was imported from; it is not an independent scientific source. In the saved example, one reference leads back to a Wikipedia revision. Compare it with the official mission documentation before writing a claim. A missing attached reference does not establish that a relationship is false.

Systems link: RDF triples, SPARQL versus SQL, identity resolution, one-to-many joins, and RAG citation quality. The step from an archive’s facility name to Q1323537 is a manually verified mapping, not an automatic string join. This bounded query avoids a scan of the whole graph; see service limits.

Case 5 · Thursday December 3 · 75-minute project workshop

The discovery hearing

The bureau’s editor has one rule: “Show the query and the uncertainty behind the headline.” Each team brings a discovery from its own project, or uses one of these cases as a practice example.

  1. 0–10 · Seal the evidence. Record the question, SQL/SPARQL, source, timestamp, filters, row unit, and result.
  2. 10–20 · Reproduce it. A partner rebuilds the chart from the CSV. Distinguish a changed live catalog from a changed query.
  3. 20–40 · Challenge it. Test one alternative grouping, denominator, missing-value rule, or retrieval configuration.
  4. 40–60 · Revise the story. Build a three-panel explanation: initial belief → evidence that changed it → defensible conclusion. Keep a visible limitation.
  5. 60–75 · Finish the project. Work on the report and demo with instructor/TA help. The report remains due December 7; presentations remain December 8.

The case file

One question. One reproducible query or retrieval run. One readable chart. One competing explanation. One qualified conclusion. One next test.

This is a workshop format for improving the existing project, not a new graded deliverable.

Keep the source with the story

Taxi records originate with NYC TLC; the hosted table follows ClickHouse’s prepared dataset. NOAA’s GHCN-Daily dataset is accessed through a transformed mirror. Save the query’s population and preparation notes with each export.

Planet data come from the NASA Exoplanet Archive, operated by Caltech under contract with NASA. Follow its acknowledgment and citation guidance and cite specific parameter references when using them. Its TAP documentation describes the query interface.

Wikidata’s structured data are CC0; sources linked by a statement have their own terms. Keep the entity and statement IDs so another reader can audit the claim. These teaching examples are investigations of existing records, not claims of new scientific discoveries.
