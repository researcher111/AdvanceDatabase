The Iterator Model

How can query operators produce results one row at a time without storing every intermediate table?
Daniel G. Graham · UVA School of Data Science

A query can pass rows between stages one at a time instead of storing each stage’s full output. Your TableScan already provides the operations needed to do that: advance to a row, read its fields, and eventually close the scan. Today we use the Volcano iterator model to give filters, projections, and products the same interface. Connecting these operators forms a query plan. The operators in this lab stream their results without materializing intermediate tables.

Companion reading: Sciore, Database Design and Implementation, ch. 8 (query processing)1 · Graefe, Volcano: An Extensible and Parallel Query Evaluation System (the paper the model is named for2).

Today's plan

We begin with Quiz 3 (records and the catalog, 10 min), then build query operators on top of your table scanner.

An implementation that materializes every stage must store each intermediate result before the next stage can use it. Our simple join first enumerates |students| × |majors| pairs, so materializing that product can require far more memory than either input table.

A query plan connects operators through a shared interface. TableScan is the input operator you have already built.

Materializing every intermediate result can exhaust memory

A straightforward staged implementation materializes the scan’s output, then the filter’s output, then the projection. Each intermediate needs memory or temporary storage. Our first join deliberately uses a Cartesian product followed by a filter; production equality joins can avoid enumerating that product.

Materializing large intermediate results can exhaust memory or require a spill to disk.

Streaming operators keep only the state needed for the next row

A streaming operator produces its next result by requesting rows from its inputs. SelectScan and ProjectScan need only the current row; ProductScan keeps a position in each input. Their state grows with the plan, rather than with the number of result rows. The underlying TableScan also holds a pinned block. Sorting and some other operators require more state, so this memory bound does not apply to every query plan3.

Materialize each stagePull one row at a time
Memorygrows with the size of the intermediate results, which can be larger than the tables themselves (a product's output is |left| × |right| rows)small cursor state per streaming operator, plus the blocks held by the input scans
First result arrivesafter the whole stage finishesas soon as the operators find the first matching row
Operators that must collect everything firstA general sort must inspect all input rows before it can identify the smallest. Hash aggregation usually waits for all input before reporting final groups. These operators can require substantial memory or temporary disk storage. Aggregation over input already ordered by its grouping key can instead emit each completed group. Lecture 9 explains these differences2.

Streaming scans, filters, and products do not store the full intermediate result.

Python generators use a similar request-and-resume pattern

Compare a generator with a list comprehension:

def high_gpa(rows):                       # lazy: a SelectScan written in Python
    for row in rows:                      #   pull one row from the input...
        if row["gpa"] > 35:
            yield row                     #   ...hand one row up, then pause right here

first = next(high_gpa(students))          # reads only as far as the first match
                                          # the rest of students is untouched

big = [r for r in students if r["gpa"] > 35]   # eager: every match in memory before
                                               # you can look at the first one

yield returns a row and suspends the function until the next request. Its local variables retain the position needed to continue. A generator can therefore filter another generator one row at a time. A list comprehension instead constructs its full list before returning it.

The same choice appears throughout data processing: stream results when possible, and materialize them when an operation requires it.

A request at the root starts the next round of work

Press pull to call next() on the top operator. That operator requests rows from its input, which may request rows from another operator. Follow the calls downward and the results upward. A filter may consume several input rows before it finds one to return.

Five methods provide a common scan interface

Each operator implements the same five scan methods. This lets operators accept other scans as inputs, provided the input supplies the fields they need. The resulting tree must still implement the query correctly.

Every operator speaks the same five methods

def before_first() # rewind
def next() -> bool # advance; False at the end
def get_val(fld) # read a field of the current row
def has_field(fld) -> bool # do I produce this field?
def close() # release pins, recursively
Hover or tap a line. These five methods define the scan interface used in this course, following the iterator approach2.

Anything with the five methods counts as a scan

Python does not require an operator to declare implements Scan. Instead, the caller uses the methods it expects the input to provide. This is duck typing. A SelectScan can filter a TableScan, a ProductScan, or a small in-memory test scan through the same interface:5

class ListScan:                            # not in microdb: a fake scan over a Python list
    def __init__(self, rows):  self.rows, self.i = rows, -1
    def before_first(self):    self.i = -1
    def next(self):
        self.i += 1
        return self.i < len(self.rows)
    def get_val(self, fld):    return self.rows[self.i][fld]
    def has_field(self, fld):  return fld in self.rows[self.i]
    def close(self):           pass

rows = [{"name": "ada", "gpa": 39}, {"name": "ben", "gpa": 31}]
plan = SelectScan(ListScan(rows), gpa_over_35)   # SelectScan never asks what it was handed
while plan.next():
    print(plan.get_val("name"))                  # ada

The test scan provides rows through the same methods as a table scan, so the filter can be tested without disk access. Python discovers a missing method when the code tries to call it; the lab harness therefore exercises all five interface methods. Your TableScan already supports the interface, and Lab 4 adds three more operators.

One forgotten close() anywhere leaks a pin

Operatorclose() doesWhy it matters
TableScanunpin its current blockeach successful pin must have a matching unpin. TableScan releases the block it currently holds.
Select / Projectclose the wrapped scanThese operators pin nothing themselves. Their only duty is to call close() on the scan they wrap, which passes the release down the tree until it reaches a TableScan.
Productclose both sidesa product has two input scans, so it must close both. Otherwise any table scans in the unclosed input can keep their blocks pinned.

In these plans, each table-scan input holds at most one pinned block at a time. Closing the root must close every input so all pins are released. The lab harness checks the pool after each query.

Select filters rows; Project exposes selected fields

Selection and projection are operations in relational algebra. Here, each class changes one part of its input’s behavior and delegates the remaining methods.

SelectScan skips rejected rows instead of copying keepers

class SelectScan: # WHERE
def next(self):
while self.scan.next():
if self.predicate.is_satisfied(self.scan):
return True
return False
# get_val / has_field / before_first / close: delegate downward
Hover or tap a line. The filter requests input rows until one satisfies its predicate, then returns that row to its caller.

ProjectScan hides columns without copying a single row

The problemTake SELECT name FROM students. The scan underneath produces full rows with three fields (id, name, gpa) and the query wants only name. Building a fresh, one-field row for every input row (copy name out, drop the other two) means 60,000 new little rows for 60,000 students.
ProjectScan's answerKeep the list of allowed field names. Delegate get_val("name") to the input when name is allowed, and raise ValueError for a field excluded by the projection. No new row object is required.
What followsProjection limits which fields callers can access without materializing another table. Attempting to read an excluded field raises an error.
class ProjectScan: # the SELECT list
def get_val(self, fld):
if fld not in self.fields:
raise ValueError(f"field {fld!r} was projected away")
return self.scan.get_val(fld)
# next / before_first / close: delegate downward
Hover a line. Select picks rows; Project picks columns; both are one idea each.

F() turns a filter term into a join condition

A predicateis a WHERE clause turned into a Python value the engine can walk. WHERE gpa > 35 AND mid = 2 becomes a list of two terms, ("gpa", ">", 35) and ("mid", "=", 2): each is a triple of the field to look at, the comparison to apply, and the value to compare against.
Joined by ANDa row passes the predicate only if every term is true for it; the first false term rejects the row.
The F wrapperthe right-hand side of a term is normally a literal such as 35. Wrapping it in F marks it as the name of another field instead, so ("mid", "=", F("mid2")) means "compare this row's mid with its mid2", which is exactly a join condition.
class F: # "this rhs is a field"
def __init__(self, name): self.name = name
def is_satisfied(self, scan):
for field, op, rhs in self.terms:
rhs_val = scan.get_val(rhs.name) if isinstance(rhs, F) else rhs
if not self.OPS[op](scan.get_val(field), rhs_val): return False
return True
Hover a line: this is the provided code, worth reading before you write the operators that consult it.

A false term rejects the row at once and the terms after it are never checked. Our first join uses a nested loop

Our first join combines two operators: ProductScan enumerates every left-right pair, and SelectScan keeps pairs that satisfy the join condition. This is simple to trace but can perform much more work than production join algorithms.

For each left row, scan the right input from start to finish

The following sketch shows how the product advances its two inputs:

def next(self):
if self.right.next(): return True
self.right.before_first()
return self.left.next() and self.right.next()

The product enumerates every pair even if the filter rejects almost all of them. Indexes in Lecture 6 and hash and merge joins in Lecture 9 can avoid much of this work.

That right-side filter therefore emits its one matching row 60 times. The counter measures total output across those repeated scans, not the number of distinct rows in the table.

Equivalent plans can perform different amounts of work

These two plans return the same 20 rows. They differ in when they apply the filters, which changes how many candidate pairs the product enumerates. The rewrite is valid because each moved filter refers only to fields in its own input.

Filtering both inputs before the product reduces candidate pairs 15×

Read each shape from right to left, bottom of the plan to top; σgpastudents is shorthand for a SelectScan on the gpa condition wrapped directly around the students scan, so the product only ever sees the rows that passed:

Filtering the inputs first reduces the product from 900 pairs to 60 while preserving the 20 result rows.

Moving each single-table filter below the product is called predicate pushdown. In this example it reduces candidate pairs by a factor of 15. The planner may make this rewrite because applying those filters earlier preserves the query’s result6.

Recap & next time

Three points to remember:

  • A common interface lets operators compose. Each scan provides the same five methods, and the planner connects compatible scans into a tree.
  • Streaming limits intermediate storage. Scans, filters, projections, and this nested-loop product retain cursor state rather than their full output. Blocking sorts and hash aggregation need more state.
  • Equivalent plans can have different costs. Filtering both inputs before the product reduces candidate pairs from 900 to 60 without changing the result.

FAQ

Is this really how Postgres works?

PostgreSQL’s executor uses a tree of nodes that request results from their inputs through calls such as ExecProcNode. DuckDB uses batches of rows and a push-based execution model. The operators serve related purposes, but their scheduling and data-transfer mechanisms differ1013.

Why does the product re-read its right side instead of caching it?

Caching the entire right input trades memory for less repeated work. The lab’s product avoids that extra storage and restarts the input instead. If its blocks remain in the buffer pool, repeated scans can reuse them from memory; otherwise they require additional reads. Production planners choose among strategies such as rescanning, materializing, and hash joining according to their costs11.

Where are ORDER BY and GROUP BY?

A blocking sort must inspect all its input before emitting sorted output. Hash aggregation also usually waits for all input, while aggregation over input already ordered by the grouping key can emit one completed group at a time. Lecture 9 explains these tradeoffs.

What about OR in predicates?

microdb’s Predicate supports AND conditions. Lab 5 offers OR as an optional parser extension. SelectScan only needs a predicate that returns true or false, so adding OR need not change its iterator interface.
