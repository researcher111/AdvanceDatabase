The Iterator Model

Scan, Select, Project, Product: four small classes, one interface, and suddenly microdb runs queries.
Daniel G. Graham · UVA School of Data Science

Your TableScan answers one question ("next row?"), and that turns out to be the only question a query engine ever needs. Today we meet the Volcano (iterator) model: every operator, from a WHERE filter to a join, implements the same tiny interface and wraps another operator that implements it too. Rows flow up on demand, nothing is copied, no intermediate table is materialized, and a stack of these operators is the query plan you saw in Lecture 1.

Companion reading: Sciore, Database Design and Implementation, ch. 8 (query processing) · Graefe, Volcano: An Extensible and Parallel Query Evaluation System (the paper the model is named for).

Dotted-underlined terms like this one are systems jargon; hover or tap for a plain-language explainer that opens right below the sentence you're reading.

Queries without room to run

Think · Pair · Share · the obvious way fails
  • Think · 2 minThe obvious way to run SELECT name FROM students WHERE gpa > 3.5: read the whole table into a list, filter the list, then trim the columns. Now the table is 100 GB and your RAM is 16 GB. Where exactly does the obvious way die, and what's the smallest change that saves it?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare fixes. Did you both land on some version of "don't hold the rows, hand them over one at a time"?
  • Share · 2 minOne sentence: if each stage only ever holds one row, how much memory does the whole query need?
Show the answer

It dies at the very first step: read the whole table into a list asks for 100 GB of RAM you do not have. Note where it does not die. The filter is fine, the column trim is fine, the answer is small. It is the materialising that kills it, and materialising is not even necessary, because nothing downstream ever looks at more than one row at a time.

The smallest change is to stop building lists and start answering a question: each stage hands up one row when asked and remembers only its cursor. Then the memory a query needs is set by the depth of the plan, not the size of the data. A three-operator plan over a 100 GB table holds about three rows. That is the whole idea of the iterator model, and your TableScan already works this way, with its one pinned block.

The fix: pull, don't build

Instead of each stage building its whole output, each stage answers "give me your next row" by pulling just enough from the stage below. One row in flight per operator; memory use is the plan's depth, not the data's size. Each stage just remembers its cursor. Your TableScan already works this way (one pinned block, remember), so the entire query engine can too.

Materialize each stagePull one row at a time
MemoryO(intermediate results), can exceed the dataO(plan depth), a few rows
First result arrivesafter the whole stage finishesalmost immediately
When it's forced anywaysort and group-by must see everything before emitting; they break the pipeline on purpose (week 9)

One interface to rule them

Think · Pair · Share · design the interface
  • Think · 2 minYou need WHERE-filtering, column-trimming, and joining to all be stackable in any order, over any table. Write the minimal set of methods every stage must offer so any stage can sit on any other. (Hint: TableScan already has almost all of them.)
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare interfaces. Did you remember rewind (the product needs it) and close (the pins need it)?
  • Share · 2 minCheck against the contract below; every difference is a capability you gained or lost.
Show the answer

Five methods, and TableScan already has four of them. before_first() to rewind, next() to advance and report whether a row exists, get_val(field) to read a field of the current row, has_field(field) so a stage can be asked what it produces, and close() to release what it holds.

The two that get forgotten are the ones the Pair step names. before_first is what makes a join possible at all, because the nested loop must rewind its right input once per left row. close is what makes a plan safe, because every TableScan at the bottom is holding a pin, and a plan that forgets to close leaks a frame out of the pool. Miss either one and you have lost a capability rather than saved a method, which is why Thursday's harness audits the pool after the join has finished.

The Scan contract

def before_first() # rewind
def next() -> bool # advance; False at the end
def get_val(fld) # read a field of the current row
def has_field(fld) -> bool # do I produce this field?
def close() # release pins, recursively
Hover a line: five methods, and every operator in every real engine speaks a dialect of them.

Python needs no formal interface declaration; duck typing means anything with these five methods is a scan. TableScan qualifies already; Thursday you write three more.

Close is a chain of unpins

Operatorclose() doesWhy it matters
TableScanunpin its current blockthe week-2 contract, honored at the bottom
Select / Projectclose the wrapped scanpass the duty down
Productclose both sidestwo tables → two pinned blocks → two releases

A plan holds one pinned block per table in the query, not per table in the database, and one forgotten close() anywhere in the tree leaks a pin. Thursday's harness checks the pool after every query.

Select & Project

The two easy operators first: together they're barely twenty lines, and they're the exact lines you'll write Thursday. Readability is the point: each class states its one idea.

SelectScan: keep the rows that pass

class SelectScan: # WHERE
def next(self):
while self.scan.next():
if self.predicate.is_satisfied(self.scan):
return True
return False
# get_val / has_field / before_first / close: delegate downward
Hover a line. The filter is five lines; the philosophy (skip, don't copy) is the whole model.

ProjectScan: a fence, not a copy

class ProjectScan: # the SELECT list
def get_val(self, fld):
if fld not in self.fields:
raise ValueError(f"field {fld!r} was projected away")
return self.scan.get_val(fld)
# next / before_first / close: delegate downward
Hover a line. Select picks rows; Project picks columns; both are one idea each.

Predicates, and the little class that enables joins

class F: # "this rhs is a field"
def __init__(self, name): self.name = name
def is_satisfied(self, scan):
for field, op, rhs in self.terms:
rhs_val = scan.get_val(rhs.name) if isinstance(rhs, F) else rhs
if not self.OPS[op](scan.get_val(field), rhs_val): return False
return True
Hover a line: this is the provided code, worth reading before you write the operators that consult it.

Product: the join's engine

Think · Pair · Share · pair everything with everything
  • Think · 2 minYou must produce every (student, major) pair (6 × 3 = 18 of them) through the one-row-at-a-time interface, using only next() and before_first() on the two inputs. Sketch the loop. Which input gets rewound, and how many times?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare loops. What must before_first() do to the LEFT side so that the very first next() finds a pair? (Subtle: most bugs Thursday live here.)
  • Share · 2 minHow many rows does the right side deliver in total? That number returns in the measurement.
Show the answer

The right side gets rewound, once per left row, so six times for the six students. The loop is three lines: if the right side can advance, you have a pair; if it cannot, rewind the right and advance the left; if the left is also exhausted, the product is done. It is a car odometer, with the right-hand digit spinning fastest.

The subtlety in the Pair step: before_first() must leave the left side already on its first row (rewind, then one next()) while leaving the right side before its first. Park both before their first rows and the opening next() pairs nothing, and you get 0 or 15 pairs instead of 18. And the Share number: the right side delivers 3 rows per left row, 18 in total, even though the table only holds 3. Remember that multiplier; Thursday it reappears as a filter that keeps 1 row and still reads 60.

The nested loop, traced

Three lines of logic: right side spins fastest, like a car's odometer:

def next(self):
if self.right.next(): return True
self.right.before_first()
return self.left.next() and self.right.next()

A join is a product wearing a filter

plan = ProjectScan(
SelectScan(
ProductScan(students, majors),
Predicate(("mid", "=", F("mid2")), ("gpa", ">", 35))),
["name", "dept"])
# (ada, cs) (cyd, cs) (eli, stat)
Hover a line: cartesian product plus predicate equals join. Everything else is performance.

The cost, honestly

rows the product builds  =  |left| × |right|

  6 students × 3 majors        =        18   (cute)
  300 × 300                    =    90,000   (hmm)
  10⁶ × 10⁶                    =     10¹²   (a laptop-year, the join problem, stated)

The nested loop is correct at any size and affordable only when its inputs are small. Making joins affordable is week 6 (indexes) and week 9 (hash and merge joins); both are ways to avoid building pairs you'll throw away.

The nested loop re-runs its right input for every left row. Thursday's measurement puts a counter on a right-side filter that keeps 1 row, and reads 60. Remember this table when the number surprises you anyway.

Show answer

Left: 6. Right: 6 × 3 = 18 (rewound per left row). Pairs built: 18. Pairs passed: 6. With a never-true predicate: only the last number changes: 6, 18, 18, 0. The product's work is fixed by the input sizes, not by the answer; that indifference is exactly what pushdown attacks, and what the optimizer will learn to predict in week 9.

Same query, different shapes

Think · Pair · Share · move the filter
  • Think · 2 minQuery: names of cs students with gpa > 35, over 300 students × 3 majors. Plan A filters after the product; Plan B filters each input before the product. Predict the number of pairs each plan builds.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCheck each other's arithmetic: A = 300×3. B = (survivors of gpa > 35) × (majors named cs). The answers differ by how much?
  • Share · 2 minBoth plans came from the same SQL. Who should choose between them, and what would the chooser need to know in advance?
Show the answer

Plan A builds 900 pairs (300 × 3) and then throws nearly all of them away. Plan B builds 60: the gpa filter leaves 60 of the 300 students, the dept filter leaves the 1 cs major, and 60 × 1 = 60. Same 20 rows out, 15× less work, purely from where the filters sit.

Who chooses? Not you: SQL names the rows, not the steps, so both plans are legal readings of the same query and relational algebra guarantees they return the same answer. That guarantee is exactly what licenses a machine to pick. The chooser needs one thing you have not built yet, an estimate of how many rows survive each filter before running it, which means statistics about the data. That is the optimizer, and it is week 9.

Measured: 15× from moving one filter

Thursday's measurement, run on the reference solution: same query, same 20 result rows:

A: filter lateProject ← Select(join ∧ gpa ∧ dept) ← Product90020

Fifteen-fold less work from sliding filters below the product; this move is called predicate pushdown, and it's the first rewrite every optimizer learns. Same answer is guaranteed by relational algebra; that guarantee is why the machine is allowed to choose.

Who chooses? (Week 9 knocks)

Not the userSQL is declarative: the whole deal (Lecture 3) was that you name the rows, not the steps.
The planner, naivelyThursday-you picks the shape by hand when building plans. Week 5's planner will pick a correct shape mechanically.
The optimizer, eventuallyWeek 9's optimizer picks a fast shape, using statistics to predict survivor counts before running anything. The 15× above is the smallest of its wins.
The lesson to keepplan shape is a degree of freedom the answer doesn't depend on. Everything an optimizer does lives in that freedom.

Pushdown in the wild

Postgrespushes predicates below joins automatically, and into index conditions when week 6's structures exist.
Parquet / DuckDBpushes filters into the file format: column chunks carry min/max stats, so whole blocks are skipped unread (week 10 measures it).
Sparkpushes filters across the network, to the node holding the data, before the shuffle (week 13's whole story).
One idea, five weeksdo the cheap discarding as close to the data as possible. You just measured it for the first time; you will not stop meeting it.

Recap & next time

Three ideas from today that the whole rest of the engine reuses.

  • One interface, infinite plans. Five methods make operators Lego: any scan wraps any scan, and a query plan is just the resulting tower.
  • Pull, don't build. Demand flows down, single rows flow up; memory is the plan's depth. Sort and group-by will be the deliberate exceptions.
  • Shape is free, work isn't. Product + select = join; filter placement changed work 15× with the answer guaranteed identical; the degree of freedom optimizers live in.

FAQ

Is this really how Postgres works?

Yes: the executor is a tree of nodes each implementing (roughly) ExecProcNode, pulled from the top exactly like today's widget. Modern analytics engines (DuckDB, week 10) pull batches of ~1000 rows instead of single rows to be kinder to CPUs; same model, bigger sips.

Why does the product re-read its right side instead of caching it?

Caching is memory, the thing we swore off. Re-reading costs I/O instead… except your week-2 buffer pool usually still has those blocks, which is the two layers quietly cooperating. When the right side is huge, real engines do materialize or hash it; that's week 9's hash join, a considered trade, not a default.

Where are ORDER BY and GROUP BY?

They need to see all rows before emitting one (you can't know the smallest row until you've seen the last). They're the operators that legitimately break the pipeline and spill to disk: week 9, alongside the optimizer.

What about OR in predicates?

microdb's Predicate is AND-only for readability; OR arrives with the parser next week if you want it (Going Further). The iterator machinery doesn't care; predicates are just a boolean box the SelectScan consults.
