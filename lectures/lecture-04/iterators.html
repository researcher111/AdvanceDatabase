The Iterator Model

Running a query stage by stage builds tables that do not fit in memory; four small classes and one interface run it without building any.
Daniel G. Graham · UVA School of Data Science

Run SELECT name FROM students WHERE gpa > 3.5 the obvious way, one stage at a time, and the filter needs a full copy of the students table before it can start; join two tables that way and the copy is the product of both, which no laptop holds. Your TableScan answers one question ("next row?"), and that turns out to be the only question a query engine ever needs. Today we meet the Volcano (iterator) model: every operator, from a WHERE filter to a join, implements the same tiny interface and wraps another operator that implements it too. Rows flow up on demand, nothing is copied, no intermediate table is materialized, and a stack of these operators is the query plan you saw in Lecture 1.

Companion reading: Sciore, Database Design and Implementation, ch. 8 (query processing)1 · Graefe, Volcano: An Extensible and Parallel Query Evaluation System (the paper the model is named for2).

Run a query one stage at a time and every stage's output has to be stored somewhere before the next stage can start. For a join that output is |students| × |majors| rows, and on real tables it does not fit in memory.

Today's claim: a query plan is just objects wrapping objects, and you already built the bottom one.

Build every stage in full and memory runs out

First, the problem. The obvious way to run SELECT name FROM students WHERE gpa > 3.5 is in stages: the scan produces a table of every student, the filter reads that table and produces a smaller one, and the projection reads that and produces the answer. Every intermediate table has to live somewhere while the next stage reads it, and for a join the first intermediate table is the product of the two inputs, which can be far larger than the tables themselves.

An engine that builds each stage's whole output before starting the next runs out of memory on exactly the queries that matter.

Pull rows on demand and memory is the plan's depth

Instead of each stage building its whole output, each stage answers "give me your next row" by pulling just enough from the stage below3. Each operator holds one row at a time, so the memory a plan needs grows with the number of operators stacked in it (its depth), not with the number of rows in the tables (the data's size). Between calls, each stage remembers only its cursor, its position in the rows it is reading. Your TableScan already works this way (one pinned block, remember), so the entire query engine can too.

Materialize each stagePull one row at a time
Memorygrows with the size of the intermediate results, which can be larger than the tables themselves (a product's output is |left| × |right| rows)grows with the number of operators in the plan: one row per operator, a few rows in total
First result arrivesafter the whole stage finishesalmost immediately
Operators that must collect everything firstORDER BY cannot hand out its first row, the smallest, until it has seen every input row, because the smallest one might arrive last. GROUP BY cannot report a group's total until it knows no more rows for that group are coming. So each of them reads its entire input into memory before producing anything: a deliberate break in the one-row-at-a-time flow, and week 9 shows what that break costs the optimizer2

1 row per operator is all a pull plan holds in memory: it grows with the plan's depth, not the data's size

A Python generator is already a scan

Deep learninga DataLoader streaming batches4the dataset as one tensor

The Python row is worth seeing as code, because a generator is a scan:

def high_gpa(rows):                       # lazy: a SelectScan written in Python
    for row in rows:                      #   pull one row from the input...
        if row["gpa"] > 35:
            yield row                     #   ...hand one row up, then pause right here

first = next(high_gpa(students))          # reads only as far as the first match
                                          # the rest of students is untouched

big = [r for r in students if r["gpa"] > 35]   # eager: every match in memory before
                                               # you can look at the first one

yield hands one row to the caller and freezes the function, local variables and all, until the caller asks for another. The frozen locals are the operator's state, the same job the cursor does inside a scan, and each next() is one turn of the crank. Wrap a generator around a generator and you have a plan: rows flow up one at a time and nothing in the middle is ever stored. The list comprehension is the intermediate table from the previous slide, built in full before the first row is visible.

The iterator model is the database instance of a pattern data science already lives by: stream when you can, materialize when you must.

Nothing moves until the caller asks for a row

The Lecture 1 demo showed rows moving up through a plan. This one shows what makes them move: nothing happens until the caller asks for a row. Each press of pull is that ask. It calls next() on the top operator, which asks the operator below it for a row, which asks the one below that, all the way down to the scan. Only then does one row come back up. Follow the request down and the row back up, and notice that no operator does any work until it is asked.

Five methods let any operator wrap any operator

Every operator, from last week's TableScan to the join, has the same five methods, so any of them can wrap any other and a query plan is whatever tower you stack.

Every operator speaks the same five methods

def before_first() # rewind
def next() -> bool # advance; False at the end
def get_val(fld) # read a field of the current row
def has_field(fld) -> bool # do I produce this field?
def close() # release pins, recursively
Hover a line: five methods, and every operator in every real engine speaks a dialect of them2.

Anything with the five methods counts as a scan

In Java you would have to write class SelectScan implements Scan and the compiler would check the five methods. Python has no such step5. An object counts as a scan for one reason only: it has these five methods. That is duck typing, and it matters here because every operator takes "a scan" as input and never checks what class it was given. A SelectScan only ever calls next() and get_val() on its input, so its input can be a TableScan, another SelectScan, a ProductScan, or something you made up five minutes ago:

class ListScan:                            # not in microdb: a fake scan over a Python list
    def __init__(self, rows):  self.rows, self.i = rows, -1
    def before_first(self):    self.i = -1
    def next(self):
        self.i += 1
        return self.i < len(self.rows)
    def get_val(self, fld):    return self.rows[self.i][fld]
    def has_field(self, fld):  return fld in self.rows[self.i]
    def close(self):           pass

rows = [{"name": "ada", "gpa": 39}, {"name": "ben", "gpa": 31}]
plan = SelectScan(ListScan(rows), gpa_over_35)   # SelectScan never asks what it was handed
while plan.next():
    print(plan.get_val("name"))                  # ada

SelectScan filters the fake exactly as it filters a real table, because the fake walks and quacks like one. That is what lets operators nest in any order, and what lets a test feed an operator hand-made rows with no disk involved. The price is that nothing checks the methods up front: hand an operator an object missing close() and you learn about it when close() is called, which is why the lab harness exercises all five. TableScan already qualifies; Thursday you write three more.

One forgotten close() anywhere leaks a pin

Operatorclose() doesWhy it matters
TableScanunpin its current blockLab 2's rule was that every pin(block) must be matched by an unpin. TableScan is the only operator that pins anything, so it is the place where that rule is finally kept.
Select / Projectclose the wrapped scanThese operators pin nothing themselves. Their only duty is to call close() on the scan they wrap, which passes the release down the tree until it reaches a TableScan.
Productclose both sidesA product wraps two scans, and each holds one pinned block, so its close() must call close() on both sides. Close only one and the other side's block stays pinned forever.

A plan holds one pinned block per table in the query, not per table in the database, and one forgotten close() anywhere in the tree leaks a pin. Thursday's harness checks the pool after every query.

Select skips rows, Project refuses columns, twenty lines total

The two easy operators first: together they're barely twenty lines, and they're the exact lines you'll write Thursday. Readability is the point: each class states its one idea.

SelectScan skips rejected rows instead of copying keepers

class SelectScan: # WHERE
def next(self):
while self.scan.next():
if self.predicate.is_satisfied(self.scan):
return True
return False
# get_val / has_field / before_first / close: delegate downward
Hover a line. The filter is five lines. Its one idea, skip a rejected row instead of copying accepted rows into a new table, is the idea the whole iterator model rests on.

ProjectScan hides columns without copying a single row

Take SELECT name FROM students. The scan underneath produces full rows with three fields: id, name, gpa. The query wants only name. One way to deliver that is to build a fresh, one-field row for every input row: copy name out, drop the other two. For 60,000 students that is 60,000 new little rows.

ProjectScan builds nothing. Every row stays where it is, inside the scan underneath, with all three fields still in it. ProjectScan sits on top holding one thing: the list of allowed columns, here ["name"]. When the caller asks get_val("name"), ProjectScan passes the question down and hands the answer back. When the caller asks get_val("gpa"), ProjectScan raises ValueError, because gpa is not on the list. That is the whole operator: a list of column names and a check.

Two things follow. Nothing is copied, so the projection costs no memory and no work per row. And a caller who reaches for a column the query said it did not want finds out at once, instead of silently reading a value that was supposed to be invisible.

class ProjectScan: # the SELECT list
def get_val(self, fld):
if fld not in self.fields:
raise ValueError(f"field {fld!r} was projected away")
return self.scan.get_val(fld)
# next / before_first / close: delegate downward
Hover a line. Select picks rows; Project picks columns; both are one idea each.

F() turns a filter term into a join condition

A predicate is a WHERE clause turned into a Python value the engine can walk. Take WHERE gpa > 35 AND mid = 2. As data it is a list of two terms: ("gpa", ">", 35) and ("mid", "=", 2), each a triple of the field to look at, the comparison to apply, and the value to compare against. The terms are joined by AND, so a row passes the predicate only if every term is true for it; the first false term rejects the row. The right-hand side is normally a literal such as 35. Wrapping it in F marks it as the name of another field instead, so ("mid", "=", F("mid2")) means "compare this row's mid with its mid2", which is exactly a join condition.

class F: # "this rhs is a field"
def __init__(self, name): self.name = name
def is_satisfied(self, scan):
for field, op, rhs in self.terms:
rhs_val = scan.get_val(rhs.name) if isinstance(rhs, F) else rhs
if not self.OPS[op](scan.get_val(field), rhs_val): return False
return True
Hover a line: this is the provided code, worth reading before you write the operators that consult it.

One false term rejects the row and stops the check

is_satisfied, one term at a time · pick a predicate, then step through the rows

Each press of check next term evaluates one triple against the current row: fetch the field, resolve the right-hand side (a literal is itself; an F is looked up in the same row), compare. A false term rejects the row at once and the terms after it are never checked. The third predicate runs over the rows a ProductScan(students, majors) would hand up, so mid and mid2 sit side by side in one row.

Two things to notice. In the join predicate the right-hand side comes from the same row as the left, because the product already glued mid and mid2 together; that is all a join condition is. And when the first term is false the second is never evaluated, so putting the cheap or selective term first is a real optimization, one week 9 will make the planner's job.

Every join runs on a three-line nested loop

microdb has no join operator. ProductScan pairs every left row with every right row, a SelectScan on top keeps the pairs whose ids agree, and the product's next() is three lines.

The product is an odometer: the right side spins fastest

Three lines of logic: right side spins fastest, like a car's odometer:

def next(self):
if self.right.next(): return True
self.right.before_first()
return self.left.next() and self.right.next()

The nested loop is correct at any size and affordable only when its inputs are small. Making joins affordable is week 6 (indexes) and week 9 (hash and merge joins); both are ways to avoid building pairs you'll throw away.

The nested loop re-runs its right input for every left row. In Thursday's measurement you put a counter on a filter that sits on the right side of a product. That filter keeps only 1 row (one major has the right dept), yet the counter reports 60 rows going through it, because the product rewinds and re-runs the filter once for each of the 60 left rows that survive their own filter. Plan shape changes the work, never the answer

Two plans for the same query return the same 20 rows; one of them builds fifteen times as many pairs to do it. Relational algebra guarantees the answer, so the shape is free to change.

Moving one filter below the product cut the work 15×

Thursday's measurement, run on the reference solution: same query, same 20 result rows. Read each shape from right to left, bottom of the plan to top; σgpastudents is shorthand for a SelectScan on the gpa condition wrapped directly around the students scan, so the product only ever sees the rows that passed:

PlanShapePairs builtRows out
A: filter lateProject ← Select(join ∧ gpa ∧ dept) ← Product90020
B: filter earlyProject ← Select(join) ← Product(σgpastudents × σdeptmajors)6020

15× less work from moving one filter below the product: 900 pairs became 60, same 20 rows out

Fifteen-fold less work from sliding filters below the product; this move is called predicate pushdown, and it's the first rewrite every optimizer learns6. Relational algebra guarantees that both shapes return the same rows, and that guarantee is what lets the database, rather than the user, choose the shape.

The database, not the user, chooses the shape

Not the userSQL is declarative: as Lecture 3 put it, you name the rows you want, not the steps to find them, so the user never sees a plan shape.
The planner, naivelyOn Thursday you pick the shape by hand when you build plans. Week 5's planner will pick a correct shape mechanically.
The optimizer, eventuallyWeek 9's optimizer picks a fast shape, using statistics to predict survivor counts before running anything. The 15× above is the smallest of its wins.
The lesson to keepthe answer does not depend on the plan's shape, so the shape is free to change. Every choice an optimizer makes is a choice of shape.

Recap & next time

Three ideas from today that the whole rest of the engine reuses.

  • One interface, infinite plans. Five methods make operators Lego: any scan wraps any scan, and a query plan is just the resulting tower.
  • Pull, don't build. Demand flows down, single rows flow up; memory is the plan's depth. Sort and group-by will be the deliberate exceptions.
  • Shape is free, work isn't. Product + select = join. Moving one filter changed the work 15× while the answer stayed identical, and choosing among such shapes is the optimizer's entire job.

FAQ

Is this really how Postgres works?

Yes: the executor is a tree of nodes each implementing (roughly) ExecProcNode, pulled from the top exactly like today's widget10. Modern analytics engines (DuckDB, week 10) move batches of 2048 rows instead of single rows to be kinder to CPUs, and push them up the tree rather than pulling; same operators, bigger sips, opposite direction13.

Why does the product re-read its right side instead of caching it?

Caching the right side means holding all of it in memory, which is exactly what the pull model set out to avoid11. Re-reading it costs I/O instead, but in practice your week-2 buffer pool usually still holds those blocks, so the re-read is served from memory anyway; the two layers cooperate without either knowing about the other. When the right side is huge, real engines do materialize or hash it; that's week 9's hash join, a considered trade, not a default11.

Where are ORDER BY and GROUP BY?

They need to see all rows before emitting one (you can't know the smallest row until you've seen the last). They're the operators that legitimately break the pipeline and spill to disk12: week 9, alongside the optimizer.

What about OR in predicates?

microdb's Predicate is AND-only for readability; OR arrives with the parser next week if you want it (Going Further). The iterator machinery doesn't care; predicates are just a boolean box the SelectScan consults.
