From SQL Text to Plan

How do a lexer, parser, and planner turn SQL text into executable operators?
Daniel G. Graham · UVA School of Data Science

The engine can store records and run operator trees, but it still needs a way to turn SQL text into those operations. Today we build the front end. The lexer produces tokens, the parser records what the statement requests, and the planner constructs a Lab 4 scan tree. In Lab 5, you will connect these stages so microdb can execute SELECT name FROM students WHERE gpa > 35 typed at a prompt.

To execute SELECT name FROM students WHERE gpa > 35, the engine must recognize the statement’s words and punctuation, check their order, and choose the operators needed to produce the result.

The parser follows grammar rules using four token-stream helpers: peek, next, match, and expect.

Separate token recognition from statement structure

In SELECT name FROM students WHERE nick = 'from', one occurrence of from is a keyword and the other is part of a quoted string. A search for that word alone cannot distinguish them. The lexer reads the quoted value as one STR token and the keyword as a KEYWORD token. The parser then works with those tokens, without having to process quote characters itself.

A costly regular expression caused a Cloudflare outage

Case study · Cloudflare’s 2019 regex outage

On July 2, 2019, a Cloudflare firewall rule containing a regular expression caused extreme CPU use and an outage lasting about 27 minutes. The expression triggered catastrophic backtracking. This is a performance risk of some patterns in backtracking regex engines, not a limitation of every regex implementation. The example shows why text-processing code needs an understood worst-case cost. Our lexer and parser also separate token recognition from statement structure3.

Five token kinds cover all of microSQL

"SELECT name FROM students WHERE gpa > 35"

   ↓ lexer (one regex per token KIND, applied left to right)

(KEYWORD select) (ID name) (KEYWORD from) (ID students)
(KEYWORD where)  (ID gpa)  (PUNCT >)      (NUM 35)

Five token kinds cover all of microSQL: KEYWORD · ID · NUM · STR · PUNCT. Keywords are ordinary words that happen to be on the lexer's fixed list of reserved words; any word on that list is labeled KEYWORD wherever it appears, which is why microdb rejects select as a table name; PostgreSQL permits it as a quoted identifier4.

Reserved words simplify microdb’s naming rules

The rulethe lexer labels any word in its keyword set as KEYWORD the moment it reads the word, before the parser has seen what comes before or after it, so select can never reach the parser as a table name.
microdb’s choiceThe parser can treat KEYWORD and ID as separate token kinds throughout the small microSQL grammar.
PostgreSQL’s choicePostgreSQL permits quoted identifiers and distinguishes reserved from non-reserved keywords. Its parser applies the naming rules for each grammatical context.4
The lessonMore flexible naming requires additional lexical or grammatical rules. microdb uses a small reserved-word set to keep the lab focused.

The lexer removes character-level concerns such as whitespace and quotes. The parser records the query’s structure. The planner then uses that structured description to build executable operators.

A small grammar defines microSQL’s supported statements

query   :=  SELECT fieldlist FROM tablelist [ WHERE predicate ]
fieldlist := * | field { , field }
tablelist := table { , table }
predicate := term { AND term }
term    :=  field ( = | < | > ) value
value   :=  number | 'string' | field          ← field here means: a join!
insert  :=  INSERT INTO table VALUES ( value { , value } )

The notation is extended BNF (EBNF). Braces { } mean repetition and square brackets [ ] mean an optional part. In this parser, each grammar rule corresponds to a method that consumes that part of the token stream5.

One grammar rule becomes one Python method

Recursive descent assigns a method to each grammar rule. Each method inspects or consumes tokens through four helpers. Read the provided INSERT parser below, then use the same patterns to implement SELECT in Lab 5.

4 verbs peek, next, match, expect: every parsing method you write is built from only these

peek() · next() · match(kind, val) · expect(kind, val)
def parse_insert(self):
self.lex.expect("KEYWORD", "insert")
self.lex.expect("KEYWORD", "into")
table = self.lex.expect("ID")
self.lex.expect("KEYWORD", "values")
self.lex.expect("PUNCT", "(")
values = [self._parse_literal()]
while self.lex.match("PUNCT", ","):
self.lex.next(); values.append(self._parse_literal())
self.lex.expect("PUNCT", ")")
return InsertData(table, values)

The parser returns a structured description rather than executable scans. This keeps planning separate from parsing. An optimizer can later use the same QueryData to choose another equivalent plan. Lecture 9 explains that possibility; implementing the optimizer is optional.

The lab planner constructs a plan in four steps

1 · scansa TableScan per table in the FROM list; layouts fetched from your Lab 3 catalog.
2 · productscombine them into ProductScans left to right: the first two TableScans become one ProductScan, that product is paired with the third table's scan, and so on: ((t1 × t2) × t3). With a single table there is no product at all.
3 · selectone SelectScan with the whole WHERE predicate, if there is one.
4 · projectone ProjectScan with the field list, unless it was *. For SELECT * FROM t, the plan is just a TableScan.

Recap & next time

Three points to remember:

  • Lexing and parsing have separate responsibilities. The lexer recognizes tokens; the parser checks how they form a statement.
  • Recursive descent follows the grammar. Each parsing method uses the four token-stream helpers, and expect() reports a mismatch consistently.
  • The parser produces data; the planner produces operators. Keeping these stages separate allows different plans to be built from the same query description.

Four helpers support token processing. Filtering inputs reduces the example join from 900 candidate pairs to 60.

FAQ

Is real SQL parsed this way?

SQL engines use several parser designs. SQLite uses a handwritten lexer and a Lemon-generated parser. PostgreSQL uses Bison to generate its parser from a grammar. DuckDB used a PostgreSQL-derived parser through v1.x and introduced a PEG parser in v2.0. Handwritten recursive descent, used in languages such as Lua and Go, makes the relationship between grammar rules and code easy to inspect89101112.

Why does microSQL forbid naming a column select?

microdb labels an unquoted word in its keyword set as KEYWORD before parsing. It therefore cannot use that token where an ID is required. PostgreSQL supports quoted identifiers and distinguishes reserved from non-reserved keywords, which requires more detailed naming and grammar rules15.

What about SQL injection? Is that a parsing thing?

SQL injection can occur when untrusted input is concatenated into SQL text and interpreted as part of the statement. Parameterized queries keep bound values separate from SQL syntax, so a value cannot introduce a new clause or statement. Parameter binding would be a useful optional extension to microdb; it is not part of the required parser13.

Could the planner cache plans for repeated queries?

Yes. Prepared statements and other plan caches can reuse parsing or planning work. microdb plans each query again to keep the implementation simple. A production cache must also handle changes to schemas, statistics, and other assumptions on which a plan depends14.
