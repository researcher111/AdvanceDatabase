Today's claim: parsing is just disciplined reading, and the discipline fits in four helper methods.

Two simple machines beat one clever regex

Here is the problem a regex cannot solve cleanly. In SELECT name FROM students WHERE nick = 'from', the word from appears twice: once as the keyword and once inside a string literal. A regex that searches the raw text for from finds both and cannot tell them apart. The lexer settles this once: when it sees an opening quote it reads to the closing quote and emits a single STR token, so the 'from' inside the quotes is a string token forever after and can never be mistaken for a keyword. The parser then reads tokens, never characters, so it never has to think about quotes at all. Two simple machines beat one clever regex.

One regex stopped much of the internet for 27 minutes

War story · the regex that stopped the internet, 2019

On July 2, 2019, Cloudflare (which fronts a large slice of the web) deployed one new firewall rule containing a regex that could backtrack3 catastrophically. On real traffic it pinned every CPU in every datacenter to 100%, and for about 27 minutes a good fraction of the internet returned errors3. Their postmortem is admirably blunt: a regex was being asked to do structural work, recognizing nested and repeating patterns, and a regex engine cannot promise an upper limit on how long that takes. That is today's lesson at planetary scale: when text has structure, you want a lexer and a parser whose worst case you can state, not one clever pattern whose worst case you discover in production.

Five token kinds cover all of microSQL

"SELECT name FROM students WHERE gpa > 35"

   ↓ lexer (one regex per token KIND, applied left to right)

(KEYWORD select) (ID name) (KEYWORD from) (ID students)
(KEYWORD where)  (ID gpa)  (PUNCT >)      (NUM 35)

Five token kinds cover all of microSQL: KEYWORD · ID · NUM · STR · PUNCT. Keywords are ordinary words that happen to be on the lexer's fixed list of reserved words; any word on that list is labeled KEYWORD wherever it appears, which is why you can't name a table select, in microdb or in Postgres4.

Every naming freedom is paid for in parser lines

The rulethe lexer labels any word in its keyword set as KEYWORD the moment it reads the word, before the parser has seen what comes before or after it, so select can never reach the parser as a table name.
What we boughta lexer that is one regular expression, and a parser that can trust every token's kind and never has to reconsider whether a KEYWORD might really be a name.
What Postgres boughtflexible naming: many keywords can also be used as table or column names. The price is a system of reserved and non-reserved keyword tiers and thousands of grammar lines that decide which reading applies4.
The lessonevery naming freedom a language grants its users is paid for with extra parser complexity, and that cost is paid for the life of the language.

Seven lines of grammar are the whole language

query   :=  SELECT fieldlist FROM tablelist [ WHERE predicate ]
fieldlist := * | field { , field }
tablelist := table { , table }
predicate := term { AND term }
term    :=  field ( = | < | > ) value
value   :=  number | 'string' | field          ← field here means: a join!
insert  :=  INSERT INTO table VALUES ( value { , value } )

This notation is BNF, and reading it is a superpower: every database, config format, and language you'll ever use5 publishes one of these. { } means repeat, [ ] means optional, and each line becomes one Python method.

One grammar rule becomes one Python method

The parsing technique is almost embarrassingly direct: one method per grammar rule, and four helper verbs on the token stream. Here is the provided INSERT parser; Thursday you write SELECT by imitation:

4 verbs peek, next, match, expect: every parsing method you write is built from only these

peek() · next() · match(kind, val) · expect(kind, val)
def parse_insert(self):
self.lex.expect("KEYWORD", "insert")
self.lex.expect("KEYWORD", "into")
table = self.lex.expect("ID")
self.lex.expect("KEYWORD", "values")
self.lex.expect("PUNCT", "(")
values = [self._parse_literal()]
while self.lex.match("PUNCT", ","):
self.lex.next(); values.append(self._parse_literal())
self.lex.expect("PUNCT", ")")
return InsertData(table, values)

Keeping the description as plain data, an AST in compiler speak, is what lets the planner be a separate, swappable stage. Week 9's optimizer will read the same QueryData and build a better plan; the parser won't change by one line.

Four planner steps, always correct, never clever

1 · scansa TableScan per table in the FROM list; layouts fetched from your Lab 3 catalog.
2 · productscombine them into ProductScans left to right: the first two TableScans become one ProductScan, that product is paired with the third table's scan, and so on: ((t1 × t2) × t3). With a single table there is no product at all.
3 · selectone SelectScan with the whole WHERE predicate, if there is one.
4 · projectone ProjectScan with the field list, unless it was *. No useless wrappers: SELECT * FROM t plans as a bare TableScan.

Correct today, fast in week 9, same QueryData

Thursday's measurement prints your planner's own plan for the join query and counts its work, next to Lab 4's hand-optimized shape:

your planner:      SelectScan[everything] ← Product        900 pairs examined
Lab 4, by hand:    Select[join] ← Product(σ(s) × σ(m))      60 pairs examined

900 vs 60 pairs examined: your naive plan against Lab 4's hand-built one, for the same join query

The two plans differ in where the filter runs. Your planner builds the full product of the two tables and filters afterward, so every pair of rows is formed and examined. Lab 4's hand-built plan filters each table first, so far fewer pairs are ever formed. Correct first, fast later, and "later" has a date: week 9's optimizer reads the same QueryData and does that pushdown mechanically, using statistics your catalog will learn to keep. The parser you write this week never changes again.

Recap & next time

Three ideas from today, each bigger than SQL.

  • Lex, then parse. Spelling and grammar are different jobs; splitting them is what makes each one simple. (Regex was doing both, badly.)

FAQ

Is real SQL parsed this way?

SQLite hand-writes its parser's lexer and uses a generated parser8 (Lemon); Postgres uses a grammar file compiled by Bison9, generated cousins of what you're writing. DuckDB forked Postgres's10. Recursive descent by hand is how Lua, Go, and most11 teaching compilers do it, because it's the readable one12.

Why does microSQL forbid naming a column select?

The lexer promotes any word in the keyword set, context-free. Real SQL maintains lists of "reserved" vs "non-reserved" keywords and contextual rules, a famous source of parser complexity. We bought a one-line lexer with a small naming rule; Postgres bought flexible naming with about twenty thousand lines of grammar15.

What about SQL injection? Is that a parsing thing?

It's a string-building thing: gluing untrusted text into SQL before the parser sees it. The parser can't tell your intent from the attacker's; both arrive as valid tokens. The fix (parameterized queries) hands values around the parser13 entirely. Week 15's security lecture returns to this with your new eyes.

Could the planner cache plans for repeated queries?

Yes: real engines hash the text and reuse plans (prepared14 statements make it explicit). microdb re-plans every time, which costs microseconds at our scale and keeps the code readable. The interesting caching questions arrive when plans depend on statistics that drift, week 9 territory.
