Text is not a program

Think · Pair · Share · the regex trap
  • Think · 2 minYou need to extract the table name and the WHERE condition from SQL text. A classmate proposes one big regex: SELECT (.+) FROM (.+) WHERE (.+). Find three legal queries that break it; then decide whether more regex can ever fix it. (Consider: commas, missing WHERE, a student named 'from'.)
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare breakers. What's the structural thing regex lacks: the thing that knows a 'from' inside quotes isn't the keyword FROM?
  • Share · 2 minOne sentence: what two separate jobs is the one regex trying to do at once?
Show the answer

Three that break it: SELECT name, gpa FROM students (no WHERE at all, so the regex simply fails to match), SELECT * FROM students, majors WHERE mid = mid2 (the greedy (.+) for the table list happily swallows the comma and anything after it), and SELECT name FROM students WHERE name = 'from', where the regex cannot tell a quoted word from the keyword.

More regex cannot fix it, because the thing regex lacks is state: no way to remember that it is currently inside quotes, and no way to nest. The Share answer names the real fault: the one regex is doing two separate jobs at once, deciding what the characters spell (is this a word, a number, a quoted string?) and deciding what the structure is (may a WHERE follow here?). Split them and each half becomes easy: the lexer settles spelling once, so a string token is a string token forever, and the parser then reads tokens and never characters.

The lexer solves the 'from'-in-quotes problem once: a string token is a string token forever after. The parser then reads tokens, never characters. Two simple machines beat one clever regex.

War story · the regex that stopped the internet, 2019

On July 2, 2019, Cloudflare (which fronts a large slice of the web) deployed one new firewall rule containing a regex that could backtrack catastrophically. On real traffic it pinned every CPU in every datacenter to 100%, and for about 27 minutes a good fraction of the internet returned errors. Their postmortem is admirably blunt: a regex was doing structural work a regex cannot bound. That is this slide's TPS at planetary scale: when text has structure, you want a lexer and a parser whose worst case you can state, not one clever pattern whose worst case you discover in production.

Tokens, concretely

"SELECT name FROM students WHERE gpa > 35"

   ↓ lexer (one regex per token KIND, applied left to right)

(KEYWORD select) (ID name) (KEYWORD from) (ID students)
(KEYWORD where)  (ID gpa)  (PUNCT >)      (NUM 35)

Five token kinds cover all of microSQL: KEYWORD · ID · NUM · STR · PUNCT. Keywords are just words that appear in one privileged set, which is why you can't name a table select, in microdb or in Postgres.

The grammar

Think · Pair · Share · write the rule
  • Think · 2 minWrite a precise rule (precise enough to hand a freshman) for what may legally follow WHERE. Cover: gpa > 35, name = 'ada', mid = mid2, and chains with AND. Notation is yours; ambiguity is the enemy.
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minTrade rules and attack: does your partner's rule allow 35 > gpa? Forbid gpa >? Decide what should be legal before arguing about notation.
  • Share · 2 minCompare with the grammar below; the lab's tests enforce exactly it.
Show the answer

The grammar the lab enforces, in two lines:

predicate := term { AND term }
term      := field ( = | < | > ) value
value     := number | 'string' | field

Read it as a rule you could hand a freshman: a predicate is one or more terms joined by AND; a term is always field, operator, value in that order; a value is a number, a quoted string, or another field name. That last alternative is the whole join mechanism, and it is why mid = mid2 needs no new machinery.

The Pair attack is the useful part. 35 > gpa is not legal here, because a term must start with a field, and being explicit about that beats discovering it from a crash. gpa > is not legal either, since a value is required. Neither restriction is forced by nature; both are decisions, and writing the grammar down is what turns them from accidents into decisions.

microSQL in seven lines

query   :=  SELECT fieldlist FROM tablelist [ WHERE predicate ]
fieldlist := * | field { , field }
tablelist := table { , table }
predicate := term { AND term }
term    :=  field ( = | < | > ) value
value   :=  number | 'string' | field          ← field here means: a join!
insert  :=  INSERT INTO table VALUES ( value { , value } )

This notation is BNF, and reading it is a superpower: every database, config format, and language you'll ever use publishes one of these. { } means repeat, [ ] means optional, and each line becomes one Python method.

Everything missing is more of the same moves, not new machinery. A grammar that fits on a slide is a grammar you can hold in your head while debugging: the readability rule, applied to languages.

Why you can't name a table select

The rulethe lexer promotes any word in its keyword set to KEYWORD, before context exists, so select can never reach the parser as a table name.
What we boughta one-regex lexer and a parser that never second-guesses a token's kind.
What Postgres boughtflexible naming, via reserved/non-reserved keyword tiers and thousands of grammar lines to referee them.
The lessonlanguage design is budget allocation: every naming freedom is paid for in parser complexity, forever.

Recursive descent

The parsing technique is almost embarrassingly direct: one method per grammar rule, and four helper verbs on the token stream. Here is the provided INSERT parser; Thursday you write SELECT by imitation:

peek() · next() · match(kind, val) · expect(kind, val)
def parse_insert(self):
self.lex.expect("KEYWORD", "insert")
self.lex.expect("KEYWORD", "into")
table = self.lex.expect("ID")
self.lex.expect("KEYWORD", "values")
self.lex.expect("PUNCT", "(")
values = [self._parse_literal()]
while self.lex.match("PUNCT", ","):
self.lex.next(); values.append(self._parse_literal())
self.lex.expect("PUNCT", ")")
return InsertData(table, values)
Hover a line: the grammar rule and the method are the same text in two notations.

The planner

Think · Pair · Share · description → tree

Write the recipe (as numbered steps) that turns any QueryData into a correct plan. Where do multiple tables go? When do you skip a wrapper entirely?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare recipes against the four-step card below. Did anyone try to be clever about filter placement? Hold that thought.
  • Share · 2 minOne sentence: why is the dumb recipe always correct, whatever the data looks like?
Show the answer

Four steps, in this order. 1. One TableScan per table in the FROM list, with each Layout fetched from the Lab 3 catalog. 2. Fold them left to right into ProductScans: ((t1 × t2) × t3). 3. One SelectScan wrapping the whole WHERE predicate, if there is one. 4. One ProjectScan with the field list, unless the query said *. Skip a wrapper entirely when it would do nothing, so SELECT * FROM t plans as a bare TableScan.

Why is the dumb recipe always correct? Because the product produces every combination and the predicate is then applied to all of them, so no row that should have survived can have been dropped early. Correctness never depends on the data. What the recipe cannot do is be fast: it always builds the full cartesian product first, which is the 900-pairs shape from last week rather than the 60-pairs one. Anyone who tried to be clever about filter placement was inventing predicate pushdown, which is right, and needs statistics to do safely, which is week 9.

The naive recipe: four steps, always correct

1 · scansa TableScan per table in the FROM list; layouts fetched from your Lab 3 catalog.
2 · productsfold them into ProductScans left to right: ((t1 × t2) × t3).
3 · selectone SelectScan with the whole WHERE predicate, if there is one.
4 · projectone ProjectScan with the field list, unless it was *. No useless wrappers: SELECT * FROM t plans as a bare TableScan.

Dying well

Think · Pair · Share · the error you deserve
  • Think · 2 minA student types SELECT name students (missing FROM). Write the exact error message you'd want back; then write the WORST message that is still technically true. What separates them?
I've done the Think step. Reveal Pair & Share
  • Pair · 3 minCompare bests and worsts. ("Error." is the classic worst. Postgres's syntax error at or near "students" is… middling.)
  • Share · 2 minAgree on the two facts every parse error owes its user.
Show the answer

The best message names two things: what the parser expected and what it found instead, ideally with where. expected 'from', found 'students'. The worst message that is still technically true is Error. or invalid syntax: both accurate, neither actionable, because they leave the user to diff their query against a grammar they have never read.

So those are the two facts every parse error owes its user: expected, and found. Notice you get them for free here rather than by writing error-handling code. Every grammar rule funnels through one expect() helper, so improving that single function improves every message in the language at once. Postgres's syntax error at or near "students" is middling precisely because it reports the found half and leaves out the expected half.

expect() is the whole error strategy

def expect(self, kind, value=None):
if not self.match(kind, value):
raise ParseError(f"expected {want!r}, found {v!r}")
return self.next()[1]
Parser("SELECT name students").parse() # ParseError: expected 'from', found 'students'

Recap & next time

Three ideas from today, each bigger than SQL.

  • Lex, then parse. Spelling and grammar are different jobs; splitting them is what makes each one simple. (Regex was doing both, badly.)
  • One rule, one method, four verbs. Recursive descent turns a BNF grammar into code by transliteration, and expect() makes good errors a structural freebie.
  • Parse to data, plan from data. The AST between the stages is the seam that lets week 9 swap in an optimizer without touching your parser.

FAQ

Is real SQL parsed this way?

SQLite hand-writes its parser's lexer and uses a generated parser (Lemon); Postgres uses a grammar file compiled by Bison, generated cousins of what you're writing. DuckDB forked Postgres's. Recursive descent by hand is how Lua, Go, and most teaching compilers do it, because it's the readable one.

Why does microSQL forbid naming a column select?

The lexer promotes any word in the keyword set, context-free. Real SQL maintains lists of "reserved" vs "non-reserved" keywords and contextual rules,a famous source of parser complexity. We bought a one-line lexer with a small naming rule; Postgres bought flexible naming with three thousand lines of grammar.

What about SQL injection? Is that a parsing thing?

It's a string-building thing: gluing untrusted text into SQL before the parser sees it. The parser can't tell your intent from the attacker's;both arrive as valid tokens. The fix (parameterized queries) hands values around the parser entirely. Week 15's security lecture returns to this with your new eyes.

Could the planner cache plans for repeated queries?

Yes: real engines hash the text and reuse plans (prepared statements make it explicit). microdb re-plans every time, which costs microseconds at our scale and keeps the code readable. The interesting caching questions arrive when plans depend on statistics that drift, week 9 territory.
