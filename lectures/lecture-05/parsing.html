Separate token recognition from statement structure

Reading a sentence requires both recognizing words and recognizing their roles. The lexer supplies token kinds and values; the parser checks their grammatical arrangement. This comparison stops at syntax: the schema and planner still determine whether fields exist and how to execute the request.

In SELECT name FROM students WHERE nick = 'from', one occurrence of from is a keyword and the other is part of a quoted string. A search for that word alone cannot distinguish them. The lexer reads the quoted value as one STR token and the keyword as a KEYWORD token. The parser then works with those tokens, without having to process quote characters itself.

Five token kinds cover all of microSQL

"SELECT name FROM students WHERE gpa > 35"

   ↓ lexer (one regex per token KIND, applied left to right)

(KEYWORD select) (ID name) (KEYWORD from) (ID students)
(KEYWORD where)  (ID gpa)  (PUNCT >)      (NUM 35)

Five token kinds cover all of microSQL: KEYWORD · ID · NUM · STR · PUNCT. Keywords are ordinary words that happen to be on the lexer's fixed list of reserved words; any word on that list is labeled KEYWORD wherever it appears, which is why microdb rejects select as a table name; PostgreSQL permits it as a quoted identifier, written "select"3.

Reserved words simplify microdb’s naming rules

The rulethe lexer labels any word in its keyword set as KEYWORD the moment it reads the word, before the parser has seen what comes before or after it, so select can never reach the parser as a table name.
microdb’s choiceThe parser can treat KEYWORD and ID as separate token kinds throughout the small microSQL grammar.
PostgreSQL’s choicePostgreSQL permits quoted identifiers, such as "select" for a column name, and distinguishes reserved from non-reserved keywords. Double quotes tell the parser to treat the enclosed text as a name.3
The lessonMore flexible naming requires additional lexical or grammatical rules. microdb uses a small reserved-word set to keep the lab focused.

Double quotes name a column; single quotes supply a value

In PostgreSQL, double quotes let us use the reserved word select as a column name. Here we create that column and store one row. This is a PostgreSQL example; microSQL does not support quoted identifiers.15

CREATE TABLE demo ("select" TEXT);
INSERT INTO demo ("select") VALUES ('ada');

SELECT "select" FROM demo;  -- reads the column: returns ada
SELECT 'select' FROM demo;  -- returns the literal text: select

In the first query, SELECT is the command keyword and "select" identifies the column to read. In the second, 'select' is a string value, so the stored value ada is not read. Writing SELECT select FROM demo without the double quotes causes a syntax error because that second select is a reserved keyword.

The lexer removes character-level concerns such as whitespace and quotes. The parser records the query’s structure. The planner then uses that structured description to build executable operators.

An AST shows what the query asks for

SELECT name FROM students WHERE gpa > 35;

An abstract syntax tree (AST) represents the structure of this request. Here is one way to draw it. The node names are illustrative; the supplied implementation does not use classes called SelectQuery or GreaterThan.

SelectQuery
├── fields
│   └── Field("name")
├── tables
│   └── Table("students")
└── predicate
    └── GreaterThan
        ├── Field("gpa")
        └── Number(35)

The tree keeps the requested field, source table, and comparison. It does not need nodes for spaces or the semicolon. Number(35) records a numeric value, while Field("gpa") names a value to read later from a row. Building this description does not read any student rows.

QueryData stores the request; the planner chooses operators

Lab 5 stores the same structure in a compact object. For this query, the parser returns the equivalent of:

QueryData(
    fields=["name"],
    tables=["students"],
    predicate=Predicate(("gpa", ">", 35))
)

The planner uses those three parts to construct the following scan tree. These labels describe the operators and their settings:

ProjectScan   fields = [name]
└── SelectScan   predicate = gpa > 35
    └── TableScan   table = students

The AST records what was requested. The scan tree specifies how this implementation will produce it: read students, keep rows with gpa > 35, and expose name. Constructing the tree still does not run the query. Calling next() on its root starts pulling rows.

A small grammar defines microSQL’s supported statements

The token example shows why word recognition alone is insufficient. Write down the legal sequences next, then connect each grammar rule to the method that consumes it.

query   :=  SELECT fieldlist FROM tablelist [ WHERE predicate ]
fieldlist := * | field { , field }
tablelist := table { , table }
predicate := term { AND term }
term    :=  field ( = | < | > ) value
value   :=  number | 'string' | field          ← a field reference reads another column
insert  :=  INSERT INTO table VALUES ( literal { , literal } )
literal :=  number | 'string'

BNF stands for Backus–Naur form, a notation for writing grammar rules. Here we use Extended Backus–Naur form (EBNF). Braces { } mean repetition and square brackets [ ] mean an optional part. In this parser, each grammar rule corresponds to a method that consumes that part of the token stream4.

Reading * and |

In fieldlist := * | field { , field }, the asterisk * is a literal SQL token meaning “all columns.” You type it in a query such as SELECT * FROM students;. Here, repetition is written with braces, not with *.

The vertical bar | means “choose one alternative” in the grammar. Read the rule as: “a field list is either *, or one field followed by zero or more comma-and-field pairs.” The bar is grammar notation; you do not type it into the SQL query.

SELECT * FROM students;          -- the * alternative: all columns
SELECT name FROM students;       -- one field, no repetitions
SELECT name, gpa FROM students;  -- one field, then one comma-and-field pair

Likewise, ( = | < | > ) means choose one comparison operator: =, <, or >. For example, WHERE gpa > 35 chooses >.

One grammar rule becomes one Python method

Recursive descent assigns a method to each grammar rule. Each method inspects or consumes tokens through four helpers. Step through the provided INSERT parser below to connect a grammar rule to its Python method, then follow the same patterns in Lab 5’s supplied SELECT implementation.

4 verbs peek, next, match, expect: the supplied parsing methods use these token-stream helpers

The token cursor identifies the next token to process. peek() reads that token without advancing. match(...) checks it without advancing. next() returns the current token and advances to the following one. A successful expect(...) checks and consumes the token, returning its value; a mismatch raises an error without advancing. Consuming means moving past a token, not deleting it from the list.

    F marks a value to read from another field

    For gpa > 35, the parser stores the numeric constant directly. For mid = mid2, it wraps the right-hand identifier in F, a field reference. The predicate will read that field's value from the current row during execution:

    ("gpa", ">", 35)          # compare with a numeric constant
("mid", "=", F("mid2"))   # compare with the current row's mid2 value

    Consider an example student, name='ben', mid=2. Here mid is the student's chosen major ID. A statistics row has mid2=2, dept='stat', where mid2 is that major's own ID. The two column names are different so ProductScan can identify which input supplies each field.

    ProductScan pairs those two rows and exposes their fields together: {name: 'ben', mid: 2, mid2: 2, dept: 'stat'}. This is the combined row: one candidate student–major pair. The predicate reads the student's mid value, and F("mid2") reads the major's mid2 value.

    Candidate pairStudent's chosen major IDMajor's own IDResult of mid = mid2
    ben and statistics2, read from mid2, read through F("mid2")2 = 2: keep (ben, stat)
    ben and data science2, read from mid1, read through F("mid2")2 ≠ 1: reject this pair

    The 2 in the name mid2 does not determine the stored value. The statistics row stores 2 there; the data-science row stores 1. F("mid2") means “read that field from the current row.” A plain string "mid2" would instead mean fixed text. A field comparison can also compare columns from the same table.

    The lab planner constructs a plan in four steps

    The parser has recorded fields, tables, and conditions without reading result rows. The planner now connects Lab 4 operators to execute that request.

    1 · scansa TableScan per table in the FROM list; layouts fetched from your Lab 3 catalog.
    2 · productscombine them into ProductScans left to right: the first two TableScans become one ProductScan, that product is paired with the third table's scan, and so on: ((t1 × t2) × t3). With a single table there is no product at all.
    3 · selectone SelectScan with the whole WHERE predicate, if there is one.
    4 · projectone ProjectScan with the field list, unless it was *. For SELECT * FROM t, the plan is just a TableScan.

    Three points to remember:

    • Lexing and parsing have separate responsibilities. The lexer recognizes tokens; the parser checks how they form a statement.
    • Recursive descent follows the grammar. Each parsing method uses the four token-stream helpers, and expect() reports a mismatch consistently.
    • The parser produces data; the planner produces operators. Keeping these stages separate allows different plans to be built from the same query description.

    FAQ

    Is real SQL parsed this way?

    SQL engines use several parser designs. SQLite uses a handwritten lexer and a Lemon-generated parser. PostgreSQL uses Bison to generate its parser from a grammar. DuckDB used a PostgreSQL-derived parser through v1.x and introduced a PEG parser in v2.0. Handwritten recursive descent, used in languages such as Lua and Go, makes the relationship between grammar rules and code easy to inspect7891011.

    Why does microSQL forbid naming a column select?

    microdb labels an unquoted word in its keyword set as KEYWORD before parsing. It therefore cannot use that token where an ID is required. PostgreSQL supports quoted identifiers and distinguishes reserved from non-reserved keywords, which requires more detailed naming and grammar rules14.

    How does parameter binding keep input out of SQL syntax?

    SQL injection can occur when untrusted input is concatenated into SQL text and interpreted as part of the statement. Parameterized queries keep bound values separate from SQL syntax, so a value cannot introduce a new clause or statement. Parameter binding would be a useful optional extension to microdb; it is not part of the required parser12.

    The task: an application wants the name of the student whose ID a user enters. In this small example, student 42 is ada and student 43 is ben. The SQL text says which table, field, and comparison to use. The ? marks one value the application will supply separately. Associating that value with the placeholder is called parameter binding.

    This complete example runs in Python using its sqlite3 library17:

    import sqlite3

connection = sqlite3.connect(":memory:")
connection.execute("CREATE TABLE students (sid INTEGER, name TEXT)")
connection.executemany("INSERT INTO students VALUES (?, ?)",
                       [(42, "ada"), (43, "ben")])

sql = "SELECT name FROM students WHERE sid = ?"
print(connection.execute(sql, [42]).fetchall())  # [('ada',)]
print(connection.execute(sql, [43]).fetchall())  # [('ben',)]
print(connection.execute(sql, ["42 OR 1=1"]).fetchall())  # []
connection.close()

    execute(sql, [42]) has two arguments: the SQL text and a list containing one value. SQLite compares sid with 42 and returns ada. Changing the list to [43] returns ben. The SQL string still contains ? in both calls.

    Why this matters: the final call passes "42 OR 1=1" as one string value. It never becomes an extra SQL condition. Neither integer ID matches that string, so this SQLite example returns no rows. Binding supplies data for the comparison; it does not paste user input into the statement.

    The supplied microSQL terminal does not support placeholders or this two-argument call. This is an optional extension. Other database libraries use their own binding APIs and placeholder conventions, and may reject an incompatible value instead of returning no rows. Parameters supply values, not table names, column names, or arbitrary SQL fragments.

    Could the planner cache plans for repeated queries?

    Yes. Prepared statements and other plan caches can reuse parsing or planning work. microdb plans each query again to keep the implementation simple. A production cache must also handle changes to schemas, statistics, and other assumptions on which a plan depends13.
