Text is not a program

Split the job: lex, then parse

StageIn → outKnows aboutIn the lab
Lexercharacters → tokensspelling: numbers, 'strings', words, punctuationprovided (read it)
Parsertokens → descriptiongrammar: what may follow whatyou
Plannerdescription → scan treethe catalog + Lab 4's operatorsyou

The lexer solves the 'from'-in-quotes problem once: a string token is a string token forever after. The parser then reads tokens, never characters. Two simple machines beat one clever regex.

War story · the regex that stopped the internet, 2019

On July 2, 2019, Cloudflare (which fronts a large slice of the web) deployed one new firewall rule containing a regex that could backtrack3 catastrophically. On real traffic it pinned every CPU in every datacenter to 100%, and for about 27 minutes a good fraction of the internet returned errors3. Their postmortem is admirably blunt: a regex was doing structural work a regex cannot bound. That is this slide's lesson at planetary scale: when text has structure, you want a lexer and a parser whose worst case you can state, not one clever pattern whose worst case you discover in production.

Tokens, concretely

"SELECT name FROM students WHERE gpa > 35"

   ↓ lexer (one regex per token KIND, applied left to right)

(KEYWORD select) (ID name) (KEYWORD from) (ID students)
(KEYWORD where)  (ID gpa)  (PUNCT >)      (NUM 35)

Five token kinds cover all of microSQL: KEYWORD · ID · NUM · STR · PUNCT. Keywords are just words that appear in one privileged set, which is why you can't name a table select, in microdb or in Postgres4.

The grammar

microSQL in seven lines

query   :=  SELECT fieldlist FROM tablelist [ WHERE predicate ]
fieldlist := * | field { , field }
tablelist := table { , table }
predicate := term { AND term }
term    :=  field ( = | < | > ) value
value   :=  number | 'string' | field          ← field here means: a join!
insert  :=  INSERT INTO table VALUES ( value { , value } )

This notation is BNF, and reading it is a superpower: every database, config format, and language you'll ever use5 publishes one of these. { } means repeat, [ ] means optional, and each line becomes one Python method.

Small on purpose

microSQL hasmicroSQL lacks (and who adds it)
SELECT · multi-table FROM · WHERE with AND · INSERT · CREATE TABLEORDER BY, GROUP BY (wk 9 operators) · OR, parentheses (Going Further) · JOIN … ON syntax (sugar for what you have) · UPDATE/DELETE (Sciore ch. 9, straightforward)

Everything missing is more of the same moves, not new machinery. A grammar that fits on a slide is a grammar you can hold in your head while debugging: the readability rule, applied to languages.

Why you can't name a table select

The rulethe lexer promotes any word in its keyword set to KEYWORD, before context exists, so select can never reach the parser as a table name.
What we boughta one-regex lexer and a parser that never second-guesses a token's kind.
What Postgres boughtflexible naming, via reserved/non-reserved keyword tiers and thousands of grammar lines to referee them4.
The lessonlanguage design is budget allocation: every naming freedom is paid for in parser complexity, forever.

Recursive descent

The parsing technique is almost embarrassingly direct: one method per grammar rule, and four helper verbs on the token stream. Here is the provided INSERT parser; Thursday you write SELECT by imitation:

peek() · next() · match(kind, val) · expect(kind, val)
def parse_insert(self):
self.lex.expect("KEYWORD", "insert")
self.lex.expect("KEYWORD", "into")
table = self.lex.expect("ID")
self.lex.expect("KEYWORD", "values")
self.lex.expect("PUNCT", "(")
values = [self._parse_literal()]
while self.lex.match("PUNCT", ","):
self.lex.next(); values.append(self._parse_literal())
self.lex.expect("PUNCT", ")")
return InsertData(table, values)
Hover a line: the grammar rule and the method are the same text in two notations.

Nesting in the grammar becomes nesting in the call stack: set a breakpoint mid-parse and the stack trace is the parse tree so far. This is why recursive descent is the debuggable parsing technique.

The planner

The naive recipe: four steps, always correct

1 · scansa TableScan per table in the FROM list; layouts fetched from your Lab 3 catalog.
2 · productsfold them into ProductScans left to right: ((t1 × t2) × t3).
3 · selectone SelectScan with the whole WHERE predicate, if there is one.
4 · projectone ProjectScan with the field list, unless it was *. No useless wrappers: SELECT * FROM t plans as a bare TableScan.

Naive, and knows it

Correct first, fast later, and "later" has a date: week 9's optimizer reads the same QueryData and does the pushdown mechanically, using statistics your catalog will learn to keep. The parser you write this week never changes again.

Recap & next time

Three ideas from today, each bigger than SQL.

  • Lex, then parse. Spelling and grammar are different jobs; splitting them is what makes each one simple. (Regex was doing both, badly.)
  • One rule, one method, four verbs. Recursive descent turns a BNF grammar into code by transliteration, and expect() makes good errors a structural freebie.
  • Parse to data, plan from data. The AST between the stages is the seam that lets week 9 swap in an optimizer without touching your parser.

FAQ

Is real SQL parsed this way?

SQLite hand-writes its parser's lexer and uses a generated parser8 (Lemon); Postgres uses a grammar file compiled by Bison9, generated cousins of what you're writing. DuckDB forked Postgres's10. Recursive descent by hand is how Lua, Go, and most11 teaching compilers do it, because it's the readable one12.

Why does microSQL forbid naming a column select?

The lexer promotes any word in the keyword set, context-free. Real SQL maintains lists of "reserved" vs "non-reserved" keywords and contextual rules, a famous source of parser complexity. We bought a one-line lexer with a small naming rule; Postgres bought flexible naming with three thousand lines of grammar.

What about SQL injection? Is that a parsing thing?

It's a string-building thing: gluing untrusted text into SQL before the parser sees it. The parser can't tell your intent from the attacker's; both arrive as valid tokens. The fix (parameterized queries) hands values around the parser13 entirely. Week 15's security lecture returns to this with your new eyes.

Could the planner cache plans for repeated queries?

Yes: real engines hash the text and reuse plans (prepared14 statements make it explicit). microdb re-plans every time, which costs microseconds at our scale and keeps the code readable. The interesting caching questions arrive when plans depend on statistics that drift, week 9 territory.
