Transactions & the Write-Ahead Log

A transaction can change several pages. How can the database preserve committed changes and undo unfinished work when a crash interrupts those writes?
Daniel G. Graham · UVA School of Data Science

A committed transaction must survive a crash, even though data pages may be flushed at different times. Write-ahead logging makes this possible by preserving recovery information before data reaches disk. Next Thursday you implement a simple FORCE/STEAL design, then test it with an abrupt process exit. We will also compare it with production designs that defer data-page writes.

Companion reading: Sciore,1 Database Design and Implementation, ch. 5 (transactions) · a production recovery algorithm: Mohan et al.,2 ARIES (1992) · Postgres's WAL introduction.

Atomicity requires incomplete transactions to leave no partial changes. Durability requires successful commits to survive a crash. The log supplies the information needed to restore the required state.

FORCE/STEAL in Lab 7: sync log records, flush dirty data pages, then sync COMMIT.

Lab 7 chooses simple ordering over speed and can issue multiple syncs per transaction. A NO-FORCE production design can make commit depend on a log flush while writing data pages later; group commit can share that flush across transactions. This is the benefit of logging redo information.

Handle fsync errors without assuming a retry is safe

Case study · PostgreSQL fsync error handling, 2018

In 2018, PostgreSQL developers investigated an unsafe assumption in handling fsync errors. On affected Linux filesystems, a failed write could leave pages marked clean, so retrying fsync could report success without saving the lost data. PostgreSQL changed its handling of these data-file sync failures to stop the server and require crash recovery. The lesson is that a successful retry does not necessarily repair an earlier I/O failure; recovery depends on which durable information is still available.678

Recovery restores values from unfinished transactions

Under the lab’s FORCE/STEAL policy, committed changes are on disk, but some changes from unfinished transactions may also be there. STEAL allows a dirty page to be flushed before its transaction commits. Recovery reads the log backward and restores the old values of unfinished transactions, then flushes those repairs.

Recovery must survive its own crash

The threata crash can interrupt recovery itself. Recovery then runs again at the next startup, and the second run must do no new damage.
Idempotenceundo-only recovery is naturally idempotent: restoring an old value twice restores it once, so repeating the pass changes nothing.
Completion recordsafter restored pages are durable, the ROLLBACK records mark undo as complete. A later pass skips those transactions. The lab runs recover() twice and checks that the balances remain unchanged.
The rulea general rule of systems design: any repair process must survive being interrupted by the disaster it repairs.

microdb uses FORCE + STEAL, which requires undo but not redo. NO-FORCE + STEAL allows commits without immediate data-page writes and allows dirty pages to be evicted. ARIES supports this combination with redo and undo. Other engines can handle unfinished work differently; PostgreSQL uses WAL redo and MVCC visibility rather than an ARIES-style physical undo pass.2

FAQ

What happens if the log is corrupted?

Production WAL formats use checksums and record boundaries to distinguish an incomplete tail from corruption. Corruption can occur elsewhere too and must not be silently discarded. The lab’s JSON-lines log detects malformed JSON but has no checksum or torn-write repair; its crash tests cover process termination, not arbitrary storage damage.

Doesn't logging every change double the write traffic?

Logging adds writes, but there is no fixed doubling factor: log record size and data-page activity differ. In a NO-FORCE design, sequential log appends let the engine defer and batch data-page writes. That can reduce commit latency despite the extra log traffic.4

How does a checkpoint reduce recovery work?

Checkpoints bound recovery work by recording durable progress. An undo-only engine can stop at a checkpoint only if no unfinished transaction needs earlier log records. A simple optional implementation first waits for all transactions to finish, flushes data, then syncs the checkpoint.

Does SQLite also use write-ahead logging?13

Yes. SQLite offers PRAGMA journal_mode=WAL, and WAL is widely used for application databases on Android. SQLite also supports rollback-journal mode: before changing a database page, it saves the old page in a separate journal. After a crash, that copy can be used to restore the previous state.1415
