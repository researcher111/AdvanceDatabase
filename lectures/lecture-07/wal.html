Transactions & the Write-Ahead Log

How can COMMIT promise all-or-nothing through a power cut, when the buffer pool flushes pages whenever it likes and every durable write costs 10 to 1000 times a buffered one?
Daniel G. Graham · UVA School of Data Science

A committed transaction must survive a crash, even though data pages may be flushed at different times. Write-ahead logging makes this possible by preserving recovery information before data reaches disk. Next Thursday you implement a simple FORCE/STEAL design, then test it with an abrupt process exit. We will also compare it with production designs that defer data-page writes.

Companion reading: Sciore,1 Database Design and Implementation, ch. 5 (transactions) · the full monty: Mohan et al.,2 ARIES (1992) · Postgres's WAL introduction.

Today's plan

No quiz today (short week; Quiz 6 lands Tuesday). Straight into the deepest promise in the stack.

Account A held $60 and account B held $90. A $50 transfer debited A, the buffer pool wrote that page to disk, and the power died before B was credited. Disk now says $10 and $90: $50 of $150 has ceased to exist, and nothing in SQL explains where it went.

Today’s claim: durability depends on write ordering. Recovery information must be durable before the data it protects, and commit must finish the work required by the engine’s buffer policy.

The moment worth replaying: recovery reads the log backwards, learns each transaction's fate (its COMMIT or ROLLBACK record) before seeing its writes, and undoes only the unfinished.

Log the old value before the page changes

WRITE-AHEAD:   log(old value) → sync log → modify page → later flush page2

one record per change:   {"kind": "SET_INT", "tx": 2, "file": "acct.tbl",

Real enginesARIES logs the new value too, so it can also redo a committed change whose page never reached disk. The write-ahead rule is the same; the record just carries more information2.

FORCE/STEAL in Lab 7: sync log records, flush dirty data pages, then sync COMMIT.

Lab 7 chooses simple ordering over speed and can issue multiple syncs per transaction. A NO-FORCE production design can make commit depend on a log flush while writing data pages later; group commit can share that flush across transactions. This is the benefit of logging redo information.

When THE fsync lies, crash the server

War story · "fsyncgate," 2018

If one fsync carries the entire durability promise, its error handling had better be perfect, and for twenty years, Postgres's wasn't.6 In 2018 the community discovered that on Linux, when an fsync fails with an I/O error, the kernel can7 mark the dirty pages clean anyway; retrying the fsync then returns success while the data never reached disk. Postgres had assumed retry-until-success was safe.8 The fix, shipped urgently across every supported version, was brutal honesty: if THE fsync fails, crash the whole server and run recovery from the WAL, because the log is now the only8 copy you can trust. Search "fsyncgate" for the full thread; it is the best systems reading of that year, and it is exactly this slide's table with real stakes.

Recovery makes unfinished work never have happened

A crash leaves the disk in a mixed state: committed work possibly complete, unfinished work possibly half-flushed, because the buffer pool may have stolen a dirty page from a live transaction and written it out. Recovery's job is simple to state: make the disk look as if every unfinished transaction never began. One backward pass over the log does it.

Three things the disk can hold, three moves

Found on disk after the crashWhy it's thereRecovery's move
committed dataFORCE flushed it before its COMMIT recordkeep it: the COMMIT record in the log says the transaction finished
uncommitted datathe buffer pool evicted (stole) a dirty page belonging to a transaction that had not committedundo it: the log's SET record holds the old value, so write that value back
missing uncommitted datathe page was still in the buffer pool, and RAM does not survive a power cutnothing: the change never reached disk, so the disk already looks as if it never happened

One backward pass: fates before writes

for rec in log.records_backwards():
if rec.kind in (COMMIT, ROLLBACK): finished.add(rec.tx)
elif rec.kind is SET and rec.tx not in finished:
restore(rec.file, rec.blk, rec.off, rec.old)
flush restored data; then sync ROLLBACK for each undone tx
Hover a line: recovery is rollback for transactions that can no longer speak for themselves.

Recovery must survive its own crash

The threata crash can interrupt recovery itself. Recovery then runs again at the next startup, and the second run must do no new damage.
Idempotenceundo-only recovery is naturally idempotent: restoring an old value twice restores it once, so repeating the pass changes nothing.
The receiptsthe ROLLBACK records written at the end of the pass (the receipts in the code above) make the second pass skip cleanly; the lab tests literally run recover() twice and check nothing moves.
The rulea general rule of systems design: any repair process must survive being interrupted by the disaster it repairs.

microdb takes FORCE + STEAL, which needs only an undo pass. Every production engine takes NO-FORCE + STEAL, the corner that needs both a redo pass and an undo pass, because the two freedoms it buys (commit without writing data pages, evict a dirty page whenever memory is needed) are worth the extra recovery work.2

FAQ

If the log is so critical, what happens when IT gets corrupted?

Production WAL formats use checksums and record boundaries to distinguish an incomplete tail from corruption. Corruption can occur elsewhere too and must not be silently discarded. The lab’s JSON-lines log detects malformed JSON but has no checksum or torn-write repair; its crash tests cover process termination, not arbitrary storage damage.

Doesn't logging every change double the write traffic?

Roughly, but the log's writes are sequential appends (the fast kind, Lab 1) while the pages they protect are random writes that can now be deferred and batched. Net effect on real hardware: WAL made databases faster, not slower.4

What's a checkpoint actually for, then?

Checkpoints bound recovery work by recording durable progress. An undo-only engine can stop at a checkpoint only if no unfinished transaction needs earlier log records. A simple optional implementation first waits for all transactions to finish, flushes data, then syncs the checkpoint.

Does SQLite have a WAL? My phone doesn't feel like a bank.13

It does (PRAGMA journal_mode=WAL), and your phone uses it constantly; every messaging app is a little bank of messages that must not vanish.14 The other SQLite mode, the rollback journal, gives the same protection a different way: before it changes a page in the database file it copies the old page into a separate journal file, so a crash can be undone from that copy.15
