Transactions & the Write-Ahead Log

What COMMIT actually promises, and the append-only file that makes the promise keepable.
Daniel G. Graham · UVA School of Data Science

Way back in Lab 1 you measured how much a durable write costs; today that number becomes the design constraint of the course. A transaction promises all-or-nothing, even through a power cut, while the buffer pool flushes pages whenever it likes. The reconciliation is one of the great tricks in systems: log the old value before every change, in an append-only file, and every promise becomes keepable with a single well-placed fsync. Next Thursday you build it and kill -9 your own engine to prove it.

The write-ahead rule

The rule, and the record

WRITE-AHEAD:   log(old value)  happens-before  page write  happens-before  page flush2

one record per change:   {"kind": "SET_INT", "tx": 2, "file": "acct.tbl",
                          "blk": 0, "off": 0, "old": 100}

the log itself:  an APPEND-ONLY file, no seeks, no slots, no structure.
                 Sequential writes are the one thing disks do at full speed,
                 which is why logging every change costs less than it sounds.4

The log stores old values because our recovery only ever undoes. (ARIES logs new values too, so it can also redo a committed change whose page never reached disk; the write-ahead rule is the same, the record just carries more information.)2

Where the fsyncs go, and don't

Eventfsync?Why
each SET recordno, buffered appendthe rule only requires that the record reach the log file before its data page reaches disk. Pages are flushed rarely (at commit, or when evicted), so the log manager can collect records in a buffer and write them out just before any page flush; no fsync per record
data pages at commityes (our FORCE policy)every dirty page the transaction touched is written to disk before the COMMIT record is appended. So if a COMMIT record exists at all, the data it vouches for is already on disk, and recovery never has to redo anything
the COMMIT recordyes, THE fsyncthis is the fsync that makes durability real. Once it returns, the COMMIT record is on disk and the transaction counts as done whatever happens next. If the crash comes before it returns, no COMMIT record exists, so recovery treats the transaction as unfinished and undoes it5
ROLLBACK recordsno; whenever the log buffer next flushesif a crash loses a ROLLBACK record, recovery sees an unfinished transaction and undoes it again. Restoring an old value twice leaves the same result as restoring it once, so the repeat is harmless (the pass is idempotent)

Lab 1 measured an fsync costing 10 to 1000 times a buffered write. Here is why that does not sink the design: a transaction touching fifty pages pays one mandatory fsync, on a sequential file. That arithmetic is why databases can promise durability and still be fast.

War story · "fsyncgate," 2018

If one fsync carries the entire durability promise, its error handling had better be perfect, and for twenty years, Postgres's wasn't.6 In 2018 the community discovered that on Linux, when an fsync fails with an I/O error, the kernel can7 mark the dirty pages clean anyway; retrying the fsync then returns success while the data never reached disk. Postgres had assumed retry-until-success was safe.8 The fix, shipped urgently across every supported version, was brutal honesty: if THE fsync fails, crash the whole server and run recovery from the WAL, because the log is now the only8 copy you can trust. Search "fsyncgate" for the full thread; it is the best systems reading of that year, and it is exactly this slide's table with real stakes.

Recovery: undo the unfinished

A crash leaves the disk in a mixed state: committed work possibly complete, unfinished work possibly half-flushed, because the buffer pool may have stolen a dirty page from a live transaction and written it out. Recovery's job is simple to state: make the disk look as if every unfinished transaction never began. One backward pass over the log does it.

Found on disk after the crashWhy it's thereRecovery's move
committed dataFORCE flushed it before its COMMIT recordkeep it: the COMMIT record in the log says the transaction finished
uncommitted datathe buffer pool evicted (stole) a dirty page belonging to a transaction that had not committedundo it: the log's SET record holds the old value, so write that value back
missing uncommitted datathe page was still in the buffer pool, and RAM does not survive a power cutnothing: the change never reached disk, so the disk already looks as if it never happened

One backward pass

for rec in log.records_backwards():
if rec.kind in (COMMIT, ROLLBACK): finished.add(rec.tx)
elif rec.kind is SET and rec.tx not in finished:
restore(rec.file, rec.blk, rec.off, rec.old)
log ROLLBACK for each undone tx; flush
Hover a line: recovery is rollback for transactions that can no longer speak for themselves.

Crash during recovery?

Then recovery runs again at the next startup, and must do no new damage. Undo-only recovery is naturally idempotent: restoring an old value twice restores it once. The ROLLBACK records written at the end of the pass (the receipts in the code above) make the second pass skip cleanly; the lab tests literally run recover() twice and check nothing moves. A general rule of systems design: any repair process must survive being interrupted by the disaster it repairs.

microdb takes FORCE + STEAL, which needs only an undo pass. Every production engine takes NO-FORCE + STEAL, the corner that needs both a redo pass and an undo pass, because the two freedoms it buys (commit without writing data pages, evict a dirty page whenever memory is needed) are worth the extra recovery work.2

microdb's choice vs the world's

microdb (Lab 7)Real engines (ARIES)

ARIES is this lecture plus bookkeeping: log new values too (redo), number every record with a log sequence number (LSN) so a page can record which log entry last changed it, and checkpoint so recovery starts from a recent point instead of reading days of log.2 The rule, log before page, never changes.

Recap & next time

  • A and D are crash promises, and one append-only log keeps both: unfinished work undone, finished work fsync'd into permanence.

FAQ

If the log is so critical, what happens when IT gets corrupted?

Real WALs checksum every record and treat the first bad checksum10 as end-of-log; a torn final record just means that transaction never committed (its fsync11 can't have returned). The log's append-only shape is what makes this safe: corruption can only live at the tail.

Doesn't logging every change double the write traffic?

Roughly, but the log's writes are sequential appends (the fast kind, Lab 1) while the pages they protect are random writes that can now be deferred and batched. Net effect on real hardware: WAL made databases faster, not slower.4

What's a checkpoint actually for, then?

Bounding recovery time. Without one, a year-old database replays a year of log; a checkpoint records "everything before here is on disk," so recovery starts12 there. Week 2's table said "flush at checkpoints"; this lecture is where that line is explained.

Does SQLite have a WAL? My phone doesn't feel like a bank.13

It does (PRAGMA journal_mode=WAL), and your phone uses it constantly; every messaging app is a little bank of messages that must not vanish.14 The other SQLite mode, the rollback journal, gives the same protection a different way: before it changes a page in the database file it copies the old page into a separate journal file, so a crash can be undone from that copy.15
