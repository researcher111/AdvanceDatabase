# Editing a visual lecture

Each lecture is registered in one of `decks/lectures-01-05.js`,
`decks/lectures-06-10.js`, or `decks/lectures-11-15.js`. A deck contains its
source reading, date, and an ordered `scenes` array.

A scene has a stable `id`, a `title`, `minutes`, `kind`,
`steps`, `states`, `notes`, and a `draw(d, step)` function. The minutes across
a lecture must total 60, excluding any quiz. `steps` counts states starting
at zero. `states` gives the presenter a brief description of each build.

Every scene provides `teaching` with `idea`, `builds`, `question`, `answer`,
and optional `context`. Each `builds` entry explains the matching animation
state. The presenter shows the current instruction first, with expandable
answers and a list of all steps. The printable guide includes every step and
answer. Lecture 5 uses this format and derives the plain-text `notes` property
from it when registering the deck, so the two versions stay consistent.
An optional `checks` array supplies a `question` and `answer` for each build.
The presenter shows the current build's question, and the guide includes them
alongside their steps. Keep the scene-level question as a final recap.

`decks/teaching-notes.js` supplies these cues for scenes that do not define
`teaching` in their deck bundle. Entries use the lecture number and stable scene
ID; edit the matching entry when changing an animation. The file loads after
the deck and before the player. It preserves the original `notes` as `reference`,
shown in an expandable **Teaching context** section and in full in the printable
guide. Existing structured notes take precedence. Worked traces derive their
main idea, step explanations, question, and answer from the shared example data.

Lecture 6 loads `decks/storage-choices.js` and `decks/btree-growth.js` after
the common notes. These files own the drawings, animation states, and teaching
cues for `four-storage-choices` and `the-fifth-key`. Edit their frame sequences
together; they preserve scene IDs and teaching minutes. The growth animation
uses key/RID entries instead of the shared trace's code/table view.

`decks/btree-clarity.js` owns the other Lecture 6 scenes. It adds short projected
step explanations, labeled routes, visible RID lists, and explicit cost units.
Its search and range drawings use the same keys and RIDs as the shared worked
examples. Keep those fixtures in sync if the shared data changes. Edit each
frame's caption and teaching cue together; do not change its minutes or ID.

The Lecture 6 reading embeds these same drawings through
`lectures/lecture-06/reading-diagrams.js`, with local step controls and enlarged
views. Its surrounding prose explains the operations for independent reading.
The static SVGs in `lectures/lecture-06/diagrams/` supply final-state figures for
printing and browsers without JavaScript. After changing an embedded slide,
run `node scripts/build_btree_reading.cjs`; use `--check` to detect stale figures.
Do not edit generated SVGs directly. With Playwright available, run
`node tests/test_btree_reading_browser.cjs` to check that every reading state
matches its slide, and verify navigation, mobile scrolling, printing, and
the live insertion widget's tree pointers.

The other 14 lectures load four files after `teaching-notes.js` and before
`_shared/deck.js`, in this order:

1. `decks/clarity-captions.js` supplies one short, audience-facing explanation
   per animation state, indexed by lecture number and stable scene ID.
2. `decks/clarity-layout.js` records the bounds of each original diagram across
   all its builds. It is generated by `scripts/measure_slide_layout.cjs`.
3. `decks/clarity-diagrams.js` supplies concrete visual walkthroughs where the
   underlying code/table trace needs a visible mechanism, and repairs labels
   on existing drawings. Keep worked values aligned with the shared fixtures.
4. `decks/course-clarity.js` applies a consistent title, current-step caption,
   and step footer. It fits each original diagram once across its full sequence,
   so objects move without the entire diagram changing scale between clicks.

Edit captions together with drawings and teaching cues. Describe what just
changed, name the active item, and state the consequence. Prefer a concrete
claim such as “Frame 0 now contains block 8” to a generic phase name. Show
inputs, destinations, units, pointer direction, and results in the diagram.
Use stable keys for rows, versions, and emitted pairs so their movement remains
visible. New native diagrams use x=50–1230 and y=205–650; the common frame owns
the space above and below. Do not repeat its title or caption inside the body.

The frame prepends the audience caption to its corresponding presenter cue,
while preserving questions, expected answers, sources, and teaching context.
Definition scenes use their term as the audience title and retain the full
definition in teaching context and the printable guide. Scene IDs, build
counts, order, and teaching minutes remain stable.

Keep the main idea to one sentence. Write each build as a concrete teaching cue
for what is visible at that step. Put the question in direct classroom language
and keep its answer separate so it can stay hidden until discussion finishes.

Keep detailed explanations, prediction questions, expected answers, caveats,
and source citations in the notes. On the projected canvas, use a short caption,
necessary diagram labels, values, and formulas. Before the clarity frame is
applied, the `definition` scene kind adds a term and a definition of at most
18 words above the diagram.

The canvas is 1280 × 720. Use the drawing methods in `_shared/visuals.js`:
`rect`, `text`, `circle`, `line`, `arrow`, `path`, `box`, and `table`.
Every object needs a unique key within its build. Retain the same key when an
object moves between builds so the player can animate its position. Do not
add timers inside a drawing function; the player owns the timing and controls.

Regular diagrams should stay within x=70–1210 and y=65–640. Definition
scenes reserve the top 220 pixels for the term and definition. Use large
labels and prefer cutting text to shrinking it. Changes to scene IDs also
change where locally saved annotations appear, so keep IDs stable when
revising existing scenes.

Run `node scripts/validate_slides.mjs` from the repository root after editing.
You can pass lecture numbers to check a subset. Then open the deck, inspect
its overview, and step through every changed animation. Check the actual
rendered labels, numerical relationships, and classroom pacing. Toy examples
must be identified as such in the notes. Recompute examples described as
measurements when their data or implementation changes.

For the course-wide clarity layer, also run `node tests/test_slide_clarity.js`
and `node tests/test_teaching_traces.js`. These check fixture results, stable
animation identities, caption coverage, preserved pacing, and shared examples.
If an original diagram changes size, regenerate its layout measurements with
`node scripts/measure_slide_layout.cjs`, then run the validator again.

With Playwright and Chromium available, run
`node tests/test_slide_clarity_browser.cjs` (optionally followed by lecture
numbers). This renders every build, checks actual text bounds and overlaps,
verifies synchronized presenter cues and printable guides, and writes contact
sheets for visual review. Set `SLIDE_QA_OUTPUT` to choose the output directory;
otherwise it uses a temporary directory. Both browser tools accept
`PLAYWRIGHT_CHROMIUM_EXECUTABLE` for an existing Chromium installation.

## Shared worked examples

Lectures 6–15 load `labs/_shared/teaching-traces.js` and
`_shared/trace-scenes.js`. The latter maps selected stable scene IDs to worked
examples that also appear in the readings and labs. Edit the example's code,
states, explanations, and check question in the shared data file. The adapter
updates the projected states and presenter notes while retaining the scene ID
and minutes. The original scene is registered first, then the adapter supplies
the worked content. Inspect the rendered deck after changing either file.

Lecture 12's chunking measurements come from
`labs/_shared/rag-measurements.js`, also used by the reading and Lab 10.
Regenerate that file with `python3 scripts/generate_rag_measurements.py`.
Use `--check` to verify it matches the Python inputs. If a measured result changes,
update any prose and static example output quoting it as well.

The Lecture 6 reading and Lab 6 also render a tree alongside each code trace.
Each B+ tree frame in `labs/_shared/teaching-traces.js` carries its own `tree`
snapshot: stable node IDs, keys and RID lists, child edges, leaf links, and the
current path or highlighted entries. `labs/_shared/btree-trace-view.js` renders
that snapshot; it must not infer the state from a numeric frame position.
The shared controller advances the code, variables, explanation, and tree
in one render. These are authored worked states, not execution of a student's
unfinished Python. The two supplied helper snippets match the starter exactly;
the lookup, split, and range traces remain labelled teaching pseudocode.

When editing these traces, run `node tests/test_btree_trace.js`,
`node tests/test_teaching_trace_ui.js`, and
`python3 -m unittest discover -s tests -p test_btree_trace_helpers.py`.
With Playwright available, `node tests/test_btree_trace_browser.cjs` checks
both pages at every step, including diagram text overlap, code highlights,
previous/reset controls, keyboard navigation, and phone scrolling.
